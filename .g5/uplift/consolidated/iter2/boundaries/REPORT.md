## Proposed canonical text for integration

Under `history.survives-rollback.temp-copy`: A rollback leaves the temporary progress copy available, but abrupt process loss and instance restart are different boundaries. In the checked SIGKILL case both rows remained and the permanent reader still showed the initial snapshot; a whole-instance restart cleared the temporary copy and retained only the durable initial permanent record.

Under `history.delete.running-records`: Deleting an accessible active twin before final persistence can leave it absent even when Finalize and PersistToTwin return success. In a different checked schedule, delete waits on a transaction-locked twin while final persistence runs; deleting after unlock is followed by the temporary object's close recreating the same finalized row, so disappearance is not guaranteed across schedules. The policy for deleting active records remains an owner question.

Under `repo.filesystem`: Cache refresh uses a local transaction and a lock manager whose default constructor releases its explicit repository lock when the method's local manager closes. A caller transaction may still be open when a competing process can acquire that lock; passing `0` to the lock manager constructor is the distinct deferred-unlock neighbor. The old outer-transaction lock promise is withdrawn, without changing the intended cache consistency obligation.

Under the CPF processor owner: Configuration is an external effect that must be read separately from the child process result. In the disposable provider, a valid role-creation merge survived database rollback, while an invalid-section merge returned an error and created no role; these examples do not establish atomicity for all CPF actions.
