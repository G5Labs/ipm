# IPM uplift consolidation proposal

Review baseline: IPM `571e04a19aba9f9b4bc0ea23fbe09182038f4e55`. Working branch `consolidated_uplift` starts at the final Verus guidance result, `0ac7b931fe6245366ae6c873393dabf1fc9590ca`. The playbook reference is `fdd3669091814f1ad8116bc0fff167082ae6edfd`. This document is the analysis and proposed work for a later instruction to begin. No product, ontology, model or baseline file was changed for it. Its only new observation is the read-only probe described under evidence.

**Reading conventions.** IDs are arm-qualified, written `G:D13` or "G D13", because the arms reuse letters with different meanings. `G:D1` is a defect and `P:D1` is a design. `G:V1`–`V12` are model findings (`G:V6` is an alias of `G:D13`), and `P:V1`–`V18` are unresolved verification items. G has a native case named D1 that is not defect D1. G's IRIS premises are `P-01`–`P-14`; P's load premises are `P1`, `P2`, `P3`, `PC`, `PI`, `PD` and `PM`. P also reuses `PR`, `PU`, `PI`, `S1…` and `U1…` across model files for unrelated things, so a P premise is cited with its file. Evidence is named by kind: *proved* (Verus, about a hand-written model, under named premises), *model-checked* (bounded Python), *native* (an IRIS observation, with its platform), *patched* (an instrumented copy), *suite* (IPM's own tests), *read* (source inspection) and *assumed* (a policy chosen without owner confirmation). No product method is called verified, because neither arm checks an ObjectScript body mechanically.

**Baseline compatibility.** Both arms pin Verus `0.2026.09.27.3cf1832`. G is one cargo crate with executable twins and bounded explorer runs, plus two follow-up Python models. P is eight standalone Verus files with per-file controls, plus Python explorers. The native evidence is on two platforms. G ran IRIS 2026.1 build 234U in x86-64 containers. P ran the same build on ARM64 and repeated its load and history scenarios on 2025.3 build 226U. P:F-RES-7 occurs only on ARM64, so architecture can change an outcome. A G observation and a P observation of the same case stay two receipts until one platform reruns both. The G artifacts that the comparison scored are the frozen copy under `results/cloud/ipm-verus-quality-review-20261113/final/.g5`. This checkout's `.g5` should be identical at `0ac7b931`, and `inventory.py --check` is the test of that. The most recent review pass had read and search access only. It did not run that check, the comparison scripts, git or IRIS. The existing counts below were recomputed by reading the frozen inventories. The new counts come from text searches of the pinned source and should be rechecked by script after the direct import, before extending the models. ## What the evidence supports

IPM can report an error after keeping a module. The observable result includes the command status, installed version, compiled resources, the caller's remaining transaction, and the action's permanent history row. The models disagree on which of those outcomes they can distinguish. Both are hand translations from ObjectScript. A Verus result proves a property of its translation under named premises. Running the same input on IRIS can establish correspondence for that observation.

The prior semantic comparison selected 25 obligations and 20 precision checks. G/P ontology coverage was 40/50 and 38/50, and precision on ten shared ontology questions was 15/20 and 17/20. On load and history the models scored 20/26 and 12/26. On twelve other operations they scored 0/24 and 16/24. Model precision on five common cases was 9/10 and 7/10. The runs had different steering, particularly the dedicated load/history audit on G. Use the underlying cases and evidence, rather than extrapolating a winner from these samples. [Comparison and rulings](../../../../docs/g5-formal-verification.html#experiment-ipm-uplift)

**What the samples establish.** The 25 obligations were chosen for the comparison. They are not a random draw from the 879 ontology IDs (149 G blocks and 730 P rows). The extended scorecard adds 22 adjudications: eight ontology units, six findings, four model links and four linked checks, eleven per arm. Its checker compares statements and citations with the source and stored evidence. It does not rerun IRIS. Eighteen rows were supported or direct within a stated scope. Four carry a qualifying verdict: a linked universal refuted with its counterexamples listed (G `load.refusal`), an obligation contradicted as built and labelled so (P UNIN-B66), a finding observed with disputed normative strength (P F-HIST-9), and a finding narrower than a general rule (P F-UNIN-5). The sample reads 8 of 879 ontology IDs, 6 of 134 finding IDs and 4 of the 40 arm-level model links. It shows which kinds of error to look for. It certifies those 22 rows and nothing else. No error rate should be projected onto the rows it did not read. [Audit sample](../../../../results/experiments/ipm-uplift-comparison-20261113/audit-sample.tsv)

At statement grain, the comparison counts 137 of P's 611 behavior and exception rows with a proof or model-check tag, and P's rows for modules 03–09 were tagged by builder agents by inspection (P:V13). **Why the unlinked code matters.** A load proof says what `LoadNewModule` does to the rows it models. Whether the operator's outcome matches depends on code the proofs do not see. Reading the pinned source found five places where that code decides the outcome.

1. *Other transaction owners.* A search for `TSTART`, `TCOMMIT` and `TROLLBACK` finds 18 `TSTART` statements in 10 class files. Four are in members with a model representation: `LoadNewModule` twice, `ImportStream` and `StudioDocument.Module.Delete`. The other 14 are in `Utils.Migration` (two), `StudioDocument.Abstract` (two), `ExtensionBase.CompositeMethodOverrides` (two), `StudioDocument.LocalizedMessages`, `ResourceProcessor.LegacyLocalizedMessages`, `Repo.Filesystem.Definition.BuildCache`, `Utils.Module.PerformBatchActivation` and `LockWithCurrentDependencies`, `Main.UpdateLanguageExtensions` and `ModuleVersion`, and `Lifecycle.Base.%Document`. One of these that runs inside a load nests in the load's transaction and shares its rollback. One that runs at level zero commits on its own. Neither arm says which commands reach which site. Implicit transactions from object saves and SQL statements are additional and were not counted.
2. *Work after the final commit.* At least six call sites can turn a committed load into a reported error. They are listed in the status row below. Two were observed natively, one by each arm, on different platforms. The rest were only read.
3. *State carried between commands.* `EnvironmentConfig` is a per-process singleton that a shell session keeps alive. Default modifiers are instance-wide. The purge keeps a last-run day marker. A killed load leaves its `ipm-temp-modules-N` repository registered first in search order (G:I2). `LoadedResource` rows stay in IRISTEMP until restart (P:DEC-SEM-1). Each lets one command change the next, and a model of a single command cannot show it.
4. *Effects with no database row.* File copies, archive extraction into the module root, lock files, pip installs, CPF merges, git clones and registry uploads are open in both arms (G Q-04 and its projections; P:V16 and P's named exclusions). `Committed` is defined over database changes, so the history record that an operator reads to decide what to undo does not see these effects either.
5. *Decisions made in SQL and macros.* Filter construction, the purge cutoff, the global readers and publish selection are query text. The update-lock timeout and the default-modifier global are macros. A member-level link cannot say that the decisive token is an absent `ORDER BY` or a quoted literal.

The member percentage therefore misleads in both directions. A linked dispatcher may cover one branch, and an unlinked helper may hold the commit point. P's write-set measurement is the one existing asset that starts from what a command changed: 46 commands, with every global hashed in the namespace databases, IRISSYS, IRISTEMP, IRISSECURITY, IRISLOCALDATA and IRISAUDIT, and 135 invariant-command pairs judged. It does not see files or read-only library databases, and it is not joined to members. [P write-set coverage](../../../../results/experiments/ipm-playbook-uplift/semantics/COVERAGE.md)

**Coverage audit to run after the direct import.** Freeze the denominator, enumerate the 1,216 rows and preload supplement, resolve fully qualified names and unique suffixes, split cross-member ranges by actual overlap, and retain ambiguous matches for review. Store exact revision, symbol and slice, ontology obligation, model transition, property, premises, checked run and observed fields. Label an edge as behavior represented, observation/projection only, cited exclusion, or candidate. For each not covered, record one evidence-based disposition: missing trace to existing abstraction, missing intent, missing model, external boundary, or deliberate lower priority with rationale. Allow “unresolved” until reviewed. Cross-tab these with native evidence and whether a distinguishing wrong transition is rejected. Publish semantic member reach, whole-body proof reach, and coverage of consequential operations as separate numerators and denominators. Require every externally visible or durable-state-changing path to have a justified disposition. Never increase a numerator just by adding a citation.

**Acceptance for the audit.** Each item is a yes or no.

1. After the direct import and before changing either model, the unmodified counting rule reproduces 1,216 members and 11, 29, 37, 32, 174 and 179 links from the pinned inputs, and `inventory.py --check` confirms that this checkout's G artifacts equal the frozen copy. Investigate a mismatch and correct the measurement before relying on that figure. Continue independent analysis.
2. Each of the 37 accepted links carries exactly one edge label. The three known non-representing citations are labelled exclusion or observation only.
3. Each false negative named above resolves to a member, or is recorded as ambiguous with the reason. Every edge records how it was resolved: qualified path, unique suffix, relative to the previous file, or bindings table.
4. Two seeded controls run. One adds a citation to an unmodeled member. The other deletes a model transition and keeps its citation. The citation count may move. The semantic numerator must stay put in the first case and fall in the second.
5. Every explicit transaction statement, lock acquisition, external process or network call, file write, and object save, delete or SQL write found by a stated search has a row. The row gives the enclosing member, the commands that reach it or "unknown", and a disposition. The searches and their hit counts are stored so a reader can repeat them. The 18 `TSTART` statements above are the first check of the search.
6. The 46 measured write sets are joined to the members that write each global, where reading can identify the writer. A global with no identified writer is listed.
7. Results appear on the frozen 1,216 and on separately named denominators: members with a body, the preload installer, durable-write sites, class queries and triggers, and consequential operations. No figure is called coverage without its numerator definition beside it.
8. A second reader labels a stated subset of edges independently. Disagreements are listed one by one. The agreement count is reported for that subset and is not extended to the rest.

An executed-code measure is a separate, optional step: run IPM's integration suites and the consolidated native cases under a line-level execution monitor, if the instance offers one, and report executed members. Use a disposable local instance to measure execution when the available profiler can do so. Report the observed run, overhead, and treatment of generated/inherited members.
