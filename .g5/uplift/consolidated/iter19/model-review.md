## Model scope and data flow

`Scenario` holds normalized root, configured repository name, physical-directory map and provider-supplied ordered subdirectories. Each `Disk` supplies a valid parsed manifest projection and actual source payload. `materialize` preserves that order and derives each Entry's `(root,name,fullVersion)` key, subdirectory and manifest from the physical map. It does not parse XML, validate arbitrary module/version text or implement FileSet/BFS/depth traversal. The successful provider domain contains distinct scanned directories and valid normalized parsed manifests; `valid_order` checks map completeness and distinctness, not generic manifest validity.

`add_valid` admits a new row or, for a recognized logical-key collision, preserves the prior row and appends a warning tuple `(key,retainedSubdir,duplicateSubdir)`. `fold` applies admissions from left to right; duplicate status is success. It begins with an empty, freshly purged cache. Same-physical-path updates, other unique/status errors, cache refresh interactions, transaction/lock behavior, concurrency and source mutation/removal are unassessed. No invalid-name/unreadable-manifest policy from the inherited model is weakened.

Rows preserve manifest and subdirectory together. The constructor's `indexed` invariant states that every row stores the same Root/Name/VersionString tuple as its map key. It is proved through admission, fold and fresh build. Generic reader correspondence requires this invariant; inconsistent hand-constructed maps are outside the product domain. The directory reader uses the stored row root, matching source, rather than silently assuming an arbitrary map is consistent.

`service_manifest` and `service_directory` reopen the same key. The latter forms the normalized directory from stored root/subdirectory. `stable_selected_source` requires a matching physical source and its unchanged manifest projection. Under successful ordinary load/compile/save providers, `install_directory` reads the physical Disk at the retained subdirectory and derives installed name, version, Description, root, supplier and payload. It does not choose the payload directly from an arbitrary final status, marker rank or supplied winner. Missing/stale/changed physical sources and failed providers are unassessed, rather than a promised refusal/rollback.

Manifest represents only name/fullVersion/Description. `marker_code` maps exact `source-A` and `source-B` projections to native observer ranks1/2, independently of payload101/202. Native whole cached/service XML text equality is a separate qualification and does not establish a generic XML/stream/serialization proof. Roots are the exact normalized `/tmp/iter19/repos/{single,ab,ba}/` literals; subdirectories have no trailing slash, while actual service/installed directories include it. Pure opposite-order inputs remain conditional model witnesses; only the three observed provider orders are natively qualified.

`shown_supplier` and `listed_for_repository` project the stored installed supplier/name for the selected ordinary CLI readers. Native output parsing checks those actual readers independently. General formatting, arbitrary filters and all CLI options remain outside this model.
