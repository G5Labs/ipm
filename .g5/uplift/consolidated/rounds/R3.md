# Round 3: history across writers and readers, filtered delete and purge

## The two questions

**What consequential outcome can IPM distinguish that our model cannot?** What the operator reads back. G models the
record's stored fields and the readers' selected sets; P reduces a record to module and success. Neither models the
`install`/`uninstall` writers' fields (action, source name, moniker, details) or the formatters through which
`history details` and `history find` present a record, including an unfinished one, nor the purge's once-a-day
marker that carries state from one command to the next.

**What wrong outcome could our checker still accept?** (a) An unfinished record presented as a failure. (b) An
unfiltered deletion: G found it on x86-64 (D2), and nothing on this platform had rechecked the exact identities.
(c) "The purge ran, so old records are gone": P found the purge deletes nothing (F-HIST-6) and the marker hides
repeated attempts.

## Distinguishing cases

| Wrong outcome | Rejected by | Neighbor |
|---|---|---|
| unfinished record reads as an error (as built: it does) | H4f row 19 | H4f row 17 (success) |
| filter matching nothing deletes nothing (as built: deletes all) | D1 | D3, D4 delete exactly the match |
| misspelled column widens the delete | D2 refuses (SQLCODE -29) | D4 |
| purge runs on every command | P2 (marker kept) | P1 (first command purges) |
| retention 0 still marks a purge | P3 | P4 |

graded them `no` for missing line ranges only).
