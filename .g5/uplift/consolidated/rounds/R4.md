# Round 4: transaction and lock owners outside load, migration, namespace

## The two questions

**What consequential outcome can IPM distinguish that our model cannot?** Commands that own their own transaction or
lock and change durable or instance-wide state outside a load: `module-version` (record and stored manifest), the
filesystem repository cache (refresh, lock, rollback), and the `%ZLANG` routines that add the `zpm` command next to
users' own extensions. Neither arm models any of them.

**What wrong outcome could our checker still accept?** (a) "A failed refresh still caches what it could" (it changes
nothing). (b) "A refresh under another process's lock waits and then succeeds" (it fails after the timeout).
(c) "Re-installing IPM drops user code in `%ZLANGC00`" (it keeps it). (d) The inherited G evaluator accepts a load
that returns with an open transaction (`load.tlevel` is never compared); see the round 1 checker calibration and the
repair recorded in `round1/checker-repairs.md`.
