### 1.1 Package loading

L1. `load <path>` accepts a local directory holding `module.xml`, a `.tgz` or `.tar.gz` archive, or an `http…` git URL with optional `-branch` (H: CLI help, wiki 02, CHANGELOG #474). An empty path is refused. A path that does not exist and is not absolute or a URL is refused (C). A nonexistent path must return an error, not `$$$OK` (H: CHANGELOG #726).
L2. An archive is extracted and its top-most `module.xml` is used (H: CHANGELOG #474). The module is then copied to `<ModuleRoot>/<name>/<version>/`, replacing what was there; directory loads stay in place (H: CHANGELOG #945, wiki 02). The temporary extraction directory is removed whether the load succeeds or fails (H: wiki 02 "[0.10.11+]"). Expected case: a `.tar.gz` path must be treated as an archive. Code at `Main.cls:2466-2467` takes only the last dot piece (`gz`), so `.tar.gz` can never match. `git log -S` shows commit `f83b207e` (#887) replaced a working two-piece check. I expect `load x.tar.gz` to fail at this revision.
L3. A `.modules/` folder under the module root acts as a temporary local repository for dependencies during the load (C, comment in `LoadInternal`).
L4. Dependencies are resolved from configured repositories and loaded one at a time, in dependency order, before the module's own phases (H: CLI help, CHANGELOG #885). Parameters propagate to dependencies except developer mode (H: CHANGELOG #316, #1036). A snapshot dependency loaded from a filesystem repository during a `-dev` load is itself loaded in dev mode (C, comment). A module from a read-only repository is always loaded in non-dev mode (H: `repo -read-only` help, wiki 00).
L5. Refusals that leave the namespace unchanged: downgrade below the installed version ("uninstall first") (H: #887 thread "always been present"); install or load of a newer version when the module defines `UpdatePackage`, unless `-force` or `-dev` (H: CHANGELOG #550, #887 isc-jili); `update -path` whose module name does not match (C); a requested version that does not satisfy other installed modules' requirements (C); `install` without `-dev` over a module installed in dev mode (H: wiki 00, wiki 05; wiki 00 adds "or use `-force`", but code checks only `PermitDowngrade`, so the `-force` escape is H? and contradicted by code); system requirements not met (C); `module.xml` with zero or several documents or no `.ZPM` document (C). Same-version `install` without flags is now allowed (H: #887 thread, check removed after isc-tleavitt's compatibility objection), superseding #903's original request (H?).
L6. Transaction per mode (H: CLI help for `-dev`, wiki 00, wiki 09; #363 decision by isc-tleavitt):
- Normal: the whole load, dependencies and phases are one transaction. Any failure rolls the namespace back to its prior state.
- `-dev`: the manifest is committed before resources load so it can be fixed after a failure. Dependencies run in a second transaction that commits only if they all succeed. The module's own Reload/Compile/Activate run outside any transaction and a failure there keeps partial work. A failure before the first commit (malformed manifest, downgrade refusal) is fully rolled back (H: #1237).
- `-DNoTransaction=1` / `-DNoJournal=1`: no transaction, partial state remains on failure; `NoJournal` also disables journaling and implies no transaction (H: wiki 00).
- Case: in `-dev` a system-requirements failure happens after the first commit, so the manifest stays (C). That fits the "keep for debugging" decision but is not stated anywhere.
L7. Dev mode is opt-in. `load` must not set dev mode unless `-dev` is given (H: #892, CHANGELOG). `-nodev` turns it off. Without either flag the stored module's existing `DeveloperMode` is kept (C), so a module loaded with `-dev` stays in dev mode on a later plain `load` (C, worth a statement or a Q).
L8. A failed non-dev load leaves no module entry behind. A failed dev load keeps the entry for debugging (H: #363 isc-tleavitt 2025-09-15: "we don't remove these entries when installing in dev mode … but will in non-dev mode").
L9. `update` refuses `-DPermitDowngrade`, refuses a module that is not installed, uses the archive at `-path` if given, otherwise installs from a repository, and runs update steps (`ApplyUpdateSteps`) instead of plain `Activate` (H: CLI help, wiki 08; C for the refusals).
L10. Lock file creation (`-create-lockfile`) applies only to the top-level module, and a lock-file error is reported but does not fail the load (C).
L11. Namespace default modifiers (`default-modifiers -set`) are merged into every command's data, including `-DNoTransaction=1` (H: CLI help example). Interaction case: they are also merged into the `zpm` sub-array that `history` reads as filters (C), so a default modifier becomes a history filter column.

### 1.2 Transaction history

H1. Logged actions: `load`, `install` (including as a dependency), `uninstall`, `update` (H: #366, PR #578 isc-dchui r2557338086, CLI help). Other commands are not logged (H: same comment).
H2. Fields: action, package, version, source registry name/moniker/details for installs, start and end time, user, `Success` (raw `%Status`), `Committed`, full command string, per-phase name/times/status (H: #366, PR #578). The `Namespace` field from #366 is superseded by per-namespace storage (H: PR #578 isc-kiyer r1925176116, isc-dchui 2025-11-24).
H3. Failed actions are still logged, and rollback of the action must not remove its record (H: #366 "if install rolls back we still need the history"). A record exists from the start of the action, so a process that dies leaves a record with no end time and a placeholder version (H: wiki 09).
H4. `Committed` means the action's changes were kept, by a commit or by writing outside a transaction (H: #1237, PR #1322, CHANGELOG, `AbstractHistory` doc). Required cases: success → committed; non-dev failure inside the transaction → not committed; `-dev` failure before the first commit → not committed; `-dev` failure after the first commit → committed; `NoTransaction`/`NoJournal` failure after writes begin → committed. Uninstall is unchanged: it has no transaction, so its `Committed` only mirrors success (H: PR #1322 body).
H5. Outcome-changing cases I expect to probe:
- Dependency records written inside the parent's transaction. `HistoryTemp.Init` saves the twin `History` row inside the open transaction, and the dependency's `%OnClose` copy also runs inside it (C). When the parent later rolls back, I expect the dependency's `History` row to vanish (insert and update both undone; the IRISTEMP row already deleted). That violates H3.
- A dependency record finalized as committed (nested `TCOMMIT` is not durable) while the outer transaction later rolls back.
- Abnormal end after a dev-mode commit. `SetCommitted` writes only the IRISTEMP twin, so the persistent row keeps `Committed=0` and `Success=0`.
- `uninstall -r` of a dependency that `Clean` skips because other modules need it. `Lifecycle/Base.cls:471-484` still finalizes that record as successful, so history shows an uninstall that did not happen.
- A phase that exits through `quit:$$$ISERR(tSC)` (invoke failure) never gets `FinalizePhase` with the error, so it stays "in progress" (C).
H6. Readers: `history find` (default, newest first, limit from `DefaultLogEntryLimit`, default 20, `0` = all), `-sort asc|desc`, `-globally` (per namespace, limit per namespace), `details <id>` with `-phases` (current namespace only), `schema`, class queries `Records` and `GlobalRecords`, plain SQL on `%IPM_General.History` (H: #366, PR #578, wiki 09).
H7. Filters: `-D<column>=<value>`, ANDed; `*` wildcard; `>`, `>=`, `<`, `<=`, `<>` prefixes (H: wiki 02/09, PR #578 thread kept the prefix syntax despite isc-kiyer's concern about literal values). Filtering on `Version_Major`…`Version_Build` is documented (H: wiki 09). Case: `ConstructSQLWhere` stops at the first column name that is not purely alphanumeric (`History.cls:103-105`), so `Version_Major` and every column sorted after it are silently dropped.
H8. Delete: `history delete` needs a filter or `-confirm` in the current namespace. `-globally` deletes across namespaces and needs no `-confirm` (H: wiki 09 states this, CLI help "Ignored if -globally is passed too"). PR #578 isc-kiyer r1816830920/r1816844714 asked that delete be filterable and scoped. Case, wrongly permitted: `history delete -DVersion_Major=1` passes the "has a filter" guard, the filter is then dropped, and every record in the namespace is deleted (with `-globally`, every record on the instance).
H9. Retention: none by default; history is kept forever unless the operator opts in with `config set HistoryRetain <days>`; `0` disables (H: isc-tleavitt on PR #992 "maintain all history by default and have purge be opt-in", wiki 09). The purge runs on IPM invocation at most once per calendar day, across all namespaces, compared on `TimeStart` (H: wiki 09). Case: the cutoff is built as `<='<date>'` with literal quotes (`History.cls:172-173`), and `DATEADD` on a `$horolog` integer may not give a timestamp, so I expect the purge to delete nothing or the wrong set. Case: a purge failure makes `Shell` return before running the user's command (C), so retention problems can block every command.
H10. Protection: a finalized record cannot be edited, by SQL or objects; inserts and deletes remain (H: PR #578 isc-kiyer r2583818448, isc-dchui r2586415526, wiki 09 "append-and-delete only"). Records that never finalized (abnormal end) stay editable (C).
H11. Self-uninstall of IPM: the record is finalized and copied before IPM's classes are deleted, and the history data is kept ("except history log" in the full-cleanup prompt) (C plus user-facing prompt text).
H12. Storage scope: per namespace (H). IDs are unique only within a namespace (H: wiki 09).

## 3. Findings

### R1-ONT-01: Dependency and nested records may vanish on rollback, and no I statement forbids it
- Severity: material
- Kind: missing intent (explicit commitment weakened into a Q)
- Source or owner: issue #366 by isc-tleavitt: "History should be logged for … 'install' (including as a dependency)" and "we still want to log failed installations … if install rolls back we still need the history". `wiki/09` L18: "IPM records every `install`, `load`, `uninstall`, and `update` it attempts, whether or not the attempt succeeded". Owners: `history.survives-rollback` (I), `history.survives-rollback.temp-copy` (D), `history.dependencies.parent-rollback` (Q), `history.committed.nested` (Q).
- Trigger: `load b2-par-depfail` (B2 A3: the dependency's own Activate fails) or `load b2-par-actfail` (B2 A1: the parent fails after the dependency loaded). Also `tstart` + `load …` + `trollback` by a program calling `%IPM.Main:Shell` (B2 D1), and Invokes that run nested `Shell` commands inside the installer's own load (`ipm-setup` metadata).
- Discrepancy: `history.survives-rollback` promises survival only for the rollback of a record's "own action". Coverage map section 5 row 2 confirms the I rule is top-level only, and the dependency case is left to Q `history.dependencies.parent-rollback`. That Q's survival half is already answered by #366, a class (a) source: a dependency install is a logged action, and a rolled-back install must keep its history. Under the current wording, an implementation that drops every dependency record when the parent rolls back satisfies every I statement. B2 confirmed this is what the product does (defect D1, including the record of a dependency that itself failed: A2, A3). The caller-transaction case (B2 D1) loses the top-level record entirely. Q `history.committed.nested` asks only about `Committed` and never about whether the record survives. D `temp-copy` says the writes happen "outside the action's transaction". Under a caller's or parent's transaction that statement is still literally true and still lets the record be lost.
- Limits: I did not check whether maintainers consider a caller-held transaction a supported use of `Shell`. The caller case is weaker than the dependency case. I did not read the Verus model, so I do not know whether it relies on the "own action" scoping.
- Proposed repair: Ontology (A3 owner). Widen `history.survives-rollback` (human-provided, #366) to: a record survives any rollback that undoes its action, including a parent load's rollback of a dependency. Move the survival half of `history.dependencies.parent-rollback` into that I or into `history.dependencies`. Keep the Q only for what `Success` should read, because `Committed` is already fixed by `history.committed` (changes not kept means uncommitted). Add a Q, or a bullet in `history.committed.nested`, for record survival under a caller's transaction, with provisional answer "survives", citing #366. Mark `temp-copy` as satisfying the rule only for top-level actions at `$TLEVEL=0`, and record D1 as a confirmed product defect in `history.dependencies` metadata with B2 runs `20261113T184617Z-repro-dep-history-lost` and `…184632Z-repro-caller-tx-history-lost`. Product repair proposal, for B to carry: write the permanent twin outside every open transaction (for example, defer the twin insert and the final copy to `$TLEVEL=0`, or write through a non-journaled path). Writers affected: `HistoryTemp.Init`, `PersistToTwin`, `%OnClose`, `LoadModuleReference`. Preserve: a top-level failure still reads `Committed=0`. Distinguishing check: B2 A1/A3 expect one dependency row with `Committed=0`, and A0 stays at two committed rows.

### R1-ONT-02: The abnormal-end rules adopt code artifacts and miss the Terminate path that B2 observed
- Severity: material
- Kind: incorrect intent, plus missing or stale evidence
- Source or owner: issue #1237 by isc-dchui, "`Committed` should reflect whether the action's changes were actually retained", with option 2's rationale "so the flag tracks how far the action actually got". `wiki/09` L215-219 recipe: "An install left the namespace in a bad state and you want to find failures whose changes were kept: `history find -Dcommitted=1 -DSuccess="0*"`". Owners: `history.record` (I), `history.record.abnormal-end` (Q), `history.locked` (I), page definition of Finalized.
- Trigger: (1) A `-dev` load SIGKILLed during Activate (B2 C4R). The manifest and classes stay, and the durable row reads `Committed=0`, `Package=""`, no phases. (2) A `-dev` load ended by `$SYSTEM.Process.Terminate` during Activate (B2 C2). The row is finalized, so it is locked, with `Success=0`, no end time and an open Activate phase. (3) A non-dev load terminated during Activate (B2 C1). `%OnClose` ran before IRIS rolled back, so its copy was undone and the IRISTEMP row with the real values was deleted.
- Discrepancy:
  - The provisional answer of `history.record.abnormal-end` ("nothing reliable … readers must not trust `Committed=0`") weakens #1237 to match the code. A3 rejected the same kind of weakening for phases in disposition R3 but kept it for `Committed`. As a result, the wiki's documented recipe misses exactly the crash case (C4R) that leaves a namespace in a bad state.
  - `history.record` makes "a placeholder version" part of the required crash outcome. That describes the start-only write (`AbstractHistory.cls:17`, `:61`) and is not a need. C2 "deviates" only by giving more information.
  - No statement or Q covers a finalized record of an action that never ended. C2 creates one, and `history.locked` then makes it uncorrectable. The page's own definition of Finalized ("a record whose action has ended") does not allow it.
  - Metadata of `history.record.abnormal-end` and `history.record` still asserts OBS-H6: start values only, the IRISTEMP copy stays until restart, the record is never finalized. B2 N-P10 refuted this for the Terminate path. It holds only for SIGKILL.
- Limits: I relied on B2's observations. I did not re-run them. P-3 (IRISTEMP after restart) is unobserved.
- Proposed repair: Ontology. In `history.record`, drop "and a placeholder version" from the required outcome. Say that fields not yet known may be missing, and keep the phase rule. In `history.record.abnormal-end`, make the provisional answer follow #1237: write `Committed` to the permanent record at each commit, so an unfinished record reports kept changes. Move "unknown outcome" to the alternative, or keep the Q and state that the current provisional answer contradicts #1237 and the `wiki/09` recipe. Add a Q under `history.locked`: may a record whose action never ended be finalized? Provisional answer "no", citing the definition. Replace the OBS-H6 metadata with B2 C1, C2, C3 and C4R and the Terminate versus SIGKILL split. Product repair proposal: persist `Committed` and the phases to the twin at each commit point when `$TLEVEL=0`, and do not set `Finalized` from `%OnClose` when `TimeEnd` is empty. Distinguishing checks: C4R expects `Committed=1`, C2 expects `Finalized=0`, and C0 stays finalized and committed.

### R1-ONT-03: A refused `load` records an empty package even though the name is known, and nothing flags it
- Severity: material
- Kind: incorrect intent (wording hides a B2-observed violation)
- Source or owner: issue #366 field list ("Package name"). `wiki/09` L69: the package "May be empty if the action failed before a name was known, for example when loading a directory that has no valid `module.xml`". Owner: `history.fields` (the `Package` bullet).
- Trigger: `load <update-simple 1.x dir>` while 3.5.0 is installed (downgrade refusal), or `load 2.x` (update-required refusal). B2 g3, g6, g7, R4: refused loads record `Package=""` and `<unset>`, so `history find -DPackage=update-simple` shows 14 of the 20 rows whose command names that module.

Neither `history.fields` metadata nor coverage-map section 4 mentions this B2 observation. It affects exactly the refusals that `history.actions` says must be recorded.
- Limits: `install` and `update` refusals carry the name from their arguments. Only `load` (and `update -path` before `SetName`) is affected. I did not check the dependency-conflict refusal.
- Proposed repair: Ontology. In `history.fields`, say `Package` is empty only when no manifest could be read. Add a suspected-gap note citing B2 g3, g6, g7 and R4 (`20261113T182832Z-cases-dg`, `…184444Z-cases-hr`). ## 5. Wrongly permitted behavior and false premise attempts

- Wrongly permitted, succeeded: R1-ONT-01. A history that drops every dependency record when the parent rolls back satisfies all I statements, because `history.survives-rollback` covers only the record's "own action". #366 says it is wrong, and B2 D1 shows the product does it.
- Wrongly permitted, succeeded: R1-ONT-03. Refused `load` records without the module name satisfy "may be empty if the action failed before the name was known". The wiki and #366 say it is wrong, and B2 g3 shows it.
- Wrongly permitted, rejected: `history delete -DVersion_Major=99` deleting everything. `history.read.filter` ("Versions are filtered by part … Filters work the same way for `find` and `delete`") forbids it, so the ontology is correct and the product (B2 D2) is not.
- Wrongly permitted, rejected: a refused downgrade with `-force` or `-dev`. `load.refusal.downgrade` forbids it. Valid completion survives: same-version load (`load.same-version`, B2 g2).
- False premise, found: D `history.survives-rollback.temp-copy` assumes the final copy runs after the action's rollback ("both writes happen outside the action's transaction"). On `$SYSTEM.Process.Terminate`, `%OnClose` runs before IRIS rolls back the open transaction (B2 N-P10, C1). The copy is undone and the only IRISTEMP copy is deleted. The premise holds for an ordinary error return, where `LoadNewModule` rolls back before the log object is released. It does not hold for process termination. Folded into R1-ONT-02.
- False premise, checked and holding: "IRISTEMP is not undone by rollback" (B2 N-P04) and "an inner commit is not durable under an outer rollback" (N-P03). The ontology's nested-commit Q is built on these and they hold.
