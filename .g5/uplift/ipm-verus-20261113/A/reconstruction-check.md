### 1.2 Package loading as reconstructed

Inputs: a path (absolute folder with `module.xml`, `.tgz`/`.tar.gz` archive, or git URL with `-branch`), `-dev`/`-nodev`, `-force`, `-env`, `-quiet`/`-verbose`, `-bypass-py-deps`, `-extra-pip-flags`, `-create-lockfile`, `-skip-sync`, `-D<name>=<value>` (including `NoTransaction`, `NoJournal`, `NoMapping`), ignored `-synchronous`.

Sequence I would build (diagram order; the page says only the blocks are required):

1. Create the history record.
2. Check the path; refuse an empty or relative path; a missing path is an error. Clone a git URL. Unpack an archive into `<ModuleRoot>/<name>/<version>/` through a temporary folder that is always removed.
3. Start a transaction unless `NoTransaction`/`NoJournal` (journaling off for the process during the change).
4. Version checks against the installed module of the same name: refuse an older version ("Cannot downgrade", nothing lifts it); refuse a newer version that declares `<UpdatePackage>` unless `-force` (and provisionally `-dev`); the same version reloads.
5. Validate and save the manifest; refuse a missing or invalid manifest.
6. Developer mode with a transaction: commit (first commit), open a second transaction.
7. Check system requirements; refuse on failure (provisionally before any write in every mode).
8. Load dependencies one at a time in dependency order, `.modules` folder searched first and its temporary repository always removed; normal mode for dependencies except filesystem `+snapshot` deps of a dev load; any dependency failure fails the load. Developer mode: commit the dependency transaction only if all succeed, otherwise roll all of them back.
9. Run Initialize, Reload, Validate, Compile, Activate (+ApplyUpdateSteps for update); developer mode runs them outside a transaction.
10. Normal mode: commit on success, roll back everything (including dependencies) on any failure.

Concrete outcomes:

| Case | Database and files | History record |
|---|---|---|
| Valid completion | Module and dependencies installed, transaction committed; temporary unpack folder and `.modules` repository removed; lock file if requested. | Parent and one record per dependency: `Success` OK, `Committed=1`, end time set, five phases (six for update) with end times, finalized and read-only. |
| Refusal before any write (downgrade) | Installed module unchanged in every mode. Files already unpacked stay (rollback scope Q). | `Success` = error, `Committed=0`, end time set, no phases. |
| Failure after the first commit, dev mode (e.g. Compile error) | Saved manifest stays; dependencies stay if they all loaded; work of phases before the failure stays. | `Success` = error, `Committed=1`, phases up to and including Compile, Compile with error status and end time. |
| Failure with `-DNoTransaction=1` | Everything written before the failure stays. | `Success` = error, `Committed=1` if the failure came after the first write (manifest save), `0` if before. |
| Dependency succeeds, parent fails | Normal mode: dependency rolled back with the parent. Dev mode: dependency kept if the failure is in the parent's phases; rolled back if a later dependency fails. | Dependency keeps its own record (provisional, Q parent-rollback) with `Success` OK. Its `Committed` value is undecidable from the text (see U3). Parent: `Success` = error, `Committed` per mode. |
| Process killed mid-load | Not stated on the load page. I would assume IRIS rolls back the open transaction, so normal mode keeps nothing, dev mode keeps what was committed, no-transaction keeps what was written. Files, the git clone and the `.modules` temporary repository stay. | A record with empty end time and placeholder version; outcome unknown; `Committed` and phases not to be trusted (provisional). |
| Filtered `history delete` | Not applicable. | See 1.3. |

### 1.3 Transaction history as reconstructed

What and when:

- Record every `install`, `load`, `uninstall`, `update` attempt, including refused and failed ones and installs started for dependencies. `update`/`uninstall` argument refusals need not be recorded (provisional). Lifecycle commands, `sync`, `list` and similar are not recorded.
- Create the record when the action starts, with empty end time, placeholder version `<unset>`, `Success=0`. Keep the in-progress record in IRISTEMP so a rollback cannot remove it. Add a phase entry (name, start, end, status) per phase. Set `Committed` at each commit, or just before the first write without a transaction. At the end, set `Success` and end time, finalize, copy to the namespace's permanent log outside the action's transaction. Finalized records cannot be changed by SQL `UPDATE` or object save, only deleted.

Fields: `Action`; `Package` (may be empty); `Version` (`<unset>` until known); source name/type/details (install only, empty for load and uninstall); `TimeStart`, `TimeEnd` (empty while running or after abnormal end); `UserName`; `Success` (status, `0` in progress); `Committed`; `CommandString`; `Phases`.

`Committed` (load/install/update): kept any change by commit or by writing outside a transaction. Success implies committed; full rollback (including dev failure before first commit) is uncommitted; dev failure after first commit is committed; no-transaction failure is committed once writing started; a refusal before any write is uncommitted in every mode. Uninstall: `Committed` equals success. Nested transactions and non-database side effects are open (provisionally: exact only outside any transaction; side effects not counted).

Reading: `history` (alias `log`) with `find` (default), `details <id>`, `delete`, `schema`; anything else is an error. `find` newest first, `-sort asc|desc` by ID, `-limit n` (0 = all, default `DefaultLogEntryLimit`=20). Filters `-D<column>=<value>`, all must match, `*` wildcard, `>`, `>=`, `<`, `<=`, `<>` prefixes, version parts such as `Version_Major`; same for `find` and `delete`; no filter may be silently dropped (provisional); default modifiers are not filters (provisional). `details` shows all fields, raw status, `-phases`; unknown ID is an error. `-globally` reads all IPM namespaces grouped by namespace, limit per namespace. API: SQL table `%IPM_General.History`, queries `Records` and `GlobalRecords`.

Deleting and keeping: `delete` removes matching records; unfiltered needs `-confirm`; `-globally` deletes in all namespaces without `-confirm`; `-verbose` reports counts and skipped namespaces. `HistoryRetain` days (0 = off) purges by start time across all namespaces at most once per day on any command; a purge failure should not stop the command (provisional). Uninstalling IPM keeps the log and should not delete other namespaces' in-progress records (provisional).

Concrete outcomes for history: as in the table in 1.2, plus:

- Filtered `history delete -DPackage=foo`: delete only matching records in the current namespace, no `-confirm` needed; with `-confirm` still only matching (provisional); with `-globally`, matching records in every namespace; an unknown or version-part column must not widen the delete (provisional).

## Verdict

The ontology lets a fresh reader find and rebuild IPM's capabilities, and in the formal scope it fixes the outcome of most loading and history cases, including the commit matrix by mode. It is ready for modeling once the six material corrections are made: R1 `deps`, R2 `history.survives-rollback.temp-copy`, R3 `history.record.abnormal-end` and `history.phases`, R4 `history.committed.nested` and `history.dependencies.parent-rollback`, R5 `load.outcome` and `transaction.opt-out`, R6 `load.outcome` and `load.refusal.manifest`. Each is a small edit to an existing owner and needs no new maintainer decision. They change the state the history model must carry during an action (R2, R3), the `Committed` value of dependency and refusal cases (R1, R4, R6), and the load model's interruption transition (R5). R7-R14 are wording or visible-condition fixes that can follow.
