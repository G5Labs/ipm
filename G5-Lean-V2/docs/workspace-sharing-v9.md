# Workspace sharing — v9

Status: historical architecture, draft 9, 2026-09-17; audience sections updated for #1107. See the [coordinated audience cutover](workspace-audience-cutover.md). This contract supersedes [workspace sharing v8](workspace-sharing-v8.md) for the proposed implementation; earlier versions remain unchanged. It incorporates the September 17 meeting and the user's subsequent access clarification. It is no longer a verbatim copy of the original `workspace.share.md` note, whose reader-preview and identical-live-read permissions are superseded here. See [design v9](lean-backend-design-v9.md), [plan v9](lean-implementation-plan-v9.md), and [Workspace VM API v9](workspace-vm-api-v9.md).

**The model in one line.** A workspace has exactly one writer, its owner. Everyone else with access browses durable state. Contributing or executing requires a fork the contributor owns, or an explicit ownership transfer.

## Access and identity

“Org admin” means org role `owner` or `admin`. Only active members with role `owner|admin|member` may own, fork or receive a transfer; `viewer` cannot (`ORG_ROLE_READ_ONLY`). Read access follows the fixed [workspace audience](../.g5/ontology/features/workspaces.g5.md#g5.workspace.audience): eligible active organization members read ordinary workspaces and Base; personal workspaces admit only their owner and active organization owners/admins. Formal review runtimes retain their restrictive workflow authority, including for owners/admins. Write access is the single `owner_user_id`, not a list. An org admin must take ownership before using owner capabilities, subject to the workspace kind restrictions. The creator and former owners have no residual administration or additional read authority. Ownership alone does not make a base workspace writable; base workspaces have no VM and require a checked fork.

| Capability | Non-owner with read access | Owner |
|---|---|---|
| Browse files, tree, docs, ontology and Changes | Git-only durable view | Live VM when attached and healthy; otherwise Git-only durable view |
| Browse durable chat history, task timelines, PRs | yes, under their own ACLs | yes, under their own ACLs |
| Clone/fetch authorized repository refs | yes | yes |
| Use VM filesystem API, watches, runtime inspection, ports or live module-log subscriptions | no | yes, with current attached healthy VM |
| Start, replace or cancel preview; access its live relay | no | yes, after explicit Start/Resume completes |
| Send into chat, answer a live native question, invoke agent/command work | no | yes, after explicit Start/Resume completes and subject to task/session policy |
| Open, attach to, write, resize or close a client/web Terminal | no | yes, with current attached healthy VM |
| Edit, upload, rename or delete files | no | yes, with current attached healthy VM |
| Push existing commits to the workspace branch, including from a laptop | no | yes, while the current workspace is running with admission open |
| Stop, resume, restart or delete the workspace | no | yes |
| Create a PR or record a workspace approval decision | no | yes, subject to PR/revision authorization |
| Transfer ownership | org admin only | yes |
| Fork into a workspace they own | eligible org member only | yes |

The client is read-only whenever the caller is not the owner or the owner's workspace lacks an attached healthy VM. Start/Resume is explicit; a clearly labeled compound Start workspace and chat/preview/terminal action may record that intent and wait for readiness. Save, upload, ordinary input submission, preview-only requests and file reads do not boot the VM implicitly. Mutation and execution APIs return `WORKSPACE_STOPPING` while stopping or transferring, otherwise `WORKSPACE_NOT_RUNNING` until readiness completes, even if a client races attachment. Healthy attachment means running, admission open and a fresh passing private health report. Explicit Start and its optional queued launch are one persisted owner/generation-bound intent in `workspace_vms`, with queue cancellation and expiry; no task or passive read can manufacture it. Durable history and metadata views do not require a VM. V9 interprets the no-VM read-only requirement to also gate user-originated mapped-branch pushes, including laptop receive-pack: current owner plus running workspace with admission open is required; otherwise return `WORKSPACE_STOPPING` during teardown/transfer or `WORKSPACE_NOT_RUNNING`, without booting. This is a v9 design interpretation of the clarification. Authorized lifecycle flush and control-plane fork/merge/import use their separate service capabilities. Native Git within the attached VM remains available without shell-command policing. The absence of a VM does not prevent control-plane lifecycle operations such as fork, transfer or explicit Start/Resume.

## Read source and isolation

`orgs.access_generation` is the single MVP ACL revision, incremented atomically with org membership/role and workspace owner/deletion changes. Scopes, caches, tickets and future stream delivery bind it; old generations never preserve authority after revocation.

Non-owner repository-content reads always use internal Git, even while the owner's VM runs. This includes file/tree/stat requests, rendered documents, ontology projections, diffs/Changes, downloads and their cache or subscription paths. They never invoke `fs.read/list/stat/watch`, inspect the live runtime, enumerate ports, follow live module logs or access a preview relay. The owner uses live VM content only while attached and healthy; otherwise the same durable Git view applies. Reads never wake a VM or request a source flush. Git/durable reads do not extend VM idle time; attached-owner file RPC may count as activity under the existing policy.

The v9 draft choice is to retain the last **complete verified flush receipt** as the durable source when available, otherwise the branch-head vector. This is a design choice completing the meeting's Git-only requirement, not a meeting agreement about snapshot selection. A response identifies `source=live|flush|committed`, the repository/OID vector or live `vm_id`, and observation time/freshness. A complete receipt may include dirty or unpushed work captured during a prior lifecycle flush; it is not the current live tree. Never combine a partial receipt with unrelated current branch heads and label it one snapshot. Reader-side Changes compares pinned durable Git revisions and cannot report current uncommitted VM edits. Document/ontology snapshot views render from the pinned Git tree, not the mutable branch projection rows. Committed views use projections only when `applied_oid` matches the selected OID; otherwise they render from Git. Provider-backed committed views expose mirror observation time/state and a stale marker. A read or fork pins its source against pruning before releasing selection locks.

Durable chat, task and PR records remain platform metadata under their own ACLs; Git-only repository browsing does not move those records into Git. Reading a stored event history must not become a live VM log subscription. Every request and stream opening revalidates current ownership, access and incarnation where applicable. Ownership/access changes close live and durable metadata streams, invalidate pending responses and clear source-dependent client/server caches; delivery checks the org access generation so no payload ordered after revocation uses earlier authority; an old owner's editor or preview URL cannot retain VM access after transfer.

## Forking and collaboration

A working workspace maps one workspace to a vector of member repositories sharing the exact proposed workspace/branch name. Checked fork is the only branch-creation path. Validate that name and ref-prefix conflicts in **every** member repository, including connected provider refs; any collision asks for a different name, with no automatic suffix or silent adoption.

Unfinished workspace_forks records (pending and aborting) are the durable all-member reservations; no separate reservation table is introduced. The exact name/member set is immutable. Admission locks existing repo rows in canonical order and then freshly queries overlapping exact/slash-prefix claims under READ COMMITTED before committing pending. All-member Git proof and retry/partial-failure recovery follow design v9 §5.8.

A request key is unique for `(org, requester)` and binds the original request digest; a changed request under that key is refused. Provider namespace verification uses the repository’s recorded connection credential and fails closed if unavailable. Successful all-member completion or verified abort cleanup ends a temporary claim. Stalled/ambiguous cleanup retains it without expiry, with admin reconcile and visible recovery status; delayed workers cannot recreate refs after settlement. Conflict checks see private unfinished operations without disclosing their details. Repository deletion and conflicting import/bootstrap paths honor the same claims.

Git clone/fetch, arbitrary-OID reads, receive-pack and host materialization enforce the same authorized object closure, not only hidden ref names. Design §5.3 specifies a self-contained immutable scoped Git view without global alternates, a scope-bearing manifest/cache key, freshness/revocation checks and a scoped receive-pack transaction that cannot resolve hidden thin-pack bases or adopt guessed sibling objects. Host warm caches export only that verified closure into a clean guest `.git`. A repository or URL match alone cannot authorize cache reuse across workspaces.

A reader fork pins the visible complete Git receipt or branch-head vector and never calls the source VM or causes it to flush, stop or wake. An owner may request a fork from their running live work through the existing owner-authorized `reason=fork` flush; without that, fork uses the selected durable source. The UI identifies the exact pinned source and its age so a reader understands that newer unflushed edits are excluded. The child branch uses each receipt’s `local_branch_oid`, independently of the source’s foreign/detached HEAD; its own checkout applies the selected snapshot as dirty edits on that branch. Copied receipts have `origin=fork_copy` and a fresh child ID without a fabricated VM identity. The completed child is created stopped; attachment is a later explicit action after the entire member vector commits. No reader can execute in or modify the parent by initiating a child.

Code changes return through the authorized PR/merge/adoption flow; a child owner does not acquire parent write access. Passive reading does not need a fork. Agent-assisted review, explanation, testing or preview does, unless the person already owns the workspace in which it runs. These may be ordinary owner conversations in an explicitly created child; they do not imply a dedicated review request/result workflow. The Workspace service owns checked child creation; generic agent-initiated workspace creation remains deferred.

## MVP workflow scope

Dedicated durable, source-versioned review/explainer returned-results workflows are deferred beyond MVP. There is no request acceptance/result return UI, producer designation, candidate/publication protocol, special child idle policy or completion-driven compute cleanup. Ordinary conversations may review or explain files and retain chat/task history under normal workspace ACLs.

Checked fork retains the ordinary source/target link and pinned source vector in `workspace_forks`. It creates a stopped workspace owned by the caller using the exact common branch name. The owner starts it explicitly and may perform ordinary work, then use normal Stop/idle/transfer rules. Fork isolation does not grant parent writes or formal approval authority. Later returned-results work requires its own post-MVP design rather than a dormant MVP schema.

## Preview

Preview HTML and WebSocket traffic use an isolated per-workspace/port origin on a separate registrable domain; platform-origin routes only bootstrap and fail closed if configuration is missing. Host-only partitioned Secure tickets support proved embedded-browser configurations; browsers that cannot establish that isolated embedded session get Open in new tab, never same-origin serving. Current-owner/incarnation/access-generation checks apply in both modes.

- Preview remains a durable **task of kind `preview`** with a service lifecycle, visible and cancellable in the task queue. It records the owner who launched it. A compound explicit Start-and-preview records a queued task before capacity/attachment waits, so the owner can see and cancel it before execution; cancellation prevents delayed readiness from launching it.
- Only the current owner may start, replace or cancel it, inspect its live ports, or access its live relay. A non-owner gets a fork path, never a reader-preview exception. Start/Resume must complete first; the preview button does not implicitly attach a VM.
- One active preview per workspace. Starts, replacements, cancellations and lifecycle barriers serialize; ambiguous starts are reconciled and the old service is confirmed stopped before replacement. A cancelled task cannot be revived by delayed delivery.
- It runs under workspace/owner identity and declared workspace secrets. The repository profile promises no tracked-file writes; that is not enforced filesystem isolation. Any writes are owner-visible Changes and are included in a subsequent lifecycle flush. A disposable-write overlay remains later hardening.
- It consumes no bounded-task concurrency slot, has no wall-clock task limit, and never automatically restarts after stop/resume, transfer, failure or rollout. Authorized owner HTTP requests and WebSocket opens count as activity, with at most ten-second write debounce; keepalives, output and a running service process alone do not suppress idle reclamation.

## Ownership transfer

The owner may transfer to an eligible active org member; an org admin may transfer to an eligible member, including themselves. Admin transfer does not require old-owner consent: it is the explicit existing recovery authority, not a live-VM bypass. Completion atomically notifies both old and new owners (deduplicated for self-transfer) and records who requested it. The old/new owner, requester, idempotency key and completion time are recorded. No live-VM handover/debug exception is in MVP.

Transfer closes admission, interrupts executions, closes preview/terminal streams, persists task/session continuation state and invalidates process-bound native requests whose provider process ended while preserving confirmed deferred questions. It then flushes with `reason=shutdown`, persists required journal/Agent state, confirms host exit, releases the incarnation, verifies retained-root purge and atomically changes owner/audit state. Transient harvest/database failures follow the ordinary stop failure policy; only explicitly invalidated provider-session bundles may use delivered-history fallback. An ineligible target discovered during recovery aborts with the old owner unchanged, without automatic reboot. An already stopped workspace needs no VM boot or flush, but still purges any retained root before transfer. Flush failure aborts transfer and retains the old owner; an ambiguous stop is reconciled, not treated as release. Transfer has no forced-loss completion.

The new owner explicitly resumes; transfer never boots a VM or releases held tasks. User stop, idle stop and unexpected loss likewise require explicit owner Resume for reattachment. Deliberate drain/rollout may carry the already recorded current-owner continuation authority only if no later stop, transfer or purpose completion superseded it; queued demand alone grants no wake authority. That fresh incarnation uses the new owner's provider account. Retained task continuations preserve their task/session/dependencies and run new attempts. Confirmed native deferred questions remain answerable by the current owner after restoring the saved native session on attached ready compute, without automatic expiry or a replacement question. Ended process-bound requests remain historical. The Agent API owns immutable first-answer handling, current-owner checks at acceptance and dispatch, native tool identity matching and delivery evidence. The previous owner retains only their independently granted read access and switches to Git-only repository browsing. Membership removal or demotion to viewer is refused with `OWNER_OF_WORKSPACES` while any workspace remains owned; administrators first complete ordinary transfers or deletions. Removing membership never silently selects a replacement owner or leaves an ex-member VM running. Org deletion is a durable offboarding operation that drains compute and confirms root/repository/credential purge before tenant rows are removed; it is not a direct cascading SQL delete. User erasure policy must preserve necessary org-owned content/provenance and is specified separately from this runtime redesign.

## Acceptance boundaries

Required implementation coverage includes non-owner denial through every file/stream/preview/terminal/task sibling API; reader Git-only reads and fork while the owner's VM is dirty/running; projection/cache source isolation; explicit owner attachment before editing/upload; owner/VM changes racing requests or stream delivery; all-member fork collision and recovery; ordinary fork source pinning and task/session history; stop/restore failure recovery; idle owned workspaces; and transfer without any reader-preview wake bypass. These are proposed implementation gates, not claims that v9 is implemented.
