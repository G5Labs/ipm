## 1. Boundary

A worker host is a slot provider. It runs `g5d host`, dials one outbound tunnel to the control plane, and boots, stops and relays workspace VMs on command. It has no task logic, no knowledge of branches or approvals, and no opinion about what runs inside a VM.

| Place | Owns |
|---|---|
| Control plane (g5-api) | The host registry, placement, org quotas, VM incarnations (`workspace_vms`), workspace tokens, provider credentials at rest, the workspace owner and transfer audit, the stop sequence and its durable cut. |
| Workspace VM lifecycle service (control plane, `WorkspaceVmService`) (post-MVP, P4.12: `vm.grants.update` and `grants.resolve`; P8.14: `lease.acquire`; P8.10: `host.credential.renew`) | The only control-plane client of the `ctl` stream: it issues `vm.start`, `vm.stop`, `vm.status`, `vm.grants.update`, `roots.purge` and `host.drain`, and consumes `host.hello`, `host.heartbeat`, `vm.event`, `lease.acquire`, `lease.renew`, `grants.resolve`, `host.credential.renew` and `host.drained`. It owns `workspace_vms`, the stop sequence and the incarnation fence, and calls `WorkerHostService::place` for placement. |
| Workspace Runtime facade | The only control-plane client that opens VM channels (`rpc`, `pty`, `http`) through a host, after the lifecycle service has made the incarnation current. Other platform systems call the facade; nothing else reaches a host tunnel. Both clients share one tunnel registry (`host_id → connection`). |
| Worker host (`g5d host`) (post-MVP, P8.14: the per-VM lease timer; P4.12: the LLM and credential proxies) | Equal-size VM slots, libkrun boot and stop, OCI rootfs templates, the host workspace root and bare-repo cache, passt networking and port forwards, the stream multiplexer, the per-VM lease timer, the LLM and credential proxies, host-local observations. |
| Workspace VM (`g5d dispatch`) | Everything inside the VM. See workspace-vm-api-v9.md. |
| Git service | Refs and policy. The host caches bare repos as an optimization and never touches a ref. |

**Post-MVP (P8.14: the host-originated lease before boot; P4.12: grant updates).** Every host command is bound to a `host_id` and a valid host credential; every VM-scoped command additionally carries `(workspace_id, vm_id)`, a positive `budget_ms` and an idempotency key. The host measures the processing budget from frame receipt using its monotonic clock and refuses `expired` before beginning work after that budget. A budget limits processing; it does not authenticate command freshness or establish lease safety. A new VM must obtain the host-originated lease in §5 before boot, even if a delayed start command passes the local budget. Starts, grant updates and new streams require the current incarnation; superseded identities return `stale`. `vm.stop` is the ownership-fenced exception: the host stops any matching VM it owns, even if superseded, and returns `not_found` only when absent. Stopping stale execution must remain possible. The owner is immutable within an incarnation; only the current owner may launch or access a live preview, and a launch audit field is never a provider-account selector. Workspace-reader access grants no host stream or VM capability.

## 2. Host registry and lifecycle

### 2.1 Host states

```
provisioning ──registered + first heartbeat──► ready ──drain requested──► draining ──every VM released──► terminated
      │                                          │                              │
      └──never registered / bring-up abandoned───┴──heartbeat missing > 3 intervals──┴──► unreachable ──credential expired──► terminated
```

`unreachable` is new: it names the window in which the control plane has lost the tunnel but the host may still be running VMs. During it the control plane places nothing on the host, keeps every incarnation current until its lease expires (§5), and expects a reconnect with an inventory (§3.3).

### 2.2 Host record

```
worker_hosts(
  host_id PK, org_id, region,
  kind                 gce | self_hosted | macos_dev,
  status               provisioning | ready | draining | unreachable | terminated,
  slots_total          int,                -- G5D_HOST_MAX_MICROVMS
  slot_cpus, slot_mem_mib, scratch_disk_mib,
  runtime_identity     jsonb,              -- self-reported host/runtime versions and hashes (§3.1) (post-MVP, P8.14)
  runtime_identity_hash, runtime_identity_changed_at,  -- (post-MVP, P8.10)
  registration_token_hash NULL, registration_expires_at NULL,  -- (post-MVP, P8.10)
  registration_redeemed_at NULL, registration_revoked_at NULL,  -- (post-MVP, P8.10)
  capabilities         text[],             -- isolation:libkrun-microvm, agent_provider:claude_code, agent_provider:codex, net:passt, …
  credential_expires_at, credential_generation, drain_requested_at, drain_reason NULL, last_heartbeat_at, last_error,  -- (post-MVP, P8.10: credential_expires_at, credential_generation)
  cloud_instance_id, provision_error_code, provision_retry_count  -- GCE path only, as today
)
```

Slot occupancy is not a column. It is `count(workspace_vms where host_id = ? and status in (starting, running, stopping))`, so placement is derived from durable reservations instead of a second mutable counter. Host inventory and local admission locks reconcile pending/crashed placement with actual occupancy; differences are expected while a command is in flight.

### 2.3 Operator API

**Post-MVP (P8.10: the registration exchange).** Exposed by g5-api to org operators. SaaS keeps the GCE bring-up/reconciler, while all host kinds use the registration exchange below. A host belongs to one org; placement cannot lend its spare slots to another org. Host capacity and `max_running_vms` quota are separate limits. `kind` is a new constrained field, backfilled `gce` for existing cloud instance rows and `self_hosted` otherwise; an ambiguous historical kind requires explicit resolution. `last_heartbeat_at` is the API/logical name for retained physical column `last_heartbeat`; no physical rename is required.

| Method | Contract |
|---|---|
| `POST /orgs/:org/worker-hosts` (post-MVP, P8.10: the one-use registration token; the MVP route mints today's 24 h host JWT) | Insert one `provisioning` host row and mint a random 256-bit one-use `g5w_*` registration token bound to its `host_id` and `org_id`, TTL 1 hour, stored only as a hash plus expiry/redeemed/revoked times on `worker_hosts`. GCE delivers it through the existing bootstrap secret channel; self-hosted/macOS returns it once. The one-use exchange is new, not the retained reusable per-task worker token flow. |
| `GET /orgs/:org/worker-hosts` | Registry rows plus derived occupancy and the last heartbeat summary. Exists today. |
| `POST /api/internal/ops/workspace-leases/observe` (post-MVP, P8.14) | Deployment-wide operator-only fresh host lease observations; complete server-enumerated placement set, no caller-selected subset. P4.5 supplies the endpoint and authorization/coverage tests (§5). |
| `POST …/:host/drain` | Request drain. The control plane runs the stop sequence for every VM on the host, sends `vm.stop` for each, and marks the host `draining → terminated`. Returns immediately with a drain id; progress is on the host record. New; today drain exists only inside the rotation loop. |
| `DELETE …/:host` (post-MVP, P8.10: the `credential_generation` increment and the renewal refusal) | Drain, then terminate the instance (GCE) or forget the registration (self-hosted). Refused while any VM is active unless `force=true`, which records the loss per VM. Termination/revocation closes the active tunnel, increments `credential_generation`, and refuses reconnect/renewal even for an unexpired credential. Retained roots must be purged before reporting physical cleanup complete. |

**Post-MVP (P8.14: the `allowed-images` route and the retirement of `runtime-labels/refresh`; the MVP keeps `runtime-labels/refresh` and registry-authoritative labels).** `GET/PUT /orgs/:org/allowed-images` manages digest-pinned guest image references in org `configs`; writes require org-admin authority. Today's `POST …/:host/runtime-labels/refresh` is retired: image selection is per VM, while the host records its separate runtime bundle identity (§4). Per-host VM listings come from `workspace_vms` by `host_id`; there is no separate route.

## 3. Host ↔ control plane protocol

### 3.0 Versioning

Hosts, VMs and the control plane deploy independently, and a VM can live across several control-plane deploys, so every message on this protocol is versioned. This is the fix for the release-channel skews seen today (G5 #1860, #1883).

- `host.hello` carries `protocol_version` (integer) and the host's `runtime_identity`. The control plane answers `host.accept {protocol_version}` with the version it will speak, which is at most the host's. If it supports no version the host offers, it answers `host.reject {reason: unsupported_version, supported: [...]}`; the host then drains itself (refuses `vm.start`, keeps running VMs, keeps lease timers) and retries the tunnel with backoff, so an old host never runs new commands it cannot parse.
- Within a version, unknown fields are ignored on both sides and required fields never change meaning. Adding a field, a `vm.event` kind, or a result variant is a minor change; removing or renaming anything, or changing a result's semantics, is a new `protocol_version`.
- `VmSpec` carries `spec_version`. A host that does not know a `spec_version` answers `spec_rejected(unsupported_spec_version)`; placement then excludes that host for that workspace instead of retrying it.
- Deploy order follows from the above: control plane first (it must accept both the old and the new host version), hosts second, and a host is only drained for a runtime upgrade, never for a protocol upgrade it already speaks.

### 3.1 Transport

**Post-MVP (P8.10).** A new host first calls `POST /api/internal/hosts/:host_id/register {registration_token, runtime_identity, protocol_version}`. The API atomically consumes the matching unexpired, unrevoked, unused token on the existing host row; the path and row fix `host_id`/`org_id`, never the caller's payload. Replay, unknown, expired, revoked and wrong-host tokens return 401 with no credential. Registration commits before returning a credential; a lost response requires an operator to issue a fresh registration token for that same host, invalidating the previous credential generation. Registration tokens never open tunnels and remain independent of the per-task `worker_tokens` removal. P4.1 creates the required host columns; P4.4a implements this same exchange and credential validator for GCE, self-hosted and macOS enrollment before the v9 ctl path is enabled. GCE changes only token delivery through its retained bootstrap secret channel, never skips redemption or receives a pre-issued long-lived credential. P4.13 adds operator provisioning/issue/reissue/revoke surfaces, not another exchange or schema owner. Retained per-task host-up bootstrap remains explicitly legacy during producer migration; fixtures distinguish it from v9 enrollment and remove it with P4.9a/b after its last consumer. P9.1 updates installer protocol, not merely the old token's label.

**Post-MVP (P8.10: the renewable host credential, its `runtime_identity_hash` and `credential_generation` claims and its renewal).** MVP behaviour: the tunnel authenticates with today's 24 h host JWT, as today's tunnel does. One outbound WebSocket per host, `GET /api/internal/hosts/:host_id/tunnel`, uses a **host credential** with `aud=g5-host`, `token_use=worker_host`, `host_id`, `org_id`, `runtime_identity_hash`, `credential_generation`, `iat`, `exp`; TTL 24 h, renewal starts 2 h before expiry. The path, claims, registry row and `host.hello.host_id` must agree before any incarnation inventory or secret is sent. A second authenticated tunnel replaces the old tunnel for that host atomically; late messages from the replaced connection are ignored. Only the new connection generation may act.

**Post-MVP (P8.14: the self-reported runtime identity; P8.10: its hash in the host credential and the identity-change drain).** `runtime_identity` requires `g5d_version`, `runtime_dir_hash`, `module_catalog_hash`, `libkrun_version`, `libkrunfw_version`, `kernel_version`, `egress_policy`, and `providers` entries `{name, version}`. The API validates the schema, rejects duplicate provider names, sorts object keys and providers by name, emits compact UTF-8 JSON with no insignificant whitespace, and computes SHA-256. It stores that identity/hash at registration and mints the hash in the credential. Here `egress_policy` identifies the pinned enforcement implementation/version and mandatory platform deny profile; the per-org destination grant and its digest are the separate immutable `VmSpec.egress_policy`, not a host identity change. This is self-reported inventory, not remote attestation. A missing required field rejects hello. Changed identity accepts only a restricted reconciliation connection: no new placement or grant expansion, existing incarnations may finish their stop sequence, renewal is refused and the control plane starts credential drain (§8). A normal reconnect must match the registered hash. A host upgrade registers a new identity only after the previous host incarnation has drained. Enrollment and credential audits record actor/host/org/result without raw registration or renewable token values.

The socket carries the existing credit-flow stream multiplexer. Streams are tagged:

| Stream tag | Initiator | Payload | Bound to |
|---|---|---|---|
| `ctl` | host, exactly one per tunnel | JSON-RPC 2.0 both ways: commands in §3.2, messages in §3.3 | host |
| `rpc` | control plane | the dispatcher's JSON-RPC plus its pushed events, verbatim (workspace-vm-api-v9.md §2, §4) | `vm_id` |
| `pty` | control plane | raw bytes of one terminal, after a `terminal.open` on `rpc`; one stream per terminal | `vm_id`, terminal id |
| `http` | control plane | raw TCP to a guest port, for preview and port forwarding; **one stream per TCP connection**, so a browser page opens several streams to the same port and a hot-reload WebSocket is one long-lived stream | `vm_id`, port |

**Post-MVP (P8.14: the workspace access generation on relays and subscriptions).** Opening a VM stream carries `(workspace_id, vm_id)` and, for `http`, the target port in the stream header. Before opening any user-facing `rpc`, `pty` or `http` path, the control-plane facade verifies the current owner, healthy attachment and incarnation. Read/org-admin access alone never admits filesystem reads/watches, terminals, live runtime/port/log inspection or preview relays. Non-owner repository browsing stays on the Git service even when the VM is running. Every live relay and durable reader subscription carries the workspace access generation. ACL/visibility/ownership changes commit the new generation with the authorization change; delivery must revalidate the current generation before emitting new payloads, and stale streams/tickets close after commit. Async close (target within 5 seconds) is cleanup, never permission to deliver during that window; source-dependent caches are invalidated. A previous relay URL cannot retain access. Lifecycle/dispatcher internal traffic uses narrowly scoped service authority, not a reader capability. The host resolves the VM's forwarded listener port and per-VM listener token, dials the guest listener through passt once per stream, and copies bytes both ways until either side closes; nothing is multiplexed inside a stream, the mux is what multiplexes streams over the one WebSocket. A stream for a `vm_id` the host does not run is refused with `stale` and closed. There is no `llm` stream: model traffic never crosses the tunnel (§6).

### 3.2 Commands, control plane → host

All commands are request and response on `ctl`, idempotent on `(command, idempotency_key)`, with the original payload hash checked on replay (a different payload is `idempotency_conflict`). They carry `budget_ms` and are answered within the caller's wait budget or with `timeout`. A `timeout` is not a negative result: the host may still be executing the command, and the caller re-issues the same command with the same idempotency key until it receives a definite result. The host keeps the result of every completed VM-scoped command for at least `result_retention_secs` (default 600) so a retry after a tunnel drop gets the original result, not `not_found`.

| Command | Arguments | Result |
|---|---|---|
| `vm.start` | `workspace_id, vm_id, spec` (§4) | `started` \| `already_running` \| `slot_unavailable(reason: slots \| disk \| boot_capacity \| workspace_busy \| draining)` \| `spec_rejected(reason)` \| `boot_failed(reason, log_tail)`. `workspace_busy`: a VM of the same `workspace_id` with a different `vm_id` is still on this host (not yet exited), and the two would share one workspace root; the control plane places elsewhere or waits for that VM's `exited`. `boot_capacity`: more than `max_concurrent_boots` (default 2) boots are in progress; placement retries after backoff. |
| `vm.stop` | `workspace_id, vm_id, mode: graceful \| kill, grace_secs` | `stopped(exit)` \| `not_found`; never `stale` for a VM this host owns. `graceful` sends SIGTERM to the host-side VMM process group (`g5d vm-exec`) and SIGKILL at `grace_secs`; no delivery to guest PID 1 is promised; `kill` kills now. No rpc method is involved: by the time `vm.stop` is sent the workspace stop sequence has already run on `rpc` (admission barrier, `workspace.flush` with `reason: shutdown` (including a transfer stop)), including session harvest and journal drain/ack. The dispatcher needs no guest-SIGTERM handler for this contract. The host frees the slot only after the VMM process has exited, and keeps the workspace root and scratch disk for `spec.workspace_root.retain_hours`. A `vm.stop` for a VM that already exited returns `stopped(exit)` from the retained result while it is retained, and `not_found` only after that. |
| `vm.status` (post-MVP, P8.14: `refresh_lease` and the host-monotonic `lease_seq` and `lease_remaining_ms`; P4.12: `sessions`) | `workspace_id, vm_id, refresh_lease?: bool` | `{state: booting \| ready \| running \| stopping \| exited, vm_id, epoch, boot_at, ready_at, resources, lease_seq, lease_remaining_ms, streams_open, sessions}`; remaining time is sampled from the host monotonic timer after optional ordinary renewal (§5); no wall-clock expiry estimate substitutes for it. |
| `roots.purge` | `workspace_id, cache_generation` | `purged` \| `not_found` \| `workspace_busy`; after confirmed release deletes the named retained root and scratch generation, never an active or newer generation. Keeps stop receipts and event journal through their normal retention. Delete and transfer persist purge intents and retry after reconnect. |
| `host.drain` (post-MVP, P8.14: the lease-expiry exception) | `drain_id, budget_ms` | `accepted`. The host stops admitting `vm.start` and reports `drained` (§3.3) when its last VM exits. Stopping the VMs is the control plane's job; the host never stops a VM on its own except for lease expiry. |
| `vm.grants.update` (post-MVP, P4.12) | `workspace_id, vm_id, credential_grants` (the full replacement list, same shape as `VmSpec.credential_grants`) | `applied` \| `stale` \| `grant_unresolved(kind, target)`, in which case the previous table stays in force. The host resolves the new references, then swaps the proxy's grant table for that VM atomically: requests already in flight finish with the credential they started with, the next request uses the new one. Nothing inside the VM changes, no process restarts, no session is lost, because no provider process ever held the credential. This rotates the current owner's key or permitted gateway without restarting the VM. It cannot change `owner_user_id`, add a session/user grant, or transfer ownership; such requests are rejected before any replacement is applied. |

Host configuration (slot count, log level, proxy settings) is process configuration read at start, as today; changing it restarts `g5d host` after a drain. There is no inspect command: `vm.status`, `vm.event` and the host's structured logs are the observability surface (§9).

### 3.3 Messages, host → control plane

| Message | When | Payload |
|---|---|---|
| `host.hello` (post-MVP, P8.14: `runtime_identity` and `config.allowed_images`) | first message on every tunnel connect | `host_id, protocol_version, runtime_identity, capabilities, slots_total, inventory: [(workspace_id, vm_id, state, boot_at)], retained_roots: [(workspace_id, cache_generation, expires_at)]`. API returns `host.accept {protocol_version, incarnation_generation, current_incarnations, config: {allowed_images, timing, limits}}` or `host.reject`. Current-incarnation sets carry a monotonic control-plane generation and are applied only if newer; an old heartbeat ack cannot revoke a subsequently accepted lease/start. Missing/non-current inventory entries are killed without a flush. Replay the durable unacknowledged event journal after acceptance. |
| `host.heartbeat` (post-MVP, P4.12: `proxy_upstream_errors`, `grant_reresolutions` and `grant_reresolutions_suppressed`; P8.14: `lease_remaining_secs`) | every `heartbeat_secs` (default 10) | `slots_in_use, boots_in_progress, load, memory_free_mib, disk_free_mib, retained_roots, proxy_upstream_errors, grant_reresolutions, grant_reresolutions_suppressed, vms: [(vm_id, state, lease_remaining_secs, cpu_pct, mem_mib)]`. Three missed heartbeats mark the host unreachable. Ack carries the generated current-incarnation set; it never renews a lease. |
| `vm.event` (post-MVP, P8.14: `lease_expired_killed`) | every VM state change | `workspace_id, vm_id, seq, kind: booted \| ready{vm_id, epoch, module_catalog_version, dispatcher_contract_version} \| exited{code, signal} \| oom \| lease_expired_killed \| stale_killed \| boot_failed{reason}, at, log_tail?`. Host durably journals events and sequence state until acknowledged, including host-process restart. API atomically inserts/deduplicates `(vm_id, seq)` in `worker_vm_events`, applies the transition only for the still-current incarnation, then acknowledges the highest contiguous stored sequence. Stale events remain historical only. Log tails are capped at 64 KiB and redacted. Ready must match the pinned catalog/dispatcher contract before status becomes running. |
| `lease.acquire` / `lease.renew` (post-MVP, P8.14: `lease.acquire`, the host monotonic timer and the kill on expiry; P4.12: the token install into proxy grants; `lease.renew` stays MVP) | acquire before boot; renew on dispatcher request or while booting at half TTL | `{workspace_id, vm_id, epoch, seq}` → `{seq, token, lease_ttl_secs, incarnation_generation}` or `stale`. Acquire is host-originated on `ctl`; renewal retains the private `rpc`→`ctl` route. API grants only the current incarnation assigned to this host, before its lease expires. Host records request departure on a monotonic clock, arms `departure + TTL`, ignores obsolete replies and refuses an already-expired reply. It atomically installs the returned token into every `source: workspace_token` proxy grant before delivering it to the dispatcher. A stale/expired lease closes proxies and kills the VM. |
| `grants.resolve` (post-MVP, P4.12) | boot, grant update, bounded 401 refresh | `{workspace_id, vm_id, grant_generation, refs, reason: boot \| update \| reresolve}` → `{generation, values: [{ref, value}]}` \| `stale` \| `unresolved(ref)`. Accept only the current incarnation on this tunnel host and refs in its persisted spec/current grant set; re-check current owner/provider binding. Audit IDs/ref/reason, never values. Values are neither journaled nor logged and are discarded on release. This is the only secret-resolution transport. |
| `host.credential.renew` (post-MVP, P8.10) | from 2 h before expiry | New credential, or `refused` on draining/terminated/revoked/changed identity. Refusal starts control-plane credential drain (§8), never an independent host stop decision. An expired or revoked credential closes the tunnel and cannot reconnect. |
| `host.drained` | after `host.drain`, when no VM remains | `drain_id` |

Disk and memory pressure are heartbeat fields (`disk_free_mib`, `memory_free_mib`), not a separate alert; the control plane alerts and stops placing on the host when they cross its thresholds.

## 4. VM start spec

**Post-MVP (P4.12: the host-allocated proxy keys).** The control plane supplies the incarnation and authorized inputs. The host supplies the cached guest image, pinned runtime bundle, cache paths, resolved secret values and host-allocated proxy keys. These have distinct provenance; a repository cannot replace the runtime bundle.

```
VmSpec {
  spec_version:  1,
  incarnation:   { workspace_id, vm_id, epoch, org_id, owner_user_id, lease_ttl_secs, idle_timeout_secs },
  image:         { ref, digest },                       -- OCI, in the host cache or fetchable
  size:          { cpus, mem_mib, scratch_disk_mib },   -- must equal the host's slot size
  workspace_root:{ retain_hours },                      -- host path is host-chosen: <workspaces_root>/<workspace_id>
  repos:         [{ repo_id, root_path, git_url, branch, branch_oid, base_branch }], -- server-pinned mapped ref OID for this attach; shared branch name, per-repo upstream
  restore:       { flush_id, repos: [{ repo_id, branch_oid, local_branch_oid, local_head_oid, head_ref, sequencer: none | rebase | merge | cherry_pick | revert, snapshot_oid, dirty }] } | null,
  env:           { G5D_WORKSPACE_ID, G5D_VM_ID, G5D_EPOCH, G5D_API_URL, G5D_DISPATCH_PORT, HOME, PATH, CLAUDE_CONFIG_DIR, CODEX_HOME },
  secrets_env:   [{ name, secret_ref }],                -- repository and task secrets, resolved by the host into the dispatcher's environment (§6.6; design §6.5) (post-MVP, P4.12: host-side resolution needs `grants.resolve`; in the MVP secrets ride the dispatch as `TaskAssignment.secrets` do today)
  network:       passt,                                 -- (post-MVP, P8.11: passt as the only mode; the MVP selects the mode with G5D_VM_NET)
  egress_policy: { version, digest, allow: [{ ipv4_cidr, protocol: tcp | udp, ports: [...] }] }, -- resolved org policy; platform denies/host DNS remain mandatory (post-MVP, P8.11)
  entrypoint:    ["/opt/g5/bin/g5d", "dispatch"],
  credential_grants: [                                   -- consumed by the host proxies, never mounted (post-MVP, P4.12)
    { kind: llm_provider, provider: anthropic | openai | gateway, secret_ref, owner_user_id },
    { kind: git_https, target_origin, repositories: [repo_path], operations: [upload_pack, receive_pack], source: workspace_token },
    { kind: g5_api, source: workspace_token, routes: dispatcher_lifecycle },
    { kind: gh,           target_host, secret_ref }      -- later phase
  ]
}
```

`VmSpec.repos` is the completed workspace’s repository vector: each entry has its own repo and checkout path, and every `branch` equals the workspace’s shared branch name. Each `base_branch` is that repository’s independent upstream/update target; it does not override the working branch. Workspaces validates this invariant and admits boot only after the checked fork has completed all member refs/receipts and current-owner explicit Start/Resume intent is recorded. Creating a fork alone does not place a VM. A clearly labeled compound Start workspace and preview/chat/terminal action may record the same intent and wait for readiness. Reads, Save/upload, ordinary queued input and reader fork never boot a VM. Name checking, unfinished workspace_forks name claims and branch creation belong to the control plane/Git service; neither the host nor a clone/restore fallback creates authoritative branch refs or chooses replacement names. Local checkout materialization consumes existing refs.

**Post-MVP (P8.12: the source manifest digest and its comparison with `source_manifest_digest`).** `VmSpec.repos[].branch_oid` is the server-observed OID of the existing mapped branch pinned for this attach. Initial materialization (`restore=null`) uses that OID; when a verified restore receipt exists, its per-repository fields take precedence. The host cannot reinterpret a later moving branch or create authoritative refs. The source manifest digest is SHA-256 of canonical server-issued `{incarnation,repos,restore}`, compared against `workspace_vms.boot_spec` and `source_manifest_digest`. P4.5 persists that validated immutable spec atomically with placement before `vm.start` under the source/GC pin barrier, using P4.1 fields. It contains only secret/account references, never resolved secrets or tokens; retried command delivery reuses it and its active source pins survive until release.

Rules the host enforces before boot, in this order; the first failure is the answer:

- `spec_version` is known, else `spec_rejected(unsupported_spec_version)`.
- `incarnation.org_id` matches the host credential, else `spec_rejected(org_mismatch)`.
- IDs are UUIDs and repo roots are relative paths with no `..` or symlink component, else `spec_rejected(invalid_path)`; specs cannot name host paths.
- Size matches the host slot and the atomic admission lock reserves a free slot/boot token with no other live VM for this workspace; otherwise named `slot_unavailable`.
- **Post-MVP (P4.12: the `credential_in_env` refusal of provider credentials and host-private proxy keys).** MVP behaviour: credentials are delivered as environment variables; GitHub and GitLab tokens still never enter the VM. `env` accepts exactly the listed platform keys; provider/SCM credentials, host-private proxy keys and reserved secret-name collisions are `spec_rejected(credential_in_env)`.
- **Post-MVP (P8.14).** The canonical digest-pinned image reference is in `host.accept.config.allowed_images`, else `spec_rejected(image_not_allowed)` before a registry request.
- **Post-MVP (P8.14: the host-originated lease acquisition).** Acquire a lease before potentially long image/secret setup. The acquired typed token must match org/owner/workspace/VM/epoch, else `spec_rejected(token_mismatch)`; no VMM/proxy guest admission occurs yet. Renew while starting so a valid 300-second image pull does not conflict with the 60-second initial acquisition deadline.
- **Post-MVP (P4.12: resolution through `grants.resolve`).** Resolve only current spec/grant-generation references through `grants.resolve`; failure is `boot_failed(grant_unresolved)`. Verify current owner binding; owner changes require a new incarnation.
- **Post-MVP (P8.11).** Install host network and runtime/repository process isolation, otherwise `boot_failed(egress_unavailable)` or `boot_failed(runtime_isolation_unavailable)`.
- Fetch/cache the approved image within `image_pull_timeout_secs` and size limits; transient failure is `boot_failed(image_unavailable)`, fetched-byte mismatch is `spec_rejected(image_digest_mismatch)`. Boot only while the acquired lease remains valid.

Slot/boot-capacity admission and same-workspace exclusion run under one host lock, reserving both slot and boot token. Every later refusal, pull/resolve failure or failed boot releases that reservation before returning. The control-plane placement transaction also locks the org quota and chosen host capacity before persisting `starting`; derived occupancy is authoritative for planning, while the host lock is the final local bound.

**Post-MVP (P8.12: the authorized-closure Git view artifact, `GitObjectViewManifestV1`, the `scope_digest` cache key and the host-only `git-views` route).** MVP behaviour: the host keeps its URL-keyed bare cache and materializer. Mounts are fixed: `/work` is the host workspace root over virtio-fs; `/opt/g5` is the host-supplied runtime directory, read only and shadowing any guest-image content at that path; provider assets are read only; the scratch disk is a block device for docker and build caches. The bare-repo cache is host-internal: the dispatcher's restore uses it only through a trusted materialization path when present and the Git service otherwise, and never depends on it. Host Git caches consume only the Git service's immutable, self-contained authorized-closure artifact, whose manifest binds org/repository, principal scope, access generations, exact authorized root vector and content digest ([main design §5.3](lean-backend-design-v9.md#53-receive-pack-policy-the-git-boundary)). Before each restore/fork materialization the service revalidates current authorization/incarnation and the host verifies the exact manifest and pack hashes. The canonical `GitObjectViewManifestV1` in main design §5.3 binds `{version,org_id,repo_id,object_format,principal_scope,access_generations,roots,pack_sha256,object_set_sha256,scope_digest}`. Cache by `scope_digest` plus verified pack/object-set digests, never repository URL alone. A workspace principal names its stable workspace/current owner; VM/epoch/lease are revalidated separately on each use so safe same-owner warm reuse does not require reusing stale authority. No global bare-repository reflink, object alternates or cross-scope object reuse is allowed. Reuse within the same authorized artifact is permitted; stale generations/roots require a new artifact. Guests never mount this cache or another workspace root. The host fetches an artifact directly from `POST /api/internal/workspaces/:workspace_id/git-views/:repo_id` with its typed host credential and `{vm_id,epoch,source_manifest_digest}`. The API checks host assignment, current starting/running incarnation and lease, then derives exact allowed roots from the retained spec/source pins; caller input cannot widen them. The authenticated response is `multipart/mixed` with exactly two ordered parts: `manifest.json` (JSON, at most 64 KiB) and `repo.pack` (binary, at most `git_view_max_bytes`). Parse fixed part names and boundaries without archive/path extraction, reject extras or oversize data, and verify both manifest digests before guest use. Never replace this stream with a guest model/Git broker or a bearer URL to a global pack. MVP `access_generations` is exactly `[{scope_kind:org,scope_id:org_id,generation:orgs.access_generation}]`; the same-transaction generation bump rules in main design §5.3 invalidate every cached view and open stream affected by an org access change. P4.4b's cold/warm/new-fork tests include a guessed inaccessible sibling OID and an ACL-generation change; performance caching must not widen object visibility. Retained roots/scratch remain scoped to their workspace, are access-controlled and are restored/reconciled against the selected durable source before use. A new owner or incarnation cannot reuse old credentials, listeners or authorization from retained data. After ordinary `vm.stop` the host keeps the root/scratch generation for `workspace_root.retain_hours`; placement prefers a valid same-workspace cache (§7). Delete persists a purge intent for every host holding that generation and reports cleanup pending until acknowledgement. Transfer purges the old retained root/scratch before changing owner; the new owner restores cold from Git, never inherits ignored secret files. Unreachable hosts reconcile purge intents before accepting a new start. Host caches are excluded from backups; logical purge is not a claim of secure physical media erasure.

### 4.1 Guest image and trusted runtime provenance

**Post-MVP (P8.14: the `allowed_images` allowlist with `IMAGE_NOT_ALLOWED`, the persisted image provenance record and the consent audit event).** MVP behaviour: the base image comes from `.g5/workspace.yaml` with today's fail-closed resolution and the org track/pin policy. The guest image is userland only. The control plane reads `.g5/workspace.yaml` from the committed restored HEAD (`local_head_oid`, or initial selected branch head) in every `role=code` member; dirty snapshot overlays and docs-role repos cannot choose the image. Zero distinct `base_image` values selects the org default, one selects that value, conflicting values fail `IMAGE_AMBIGUOUS`, malformed/unreadable YAML or unpinned refs fail `IMAGE_INVALID`. The canonical registry/repository/digest reference must appear in the org-admin-managed `allowed_images`; otherwise `IMAGE_NOT_ALLOWED`. Never resolve mutable tags or silently fall back. Resolve before `starting` and before any pull; persist `{image_ref, image_digest, image_source, image_resolved_from: [{repo_id, oid}]}` plus a durable audit event naming the actor and consent.

**Post-MVP (P8.14: image consent and the allowlist hold).** An owner authorizes an allowed image when explicitly starting/restarting; the client shows the resolved pending image beside the running image before that action. A commit alone never restarts compute. Automatic rollout continuation cannot silently change a repo-selected digest: changed pins require owner Start/Resume. Org-default rollouts may update the default with a recorded operator action, but never override a repo pin; removing a pin from the allowlist holds its restart with `IMAGE_NOT_ALLOWED` until repaired.

The host runtime bundle contains `bin/g5d`, pinned provider CLIs, and `modules/catalog.json`; Worker & Host owns its build/staging. It is mounted read-only at `/opt/g5`, independently of the guest image. `runtime_identity.runtime_dir_hash` covers its manifest and `module_catalog_hash` covers the catalog bytes. P4.2b exports the catalog; P4.4b extends `scripts/stage-local-worker-runtime.sh`/CI images to stage it with `g5d dispatch` and fake provider CLIs. `runtime.ready` carries `vm_id`, `epoch`, `module_catalog_version`, `dispatcher_contract_version`; the host/control plane compare those with the selected bundle before accepting ready. Missing/mismatched runtime files fail boot, never silently use guest-image copies.

## 5. Incarnation, lease and token

**Post-MVP (P8.14: host-originated `lease.acquire` and the host timer state).** MVP behaviour: the API grants the lease at placement and extends it on `lease.renew`; an expired lease marks the row failed and the fence rejects the old token. A placement CAS records a new VM/epoch and a `start_by` control-plane deadline, but grants no guest authority. On receipt of `vm.start` the host reserves capacity and sends `lease.acquire` with a monotonic per-incarnation sequence. The API grants only the current `starting` incarnation assigned to that host with a still-valid start intent/deadline; a late command for a cancelled, superseded or expired start gets `stale` and cannot boot. Acquiring again for the same live incarnation is idempotent in identity and only advances the lease for a newer sequence. The row stores the latest granted sequence; duplicate requests return the same grant and never extend it. Retries of the same sequence retain its original first-departure timestamp; receipt of a duplicate grant never starts a fresh host timer. Persist the request sequence/deadline with the host OS boot identity so process restart cannot reset elapsed time; if that timing state cannot be recovered, fail closed and stop rather than reconstructing a longer lease.

**Post-MVP (P8.14: the host timer).** For acquisition and renewal the API records its handling time plus `lease_ttl_secs`; the host timer is request departure plus the returned duration. An obsolete sequence or reply whose host timer has already elapsed cannot install a token or reopen a proxy. API/token expiry and host timer can therefore be evaluated without synchronized clocks, and the host deadline never outlives the corresponding server grant. During long image setup the host renews for the same current `starting` incarnation. At half TTL the live dispatcher requests renewal through the private `rpc` path. Heartbeats, reconnects and API restart never extend or revive expired leases.

**Post-MVP (P4.12: the replacement of `source: workspace_token` proxy values and the rule that token values never enter launch environments).** MVP behaviour: the incarnation token is an environment variable, `G5D_WORKSPACE_TOKEN`, and processes in the VM can use it, as today. The token has `aud=g5-workspace-incarnation`, `token_use=workspace_incarnation`, `org_id`, `workspace_id`, `owner_user_id`, `vm_id`, `epoch`, `iat`, and `exp` equal to the server lease grant. User, host and incarnation validators reject the other token types. Every request also checks current VM/epoch, placement/owner and route scope; validity of a JWT alone is insufficient. On accepted renewal the host atomically replaces all `source: workspace_token` values before delivering the token to the dispatcher. In-flight requests may finish with the old token; every new request uses the latest token. Token values never enter repository/provider launch environments.

**Post-MVP (P8.14: the host-side kill on expiry with `lease_expired_killed`, and acquisition).** MVP behaviour: a VM that is no longer current is stopped by the reconnect inventory rule or by `vm.stop`, never by a host timer. A current incarnation can be `starting`, `running` or `stopping`; only admission-open running state authorizes user activity. Internal stop/flush/harvest may finish on a stopping incarnation. Expiry closes proxies before killing the VMM and reports `lease_expired_killed`. A replacement is admitted only after confirmed exit, or expiration of the last issued grant; a never-acquired cancelled start cannot subsequently acquire. Inventory reconciliation never revives an expired lease, even immediately after an API deploy. `vm.stop` accepts any exact VM the host owns regardless of currency. After retained stop results expire, `not_found` plus absence from the current authenticated inventory proves release; timeout alone never does.

**Post-MVP (P8.14: the start-acquisition deadline and the deploy budgets).** Platform defaults are lease TTL 300 seconds, renewal at half TTL, heartbeat 10 seconds, start-acquisition deadline 60 seconds, image pull timeout 300 seconds, full ready deadline 420 seconds and VMM termination grace 30 seconds. The deploy budgets are separately configured: preflight-to-shutdown delay 15 seconds, control-plane unavailability 120 seconds, and tunnel/inventory/first-renewal recovery 60 seconds. These are draft bounds to verify, not measured availability claims. TTL must exceed their sum and be at least six heartbeats. No reconnect grace extends or revives an expired grant.

**Post-MVP (P8.14).** **Deployment lease observations.** `POST /api/internal/ops/workspace-leases/observe {refresh_lease:true}` is a new narrow operator endpoint owned by P4.5. Existing operator authorization must grant deployment-wide lease observation/refresh; the configured deployment scope must include every org with a current placement. Ordinary product users, org-only operators without that complete scope, host/incarnation credentials and provider/bootstrap capabilities are denied. The API derives the complete `starting|running|stopping` set from `workspace_vms` in that deployment; callers cannot supply an org/workspace filter, omit an unreachable host or choose a narrower VM list. Through the real `HostCommandClient`, it requests `vm.status(refresh_lease=true)` for each current assigned host and returns a bounded `protected_incarnations:[{org_id,workspace_id,host_id,vm_id,epoch}]` vector plus one observation per entry: `observed {lease_seq,lease_remaining_ms}`, `released`, `unreachable`, `pending_acquisition`, `stale` or `error`. `released` requires confirmed database release after enumeration; every other incomplete status blocks deployment. Revalidate row/host/VM/epoch when matching each reply; never substitute API wall-clock lease expiry or cached heartbeat evidence. A response-size or deadline bound that prevents complete coverage fails the observation instead of silently truncating the vector. The response contains no credentials, paths or repository content. Token-free audit records actor/deployment scope, coverage and refusals. The wrapper holds its external placement lock, verifies exact vector coverage, subtracts its whole HTTP request round-trip plus subsequent observation age from each reported host duration, and repeats this endpoint immediately before Helm and for post-ready renewal verification. Endpoint authentication, omission/unreachable/stale cases and positive complete coverage are P4.5 acceptance tests. This operator POST does not alter the product `GET /workspaces/:id/vm` contract, which remains database/last-report only.

**Post-MVP (P8.14).** MVP behaviour: no deploy guard (none exists today) and no host-side lease kill timer. **MVP deploy guard.** `vm.status(refresh_lease=true)` first requests a fresh lease using the ordinary monotonic/sequence rules, then reports `{vm_id, epoch, lease_seq, lease_remaining_ms}` from the host's actual monotonic deadline. Status cannot extend a lease itself. The guard subtracts the complete request round-trip and subsequent observation age from reported remaining time; API `lease_expires_at` alone is not evidence because it can be later than the host deadline. Every current `starting|running|stopping` incarnation must have matching fresh evidence with conservative remaining time greater than `start_delay + outage + recovery` (195 seconds at the defaults). Unreachable hosts, pending acquisition, stale sequences or insufficient bounds block the deploy; a confirmed released incarnation may be removed from the set.

**Post-MVP (P8.14).** P4.5 adds `scripts/deploy-with-workspace-lease-guard.py` (new implementation target), invoked **inside the existing `helm-deploy` step** of `infra/ci/cloudbuild-deploy.yaml`. This external wrapper holds a PostgreSQL session advisory lock for the whole preflight → Helm Recreate → host reconciliation/first-renewal interval, using reserved advisory key `(0x47354c39, 1)`; an earlier Cloud Build step that exits cannot hold the guard. Workspace placement takes a shared transaction lock on that reserved key using try-lock; while blocked, it preserves typed start intents and reports deployment capacity waiting without allocating another incarnation. Lease renewals, stop/flush and release do not require this lock. The wrapper uses a least-privileged deploy DB identity for the lock and a scoped operator API for lease observations; no workspace/provider credential is exported. Holding the lock makes the protected incarnation set closed to new placements; stopped entries may leave it. Recheck evidence immediately before invoking Helm and refresh if the 15-second start window elapsed. No current incarnation may be omitted because its host is unavailable.

**Post-MVP (P8.14).** The wrapper remains outside API pods across Recreate, measures unavailability through API readiness and then verifies every surviving host's inventory and successful renewal within the recovery budget. Release the lock in `finally`/connection close on success, failure or timeout; restored placement still requires fresh owner/generation-bound start intent and normal lease acquisition. Failure marks the deploy failed and records any expired/fenced incarnation truthfully, rather than extending its lease or claiming rollback preserved it. Existing deploy authorization/freshness gates remain. P4.4b supplies host lease evidence; P4.5 owns the guard and a positive within-budget API restart test preserving VM/epoch, file RPC, flush recovery and queued start intent, plus an above-budget loss test. P4.6–P4.8 add active-turn/native-wait cases as those paths land. P8.7 extends this already-required MVP guard for fleet rollout. Required tests and QA measurement are evidence to obtain during implementation, not results of this design revision.

## 6. Host-side proxies

**Post-MVP (P4.12).** This section is not part of the MVP. Its **Host-enforced egress** paragraphs and its trusted-runtime process isolation paragraph are marked P8.11, everything else up to §6.5 is P4.12, and §6.6 and §6.7 stay MVP except where marked. MVP behaviour: the provider key reaches the VM as environment and an in-guest proxy attaches it, the account being the current workspace owner's, resolved at dispatch; the VM's platform token is an environment variable and git and API calls go straight to the control plane.

Provider keys and SCM tokens stay on the host; the workspace token is held only by the host proxies and trusted dispatcher, never repository/provider processes. The VM reaches the outside world through one host-side service, reachable from inside the guest at the fixed name `g5-llm`, which serves both the LLM proxy and the credential proxy in §6.4. For model traffic the proxy terminates the provider CLI's HTTP, attaches the current workspace owner's provider credential from the VM's `credential_grants`, forwards to the provider or the org's gateway, and returns the response. It refuses with 403 when the VM's `vm_id` is not current, tags every request with `(workspace_id, vm_id, session_id)` from the per-session path in §6.1, exposes the per-session view on the local status endpoint in §6.2 and on `vm.status`, and records usage per session for accounting. The proxy assigns a unique request UUID before upstream submission and journals UsageV1 under that key for idempotent control-plane ingestion; multiple model requests in one attempt are distinct rows. Execution/attempt correlation comes from trusted supervisor registration, never a claimed session path. Adapter usage frames are display/reconciliation data, not a second billing producer; quota headers use a fixed safe allowlist. The detailed UsageV1 schema is agent-api §4.

**How the guest reaches it.** The proxy is a host process with one listener per VM on a per-VM port on host loopback. The guest has a real NIC (`10.85.0.2`) served by a per-VM passt process, and reaches host loopback through the passt door `169.254.1.2`, which the host seeds into the guest's `/etc/hosts` as `g5-llm`, the way today's `g5-host` alias is seeded. The host allocates the port, opens the listener, and adds `G5D_LLM_PROXY_URL=http://g5-llm:<port>` to the dispatcher environment after spec validation; the control plane never guesses the port.

The VM proxy secret is a transport credential for the trusted dispatcher, not authority for every guest process. The dispatcher holds `G5D_LLM_PROXY_SECRET` privately and brokers model/internal-Git traffic for repository processes through restricted local endpoints; it never exposes a generic credential-injecting `/api` route to them. The host authenticates the per-VM secret and current lease on every proxy endpoint, including `/_g5/status`.

**Post-MVP (P8.11).** MVP behaviour: passt starts with no firewall rules, and the network mode stays selectable by `G5D_VM_NET`. **Host-enforced egress.** Linux MVP uses nftables OUTPUT filtering on an exclusive host UID assigned to each incarnation's passt process. Worker & Host allocates that UID with the slot, installs rules before passt can create network sockets or the VMM is admitted, and verifies their policy digest. The optional shared UID/cgroup hooks in retained `backend/g5d-isolation/src/isolation/passt.rs` are reuse points, not existing enforcement. Repository processes cannot choose the UID or receive NET_ADMIN. Reap passt and close its sockets before deleting rules/reusing UID or proxy port; stale conntrack/rule state cannot authorize the next incarnation. A missing capability, rule-install failure or policy mismatch is `boot_failed(egress_unavailable)` before guest execution. No process fallback satisfies this production gate.

**Post-MVP (P8.11).** The resolved `VmSpec.egress_policy` is `{version, digest, allow:[{ipv4_cidr, protocol: tcp|udp, ports:[...]}]}` from the registered org `workspace_egress_policy` config; org admins edit bounded explicit destinations, with default empty allow. Worker & Host owns validation/compilation, and platform deny rules cannot be overridden by an org grant. Platform host configuration pins the IPv4 DNS upstream and passt binary; repository files and workspace settings cannot select them. CIDR/port rules authorize destination tuples, not hostnames. Domain-to-IP-set policies are deferred; DNS answers and redirects must each pass the destination check. Provider and internal-Git traffic use their separately scoped brokers. Package registries need explicit approved destination tuples, never an arbitrary-egress fallback.

**Post-MVP (P8.11).** Rules name both guest addresses and the host socket destinations after passt translation. Guest `169.254.1.2:<own_proxy_port>` maps to the exact host `127.0.0.1:<own_proxy_port>` TCP listener; allow only that tuple for this UID, never sibling ports. Guest DNS `169.254.1.1:53` UDP/TCP maps only to the platform-pinned resolver's exact IPv4:53 tuple. Pin a passt build supporting explicit `--dns-host <resolver-ip>` with `--dns-forward 169.254.1.1`, keep `-4` and disable search-domain inheritance; validate its actual behavior at the selected binary before admission. The [upstream passt manual](https://passt.top/builds/latest/web/passt.1.html) documents these mappings, but is not proof for a shipped binary. Port 853 and alternate resolvers are denied in MVP.

**Post-MVP (P8.11).** These two translated exceptions precede the deny set; no other host-loopback endpoint is allowed. Deny remaining `169.254.0.0/16` (including metadata 169.254.169.254), `127.0.0.0/8`, host/sibling/control-network addresses, multicast/broadcast and IPv6. Other private/VPC and public destinations default-deny unless a bounded org tuple explicitly allows them; protected host/metadata denies still win. Apply the same destination checks to every new connection, including DNS aliases and redirects. Conntrack marks bind allowed flows to the incarnation: allow replies only for those flows or the exact host-initiated dispatcher/PTY/HTTP forwards registered by the supervisor. Do not add a blanket established-flow exemption that retains revoked or previous-incarnation authority. Purge the incarnation flow marks before UID/port reuse; relay replies must still pass the real fs/PTY/preview tests. The own-proxy network exception still requires its private proxy secret: a raw repository request cannot gain dispatcher authority by reaching the port.

**Post-MVP (P8.11).** P4.4b adds `backend/g5d/tests/workspace_vm_egress.rs` and strict `workspace-vm-egress` in `infra/ci/cloudbuild-ci-e2e.yaml` (both new implementation targets), after `setup-kvm-libkrun` and runtime staging; its explicit result feeds `assert-ci-status`. It boots real libkrun/passt with private fixture roots and fails on missing KVM, passt pin or nftables support. Existing skip-capable `isolation-backends`/docker-ci1b are not substitutes. Probe approved destination/DNS/own proxy success, unauthenticated proxy refusal, metadata/other link-local/host/sibling/direct-unapproved/DNS-alias/redirect/IPv6 denial, install failure and UID/port reuse. P4.12 repeats the own-proxy cases with the real credential broker. Local docker-ci has an explicit required-security target with the same no-skip rule; P9.1 applies it to self-hosted Linux. macOS development may run a clearly marked local test backend with synthetic credentials only; production grants/VM placement are refused until an equivalent kernel boundary is implemented and separately verified. A self-reported capability string cannot waive enforcement.

**Execution authority.** `G5D_EXEC_ID`/`G5D_SESSION_ID` are correlation only. MVP provider processes, MCP tools and shell `g5d` receive no generic platform-write capability or API injector. Their platform task/PR/result mutations are deferred; ordinary native Git, files, shared conversation and native Claude question/approval transport remain. The only module-created task delegation is the platform-shipped `workspace.bootstrap` supervisor: at `modules.invoke` the API issues a random 256-bit capability bound to its module/version/hash, command task/attempt, org/workspace/job, current owner/lifecycle generation and VM/epoch. It authorizes only `POST /api/internal/jobs/:job_id/tasks` with the typed bounded agent-child graph of Agent API §6.6. The trusted supervisor uses a private HTTPS client through the dispatcher-authenticated host platform broker for that exact API route, presenting its scoped capability. The broker forwards only that method/path to the configured control-plane origin, injects no generic workspace token, and rejects arbitrary destinations. There is no direct guest control-plane egress. This runtime-only transport is inaccessible to provider/repository endpoints; repository scripts/providers/terminal inherit neither capability nor privileged descriptors. The API validates the grant and fixed graph limits, derives identity from it and admits children under the owner's explicit job policy. A socket name or copied exec ID grants nothing. No provider-private write bridge is an MVP dependency.

**Post-MVP (P8.11).** MVP behaviour: guest users and images as shipped: the agent runs as uid 1000 (`G5D_GUEST_SIDECAR_NONROOT`) and images carry rootful Docker. Trusted runtime/control processes use a separate UID and private directories (0600/0700), protected `/proc` access and no inherited privileged FDs. Repository shells, previews and builds run unprivileged with dropped capabilities; no sudo, rootful Docker socket or other route to runtime credentials (use rootless Docker). A guest image not supporting that separation is not an allowed production image. Process checks cover descendants and debug/ptrace paths, not just environment variables. These are required security gates, not a claim that the retained runtime already enforces them.

This target consolidates proxy routing around the workspace incarnation. The current repository already has a host-side injection path in `backend/g5d-agent/src/llm_proxy.rs`, which strips real provider credentials from the guest overlay and substitutes placeholders. That is reuse evidence, not proof that owner-bound workspace grants, transfer fencing or the new host contract are implemented.

**Changing a credential while a VM runs.** Grants are references, so the value behind one can change. The control plane pushes the new list with `vm.grants.update` (§3.2) and the host swaps the proxy's table atomically; in-flight requests complete with the old credential, the next request uses the new one. The target takes effect on the next model request without restarting a provider process. The replacement list remains bound to the same owner and incarnation; it cannot be used to hand the live VM to another owner. An upstream 401 may trigger one single-flight `grants.resolve(reason=reresolve)` per proxy-attached grant per 60 seconds, with exponential backoff capped at 15 minutes and a 5-second resolver timeout. Client-supplied credentials never trigger resolution; on timeout/suppression the original 401 is surfaced. Heartbeats count attempted/suppressed resolutions; values are never logged.

Session tags and local status below serve liveness and accounting only. They do not select a user, provider account or credential. All sessions and previews in one incarnation use its owner context. The credential proxy keeps provider/SCM/platform credentials out of module processes; workspace build/task secrets are the separate exception in §6.6.

### 6.1 Per-session request tagging

**Post-MVP (P4.12).** This section is not part of the MVP. MVP behaviour: the provider key reaches the VM as environment and an in-guest proxy attaches it.

The dispatcher, not the host, decides which process belongs to which session. It does so by giving every provider process a base URL that carries the session id on the restricted guest-local model broker (no platform API route):

```
ANTHROPIC_BASE_URL = http://127.0.0.1:<broker_port>/s/<session_id>        # Claude Code
OPENAI_BASE_URL    = http://127.0.0.1:<broker_port>/s/<session_id>/v1     # Codex
```

The dispatcher forwards the broker request to its authenticated host-side `g5-llm` listener (`G5D_LLM_PROXY_URL`). The host proxy strips the `/s/<session_id>` prefix before forwarding, records `session_id` on the request, and rejects a request with no session prefix (`400 missing_session`) so an untagged client cannot hide inside the VM's accounting. `session_id` is opaque to the host; Agents supplies the shared `chat_sessions` identity for both human and templated workflow inputs. Both run as `kind=agent`, and continuation attempts retain the same logical task/session and job/dependency grouping. The host does not classify input origin, select permission policy or create a replacement task. Changing the tag cannot change the provider account: one workspace incarnation has one owner account context. The launch environment is supplied by `agent.turn`, and session tags are not authorization grants.

### 6.2 Local status endpoint

**Post-MVP (P4.12).** This section is not part of the MVP. MVP behaviour: the provider key reaches the VM as environment and an in-guest proxy attaches it.

The host listener serves one read-only endpoint authenticated by the dispatcher-only proxy secret, so the dispatcher can see what the proxy sees without a round trip through the control plane:

```
GET ${G5D_LLM_PROXY_URL}/_g5/status
→ {
    vm_id, current: true | false,
    sessions: [
      { session_id, requests_open, last_request_started_at, last_response_at,
        input_tokens, output_tokens, cost_usd }
    ]
  }
```

`requests_open` is the number of upstream model requests in flight for that session. `current` is the host's cached answer to "is this incarnation still current"; a `false` here means the proxy is already refusing traffic and the dispatcher should expect `vm.stop`. The endpoint never returns credentials or request bodies. The control plane sees the same `sessions` array on `vm.status`.

### 6.3 Refusal codes

**Post-MVP (P4.12).** This section is not part of the MVP. MVP behaviour: the provider key reaches the VM as environment and an in-guest proxy attaches it.

| Situation | Proxy answer | Meaning for the client |
|---|---|---|
| `vm_id` not current | `403 {"error":"stale_incarnation"}` | The VM has been superseded; stop retrying |

### 6.4 Credential proxy for Git and platform calls

**Post-MVP (P4.12).** This section is not part of the MVP. MVP behaviour: the VM's platform token is an environment variable and git and API calls go straight to the control plane; existing `g5d` and MCP platform tools keep authenticating with it, and GitHub and GitLab tokens still never enter the VM.

MVP issues only internal Git grants scoped to canonical origin, exact repository path and `upload_pack|receive_pack` operations. The Git service still enforces the authorized ref/object set, mapped-branch write policy and flush-operation authority. No grant authorizes every repository on a host. Decode/canonicalize a path once; reject ambiguous encodings, non-Git paths, host/port changes and redirects. Strip guest Authorization/cookies and inject only the selected grant; never forward arbitrary client credentials through a privileged injected route. `git push` reaches only internal Git; external publication stays an explicit control-plane action. Later private-dependency grants are exact-repository `upload_pack` only, never receive-pack; `gh` injection remains deferred.

| Principal | API surface | Denied |
|---|---|---|
| Trusted dispatcher incarnation | Own lease, ready/events/outcomes, receipt/harvest/session-file operations and authorized Git refs | User/admin/org/workspace-create/transfer routes, arbitrary cross-workspace access, provider platform-write tools |
| Platform-shipped `workspace.bootstrap` supervisor | Only scoped `POST /api/internal/jobs/:job_id/tasks` delegation, with immutable module/attempt/job grant and typed bounded agent-child graph (Agent API §6.6) | Caller-selected workspace/job/owner, command/preview child escalation, arbitrary API writes or token handoff to scripts |
| Repository/provider process (terminal, preview, build, shell or MCP) | Restricted model/internal-Git egress and native workspace files | Generic platform API injection, task/PR/result writes, lifecycle authority, identity based only on environment IDs or socket names |

Every privileged route verifies its actual principal before side effects; the VM secret is not a shared guest write credential. Plain human laptop Git keeps the user/device-flow credential and current user authorization. Broader agent platform tools are deferred until their own concrete transport and permission contract is accepted.

### 6.5 Client steering and secret provenance

**Post-MVP (P4.12).** This section is not part of the MVP, except that `secrets_env` and `G5D_WORKSPACE_TOKEN` stay (amendment §7 point 5: `secrets_env` also moves to P4.12, because its references resolve through `grants.resolve`; in the MVP repository and task secrets ride the dispatch like the provider key). MVP behaviour: the provider key reaches the VM as environment and an in-guest proxy attaches it; the platform token is an environment variable.

`agent.turn` sets `ANTHROPIC_BASE_URL` / `OPENAI_BASE_URL` to the restricted model broker with the accounting session path; provider keys are absent or placeholders. Dispatcher-managed Git configuration routes exact internal repositories through its restricted Git broker; repo code never sees the workspace token. The platform-shipped bootstrap supervisor's narrow child-creation channel is separate from these endpoints and from provider/native question transports. The dispatcher keeps the control-plane API URL from the spec for private lifecycle traffic; it does not advertise a generic `/api` credential injector in every launch environment.

### 6.6 Workspace secrets, previews and transfer

Repository/task secrets needed for builds and tests are workspace-scoped, not per-user isolated. The host resolves `secrets_env` into the trusted dispatcher; the dispatcher refreshes the set before each module launch and passes them into agent, preview and other allowed module processes. A resident terminal retains its initial values. Git author configuration in the VM uses the current workspace owner. Historical commits are not rewritten on transfer.

**Post-MVP (P8.13: the separate registrable preview domain, `PREVIEW_ORIGIN_UNCONFIGURED` and the removal of the same-origin fallback).** MVP behaviour: preview origin as today, a per-preview subdomain under the platform domain when `G5_PREVIEW_HOST_SUFFIX` is set, with the single-use handoff ticket, the `__Host-g5_preview` cookie and CSP, and the path relay otherwise. A preview launcher is the current workspace owner; the actor field exists in durable task/audit state. The host does not select the launcher's provider key, create a second account context, know task kinds, or allocate a separate preview VM. TaskService owns the preview task and dispatch/cancel state; `workspace.preview` supervises the service and the host relays only control-plane-authorized owner HTTP streams. The control plane rejects non-owner preview start/replace/cancel/relay requests before host admission; there is no reader-preview exception. Preview is exempt from bounded-task concurrency and wall-clock limits, but still uses one workspace VM slot and normal org VM capacity. Activity means an admitted owner HTTP request or a new authorized preview stream/WebSocket upgrade, counted once at the API relay and coalesced at most every 10 seconds into `workspace_vms.last_activity_at`; bytes, ping frames and an already-open hot-reload socket do not refresh it. Denied readers do not update activity. A stopped preview is never resumed automatically. Preview content requires a per-workspace/port origin on a separate registrable domain from the platform, host-only ticket cookies and no platform session cookies. Missing isolated-origin configuration fails `503 PREVIEW_ORIGIN_UNCONFIGURED`; shared/self-hosted deployments have no same-origin fallback. The platform API bootstrap route returns a redirect/handoff only, never repository HTML. Ticket cookies are host-only, Secure, HttpOnly and SameSite=None; embedded preview uses Partitioned cookies in supported browsers. The handoff redeems once for the authorized preview origin without exposing platform cookies. Verify successful owner rendering in the supported-browser iframe matrix as well as denial probes. If the browser cannot retain the partitioned embedded ticket, show an explicit Open preview in new tab action using a fresh owner-authorized top-level handoff; do not silently relax cookie/origin isolation or fall back to platform-origin HTML. Tests cover iframe and new-tab positive load, unsupported embedded-cookie fallback, stolen/expired ticket refusal and platform-cookie exclusion. CORS, CSRF/Origin checks and `postMessage` validation keep preview code from spending platform-session authority.

Ownership transfer is a Workspace lifecycle operation with reason `transfer`. Workspaces closes admission, interrupts executions and closes preview/terminal processes, persists Agent attempt/task continuation and session state, completes the shutdown flush, sends `vm.stop`, confirms host exit and releases the incarnation, then commits the owner/audit change atomically. Agents retires process-bound native requests when their provider process ends and preserves confirmed deferred questions for native restoration; the host has no question-answer transport or replay authority. The host closes all old proxy listeners and forgets credential values on exit. A failed flush aborts transfer with the old owner retained; an ambiguous stop is reconciled and never treated as release. Transfer does not permit a force-loss completion. A workspace already stopped needs no VM stop, but still purges any retained root/scratch before transfer completes.

Transfer invalidates prior start/continuation authority by advancing the workspace lifecycle generation and clearing its typed `workspace_vms.start_intent`. Only explicit current-owner Start/Resume records a new owner/generation-bound intent; the next `VmSpec` uses the new owner and retained queued agent/command work dispatches only after attachment is ready. There is no reader-preview wake path. Live file/terminal/preview/log streams are closed before release, and the previous owner's client becomes a Git-only reader if they retain read access. Question history and provider-session artifacts stay with the workspace; old process callback IDs and provider credential selections never authorize a new attempt. An agent continuation keeps its logical task/session/dependencies and runs a new attempt under the current owner; a confirmed deferred question resumes its saved native tool when the current owner answers on ready attached compute. Ordinary ended requests remain historical. A question cannot wake a VM or keep it active. Retained filesystem caches cannot authorize the old owner or bypass restore and fresh proxy/account setup. Read-only UI never boots a VM; non-owner repository browsing never contacts the VM at all. The Git service separately requires current-owner, running/admission-open workspace authorization for user-originated mapped-branch receive-pack, including laptop pushes; host proxies cannot bypass that policy. Shutdown/fork flush and authorized control-plane fork/merge/import retain their distinct service grants.

**Post-MVP (P8.14: the 1 GiB session cap).** Provider-session bundles are opaque to the host. Their durable bytes remain raw Postgres artifacts with zstd wire transport, a 128 MiB decompressed-file/1 GiB session cap and supervisor-only access; they are never part of Git, retained repository caches or reader-visible exports. Harvest/restore validates the current incarnation and manifest generation through Agents. Deleting a host cache cannot delete a durable session bundle, and retaining a cache cannot authorize an older bundle. The main design §12 defines retention and the evidence required before any future private-artifact-store migration.

The host neither handles Claude `AskUserQuestion` nor infers approval policy from human/workflow origin. Agents carries an explicit permission policy and owns the `provider_requests` question/approval projection and its lifetime rules ([Agent API §8.2](agent-api-surface-v9.md#82-native-request-projection-and-reply)), Claude direct-CLI stdin control responses, and the absence of an interactive-question fallback in MVP Codex `exec --json`. Later Codex App Server stdio support remains inside the provider adapter. User stop, idle stop, transfer and unexpected loss require explicit owner Resume before reattachment. Deliberate drain/rollout may continue the same logical task after the new incarnation is ready only under previously recorded current-owner continuation authority recorded in the typed start intent against owner/lifecycle generation and not superseded by a later stop or transfer; queued demand alone grants no wake authority. These decisions never become host task scheduling.

### 6.7 MVP workflow scope

Ordinary owner-created tasks and optional jobs use the shared session/attempt lifecycle. A checked fork creates a stopped ordinary workspace; only owner Start/Resume allocates compute. Task completion preserves its normal transcript/history and does not imply a special result-publication or child-workspace stop operation. Ordinary idle, explicit stop/restart, transfer and fleet lifecycle rules own compute release. Review/explainer request/result/reply orchestration and completion-specific cleanup are deferred as a unit; the host has no MVP command, grant or stop reason for them.

## 7. Placement and capacity

**Post-MVP (P8.14: the `worker_host_region` key in `configs` and the rule that a configured region never silently falls back across regions).** MVP behaviour: the fallback-region basket for stockouts stays. Placement is `WorkerHostService::place(workspace, org)` (P4.13), called by `WorkspaceVmService::resume`; the host only accepts or refuses. Both org ID and configured region are mandatory filters. Store `worker_host_region` and `max_running_vms` in org `configs`; region defaults explicitly to the deployment region at org provisioning and quota defaults to 10 active starting/running/stopping VMs. A configured region never silently falls back across regions. MVP capacity is a static operator-provisioned org pool: a new org has zero hosts until provisioned; queue state reports missing capacity, not an implicit scale-up promise. Automatic scale-out/in and cross-org pooling are deferred; retained rotation must be explicitly enabled/configured for replacement. The control plane picks, in order: a host in the org's region with a free slot that still holds this workspace's root and scratch disk (`retain_hours` not yet elapsed, from the host's `retained_roots`), then any host in the region with a free slot, then `no_capacity`, which the workspace module surfaces to the user and to a queue. Org quota is `max_running_vms` and is enforced before `vm.start` is sent. A host that answers `slot_unavailable` despite the registry's count is treated as authoritative and the control plane re-places; `workspace_busy` in particular means the previous incarnation of the same workspace has not exited on that host yet.

Useful bare-repository and workspace-root caching must survive the redesign or be replaced with measured equivalent materialization behavior. Validate cold restore, warm resume and new-fork startup, including eviction and ownership changes; performance work must retain the authorization/source checks in §4. P4.4b records three runs each of cold/no-root restore, same-host warm resume and a new child with cached objects, using the same committed multi-repo fixture, pinned images, slot size and KVM lane. Measure `vm.start` send → validated `runtime.ready` wall time and Git restore bytes; record run values/medians, fixture commit, host/image hashes and lane artifact URL in the status Notes/PR evidence. P4.9a repeats the same recipe before deleting old cache code and explains regressions. These are comparable observations, not an invented latency SLA. The meeting did not require same-host placement of parent and child VMs or a new packing scheduler.

Retained roots are a cache, not a promise. Under disk pressure the host evicts retained roots oldest first before refusing `vm.start` with `slot_unavailable(disk)`, and `retained_roots` on the next heartbeat reflects it; a resume placed on a host that evicted the root simply restores from Git.

## 8. Drain and rotation

**Post-MVP (P8.10: credential renewal as the drain trigger; P8.14: the host lease timers).** MVP behaviour: with the 24 h host JWT, `cloud/rotation.rs` replaces each cloud host before expiry. Rotation is drain and replace. The control plane provisions the replacement first, then sends `host.drain`, then for each VM on the host runs the workspace stop sequence to its durable cut (the receipt in workspace-vm-api-v9.md §5) and sends `vm.stop`. A VM whose stop sequence fails keeps the host `draining` and retries with backoff until the operational drain deadline; a deadline-bound release records unflushed loss per VM. User ownership transfer has no such bypass and aborts on flush failure. `host.drained` is followed by instance termination. WorkerHostService starts `drain_reason=credential` when renewal is refused or no renewal succeeds by 30 minutes before expiry. It sends `host.drain` and owns stop orchestration, targeting completion at least 5 minutes before expiry; if the remaining time is shorter, the deadline is immediate and recorded-loss policy applies. It never asks the host to decide workspace idleness/completion. At credential expiry the tunnel closes; host lease timers continue enforcing their earlier grants. Revocation/termination may close it earlier (§2.3).

## 9. Observability

| Surface | Caller | Returns |
|---|---|---|
| `host.hello`, `host.heartbeat` | control plane | Runtime identity, capabilities, slot occupancy, load, disk and memory free, per-VM liveness and lease freshness. What the operator surface renders. |
| `vm.status`, `vm.event` | control plane | Per-VM lifecycle, resource usage, lease freshness, open streams, per-session `requests_open`, boot log tail on `boot_failed` and `exited`. |
| Host logs | operators | Structured, per host, shipped as today. VM console output up to `ready` is captured into the boot log tail; after `ready`, VM logs belong to the dispatcher's journal. |

Operational metrics are exported by an internal authenticated `/metrics` endpoint; they contain bounded status/reason labels, not user IDs, paths, prompts or secrets. Host/control-plane owners expose `g5_host_unreachable_total`, `g5_vm_lease_expired_killed_total`, `g5_vm_stale_killed_total`, `g5_slots_in_use`, `g5_slots_total`, `g5_vm_boot_seconds{source=cold|warm|child}`, `g5_proxy_refusals_total{code}`, and `g5_tunnel_reconnects_total`. Workspace/Agents/Git add their owned flush, loss, cleanup, queue, attempt, timeout and verification metrics at the PR implementing that failure path. Structured logs correlate workspace/VM/task/attempt/command IDs without high-cardinality metric labels.

P4.13 installs alerts for unexpected lease kills/unflushed loss, spec/integrity rejection, hosts unreachable over 60 seconds, and stop/cleanup work beyond its recorded deadline. Disk below one slot's required reservation or below 10% stops placement and alerts; memory below one slot's reservation also stops placement. P8.7 records attach-success rate, warm-attach latency distribution, receipt completion rate and deploy outage duration in the QA rehearsal. These are measurements with declared denominators/windows; product SLO targets require observed baselines, not invented availability promises.

`worker_vm_events(org_id, workspace_id, host_id, vm_id, seq, kind, payload, at, received_at, PRIMARY KEY(vm_id, seq))` stores dedupe/history under org RLS. Transition and insert are one transaction; cumulative ack comes from the durable contiguous sequence. Keep events for at least 7 days after release and until every retained host journal event is acknowledged; never prune active incarnation dedupe. A small per-incarnation watermark/tombstone persists until the host's journal/result retry horizon has passed so delayed replay cannot recreate side effects. Host log-tail history is stored in the event payload, not solely a mutable workspace last-error field.

There is no host shell and no arbitrary inspect command. Operators use the registry, lifecycle events and metrics; new recovery operations must be scoped, idempotent and audited.

## 10. Failure matrix

| Failure | Detected by | Host does | Control plane does |
|---|---|---|---|
| Tunnel drops (post-MVP, P8.14: the host lease timers) | host: socket error; control plane: missing heartbeats | reconnects with backoff, keeps VMs running, keeps lease timers running | after 3 missed heartbeats: host `unreachable`, no new placement; incarnations stay current until lease expiry |
| Host reconnects with a VM the control plane replaced | `host.hello` inventory vs `current_incarnations` | kills the stale VM, `vm.event stale_killed` | nothing; the replacement already restored from the durable cut |
| Lease expires on a partitioned host (post-MVP, P8.14: the host timer and the host-side kill) | host timer | kills the VM, `vm.event lease_expired_killed` when the tunnel returns | reconciler marks the incarnation `failed` and active attempts lost; Agents retires their process-bound native requests, preserves confirmed deferred questions and applies retry policy to the same logical task; next resume places elsewhere |
| VMM process exits unexpectedly | host wait() | `vm.event exited{code}` with log tail, frees the slot | incarnation `failed`; active attempts are lost and process-bound native requests invalidated; confirmed deferred questions persist; Agents continues or terminates the same logical task under its retry policy |
| Dispatcher dies inside a live VM | host: guest listener refuses `rpc` | reports `vm.event exited` only if the VMM exits; else `vm.status` shows `streams_open = 0` and listener failures | treats listener loss as VM loss and issues `vm.stop kill` |
| Boot fails | host | `boot_failed(reason, log_tail)` | incarnation `failed`, retry placement once, then surface to the user |
| Slot exhausted under a race | host | `slot_unavailable` | re-place on another host |
| Image temporarily unavailable | bounded host pull | `boot_failed(image_unavailable, log_tail)`, free slot | retry placement once on another eligible host; then `failed`/`IMAGE_UNAVAILABLE`, no integrity alert |
| Spec rejected | host validation | `spec_rejected(reason)` | do not retry unchanged spec; alert on digest/invariant mismatch, surface named invalid configuration, exclude incompatible protocol/spec hosts |
| OOM inside the VM | host cgroup | `vm.event oom`, VM killed | as VM loss, with the reason shown to the user |
| Host disk full | host | heartbeat `disk_free_mib` below threshold, refuses `vm.start` with `slot_unavailable(disk)` | stops placing on the host, drains it |
| Control plane restarts (post-MVP, P8.14: the host-side lease kill timer behind the lease-expiry loss) | host: tunnel drop | reconnects; `host.hello` replays inventory, then the unacknowledged `vm.event` journal | rebuilds registry from hello; VMs survive only while their remaining leases cover the outage. | `vm.start` sent, tunnel drops before the result | control plane: `timeout` | boots or not; result retained | on reconnect reads the inventory: listed → treat as `started`; absent → re-send the same idempotent command |
| Two incarnations of one workspace placed on the same host | host | second `vm.start` gets `slot_unavailable(workspace_busy)` | places elsewhere or waits for the first VM's `exited` |
| Control plane and host disagree on protocol | `host.hello` | on `host.reject`: self-drain, keep VMs and leases, retry with backoff | deploys the control plane first so both host versions are accepted |

| Replayed/expired/unknown registration (post-MVP, P8.10) | API exchange | no tunnel/credential | 401, durable security audit, no new host row |
| Host identity/claim mismatch (post-MVP, P8.10: the changed-runtime-identity credential-drain path) | hello/tunnel validator | no admission | reject before inventory/secrets; changed registered runtime gets restricted credential-drain path only |
| Terminated/revoked host reconnects (post-MVP, P8.10: the credential generation check) | credential generation/registry | connection refused | close old tunnel, reject even unexpired credential, settle/fence affected VMs with recorded loss |

## 12. Invariants

1. The host runs what the control plane names and nothing else: every VM on a host corresponds to a `(workspace_id, vm_id)` the control plane issued, and every reconnect reconciles the two sets by killing the difference.
2. **Post-MVP (P4.12).** MVP behaviour: credentials are environment variables, the provider key being the current owner's, resolved at dispatch, and the platform token the incarnation's; GitHub and GitLab tokens still never enter the VM. A provider, SCM or platform credential never enters a provider process; declared workspace build/task secrets are intentionally available there (§6.6). Provider, git and platform credentials reach the host by reference in `VmSpec.credential_grants`, live in host memory, and are attached only by the host proxies for the incarnation that owns them. The dispatcher alone holds the workspace token, bound to the incarnation, for its own calls to the control plane.
3. **Post-MVP (P8.14: the lease-expiry exception).** The host never decides that a VM is done, idle, or lost. It reports; the control plane decides. The single exception is lease expiry, which the host enforces locally because it is the same value the control plane waits for before placing a replacement.
4. Slot occupancy is derived from `workspace_vms`, never stored on the host row, so a crashed start cannot leak a slot.
5. **Post-MVP (P4.12: grant updates).** Starts, grant updates and new streams reject stale incarnations, including after reconnect; a draining incarnation is current. `vm.stop` accepts any VM this host owns so a superseded VM can always be stopped.
6. Model traffic and git traffic egress from the host, never through the control plane tunnel, so a single control-plane replica is not on the data path of a running agent.
7. **Post-MVP (P8.14: the monotonic lease timers and host-originated lease acquisition).** Lease safety uses bounded monotonic timers (§5), never reply-arrival time; processing budgets are checked before execution; initial boot requires host-originated lease acquisition, events use per-VM sequence numbers, and commands are matched by idempotency key.
8. A host never runs a command it cannot parse: the protocol version is negotiated at `host.hello`, the spec version is checked before any side effect, and an unknown version is a refusal that leaves running VMs untouched.
9. Every refusal is definite and named. A host answers `slot_unavailable(reason)`, `spec_rejected(reason)`, `busy` or `too_many_streams`; it never hangs on a limit.

## 13. Settled host decisions

- **Post-MVP (P4.12: the proxies; P8.10: the registration exchange and operator issuance).** P4.4a owns the versioned transport/types/event ingestion, P4.4b boot and kernel boundary, P4.12 proxies, and P4.13 placement/operator issuance lifecycle; P4.1 owns schema and P4.4a owns the all-kind registration exchange. `WorkspaceVmService` calls placement; it does not independently choose a host.
- Protocol and `VmSpec` versions remain separate. Unknown versions refuse safely and running VMs retain only their existing bounded leases.
- **Post-MVP (P8.14: the self-declared runtime identity and the org image allowlist).** Runtime bundle and guest image are distinct. Hosts report self-declared runtime identity; there is no retained remote host-attestation guarantee. The repo-selected guest image is bounded by the org allowlist.
- **Post-MVP (P8.11: passt as the only network mode and the nftables mechanism; P4.12: the proxy secret).** MVP behaviour: network mode stays selectable by `G5D_VM_NET`, TSI by default and passt on GCE, and passt starts with no firewall rules. Passt is the network mode. Per-VM network isolation plus the proxy secret is mandatory before production admission; exclusive per-incarnation passt UID plus nftables and the exact translated proxy/DNS exceptions in §6 are the selected Linux mechanism.
- `vm.stop graceful` signals the VMM process group after private stop/flush/harvest completes. It does not promise a signal to guest init.
- The tunnel registry is process-local for MVP. Reconnect rebuilds it only inside existing lease bounds; multi-replica work is triggered when measured deployment/availability needs cannot fit those bounds.
- **Post-MVP (P4.12: session-path model routing and credential brokering).** Agents supplies session-path model routing and native provider question/approval control; a session tag is accounting data, never a credential or execution identity. Worker & Host supplies the pinned runtime bundle and brokers credentials only to declared boundaries.

## 14. V9 boundary acceptance

**Post-MVP (P4.12: spoofed session ids, live same-owner key rotation and delayed grant updates; P8.12: cache isolation).** Tests must exercise owner-only credential selection across multiple sessions, spoofed session ids, human and workflow inputs sharing the agent session/task path, rejection of non-owner preview/PTY/HTTP/live-file/log/inspection paths while owner preview remains visible/cancelable, live same-owner key rotation, stale old-incarnation requests, delayed grant updates, and transfer interrupted at flush, host exit or owner/audit commit. After transfer a continuation uses the same logical task under the new owner's account only after owner resume; the ended attempt's process-bound requests stay historical. A confirmed deferred question retains its card and native tool identity for an answer through the restored callback without a replacement user prompt, and an interrupted attempt cannot release task dependencies as success. Lost host stop replies must not permit concurrent old/new owner VMs. Preview cancellation/replacement belongs to task and module tests, while the host boundary proves old listeners close and replacement placement follows confirmed exit or lease fencing. Lifecycle flushes have only shutdown/fork reasons; the host introduces no Commit, explicit-flush or workspace-search surface. Also prove that reader browsing/fork never opens a source VM stream, explicit attachment precedes owner execution and upload, transfer revokes old live streams, and ordinary stop/Resume races preserve incarnation fencing and session history. Validate stale generation-bound retries and cold/warm/new-fork cache isolation and startup behavior. These are required implementation gates, not evidence that current deployments satisfy v9.
