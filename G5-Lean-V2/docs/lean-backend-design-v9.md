## 0. What changed since draft 8

1. **Non-owners browse durable data only.** Repository content, trees, diffs and document/ontology views read internal Git even while the source VM is running. Chat/task/PR history still reads durable platform metadata. Non-owners cannot call the source VM's file APIs, observe its live filesystem or use its ports, preview relay, terminal, inspection or live log streams. (§5.1, §6.6, §9.1)
2. **Preview is owner-only.** Start, replace, cancel and live relay access require the current owner. Preview remains a visible, cancellable `preview` task, separate from `agent` and `command`. The v8 reader-preview exception and its accepted disruption are removed across UI, APIs, CLI and grants. (§6.8)
3. **No attached VM means read-only.** The owner explicitly starts/resumes before editing, uploading or executing. Save never boots a VM. An explicitly labelled compound Start workspace and … action may attach then execute after ready; passive browsing, queued work and an old Save cannot cause a wake. User-originated Git writes are gated too. (§5.3, §5.8, §9.2)
4. **Fork is the normal contribution path.** A non-owner forks into a workspace they own, works there, and submits changes for authorized merge/adoption. A reader fork uses a pinned durable Git snapshot and never asks the source VM to flush or quiesce. An owner may live-flush their own source for a fresh cut. Every entry point retains exact shared branch names, all-member collision checks and recoverable creation. Ordinary fork creates metadata/refs without booting the child. (§5.8)
5. **The MVP is the backend refactor and simplification.** Dedicated review/explainer requests, source-versioned returned results, result/reply APIs or CLI/UI, special producer publication and completion-driven child cleanup are excluded by the latest user scope decision. Ordinary forks and shared agent conversations remain. (§5.9)
6. **Runtime history and cleanup retain ordinary semantics.** Agent output persists in its shared transcript; final logical task outcomes release dependencies. Normal Stop, idle and operational teardown flush/release compute without deleting history. No product-result publication barrier or completion-specific stop reason is added.
7. **Delivery and testing have concrete owners.** Security mechanisms and their production-boundary tests belong in introducing PR Do/Acceptance steps. Optional product workflows do not add MVP dependencies. The implementation checkpoint records API-boundary ownership and test coverage, not a claim of runtime proof.

V8's retained contracts remain: exactly one owner; transfer stops/flushes/releases before changing owner and requires new-owner Resume; shared branch names allocated only by checked fork; no workspace search, Commit or Flush now controls; private flush reasons `shutdown|fork`; shared `agent` sessions and same-task continuations; explicit permission policies; direct Claude native requests and noninteractive Codex exec for MVP, with later stdio app-server migration. Earlier documents and the [v8 security review](lean-backend-design-v8-security-review.md) remain historical evidence. Cross-workspace Git-object isolation, untrusted preview-origin isolation and guest egress enforcement are explicit MVP contracts and tests owned by P4.3a, P5.1 and P4.4b/P4.12. This revision addresses the design omissions; it does not claim those runtime findings are implemented or closed.

The exact Git snapshot fallback, explicit Start/Resume presentation, lifecycle defaults and recovery below are v9 design choices made to turn the agreed workflow into a coherent contract. They are not represented as verbatim meeting decisions. See the [decision record](v9-meeting-decisions.md).

## 1. Summary

G5 today runs one microVM per task attempt, keeps uncommitted edits in a server-hosted CRDT, kept branch heads in Postgres until Phase 1 made git refs authoritative, keeps chat VMs alive between turns through a sticky-runtime protocol, and layers approvals, merge runs and remote-tracking sync on top. The target is a developer-laptop model: one VM per workspace, ordinary files in each member repository on the workspace’s shared branch name, native git, agents that commit and push their own work, and a control plane that only steps in at the boundaries. The VM is not as persistent as a laptop: it is terminated when idle and re-provisioned on request, and when G5 terminates it gracefully it first flushes uncommitted state to internal git so the next VM can pick up where the last one left off.

|---|---|---|---|
| 1 | One VM per workspace; tasks are processes launched by a dispatcher through declared modules | §6, §7 | per-task VM boot, materializer, host poll/claim/ack, golden images |
| 2 | Remove the CRDT layer | §9 | `g5-crdt`, both CRDT peers, drafts, task-commit protocol, yjs in the UI |
| 3 | Internal git as persistence: agents push; G5 flushes at graceful teardown; restore from a receipt | §5.4, §5.5 | staging refs, Postgres-owned heads, the draft 6 checkpoint cron |

## 2. Goals, constraints, non-goals

**Goals.** Simplest possible backend; easy to keep stable; the nine proposals; laptop-like developer experience with a first-class workspace that maps to one branch per member repository, using the same branch name in every entry; UI like GitHub Codespaces; a dispatcher core that is small, well tested and never edited for features once it ships, with features as modules outside it.

**Constraints.**
- Incremental: the existing source is modified and the frontend components reused; every PR leaves a buildable, testable product; vestigial references to the old architectures are removed as they are met.
- The control plane remains one deployed binary; a split into separately deployed services is not attempted now.
- Schema: the baseline is frozen; every change is a forward migration; no data compatibility with the original G5 platform is required, but dev and QA databases are not disposable (§12).
- Providers: Claude Code and Codex, pinned CLIs (`scripts/claude-code-cli-version`, `scripts/codex-cli-version`), one provider process per attempt, which can span Claude's own follow-up turns (§8.3). No long-lived agent process between attempts in the MVP. The Claude Agent SDK is not used: the runner drives the CLI's own stdio protocol, which is what the SDK wraps; the SDK's published type definitions may serve as a schema source (§8.7).
- Platform login: GitHub in the SaaS; Microsoft Entra for self-hosted installations returns in the self-hosted phase (§16). Repository providers: GitHub and GitLab, and local-only repos.
- Deployment targets: the GCP SaaS (GKE control plane, GCE worker hosts, the QA project as CI/CD), self-hosted Linux hosts on pre-provisioned VMs with the Azure canary lane, macOS hosts for development only. Customer-specific worker images are dropped.
- Ontology and grounding: the G5-Lean codebase is developed without its own ontology and grounding gate; the ontology product surface (uplift, downlift, sync, grounding tools, ontology projections) is retained in the code and decoupled from git and CRDT as in draft 6, but it is not part of the MVP acceptance and is revisited afterwards. This is the reading this draft takes of the team's decision to remove the ontology during MVP development; it needs confirmation.
- External CI integrations are postponed; agents run tests in the workspace VM with local compute.
- Credentials: environment variables are the credential mechanism in the MVP, as in the original: the provider key, repository and task secrets and the VM's platform token reach processes as environment (§6.5). Files, secrets managers and HTTPS-proxy capture come later. GitHub and GitLab tokens still never enter the VM; publication is server-side. **Post-MVP (P4.12).** Provider, git and platform credentials never enter a provider process (§6.5).

**Non-goals for this iteration.** Real-time co-editing or presence (a document-only CRDT can come later behind the Save API); additional hardening beyond the explicit Git authorization, preview-origin, guest-egress and credential-isolation contracts in this draft; new cloud providers; tracking of provider subagents (the provider process is the unit); interactive Codex questions and approvals in the MVP (scheduled stdio app-server phase, §17.2); live steering of a running turn (a resident-process capability, §8.7); agent-initiated workspace creation (§17.3); multiple API replicas (§17.2); a CI service outside workspaces.

## 4. Target architecture

### 4.1 Components and owners

Ownership follows the capability, not the process a component runs in. Four capabilities own the system; three have named owners in the plan, the fourth is assigned by the team.

| Capability | Owns | Runs in |
|---|---|---|
| **Workspace** | Workspace registry and members, `workspace_vms` and incarnations, the six actions including ownership transfer, the stop sequence, the flush and restore, the Workspace Runtime facade, the dispatcher (`g5d dispatch`) and the module runtime, the built-in `workspace.*` modules (changes, preview, bootstrap, diagnostics), the workspace shell UI (files, Save, Changes, terminal, ports, preview) | g5-api, the VM |
| **Agents** | Tasks, attempts and jobs, chats and the inbox, questions and permissions, provider accounts and workspace-owner credential bindings, session files, usage, the provider adapters and the `agent.turn` module, the chat and task UI | g5-api, the VM (module only) |
| **Worker & Host** | `g5d host`, the `ctl` protocol on both ends, `worker_hosts` and host states, placement and quotas, `VmSpec` and images, the host proxies (post-MVP, P4.12), drain and rotation, the operator API, the runtime image and the pinned provider binaries in it | the host, g5-api |
| **Git and governance** | The internal git service and `RepoStorage`, receive-pack policy, the flush-ref namespace rules, protected-branch mirroring and publish, pull requests, approval rules and decisions, the merge operation, the projections' convergence | g5-api |

The control plane is one binary (`g5-api`) with these four bounded contexts as crates or modules with internal interfaces; a split into services is not a goal now. The frontend follows the same ownership per panel.

**g5-api (control plane).** Postgres-backed. Owns identity and orgs, the four capabilities above, the internal git server, the tunnel registry, the browser WebSocket, and the preview and terminal relays.

**Internal git store.** One bare repo per connected repository under `RepoStorage` (local disk for self-hosted, Filestore for the SaaS). Holds mirrored protected branches, every workspace branch, and the immutable flush refs. Git refs are authoritative for files.

**Worker host (`g5d host`).** A Linux machine with KVM (GCE VM, a self-hosted VM with nested virtualization, or a macOS dev host with HVF). Registers, dials one outbound tunnel, boots and stops equal-size workspace VMs on command, and relays streams (host-side proxies are post-MVP, P4.12; the host-side lease timer is post-MVP, P8.14). No task logic, no knowledge of branches or approvals.

**Workspace VM.** One libkrun microVM per non-base workspace, attached only on explicit owner Start/Resume (including an explicitly requested compound start action) and terminated by the stop sequence or by loss. Each attach is a new incarnation (`vm_id`, `epoch`). Its disk is a cache. It runs the **dispatcher** (`g5d dispatch`): restores the workspace from the last flush receipt, serves the Workspace Runtime API, runs declared modules, journals their events, and performs the flush when asked. Chat turns, agent tasks, the preview and terminals are processes in this VM, in one folder, on the workspace branch.

**Frontend.** The React shell with a Codespaces-like center: file tree and editors with explicit Save, a Changes panel, a terminal, Ports and Preview, chat with a queued-message strip, tasks, PRs and approvals.

**Providers.** The pinned `claude` and `codex` CLIs on the VM's runtime mount, launched by the `agent.turn` module, one process per attempt. Model traffic goes through the in-guest proxy with the workspace owner’s key delivered as environment, as in the original (§6.5). **Post-MVP (P4.12).** Model traffic goes through the host proxy using the workspace owner’s account, with a per-session URL for accounting; no provider key or platform token enters provider/repository processes.

### 4.3 Invariants

1. **Two sources of truth.** Files: git in the internal store (branches and flush refs). Metadata, chat messages and timeline, inbox, questions, provider session files, workflow requests/results and flush receipts: Postgres. The VM disk is a cache. A VM never writes the database; every write goes through the API, and transient VM state (open ports, resource use) is read over the runtime API, not stored.
2. **One working workspace, a vector of same-named repository branches, one VM incarnation, one dispatcher.** Each member repository has its own checkout under the shared workspace root; concurrent tasks use those same checkouts. Only workspace fork creates the authoritative member branch refs; it must first accept one collision-free name across the whole vector. The `workspace_vms` row with its lease, `vm_id` and `epoch` is the only custody record; every boundary rejects an incarnation that is not current (§6.4).
3. **One write path for files.** All file writes happen inside the VM: agents natively, the UI through `fs.write`. The API never writes a working tree.
4. **Branch protection lives in receive-pack.** User-requested protected-ref changes go through the API's merge operation after approval checks; repository bootstrap and provider imports are separate API-only paths. Flush refs accept create-only writes from the workspace's current incarnation or the API's checked fork-copy operation, and deletions only from the API.
5. **An attempt is a process; an agent task is a logical unit.** Bounded attempt completion derives from process exit plus the adapter outcome. Agent continuations retain the same task/session/job/dependency identity; only final logical success releases dependents (§7). A preview is a service: readiness is running, cancellation ends it normally, and unexpected exit is failure (§6.8). Execution identity is `(task_id, attempt, vm_id)`; confirmed starts distinguish intent from execution (§7.5).
6. **Platform code runs only as declared modules.** Nothing in the control plane can spawn an arbitrary process in a VM; a feature that needs to run workspace code declares a module with a contract, limits and requested capabilities (§6.7).
7. **Durability boundaries are the flush and the push.** Pushed commits are durable. Everything else survives only through a complete flush receipt, and a receipt is complete only when every repository's snapshot is retained by an immutable ref that the API has verified (§5.4).
8. **Stop is a barrier.** A VM is released only after the flush receipt and the session-file harvest are durable, or after a deadline-bound teardown has recorded that the flush failed; the draining incarnation stays current until release (§5.8).
9. **Credentials are environment variables.** The provider key is the current owner's, resolved at dispatch; the platform token is the incarnation's. Transfer releases the old VM before the new owner's first dispatch, so an old owner's key or token is never used after the owner commit. **Post-MVP (P4.12).** **No secret in a provider process.** Provider/SCM keys remain host-only and proxies attach them for the current incarnation. The workspace token is held by the host and trusted dispatcher only; repository/provider processes cannot access it (§6.5).
10. **Projections converge from git.** Events are hints; every projection can be rebuilt from authoritative OIDs without an event (§9.4).
11. **Nothing crosses the VM boundary at-most-once.** Starts, answers, events and outcomes are persisted on one side and confirmed by the other; duplicates are detected by key, never by ordering (§7.5).
12. **One human writer.** The workspace owner alone mutates it; read access never implies write access. Fork creates a separate workspace owned by the caller; it grants no source mutation or VM access. Repository reads by non-owners always resolve durable Git. An ownership change is committed only after the old incarnation is released, with an audit record in the same transaction.
13. **Versions are negotiated, never assumed.** Host, VM image and control plane deploy independently; the protocol version is negotiated per tunnel, the spec version per boot, the module catalog version per incarnation; the control plane deploys first and hosts may be at most one version stale (§6.10).

Every new tenant-owned table, including joins, operation records, event tables and scoped configuration, carries `org_id NOT NULL`, enables and forces RLS, and uses the baseline `tenant_isolation` USING/WITH CHECK policy with `authz.current_org_ids()`. Org/user/workspace config records are tenant-scoped, including user settings per org membership. **Post-MVP (P8.14).** **Access-generation owner.** MVP uses the existing org row’s single `orgs.access_generation` counter. The same transaction that changes org membership/role or workspace invitations, visibility, ownership or deletion increments it under the org authorization barrier. Read admission, Git scopes, host artifact requests, preview tickets and stream delivery bind that value and recheck current predicates; a changed generation fences future delivery and invalidates all org-scoped cached authorization/views. This intentionally coarse invalidation avoids a second fine-grained ACL state machine. `GitObjectViewManifestV1.access_generations` has exactly one MVP entry `{scope_kind:org, scope_id:org_id, generation}`. P4.1 adds the counter; P4.3a/P4.5 update every authorization writer/consumer with it.

`workspace_repos` carries no authoritative head; `head_sha_cache` is a projection (§9.4). A working workspace spans N repos (code repos plus the org docs repo). Its mapping is `workspace_id → [(repo_id, workspaces.branch_name), ...]`: identical branch names are enforced, while commits and OIDs are independent per repository. `workspaces.branch_name` is the single authoritative name, not a per-repo option; `workspace_repos.base_branch` is each repository’s upstream/update target, inherited from the source mapping or selected protected default; it may differ across repositories. The fork manifest separately pins each actual source branch/OID. The target CHECK is `(is_base AND branch_name IS NULL) OR (NOT is_base AND branch_name IS NOT NULL AND name = branch_name)`: working workspaces require non-null `branch_name` equal to their accepted name. Keep the existing role/display/routing fields for compatibility; these checks prevent them becoming independent authorities. P4.1 stages the fields and P4.5 validates reconciled legacy rows before tightening. A read-only base workspace has no fork-created working branch (`branch_name` is null) and resolves its existing protected refs per repo; the identical-name constraint applies to the working branch vector created by its fork. Pushes are per repo, like a laptop with several clones. There are no job or task branches and no workspace status column: a workspace exists or is deleted, and its VM state lives in `workspace_vms`. `vm_id` is the globally unique current incarnation fence; `epoch` monotonically orders that workspace’s attaches and session harvests. Both change on every attach and `vm_id` is cleared at release. `last_flush_id` names the receipt the next attach restores.

`workspace_forks` is both the operation record and the durable name reservation. A committed row in `pending` or `aborting` claims its exact `proposed_name` in every member repository listed in `repo_manifest`, including while cleanup is stalled with `error.recovery_required`. Freeze and validate the nonempty, duplicate-free same-org member IDs and proposed name before inserting `pending`; those claim keys never change. Source OIDs, flush/copy evidence and per-member progress are populated or pinned later under the operation contract, without changing its claim set. An idempotent retry resumes this same record. There is no `workspace_fork_reservations` table, parallel reservation list or expiry-based release.

The operation pins source OIDs before writing refs. Only `completed` after all-member verification/publication, or `aborted` after verified cleanup and exclusion of delayed writes, ends its temporary reservation. In `completed`, the existing destination Git refs enforce subsequent name collisions. Interrupted, failed or stalled work remains `pending`/`aborting`, survives API restart and is never pruned or hard-deleted to free its name. Existing Git names and slash-prefix conflicts still refuse creation independently of the operation query. The destination is unusable and cannot boot until all branches and copied snapshot refs exist and final workspace/receipt metadata commits. The fork row does not become another workspace lifecycle or head authority.

A non-unique partial index on `workspace_forks(org_id) WHERE status IN ('pending','aborting')` bounds lookup to unfinished tenant operations; historical forks do not participate. The existing `(org_id, requested_by, idempotency_key)` unique constraint remains. Neither that index nor a unique index over a JSON member vector enforces overlapping member claims. Correctness comes from §5.8's locked admission and status-transition protocol. Service validation protects the manifest's repository references; repository deletion takes the same repository lock and refuses while any unfinished manifest names it. Terminal audit rows retain their historical member IDs under ordinary retention.

`owner_user_id` names exactly one active org member with role `owner|admin|member` and is the authority for human writes; `created_by` is immutable provenance, not permission. The owner always reads their workspace. “Org admin” means role `owner` or `admin`; viewers cannot own, fork or receive a transfer (`ORG_ROLE_READ_ONLY`). Org admins read any workspace; other org members read when visibility is `org` or their invite is present in `workspace_members`. An invite grants read access only. Invite add/remove and visibility changes are owner capabilities; an org admin who is not the owner must transfer ownership before changing them or writing. The creator, former owner and membership role never confer an extra permission. The transfer audit preserves the old owner, new owner, requester and completion time (§5.8); a pending or aborted operation is not a completed transfer. Base workspaces retain an owner for administration but remain read-only and have no VM.

Non-owners browse repository content through internal Git and read authorized durable chat, task and PR metadata. They never use live VM file, watch, port, relay, inspection or log APIs. The owner alone edits/uploads, sends chat, answers native questions, uses terminal, starts/cancels any task kind, changes settings and performs lifecycle actions. An org admin takes ownership before exercising these owner capabilities. Fork is available to authorized readers, creates a workspace owned by the caller and never wakes or flushes a non-owned source. Code changes return through a separately authorized merge. Ordinary agent conversations may discuss or review the files in their own workspace; a dedicated returned-results workflow is outside the MVP (§5.9).

|---|---|---|
| Browse repository files, docs, tree and Changes | durable Git only | live VM when attached; durable Git otherwise |

Resume need is derived from lifecycle and consent, not a stored inverse flag. A stopped/failed workspace without a valid current-owner `start_intent` requires explicit Start/Resume; queued tasks, reads and held-session existence never supply consent. A consumed intent authorizes its admitted incarnation, not a later VM. Transfer separately closes admission until completion/abort. Same-incarnation retries remain allowed by task policy; deliberate drain/rollout may use the persisted owner/generation-bound successor intent unless a later stop/transfer/loss revokes it.

The single current Start/Resume authorization is `workspace_vms.start_intent`, not an additional table: `{id, kind: resume|restart|compound_start|rollout_continuation, owner_user_id, lifecycle_generation, status: pending|queued_for_capacity|starting|consumed|expired|cancelled|failed, launch_task_id?, created_at, expires_at, attempts, consumed_vm_id?, superseded_reason?}`. There is one active intent per workspace row. Its owner/generation/expiry are checked on every placement and readiness transition (§5.8); queue state survives an API restart. A compound action creates its launch task/input in the same transaction as this intent.

Workspace deletion is a tombstone (`workspaces.deleted_at`). Completed `workspace_forks` records retain the ordinary source/target parent link and pinned source vector under operation-audit retention; they do not grant source read access after revocation. Chats, session files and task rows follow the ordinary deletion/retention policy. Git refs/receipts and retained roots are purged only after active fork/read/restore pins settle. Usage and operation audit survive under retention. Owner membership removal/demotion is refused with `OWNER_OF_WORKSPACES` until explicit transfers/deletions finish; no silent admin assignment or ex-member dispatch is permitted.

### 5.2 Branch naming and identities

- Workspace branch: the user’s proposed workspace name, validated as a Git branch name and used unchanged as `refs/heads/<name>` in every member repository. For a new working workspace, `name = branch_name`; do not silently slugify it, append a workspace ID, choose a fallback or reuse an existing branch. A URL slug is routing metadata only. Invalid names and collisions return a field error asking the user to choose another name.
- Base workspace: is a read-only view of each member repository’s existing protected/default ref. Those source refs may have different names (`main` in one repo, `master` in another); they are not the working branches allocated by a fork. Repository onboarding and initial protected-ref bootstrap remain repository setup, not alternate creators of workspace branches. A fork from this base creates the proposed common destination name in every member. Base has no VM; chat, preview and terminal offer "fork and …" through that checked operation. Network pushes to protected refs are denied.
- Identities seen by the git service: **user** (current workspace owner for receive-pack; any authorized reader for upload-pack, JWT as today); **workspace incarnation** (the workspace token, a typed JWT with audience/use, org/workspace/owner/VM/epoch and lease-bound expiry (§6.4), minted at `lease.acquire`, renewed through `lease.renew` while the incarnation is current, held by the dispatcher and by the host credential proxy, never by a provider process; **Post-MVP (P8.14: `lease.acquire` and the lease-bound expiry; P4.12: the host credential proxy and the no-provider-process rule).** in the MVP the API mints the token at placement, its expiry follows §6.4 "Lease in the MVP", and it is an environment variable of the dispatcher and of the processes it launches, as `G5D_TOKEN` is today); **API server identity** (merges, forks, protected-ref bootstrap/import and internal-ref pruning, in-process).

**Only fork creates the mapping.** Every user/API/CLI action that creates a working workspace, including a UI labelled Create, forks a source workspace (which may be a base workspace) through §5.8. A raw branch-creation endpoint, clone/ensure fallback, missing-ref repair or member-repo edit must not mint a branch outside that operation. MVP has no independent rename of a working workspace or its mapped branch; its name remains the exact shared branch name. Changing the URL slug cannot change that mapping. Local Git experimentation cannot create a new platform workspace or published member-branch mapping.

**Legacy mapping cutover.** Before Helm enables the v9 mapping readers/writers, an operator-approved preflight dry run records the source revision, workspace/member row versions, proposed owner and exact existing common branch per workspace. The approved bulk policy may preserve an existing common Git-valid branch name when every member already has that same mapping/ref; no per-row manual name is needed for this unambiguous case. It sets the workspace name to that explicitly approved existing branch name when necessary, reports that display-name change for approval, and preserves the URL slug. It creates, renames and overwrites no Git ref. An owner is copied only from an explicitly approved eligible existing owner/creator policy with current membership validation, never guessed for orphaned or ambiguous rows. Divergent member names, missing refs, conflicts or ineligible/unknown owners remain blocked with a concrete report; operator-selected resolution or a separately authorized checked fork is required. The apply command compare-and-swaps the recorded row/ref versions, records each reconciled row and is idempotent; drift triggers a new preflight rather than silently accepting a new state. P4.1 retains the compatibility writer during staging; P4.5 blocks the feature flip until every live mapping has a verified marker and the base/working CHECK passes. Positive fixtures prove common-name rows migrate under one bulk approval; divergent and orphaned fixtures prove the unattended deploy refuses without invented names/owners. This is a one-time migration of existing mappings, never another ordinary branch-creation path.

A base is administered by the connecting user as owner and defaults to org visibility; invite-only uses the same read rule. An org admin may transfer it. It has no VM: Start/stop/restart returns `WORKSPACE_IS_BASE`, and Delete is refused while its repository remains connected. Administration never grants direct protected-ref writes.

### 5.3 Receive-pack policy (the git boundary)

`routes/git.rs` keeps its shape: parse ref updates, decide in Rust, spawn `git receive-pack --stateless-rpc`.

| Ref | user (current owner) | workspace incarnation (current) | API server identity |
|---|---|---|---|
| `refs/heads/<protected>` | deny | deny | approved merge (§10.6); repository bootstrap or provider import (§5.2, §5.6), honoring fork reservations |
| `refs/heads/<workspace branch>` | update existing mapped ref only: FF or rewrite (below); never create | same | create only through the checked fork; authorized merge updates an existing target (§10.6) |
| `refs/heads/<other workspace's branch>` | deny | deny | n/a |
| `refs/g5/flush/<workspace id>/<flush id>/{snapshot,branch}` | deny | create only (no update, no delete) | checked fork-copy create only (§5.8); delete (pruning/verified fork cleanup) |
| `refs/g5/merges/<merge op id>` | deny | deny | merge operation only |
| `refs/g5/forks/<fork id>` | deny | deny | fork receipt creation/cleanup only (§5.8) |
| delete of a workspace branch | deny | deny | workspace deletion |
| tags, other namespaces | deny | deny | n/a |

A token whose `vm_id` is not the workspace's current incarnation is rejected before any ref is considered; a draining incarnation (`stopping`) is still current (§6.4).

User-originated updates of a mapped workspace branch, including laptop receive-pack, require the current owner, a running VM and open human mutation admission; otherwise reject with `WORKSPACE_NOT_RUNNING` or `WORKSPACE_STOPPING`, without booting. This closes a bypass of the unattached workspace's read-only rule. Current-incarnation shutdown/fork snapshot publication and authorized control-plane merge/import/fork operations are separate service authorities, not a stopped user's edit path. Native Git inside an attached VM is unchanged; no shell-command policing is introduced.

**Rewrites of the workspace branch.** Agents rebase onto each member repository’s configured upstream (`workspace_repos.base_branch`), so the workspace branch accepts non-fast-forward updates from the workspace's own identities. The server enforces exactly git's update-command check: the `old_sha` the client sends must equal the ref's current value, and a zero `old_sha` is refused for every user/incarnation update of a workspace branch, even if the ref is absent. An absent mapped branch is an integrity error, never permission to recreate it by push; only the identified fork operation can finish its own pending creation. That rejects a ref that moved during push negotiation and makes `--force-with-lease=<branch>:<expected>` work as designed; it does not prove that the pusher incorporated the previous head. Lease safety is a client obligation: the profiles require `--force-with-lease` and forbid bare `--force`. In the shared-folder model every agent in a VM shares the same clone of each member repository, so a rewrite that discards an unseen commit can only happen between the VM and a user pushing from a laptop, which is the laptop semantics asked for. The platform never moves the agent's remote-tracking refs behind its back: the flush observes the internal head with `git ls-remote` and never fetches.

**MVP Git service contract.** In the MVP upload-pack and receive-pack run on the authoritative repository with the repository-level read check and the landed receive-pack policy, plus the owner, ref-scope and flush-ref rules of this section. Workspaces that share a repository can fetch each other's objects by OID, as in the original; this exposure is accepted for the MVP.

**Post-MVP (P8.12).** The rest of this subsection up to "`git-upload-pack` requires" specifies the per-principal upload-pack roots, the authorized object views, the view budgets, the host artifact transport and the scoped receive-pack transaction, and is not part of the MVP.

**Upload-pack authority.** `info/refs` and upload-pack share the same freshly authorized ref and reachable-object view:

| Principal | Visible roots in a member repository |
|---|---|
| User reader | Protected/base refs the user can read, existing mapped branches of readable workspaces, and complete unpruned flush leaves of those readable workspaces. |
| Workspace incarnation | Its own mapped branch and complete receipt leaves plus its authorized protected/base update refs; no sibling workspace refs. |
| API service | Only roots required by its identified fork/import/merge/maintenance operation; proof refs are never advertised to ordinary clients. |

**Agent push and provider forwarding.** Agents run ordinary `git push` to the
configured internal origin. Runtime Git configuration routes that exact URL
through the credential-isolated relay and supplies the workspace upstream.
Accepted branch updates enqueue remote integration; flush refs do not. The
workspace's auto-push toggle decides whether saved commits forward implicitly
to its configured, already-existing provider branch. Manual mode saves only to
G5. Provider publication checks ancestry and leases the observed destination,
refusing deletion or concurrent movement; implicit push never creates a branch.
Auto-push recovery runs independently of auto-pull. Git success means saved and
queued at G5; provider delivery and external CI remain asynchronous outcomes.

**Immutable authorized object views.** The Git service owns disposable views at `<git_view_root>/<org>/<repo>/<scope_digest>/repo.git`; the authoritative bare repository remains the only ref authority. `GitObjectViewManifestV1` is `{version:1, org_id, repo_id, object_format, principal_scope:{kind:user|workspace_incarnation|api_operation, subject_id, owner_user_id?}, access_generations:[{scope_kind,scope_id,generation}], roots:[{ref_name,oid}], pack_sha256, object_set_sha256, scope_digest}`. `subject_id` is the user, workspace or identified service-operation ID; workspace scope also binds its current owner. The digest covers canonical version/identity/scope/generations/sorted roots; the pack and sorted object set have separate SHA-256 digests. Current incarnation/epoch/lease is revalidated when a host fetches or materializes the artifact, not inferred from its cache key; this permits same-scope warm reuse without retaining old incarnation authority. Resolve these from current authorization under the repository/access/source-pin barriers, never from a caller-supplied path. Pin roots while building/serving. Build in a private temporary directory: initialize an empty bare repo, enumerate only the captured roots’ reachable closure, export a self-contained non-thin pack of that closure, verify its complete object set/connectivity, install only the selected refs and atomically rename the complete view. Disable replace/graft/shallow/global-config effects. No unrestricted alternates, global object-directory mounts, copied global refs/reflogs/hooks/config/credentials or reused source pack containing unselected objects is permitted. Shared ancestors reachable from an authorized branch are readable history; this is not historical redaction.

Both `info/refs` and upload-pack run only against that view. Deny guessed unadvertised wants; hideRefs and `uploadpack.allowAnySHA1InWant=false`/`allowReachableSHA1InWant=false` are defense in depth, never the object boundary. Every HTTP operation re-resolves current roots and principal/access generations before selecting a cached view. An ACL change fences future delivery and cancels old streams; bytes already delivered cannot be revoked. A branch change between advertisement and fetch can require a fresh advertisement/retry, never global-store fallback. Raw file/tree/download/diff/projection OID lookups require the same authorized reachability. A build failure or stale authorization returns a typed refusal/retry without serving the global repository.

**View storage and cost.** Platform deployment settings own `git_view_cache_bytes=64 GiB` per API cache instance, `git_view_org_bytes=16 GiB`, `git_view_max_bytes=8 GiB`, `git_view_build_concurrency=2` (at most one per org), `git_view_build_timeout_secs=180` and `git_view_idle_ttl_secs=900`. These are initial adjustable capacity defaults, not meeting SLAs. Coalesce concurrent builds for one key, reserve twice the maximum view size for a build/import, and preserve 10% filesystem free space. Enforce the same bound on temporary receive-pack repositories. Oversized views return `GIT_VIEW_TOO_LARGE`; exhausted budget/time returns `GIT_VIEW_UNAVAILABLE` with Retry-After. Evict least-recently-used unpinned views, expire unpinned idle entries and reclaim abandoned temporary builds on restart. A held stream pins its entry. Eviction forces an authorized rebuild, never a looser source. Record build time, packed bytes/object count, cache hits and cold/warm/ref-churn measurements in P4.3a; pack/history duplication is an explicit cost. Hosts own their local cache budget under worker-host §7 and consume the same scope-bearing artifact, not the API's filesystem path.

**Host artifact transport.** `POST /api/internal/workspaces/:workspace_id/git-views/:repo_id` takes `{vm_id, epoch, source_manifest_digest}` and accepts only the assigned host’s current `g5-host` credential. It verifies current starting/running placement, owner, live lease and org access generation; user, workspace-incarnation and provider tokens cannot call this route. The digest is SHA-256 of canonical server-issued `VmSpec {incarnation,repos,restore}` retained with the boot command. The API resolves roots from that spec and its source pins, never caller-supplied roots or OIDs. The authenticated response is bounded `multipart/mixed` with exactly two ordered parts: `manifest.json` (at most 64 KiB) and `repo.pack` (at most `git_view_max_bytes`). These are fixed entry labels, never archive paths to extract. The host verifies manifest identity/root scope and both pack/object-set digests before materializing; cached bytes require the same current authorization check. There is no guest/model-broker access or presigned global-pack URL. P4.3a owns this producer; P4.4b consumes it after that dependency lands. No new database table or cross-scope object-sharing optimization is required.

**Scoped receive-pack transaction.** Create a writable temporary bare transaction repo from the caller’s self-contained authorized view. Run receive-pack, its quarantine/index-pack and connectivity checks only there; there is no alternate or fallback to the authoritative global object directory. Thin-pack bases can resolve only from authorized existing objects or objects supplied in this request. Validate each proposed ref command against the writable-ref/receipt policy. Git success in this temporary repo is provisional: before reporting success, reacquire the authoritative mutation/ACL/receipt barriers, recheck identity/generation/current incarnation and every old-OID CAS, import a verified self-contained pack of the accepted reachable closure, then atomically update the accepted authoritative refs. Emit branch hints/final Git success only after that commit. Denial leaves all authoritative refs unchanged; unreferenced imported objects follow conservative GC. A guessed hidden tip/parent/tree/blob or thin base cannot be borrowed from the global store to complete the closure. Supplying the complete object bytes may introduce them normally; an OID alone is not evidence of possession or read permission.

P4.3a directly implements/tests advertisement, named/known-OID reads, arbitrary-OID APIs, hidden-parent/tip pushes, hidden thin bases, build/revocation/eviction races and accepted native pushes. P4.4b binds host cache identity to org/repo/principal scope/root vector/access generation and materializes only the verified artifact into a clean guest `.git`; it must not reflink the legacy URL-keyed whole bare cache. Warm a private sibling before materializing an excluded workspace and prove its known objects are absent inside the guest. P4.9a repeats that evidence before retiring legacy caching.

`git-upload-pack` requires the repository-level read check in the MVP; this object-scoped workspace read authority (§5.1) is post-MVP (P8.12). `git-receive-pack` checks `owner_user_id` at the write boundary, including laptop pushes; neither original creator, former writer role nor org-admin status bypasses it. An admitted push and transfer share the workspace mutation barrier so a push cannot complete with stale human authority after ownership changes. VM commits are authored as the incarnation’s owner; workspace-incarnation pushes retain their audit identity. Transfer closes admission to new human pushes, drains admitted writes, and still permits the old current incarnation’s flush before release. After a successful push the handler publishes `branch.updated {repo_id, ref, old, new, actor}` as a hint; projections converge from git regardless (§9.4).

Flush receive-pack requires an already-started, unfinished `origin=flush` row for exactly the current workspace/VM/epoch and a required member repository. Only its `/snapshot` and `/branch` commit refs may be created; identical-OID retries are no-ops and changed-OID/deletion requests fail. An unknown ID returns `FLUSH_REF_UNKNOWN`. Fork-copy refs are created only by the fork service against its durable manifest, never guest authority.

### 5.4 Durability: agents push, G5 flushes

There are two durability paths. Agents make regular native commits and pushes when work is ready; G5 has no Commit button/endpoint, and Push publishes existing commits only. Pushed reachable commits survive VM loss. Privileged `workspace.flush({reason: shutdown|fork, interrupt?})` captures repository state at lifecycle boundaries without creating a commit on a workspace branch. Every graceful teardown uses `shutdown`; an owner-selected live fork uses `fork`. There is no public explicit flush or new checkpoint task.

A flush closes module/file mutation admission, drains already-admitted writes and freezes the complete member-repository set. Shutdown follows quiescence and closed terminals/previews. A live fork waits up to `quiesce_secs` (30 seconds), then refuses `WORKSPACE_BUSY` unless its owner authorized interruption; exact capture also closes listed terminal/preview writers with owner consent. Readers never request source flush or quiescence. Admission reopens after completion/refusal/failure when the workspace remains running.

1. Before pushing, create one receipt row with `flush_id` (UUIDv7), current incarnation and `required_repo_ids`. Serialize attempts per workspace. The same ID, tree and vector are reused for transport/completion retries; recomputing after failure marks that attempt failed and creates a new ID.
2. For every member, observe the internal branch via `ls-remote` without moving remote-tracking refs. Record `branch_oid`, the local mapped branch as `local_branch_oid`, current `local_head_oid`, `head_ref` (full local ref or `detached`) and sequencer state (`none|rebase|merge|cherry_pick|revert`). A missing mapped branch is an integrity error; unrelated local branches/stashes are outside the retained set.
3. Capture the worktree into a temporary index without altering the real index, HEAD or branch. Seed from the real index, refresh/re-hash files and `git add -A`; tracked ignored files remain tracked, untracked ignored/platform-cache paths are excluded. Write tree T. If T equals HEAD’s tree, `snapshot_oid=local_head_oid` and `dirty=false`; otherwise create S with T and parent `local_head_oid`, `dirty=true`. Conflict-marker files may be captured, but the receipt does not promise restoration of index stages or a live sequencer.
4. Push two create-only refs per member: `refs/g5/flush/<workspace_id>/<flush_id>/snapshot` at S/HEAD and `/branch` at `local_branch_oid`. They retain both checked-out ancestry and mapped-branch ancestry even when neither contains the other. A `<flush_id>` leaf cannot coexist with `<flush_id>/branch`; the two-leaf namespace is mandatory. Same-OID retry is accepted.
5. Completion compares the duplicate-free reported repo set with the frozen/current member set under the workspace lock. Verify both expected refs in each mirror, their commit types/OIDs, HEAD existence and reachability from snapshot, and clean implying snapshot equals HEAD. `branch_oid` is an observation, not a concurrency assertion. `FLUSH_INCOMPLETE_VECTOR` or invalid proof records failure without changing `last_flush_id`. Atomically mark `complete_at` and select `last_flush_id`; identical completion retries return the receipt, changed manifests conflict. Order receipts by successful completion, not UUID alone.

**Bounds and failure.** Defaults are 100 MiB per captured file, 2 GiB captured tree and 2 GiB upload pack, with matching advertised transport limits. Preflight includes every otherwise captured path; `FLUSH_TOO_LARGE` identifies the repository/path or pack size. Only the documented ignored/cache rules define exclusion. An exclusion list cannot turn an omitted tracked or nonignored oversized file into a complete capture: the whole cut fails, `last_flush_id` stays unchanged and the VM remains available for repair under ordinary owner admission.

Transient idle-flush failures abort the stop and set a five-minute retry cooldown. Deterministic size/proof failures instead persist `workspace_vms.last_error.flush_block` with `code`, `flush_id`, `failure_fingerprint`, `limits_digest`, bounded offending-path/size details and `blocked_since`. Other lifecycle errors update `last_error.latest` without clearing this block; only a complete verified flush from an explicit lifecycle retry or recorded incarnation loss clears it. `idle_retry_after` is null and the idle reconciler performs no periodic capture retry while that block exists. The fingerprint binds the frozen member vector, measured offending inputs and limits and deduplicates `workspace.flush_blocked` notification to the current owner. Operator lifecycle status/metrics expose the blocked VM, age and category without granting reader filesystem access. The owner repairs/removes/externalizes the files through ordinary agent/terminal work or changes an authorized limit, then retries the intended Stop/Restart/Delete/live-fork action; that explicit action performs a fresh preflight and clears the block only after a complete verified flush. No Flush-now or user Commit action is added. A changed file alone does not create an automatic retry loop.

User Stop/Restart/Delete, transfer and live fork abort without release on failed durability. If a blocked VM consumes needed capacity, an operator may contact its owner or use only an already-authorized `capacity`/drain/rollout/credential deadline teardown; these record lost Git/session/event state and notify the owner. Explicit force Delete retains its existing recorded-loss semantics. Neither a size failure nor elapsed idle time silently grants force or discards work. Next attachment after recorded loss restores the previous complete receipt.

**Retention and GC.** Keep the newest two complete receipts plus `last_flush_id`, pending fork source pins and active read/restore pins. Source selection establishes its pin under the same lock as pruning. Pending fork-copy refs are protected by their fork manifest before child receipt publication. Pruned receipt rows remain with `pruned_at`; explicit selection returns `FLUSH_PRUNED`. Failed/incomplete refs become eligible after 24 hours; unknown refs not claimed by any receipt or fork operation are swept conservatively under the same producer locks. In the MVP object reclamation stays with the existing repository GC maintenance (`repo_gc`), as in the original. Fork proof refs remain through pending/aborting, then seven days after completion or until verified abort cleanup. Deleting a source waits for pins or refuses `WORKSPACE_IN_USE`. **Post-MVP (P8.14).** Ref pruning schedules the retained serialized `repo_gc` path for packed as well as loose objects, with a 24-hour unreachable-object grace and repository mutation/backup barriers; ref deletion alone does not reclaim disk.

**Guarantee.** A complete verified flush preserves the mapped-branch tip, current HEAD ancestry and Git-capturable worktree for graceful restore or the selected fork. It does not preserve unrelated branch tips, stash/reflogs, ignored caches, provider files or active Git operation metadata. Provider-session durability is separate (§8.5). Ungraceful loss and deadline teardown with a failed cut lose work since the last complete receipt; the loss is explicit.

### 5.5 Restore on attach

Warm and cold restore use the same authoritative recipe; a warm root is a cache, never evidence of equality.

1. Resolve the complete mapping and current authorization; materialize the verified scoped artifact and fetch only its allowed existing mapped branch. The server-issued `VmSpec.repos.branch_oid` pins each existing mapped ref for that attach and participates in its source digest; `restore` overrides checkout content when a receipt exists. With no receipt, use that pinned OID rather than re-resolving a newer branch during boot. Missing mapping/ref fails attach; restore never creates an authoritative internal ref. **Post-MVP (P8.12: the verified scoped artifact and the source digest).** In the MVP the host materializes the checkout from today's URL-keyed bare cache and fetches the existing mapped branch with the incarnation token.
2. Remove/abort stale rebase, merge, cherry-pick, revert and sequencer state from the previous incarnation. With no receipt, force checkout the mapped branch at the spec’s pinned internal `branch_oid` and remove nonignored paths absent from that tree. This applies equally to a dirty warm root.
3. Otherwise fetch both receipt leaves, verify the pinned manifest and set local `refs/heads/<mapped>` to `local_branch_oid`, preserving upstream `origin/<mapped>`. Reproduce the recorded foreign branch or detached HEAD at `local_head_oid` without resetting the mapped branch to that OID. A receipt with interrupted sequencer restores detached, clears operation metadata and reports its interruption; it does not resume an incomplete rebase automatically.
4. Force materialize the snapshot tree as unstaged work relative to restored HEAD, removing tracked/nonignored paths absent from it while retaining safe ignored caches. Local post-receipt commits, stashes, reflog and dirty warm content are discarded. A second restore produces exactly the same bytes/modes/symlinks as a cold restore regardless of prior HEAD or operation metadata.
5. The internal branch may have advanced independently. Do not auto-merge or widen implicit force-with-lease expectations. Changes reports association, ahead/behind and interrupted-sequencer state; the owner/agent repairs it explicitly.

A fork copies both retained refs into a fresh child `flush_id` with `origin=fork_copy`, null VM/epoch, source receipt ID and copied source reason. The child branch starts at the source `local_branch_oid`; its receipt changes `branch_oid` to that value and deliberately normalizes `head_ref` to the child’s own branch and `local_head_oid` to `local_branch_oid`. Rebuild a child snapshot commit with the selected source snapshot tree and the child branch as parent when those trees differ (otherwise clean snapshot equals child HEAD), and retain the source vector in fork provenance. This avoids a dirty=false lie or a child pointing at the source’s foreign branch. The source foreign HEAD remains retained by the pinned source proof until copy verification; the child promises the selected tree and mapped-branch ancestry, not unrelated local history. Verify both child refs and the complete manifest before atomically publishing the child receipt and stopped workspace.

### 5.6 Provider integration (GitHub / GitLab)

**Inbound is an MVP requirement.** A protected-ref mirror loop polls every five minutes using the repository’s recorded provider connection (`ScmTokenManager`); an absent/expired connection fails closed and surfaces reconnect. It fetches only explicitly configured protected refs into a private temporary ref through a dedicated `GitRepo::fetch_protected_ref`, then updates the protected mirror under the shared per-repo lock. The legacy forced wildcard `GitRepo::fetch` and `g5_workspace_ops::fetch` are not this path and must not import workspace branches.

The provider is authoritative for its protected ref. Fast-forward and force-rewrite both update it by expected-OID CAS; rewrite records old/new OIDs in `repo_mirror_refs`, emits `branch.updated` and shows a rewrite notice. Existing pinned fork refs remain immutable. Provider deletion never silently deletes the internal protected ref: retain it with `state=provider_missing`. Fetch failure keeps the last good OID and records `fetch_failed`. Every attempt updates observation/error fields; reads, forks and Update include the observation time/state. Stale means no successful observation within three poll intervals or missing/failed state; the latest rewrite remains visible until a later successful ordinary observation. Adding a protected name that overlaps a workspace mapping or pending fork claim is refused. Post-merge import uses this same policy. Local-only repos have no provider freshness marker.

The poll is the MVP trigger. Webhooks are explicitly post-MVP in P1.5: the future provider-specific route requires a configured secret and verified raw-body signature, fails closed if missing, coalesces deliveries and only schedules authenticated fetch. Payload OIDs never directly update refs. Repo connect/Make Remote must register or explicitly report no webhook; a nullable secret column does not prove an existing route. There is no newly unauthenticated MVP webhook surface.

**Outbound** remains explicit PR/branch publication and merge republish under the acting user’s stored token. First publication is create-if-absent; an independently created provider branch is a collision even at the same OID. Later pushes use an explicit recorded lease for that workspace publication. VM-held credentials cannot publish to a provider. Private provider dependencies need an explicit read-only proxy grant or are unsupported.

**Update** runs native Git against the internal mirror’s protected base branch in the selected checkout. It returns mirror freshness/rewrite state before rebasing; it does not silently adopt a different source. Connecting a local repo records provider connection identity and enables the protected mirror. P1.5 later removes tracking_mode/push_mode/sync runs/pair leases/branch-integration machinery; until then those legacy paths cannot write protected refs or workspace heads behind this authority.

### 5.7 The workspace↔branch association check

`workspace.changes get` reports, per member repo, the symbolic `HEAD`, any interrupted sequencer marker, whether it equals `workspaces.branch_name`, the dirty set, and ahead/behind against `origin/<branch>`. After current-owner authorization, the API requires an already-running, admission-open incarnation and calls it before every UI-triggered mutation of that workspace (Save/upload/delete/rename, Push, Update, preview start, PR create). It never attaches from this check; an explicit Start/Resume action must finish first. A mismatch returns:

```
409 WORKSPACE_BRANCH_MISMATCH
{ repo: "backend", expected: "fix-login", actual: "main", detached: false }
```

The UI shows the mismatch in the status strip with one action, "Switch back" for the owner (`workspace.changes switch_back`: `git switch <branch>` if clean, otherwise stash or commit first). Nothing prevents an agent or a terminal user from running `git checkout`; the profile text tells agents to stay on the branch and the check catches drift at the next UI operation. Several chats share the same member-repository checkouts and reconcile their edits with native Git. A local branch change cannot create another managed branch through receive-pack, and association checks still require the workspace’s shared branch name in every member repo.

### 5.8 Workspace actions, teardown reasons and the stop sequence

Create is checked fork, the only new internal workspace-branch creator. Stop/resume/restart/delete require the current owner; transfer also permits an org admin. There is no archive, manual Commit or Flush now action. [Workspace VM API §5](workspace-vm-api-v9.md#5-workspace-flush) owns the shared receipt and lifecycle field contract.

| Action | Contract |
|---|---|
| Fork | Authorize source read and eligible destination owner, check the exact name in every member, pin the durable source, publish only the whole stopped child. Reader fork makes zero source VM calls. Owner live fork may request a fresh `reason=fork` cut. |
| Stop | Run `stop_reason=user`; preserve branch, receipt and durable history; new compute needs explicit owner Resume. |
| Resume | Persist the current owner’s start intent, queue/attach, restore and consume it only on `runtime.ready`. |
| Restart | Persist owner consent for one successor generation, stop with `restart`, then attach with the selected image after release. |
| Transfer | Block new mutations, stop/flush, confirm exit/release and retained-root purge, then atomically commit owner/audit/notifications. No hot handover. |
| Delete | Stop (or explicit force with recorded loss), tombstone the workspace, remove unpinned refs and operational history under retention, preserve usage/operation audit and reconcile durable host purge. It disappears from listings. |

**Checked fork: reserve in the operation.** Resolve `(org_id, requested_by, idempotency_key)` and compare the original request digest before re-resolving source members or OIDs. A changed request returns `IDEMPOTENCY_KEY_REUSED`. An authorized completed/aborted replay returns its recorded outcome without recreating a claim or requiring historical repository rows still to exist. An unfinished replay uses the operation's stored frozen member IDs/name, takes their canonical repository locks, then rereads its status/digest and current action authorization; it resumes only that proven operation, never treats its own claim as a competing fork. If the first lookup finds no row, the unique-key insert/retry path handles a concurrently admitted duplicate without creating a second operation.

For a new operation, validate actor/source access, exact Git-valid proposed name and complete same-org member set, then open a short `READ COMMITTED` transaction. Lock all existing member `repos` rows in canonical repository-ID order. After every lock has been acquired, require that the locked rows equal the full frozen distinct member set, still belong to the org and remain eligible under the repository-deletion barrier; a member deleted while acquisition waited makes admission fail before insert or side effects. Recheck the idempotency key, then issue a separate fresh query over all same-org `workspace_forks` in `pending` or `aborting`, excluding only the proven same operation on resume. A conflict requires an overlapping repository ID and an equal name or slash-boundary ancestor/descendant name (`feature` conflicts with `feature/x`, but not `feature-x`). Compare literal names/prefixes, not unescaped SQL `LIKE` patterns. Reject the entire operation on any conflict; never reserve a partial member set, suffix a name or adopt an existing branch.

If no conflict exists, atomically insert the `pending` fork with destination/source IDs, exact name, fixed member IDs, requested source selector and request digest, then commit. This row is the durable claim before any slow provider verification, live-source flush or Git creation. `(org_id, requested_by, idempotency_key)` still identifies retries: a matching request resumes its existing operation; changed input returns `IDEMPOTENCY_KEY_REUSED`. The digest binds original requested inputs, not freshly resolved OIDs. A completed/aborted idempotent replay reports that recorded outcome rather than inserting a new claim. A concurrent duplicate insert follows the unique-key outcome/retry and then rechecks authorization; it never creates another operation.

The lock-and-query ordering is required, including on a single API replica: concurrent requests can otherwise both observe no conflicting row. Locking only existing fork rows does not protect an empty result. Combining lock acquisition and conflict checking in one statement or reading from an earlier repeatable-read snapshot is not this protocol; the conflict query must see any claimant that committed while lock acquisition waited. Claim lookup is a server-owned tenant query over every unfinished operation for the locked repositories, including private source/target workspaces. It must not inherit caller-visible workspace filtering. A refusal may identify the caller's conflicting repository/name, but cannot reveal an inaccessible workspace, owner, fork manifest or history.

**Check and create.** Release admission transaction locks before provider I/O or a live-source flush. Check internal and connected-provider namespaces, including prefix conflicts, before creating any destination ref. Provider verification uses the repo's recorded connection; unavailability is not evidence of an absent name. Failure either stays retryable with the claim retained, or enters verified abort; it never silently frees the name. Resolve and pin the actual source OID vector once. Source receipt selection takes its prune pin under the established repository/flush lock order. Recheck source access before publication. A provider check observes its namespace at a point in time; neither a fork-row claim nor the former reservation table can lock out independent external provider writers.

Every local ref create, retry and cleanup uses the same canonical repository locking and existing Git writer barrier, rereads the fork's current status/claim keys after acquiring those locks and acts only for that operation. Lock ordering for fork-row updates follows the repository locks; no worker may keep an earlier status observation as permission for a later write. Recheck actual internal refs under this boundary. Create each destination branch and `refs/g5/forks/<fork_id>` proof at the pinned mapped-branch OID in one per-repo create-if-absent transaction. Existing refs without this operation's proof conflict even at the same OID. A durable claim records exclusion and intent; it does not prove a Git transaction committed. Keep the atomic proof and expected-OID recovery rather than replacing them with status inference. Copy/materialize a child receipt using §5.5; never fabricate a source VM identity or carry a foreign HEAD as the child branch.

**Settle or recover.** Enforce the state transitions under the repository locks: `pending → completed` publishes; `pending → aborting` retains the full claim and switches to cleanup-only; `aborting → aborted` requires verified cleanup and fenced/quiescent writers. Only `pending` can admit new source capture or destination ref creation. Terminal states never reopen. A finalizer that loses the CAS to abort cannot publish, even if it previously verified all refs. After every member/proof verifies, acquire all member locks in the same order, verify no mutation is still ambiguous, and atomically publish workspace/mappings/receipt plus `status=completed`; this status transition ends the temporary claim. Finish chat carry idempotently. The child is stopped without a start intent; only explicit owner Start/Resume admits compute. Recovery resumes the fixed manifest or enters `aborting` and deletes only operation-proven refs with expected-OID checks. Advanced/preexisting branches are never rolled back. Hold claims throughout partial failure, provider uncertainty and cleanup. Transition to `aborted` only after all cleanup proves safe and prior ref writers are quiescent/fenced under the same writer barrier. A delayed creation worker then observes terminal/aborting status and cannot recreate a removed ref. Unknown writer completion keeps the operation unfinished; timeout is not proof of cleanup.

After five failed cleanup retries, keep `aborting` with `error.recovery_required`, pause automatic retries and expose admin `POST /orgs/:org/fork-operations/:id/reconcile`; this route cannot force a terminal state or delete the record to free a name. Unfinished records/proof refs survive retention. Proof refs remain through settlement and seven days after completion. Repository deletion and every other platform path capable of introducing a conflicting ref, including protected-ref bootstrap/import, acquire the same repository locks and check these unfinished manifests before acting. They cannot bypass the claim because there is no separate reservation foreign key. A workspace member change still requires a new checked fork; it cannot mutate an active claim or mint a missing branch.

**Explicit start and queue.** Only owner resume/restart routes or already-authorized rollout write the typed `workspace_vms.start_intent`; generic dispatch, readers, Save, queued/held tasks and history reads never do. `POST /workspaces/:id/resume` accepts an idempotency key and optional typed compound launch, creates its queued task/input and intent atomically, and returns intent/task identity. Terminal launch is a client follow-up after readiness. A pending intent is valid only for the current owner, generation and unexpired deadline (default 15 minutes). `no_capacity` persists `queued_for_capacity`; within each org order by creation time, expose rank/cancel/expiry, and reconcile every two seconds or on host-ready/free-slot events. Quota counts starting/running/stopping. Definitive boot failures consume a bounded three-attempt budget; ambiguous delivery reconciles the same incarnation. `runtime.ready` consumes once and admits the queued launch only if still authorized. Cancellation withdraws only its own demand.

Admission of a stop intent advances `lifecycle_generation`, cancels older start consent and records that new value as `stop_generation`. An explicitly authorized restart/rollout atomically mints its one successor intent for that same newly advanced generation. Release does not advance the generation again. A later superseding Stop, transfer, deletion, loss or safe explicit supersession advances generation again and cancels older consent; delayed work must still match the current operation, incarnation and generation. After release, absence of a valid successor intent means the UI offers Resume and placement remains forbidden; no `owner_resume_required` column exists. Drain/rollout never infer consent from queued work.

**Admission order.** Authorize actor and read scope first; then base restriction; pending transfer/stopping returns `WORKSPACE_STOPPING`; absent/starting/failed/unhealthy incarnation returns `WORKSPACE_NOT_RUNNING`; then valid incarnation admission, association/precondition, and dispatcher admission. Running/healthy means current incarnation, open admission and a passing private health report no older than 30 seconds (10-second sampling default). A workspace mutation lease spans authorization through completion, including laptop receive-pack. Transfer/stop closes this lease, waits for admitted mutations, and fences both Agents reservation and dispatcher mutation/module admission before flush/owner CAS. Status and other durable control-plane actions are separate from guest admission.

| Stop reason | Decider | Failure policy |
|---|---|---|
| `user` | owner Stop/Delete | Abort while VM is known running; reopen admission and show error. |
| `restart` | owner Restart | Same as user; failed stop never attaches the successor. |
| `transfer` | owner or org admin | Abort with old owner unchanged; no forced-loss completion. |
| `idle` | lifecycle idle reconciler | Abort on failure; transient errors retry after cooldown, deterministic size/proof errors block until an explicit repaired lifecycle action (§5.4). Org default is 30 minutes with ordinary workspace override. |
| `drain` | authorized operator/rotation orchestrator | At stop deadline release only with recorded loss. |
| `rollout` | authorized rollout orchestrator | Same deadline policy. |
| `credential` | API lifecycle reconciler observing host credential expiry | Nudge/quiesce before the host safety deadline, then recorded-loss policy. |
| `capacity` | explicit authorized operator action, never eviction by a queued user | Same deadline policy. |

Idle activity is running bounded work, open owner terminal, admitted owner file RPC, valid live native response wait, or authorized owner preview HTTP request/WebSocket open. Preview keepalives/output, service existence, durable reads and open browser tabs do not count. Preview activity writes debounce at most ten seconds.

**Nudge then stop.** A deadline stop first persists `pending_stop_reason`, `pending_stop_deadline_at`, `nudged_at` and operation ID while still running with admission open. The default nudge is 30 minutes, bounded by credential/operational deadlines. The same transaction creates one current-owner notification (`workspace.teardown_pending`) and a system timeline notice with queued notice-delivery metadata in `chat_messages.artifacts` for every session with nonterminal agent work (not an ordinary session input). Readers/non-owning admins get no lifecycle notification fanout; they may see a durable banner. No new task or provider frame is created. Next ordinary input includes queued notices as a platform preamble under `input.accepted.system_notice_ids`; remaining notices are withdrawn at release/cancel. A restart reads persisted deadlines and cannot duplicate notices. At the pending deadline set `stopping`, copy the reason, and set `stop_deadline_at` for flush/harvest (default ten minutes, never beyond host safety deadline). Owner Stop/transfer supersedes the nudge. MVP includes an operator capacity-stop service/route and credential-expiry reconciliation; P8.7 later calls the same tested primitive for fleet drain/rollout.

**One ordinary stop intent.** `workspace_vms.stop_operation_id`, `stop_reason`, `stop_generation`, `stop_retry_at`, the row’s current `vm_id`/`epoch`, lifecycle `status` and `last_error` own stop progress. Every asynchronous step carries `(stop_operation_id, vm_id, epoch, stop_generation)` and compare-and-swaps those preconditions before acting. Neither a new stop nor a new attach silently overwrites an unresolved operation. Successful release commits Agent/host stop evidence and clears pending stop fields atomically. A known-running non-deadline failure aborts the operation and reopens ordinary admission, recording any deterministic flush block (§5.4); a host stop that may have been sent remains unresolved until exit/release is known. Retries reconcile that same operation, never create replacement stop demand from a completed task. Later explicit Resume/Restart cannot be stopped by a stale operation or generation.

**Stop sequence.** Keep the incarnation current and renew its lease while stopping. (1) Persist stop identity/reason/deadline and close human admission. (2) Agents prepare closes reservations; dispatcher drains admitted file writes. (3) Interrupt bounded modules, invalidate ended process-bound native requests, preserve confirmed deferred questions (§8.4), hold unfinished logical tasks without releasing dependencies, close terminals and cancel preview. (4) Complete Git flush. (5) Harvest the frozen session bundles and required event/task journal; retry transient failure up to 120 seconds within the operational deadline. Only an over-cap/invalid provider bundle may be durably marked unrestorable with notice and history fallback; never discard task events under that exception or accept stale-incarnation harvest. Non-deadline failures abort while the VM is known running (Agents abort reopens reservations), with the flush block/error visible when applicable. Deadline failure records exactly what was not durable. (6) Send idempotent host stop and wait for confirmed exit. (7) Atomically commit Agents stop receipt and workspace release; database failure leaves `stopping` for reconciliation. After release the old incarnation is fenced. `workspace.flush_aborted`, `workspace.unflushed_loss` and session-loss notices target only the current owner, deduplicated by workspace/category/stop operation.

**Transfer.** The durable operation binds expected old/new owners and request digest, serializes with lifecycle/dispatch/mutations, and validates target eligibility again at commit. After release and retained-root purge, atomically set new owner, cancel previous-owner start intents, completed audit and notifications to old/new owners. A target that became ineligible aborts with old ownership unchanged; an already-stopped workspace needs no boot/flush but still purges retained roots. Repeated requests return the same result. Chats/tasks/history stay; new owner explicitly Resume/Continue using their account. Creator/old-owner privilege disappears except independent visibility/invites/admin read access. Stream delivery and outstanding responses are fenced by ACL generation, not only eventual connection close.

Until legacy dispatch disappears, transfer refuses any nonterminal legacy task/job/chat, pending/unacknowledged claim or sticky runtime (`WORKSPACE_LEGACY_WORK_PENDING`), under the same admission lock. The retained claim UPDATE and frozen account resolver must check current owner/hold/transfer state in P4.5, before transfer is enabled. This temporary guard is removed only when the legacy consumer is deleted, not merely when a new route exists.

Removing or demoting an owner returns `OWNER_OF_WORKSPACES`; explicitly transfer/delete first. Org deletion is a durable offboarding flow that drains/purges compute, roots, repositories and credentials before deleting tenant rows, never a direct cascade. This includes completing formal-review cleanup, removing review-linked approval statuses and clearing the disposed temporary workspaces’ review links, then deleting formal review rows (retries before their originals), retained artifacts, tasks and approval requests before the remaining tenant rows and organization. Delete the private `refs/g5/approval-evidence/<resolutionId>/<repoId>/source|base` refs together with their retained evidence during this offboarding flow, before repository storage is purged. Ordinary temporary-workspace cleanup never removes these refs. Retention during ordinary workspace cleanup does not exempt evidence from tenant offboarding. User erasure requires a separate policy for org-owned content and audit retention; this redesign does not promise impossible Git-history erasure by changing author IDs.

**Admission rate bounds.** In the MVP the existing API rate limiter applies and no per-operation admission bound is added. Cached provider existence can reject a known collision, but a cached “free” result cannot replace the current reservation/preflight proof. **Post-MVP (P8.14).** Initial configurable defaults: 60 fork requests per org/hour, four pending forks per requester, six Start/Resume/Restart requests per workspace/minute, and 100 queued ordinary inputs per session. Enforce at the API before provider preflight or allocation; return 429 with Retry-After and make idempotent retries return their existing operation without consuming another creation slot. These are v9 draft defaults, not meeting SLAs.

### 5.9 Deferred returned-results workflow

The durable, source-versioned review/explainer returned-results workflow is outside the MVP. It introduces no request/result/reply tables, producer-task designation, attempt result candidate, publication-dependent task completion, review-specific child UI/CLI, idle override or completion-triggered stop. Its schema, protocol and delivery plan require a separate post-MVP design decision.

MVP retains ordinary checked fork with parent/source linkage in `workspace_forks`, exact common member branch names, explicit owner Start/Resume, normal agent conversations and retained chat/task history. An owner may ask an ordinary agent to review or explain its workspace; that output remains ordinary conversation/task history and does not become a source-versioned parent result, formal approval or parent write permission. Normal stop/idle/transfer rules apply to every workspace.

## 6. Workspace VM, host and dispatcher

### 6.1 VM lifecycle and host states

```
stopped ──resume/restart──► starting ──runtime.ready──► running ──stop sequence──► stopping ──release──► stopped
                             │                            │                           │
                             └──boot failure──────────────┴──lease lost / VM exited───┴──► failed ──next resume──► starting
```

| Transition | Actor | Details |
|---|---|---|
| resume | the Workspace lifecycle service, on recorded current-owner Start/Resume intent or an authorized rollout continuation (§7.3) | one compare-and-swap update on `workspace_vms` sets `status=starting`, a new `vm_id`, `epoch + 1`, the chosen `host_id`, the image and start-acquisition deadline; no guest authority exists until `lease.acquire` (post-MVP, P8.14; in the MVP the API grants the lease and mints the token at placement); the service sends `vm.start(spec)` on the host's `ctl` stream |
| runtime.ready | the dispatcher, forwarded by the host as `vm.event ready` | restore done; runtime API listening; `module_catalog_version` recorded; the row becomes `running` |
| stop | the stop sequence (§5.8) | the incarnation stays current until release |
| lease lost | the reconciler: the lease was not renewed, or the host reported `exited`, `oom`, `lease_expired_killed` (post-MVP, P8.14) or `stale_killed` | VM `failed`, `vm_id` and `host_id` cleared; confirmed and unconfirmed active executions settle as `vm_lost` (§7.5); the next resume restores from the last receipt on any host |

Hosts have their own states: `provisioning → ready → draining → terminated`, with `unreachable` for a host whose tunnel is lost while it may still run VMs (three missed heartbeats). During `unreachable` the control plane places nothing on the host, keeps every incarnation current until its lease expires, and expects a reconnect with an inventory. Slot occupancy is not stored on the host row; it is derived from `workspace_vms`, so a crashed start cannot leak a slot.

### 6.2 Host daemon and protocol (`g5d host`)

The host is a single-org slot provider. Reuse libkrun `vm-exec`, OCI rootfs/cache materialization, passt and the outbound credit-flow tunnel; remove per-task poll/claim/materializer and golden/parked runtimes. The retained provider injection code is reuse evidence, not proof of v9 security. `WorkerHostService::place` owns placement and quota; `WorkspaceVmService` calls it. **Post-MVP (P8.10, P8.14).** Remove fixed host JWT assumptions (P8.10). Runtime identity is self-reported inventory; there is no retained remote host-attestation guarantee (P8.14).

[Worker Host API v9](worker-host-api-v9.md) §§2–5 is the normative full wire/schema contract. One authenticated host WebSocket carries `ctl` JSON-RPC, dispatcher `rpc`, terminal `pty`, and one `http` stream per preview TCP connection. User live streams require current owner, healthy attachment and admission; reader browse never opens them. In the MVP model, Git and API traffic leaves the guest over its own network, not this tunnel (§6.5). **Post-MVP (P4.12).** Model/Git traffic exits through host proxies, not this tunnel.

**Host identity in the MVP.** The MVP keeps today's host identity: `POST /orgs/:org/worker-hosts` mints a 24 h host JWT at provisioning (`mint_host_jwt`), delivered by the startup script on GCE and by `scripts/seed-ci-org.sh` in CI. External hosts receive a fresh token on the heartbeat response (`HeartbeatResponse.host_token`), and cloud hosts are rotated before expiry (`cloud/rotation.rs`, §6.10). The `ctl` tunnel authenticates with that JWT, as today's tunnel does. The MVP also keeps `runtime-labels/refresh` and registry-authoritative runtime labels; retiring that route is post-MVP (P8.14). The `ctl` stream, hello with accept or reject, the heartbeat, journaled `vm.event`, idempotent commands, drain and the operator API are MVP.

All VM commands bind workspace/VM, idempotency key and payload hash, with a host-monotonic `budget_ms` processing limit. Timeout is ambiguous and reuses the same key; completed results remain for 600 seconds. Processing budgets are not lease safety. In the MVP the API grants the lease at placement (§6.4). **Post-MVP (P8.14).** Before initial boot a host-originated `lease.acquire` must still succeed (§6.4); a late cancelled start cannot acquire.

Host messages in the MVP are `host.hello`, `host.heartbeat`, `vm.event`, `lease.renew` and `host.drained`. Hello/current-incarnation sets carry a monotonic generation so stale heartbeat acks cannot revoke a newly accepted start. Journal events and sequence state survive host restart; API inserts `worker_vm_events` and applies a current-incarnation transition atomically, then acknowledges a durable contiguous prefix. Old-incarnation events remain history only. Ready includes VM/epoch/catalog/dispatcher versions; mismatch never becomes running. **Post-MVP (P4.12, P8.10, P8.14).** Host messages also include `lease.acquire` (P8.14), `grants.resolve` (P4.12) and `host.credential.renew` (P8.10). `grants.resolve` is the only secret-fetch transport: current placement on this tunnel host, refs in the persisted spec/current grant generation, current-owner revalidation, audit refs but never values.

**Post-MVP (P8.10).** The rest of this subsection up to "Version negotiation supports" specifies the one-use registration exchange, the renewable host credential, credential generations and the runtime identity hash, and is not part of the MVP.

**Host enrollment and identity.** Org operators create one provisioning host row and a random 256-bit single-use `g5w_*` token with one-hour expiry; the row stores only its hash/expiry/redeemed/revoked times. GCE delivers that same bootstrap token through its existing secret channel. `POST /api/internal/hosts/:host_id/register` atomically consumes it and issues the first renewable credential, binding path/host/org to the stored row. Replay/expired/revoked/wrong-host tokens fail; a lost response requires operator reissue on the same row and credential-generation revocation. This replaces, and does not depend on, legacy reusable per-task `worker_tokens`. P4.1 creates the required host columns; P4.4a implements this same exchange and credential validator for GCE, self-hosted and macOS enrollment before the v9 ctl path is enabled. GCE changes only token delivery through its retained bootstrap secret channel, never skips redemption or receives a pre-issued long-lived credential. P4.13 adds operator provisioning/issue/reissue/revoke surfaces, not another exchange or schema owner. Retained per-task host-up bootstrap remains explicitly legacy during producer migration; fixtures distinguish it from v9 enrollment and remove it with P4.9a/b after its last consumer. P9.1 updates installer protocol, not merely the old token's label.

Host credentials carry `aud=g5-host`, `token_use=worker_host`, host/org/runtime-identity hash/credential generation/iat/exp, TTL 24 hours, renewed from two hours before expiry. The API computes a canonical JSON SHA-256 identity from required host/runtime hashes and versions (worker-host §3.1). Path, claims and hello identity must match before any inventory or secret. One active authenticated connection per host; replacement makes older messages inert. Termination/revocation closes it and rejects unexpired old credentials. Changed runtime identity permits only restricted reconciliation/drain, with no new placement/grant expansion. WorkerHostService triggers credential drain on refused renewal or 30 minutes remaining without renewal, targeting completion five minutes before expiry; the host never independently decides workspace stops.

Version negotiation supports current and previous host protocol; specs have a separate version. Unsupported versions refuse without interpreting commands, while existing VMs retain only their bounded leases. Host limits are in worker-host §7.1, including pull timeout 300 seconds, unpacked image cap 20 GiB, slot/boot locks and named refusal behavior. Operator registration, drain/delete and revocation are MVP P4.13, on the existing provisioning route and token service; the one-use exchange is post-MVP (P8.10). **Post-MVP (P8.14).** Allowed-image administration joins that operator surface.

### 6.3 VM start spec, images and retained roots

In the MVP the control plane supplies authorized inputs; the host supplies the pinned runtime bundle and image/cache paths and builds the boot environment as today (no `secrets_env` and no grants: secrets ride the dispatch, §6.5). The host validates known spec/org/paths, reserves size/slot/boot capacity under one lock, validates the environment, then pulls/verifies the image and boots. The API has granted the lease at placement (§6.4). Every failure frees reservations.

**Post-MVP (P4.12, P8.11, P8.14).** The control plane supplies authorized inputs; the host supplies the pinned runtime bundle, image/cache paths, resolved secret values and host-allocated proxy keys. Validate known spec/org/paths, reserve size/slot/boot capacity under one lock, validate environment and exact approved image reference, then acquire a typed lease before potentially long image/secret setup. Resolve grants, install host/process isolation and pull/verify the image while renewing the starting incarnation; boot only while the lease is valid. Every failure frees reservations. Full order and named refusals are worker-host §4.

**Image selection and runtime provenance.**

The guest image is userland only. The MVP resolves the base image as today: from `.g5/workspace.yaml`, with today's fail-closed resolution and the org track/pin policy. The control plane reads `.g5/workspace.yaml` from the committed restored HEAD (`local_head_oid`, or initial selected branch head) in every `role=code` member; dirty snapshot overlays and docs-role repos cannot choose the image. Never resolve mutable tags or silently fall back. Resolve before `starting` and before any pull; persist `{image_ref, image_digest, image_source, image_resolved_from: [{repo_id, oid}]}`. **Post-MVP (P8.14).** The canonical registry/repository/digest reference must appear in the org-admin-managed `allowed_images`; otherwise `IMAGE_NOT_ALLOWED`. Persist with the resolution a durable audit event naming the actor and consent.

**Post-MVP (P8.14).** An owner authorizes an allowed image when explicitly starting/restarting; the client shows the resolved pending image beside the running image before that action. A commit alone never restarts compute. Automatic rollout continuation cannot silently change a repo-selected digest: changed pins require owner Start/Resume. Org-default rollouts may update the default with a recorded operator action, but never override a repo pin; removing a pin from the allowlist holds its restart with `IMAGE_NOT_ALLOWED` until repaired.

The host runtime bundle contains `bin/g5d`, pinned provider CLIs, and `modules/catalog.json`; Worker & Host owns its build/staging. It is mounted read-only at `/opt/g5`, independently of the guest image. `runtime_identity.runtime_dir_hash` covers its manifest and `module_catalog_hash` covers the catalog bytes. P4.2b exports the catalog; P4.4b extends `scripts/stage-local-worker-runtime.sh`/CI images to stage it with `g5d dispatch` and fake provider CLIs. `runtime.ready` carries `vm_id`, `epoch`, `module_catalog_version`, `dispatcher_contract_version`; the host/control plane compare those with the selected bundle before accepting ready. Missing/mismatched runtime files fail boot, never silently use guest-image copies.



**Mounts and retention.** `/work` is the workspace root; `/opt/g5` is the complete read-only host runtime mount shadowing guest image content; provider assets are read-only and scratch serves Docker/build caches (the rootless-Docker requirement is post-MVP, P8.11). Provider/dispatcher homes stay outside working trees. Platform excludes keep runtime artifacts out of flush and agent native Git even without repository ignore files. In the MVP the host keeps its URL-keyed bare cache and materializer, as in the original (`backend/g5d-foundation/src/workspace/repo_cache.rs`). **Post-MVP (P8.12).** Host Git caches consume only the Git service's immutable, self-contained authorized-closure artifact, whose manifest binds org/repository, principal scope, access generations, exact authorized root vector and content digest (§5.3). Before each restore/fork materialization the service revalidates current authorization/incarnation and the host verifies the exact manifest and pack hashes. The canonical `GitObjectViewManifestV1` in §5.3 binds `{version,org_id,repo_id,object_format,principal_scope,access_generations,roots,pack_sha256,object_set_sha256,scope_digest}`. Cache by `scope_digest` plus verified pack/object-set digests, never repository URL alone. A workspace principal names its stable workspace/current owner; VM/epoch/lease are revalidated separately on each use so safe same-owner warm reuse does not require reusing stale authority. No global bare-repository reflink, object alternates or cross-scope object reuse is allowed. Reuse within the same authorized artifact is permitted; stale generations/roots require a new artifact. Guests never mount this cache or another workspace root. Host fetch uses the host-authenticated exact artifact route and bounded manifest/pack stream in §5.3; MVP access generation is `orgs.access_generation`, revalidated on every use. P4.4b's cold/warm/new-fork tests include a guessed inaccessible sibling OID and an ACL-generation change; performance caching must not widen object visibility.

Ordinary stop retains root/scratch for org-configured 24-hour default. Warm restore reconciles tracked content against the durable receipt; retained ignored/cache files are never durable truth. Delete persists purge intents for every recorded host/cache generation and reports pending until acknowledgements. Transfer purges the old root/scratch before owner commit, so the next owner restores cold rather than inheriting ignored secret files. Purge does not delete stop receipts/event journals. Unreachable hosts process pending purge before new admission. Caches are excluded from backup; logical deletion is not physical media-erasure certification.

P4.4b measures three runs each of cold/no-root, same-host warm, and new-child/cached-object startup using one committed multi-repo fixture, pinned runtime/guest/host versions and slot size in the mandatory KVM lane. Record start-send to validated-ready wall time, Git restore bytes, raw values/medians and lane artifact/fixture IDs. P4.9a repeats the same recipe and explains regressions before deleting cache code. There is no meeting-mandated latency SLA or same-host child packing requirement.

### 6.4 Incarnation, lease and fence

**Lease in the MVP.** The MVP keeps the incarnation fence at every boundary and the server-side lease. The API grants the lease at placement, the dispatcher renews it through `lease.renew` relayed by the host, expiry marks the row failed and the fence rejects the old token. A VM that is no longer current is stopped by the reconnect inventory rule or by `vm.stop`, never by a host timer. The MVP has no host-side lease kill timer and no deploy guard. Because processes in the VM hold the token in their environment for their whole life, its expiry is not the lease TTL in the MVP: the API mints it at placement with a platform default of 24 h, the dispatcher still installs the renewed token that `lease.renew` returns, and currency is enforced by the fence, not by expiry.

**Post-MVP (P8.14).** The rest of this subsection up to "The token has" specifies the host-originated `lease.acquire` and the host-monotonic kill timer, and is not part of the MVP.

A placement CAS records a new VM/epoch and a `start_by` control-plane deadline, but grants no guest authority. On receipt of `vm.start` the host reserves capacity and sends `lease.acquire` with a monotonic per-incarnation sequence. The API grants only the current `starting` incarnation assigned to that host with a still-valid start intent/deadline; a late command for a cancelled, superseded or expired start gets `stale` and cannot boot. Acquiring again for the same live incarnation is idempotent in identity and only advances the lease for a newer sequence. The row stores the latest granted sequence; duplicate requests return the same grant and never extend it. Retries of the same sequence retain its original first-departure timestamp; a duplicate reply cannot start a fresh timer. Persist the sequence/deadline with the host OS boot identity; if process restart cannot recover it, fail closed and stop instead of reconstructing a longer lease.

For acquisition and renewal the API records its handling time plus `lease_ttl_secs`; the host timer is request departure plus the returned duration. An obsolete sequence or reply whose host timer has already elapsed cannot install a token or reopen a proxy. API/token expiry and host timer can therefore be evaluated without synchronized clocks, and the host deadline never outlives the corresponding server grant. During long image setup the host renews for the same current `starting` incarnation. At half TTL the live dispatcher requests renewal through the private `rpc` path. Heartbeats, reconnects and API restart never extend or revive expired leases.

The token has `aud=g5-workspace-incarnation`, `token_use=workspace_incarnation`, `org_id`, `workspace_id`, `owner_user_id`, `vm_id`, `epoch`, `iat`, and `exp` equal to the server lease grant. User, host and incarnation validators reject the other token types. Every request also checks current VM/epoch, placement/owner and route scope; validity of a JWT alone is insufficient. In-flight requests may finish with the old token; every new request uses the latest token. In the MVP a renewed token is delivered to the dispatcher (§6.5). **Post-MVP (P4.12).** On accepted renewal the host atomically replaces all `source: workspace_token` values before delivering the token to the dispatcher. Token values never enter repository/provider launch environments.

A current incarnation can be `starting`, `running` or `stopping`; only admission-open running state authorizes user activity. Internal stop/flush/harvest may finish on a stopping incarnation. A replacement is admitted only after confirmed exit, or expiration of the last issued grant. Inventory reconciliation never revives an expired lease, even immediately after an API deploy. `vm.stop` accepts any exact VM the host owns regardless of currency. After retained stop results expire, `not_found` plus absence from the current authenticated inventory proves release; timeout alone never does. **Post-MVP (P8.14).** Expiry closes proxies before killing the VMM and reports `lease_expired_killed`. A never-acquired cancelled start cannot subsequently acquire.

Platform defaults are lease TTL 300 seconds, renewal at half TTL, heartbeat 10 seconds, start-acquisition deadline 60 seconds, image pull timeout 300 seconds, full ready deadline 420 seconds and VMM termination grace 30 seconds; these are draft bounds to verify. No reconnect grace extends or revives an expired grant. **Post-MVP (P8.14).** The deploy budgets are separately configured: preflight-to-shutdown delay 15 seconds, control-plane unavailability 120 seconds, and tunnel/inventory/first-renewal recovery 60 seconds. These are draft bounds to verify, not measured availability claims. TTL must exceed their sum and be at least six heartbeats.

**Post-MVP (P8.14).** The rest of this subsection specifies the ops lease-observe route, the deploy lease guard and its advisory lock, and is not part of the MVP.

**Deployment lease observations.** `POST /api/internal/ops/workspace-leases/observe {refresh_lease:true}` is a new narrow operator endpoint owned by P4.5. Existing operator authorization must grant deployment-wide lease observation/refresh; the configured deployment scope must include every org with a current placement. Ordinary product users, org-only operators without that complete scope, host/incarnation credentials and provider/bootstrap capabilities are denied. The API derives the complete `starting|running|stopping` set from `workspace_vms` in that deployment; callers cannot supply an org/workspace filter, omit an unreachable host or choose a narrower VM list. Through the real `HostCommandClient`, it requests `vm.status(refresh_lease=true)` for each current assigned host and returns a bounded `protected_incarnations:[{org_id,workspace_id,host_id,vm_id,epoch}]` vector plus one observation per entry: `observed {lease_seq,lease_remaining_ms}`, `released`, `unreachable`, `pending_acquisition`, `stale` or `error`. `released` requires confirmed database release after enumeration; every other incomplete status blocks deployment. Revalidate row/host/VM/epoch when matching each reply; never substitute API wall-clock lease expiry or cached heartbeat evidence. A response-size or deadline bound that prevents complete coverage fails the observation instead of silently truncating the vector. The response contains no credentials, paths or repository content. Token-free audit records actor/deployment scope, coverage and refusals. The wrapper holds its external placement lock, verifies exact vector coverage, subtracts its whole HTTP request round-trip plus subsequent observation age from each reported host duration, and repeats this endpoint immediately before Helm and for post-ready renewal verification. Endpoint authentication, omission/unreachable/stale cases and positive complete coverage are P4.5 acceptance tests. This operator POST does not alter the product `GET /workspaces/:id/vm` contract, which remains database/last-report only.

**MVP deploy guard.** `vm.status(refresh_lease=true)` first requests a fresh lease using the ordinary monotonic/sequence rules, then reports `{vm_id, epoch, lease_seq, lease_remaining_ms}` from the host's actual monotonic deadline. Status cannot extend a lease itself. The guard subtracts the complete request round-trip and subsequent observation age from reported remaining time; API `lease_expires_at` alone is not evidence because it can be later than the host deadline. Every current `starting|running|stopping` incarnation must have matching fresh evidence with conservative remaining time greater than `start_delay + outage + recovery` (195 seconds at the defaults). Unreachable hosts, pending acquisition, stale sequences or insufficient bounds block the deploy; a confirmed released incarnation may be removed from the set.

P4.5 adds `scripts/deploy-with-workspace-lease-guard.py` (new implementation target), invoked **inside the existing `helm-deploy` step** of `infra/ci/cloudbuild-deploy.yaml`. This external wrapper holds a PostgreSQL session advisory lock for the whole preflight → Helm Recreate → host reconciliation/first-renewal interval, using reserved advisory key `(0x47354c39, 1)`; an earlier Cloud Build step that exits cannot hold the guard. Workspace placement takes a shared transaction lock on that reserved key using try-lock; while blocked, it preserves typed start intents and reports deployment capacity waiting without allocating another incarnation. Lease renewals, stop/flush and release do not require this lock. The wrapper uses a least-privileged deploy DB identity for the lock and a scoped operator API for lease observations; no workspace/provider credential is exported. Holding the lock makes the protected incarnation set closed to new placements; stopped entries may leave it. Recheck evidence immediately before invoking Helm and refresh if the 15-second start window elapsed. No current incarnation may be omitted because its host is unavailable.

The wrapper remains outside API pods across Recreate, measures unavailability through API readiness and then verifies every surviving host's inventory and successful renewal within the recovery budget. Release the lock in `finally`/connection close on success, failure or timeout; restored placement still requires fresh owner/generation-bound start intent and normal lease acquisition. Failure marks the deploy failed and records any expired/fenced incarnation truthfully, rather than extending its lease or claiming rollback preserved it. Existing deploy authorization/freshness gates remain. P4.4b supplies host lease evidence; P4.5 owns the guard and a positive within-budget API restart test preserving VM/epoch, file RPC, flush recovery and queued start intent, plus an above-budget loss test. P4.6–P4.8 add active-turn/native-wait cases as those paths land. P8.7 extends this already-required MVP guard for fleet rollout. Required tests and QA measurement are evidence to obtain during implementation, not results of this design revision.

### 6.5 Credentials and secrets

**Provider key.** In the MVP the provider key reaches the VM as environment and an in-guest proxy attaches it, as in the original. The account is the current workspace owner's: it is resolved at dispatch (`ProviderAccountService::resolve_frozen_for_dispatch`) and the key is delivered with that dispatch, the way `TaskAssignment.secrets` travel today. `agent.turn` starts the in-guest LLM proxy with it and builds the provider environment as the P3.2 runner does. The key is inside the VM, as today.

**Platform token.** The dispatcher owns the rotating incarnation token (`G5D_WORKSPACE_TOKEN`). Native Git uses a member-scoped loopback relay, configured transparently for origin; the relay authenticates to the control plane and never hands the token to repository Git, hooks or agent processes. Provider credentials remain server-side. The incarnation fence rejects stale credentials at every control-plane boundary (§6.4). Trusted bootstrap operations retain their scoped API transport and current-incarnation authorization.

**Secrets.** Repository and task secrets travel as the provider key does: the API resolves them at dispatch and they ride it, the way `TaskAssignment.secrets` do today, and the dispatcher puts them in the environment of the process it launches (a module execution, the preview, a terminal at `terminal.open`). A changed secret or provider key applies at the next launch; there is no mid-turn rotation. `VmSpec.secrets_env`, whose references the host resolves through `grants.resolve`, is post-MVP with the grants (P4.12).

Declared repository/task build secrets intentionally reach allowed workspace processes and are not per-user isolated. Resolve them into the dispatcher and refresh before launch; a resident terminal retains its original values. They cannot shadow runtime credential keys. Redact known values from stored logs/projections. Preview uses the owner workspace context and cannot choose another account; transfer releases the incarnation and purges old retained roots before rebinding.

**Guest network.** passt starts with no firewall rules; the uid and cgroup hooks in `backend/g5d-isolation/src/isolation/passt.rs` stay unused. The network mode stays selectable by `G5D_VM_NET`: TSI by default (CI, self-hosted), passt on GCE. A guest can reach the internet, the metadata address and host-loopback services through the door, exactly as in the original (its decisions D50, D51, D55); this exposure is accepted for the MVP. Guest users and images stay as shipped: the agent runs as uid 1000 (`G5D_GUEST_SIDECAR_NONROOT`) and images carry rootful Docker.

**Post-MVP (P4.12, P8.11).** The remainder of this section specifies the host-side proxies, the grants, the brokers and the bootstrap capability (P4.12), and the host-enforced egress and the runtime process isolation (P8.11). It is specification for those PRs and is not part of the MVP.

Provider/SCM credentials stay in host memory; the workspace token belongs only to host proxies and the trusted dispatcher. [Worker Host API v9](worker-host-api-v9.md) §6 defines the principal matrix. Repository/provider descendants use restricted model/internal-Git brokers, never a generic `/api` credential injector. `G5D_EXEC_ID` and session IDs are correlation, not authentication. Generic provider/MCP/shell `g5d` platform-write tools are deferred from MVP; there is no unnamed private bridge gate for ordinary agent turns. Native Claude questions/approvals still use their direct CLI control protocol, and Codex MVP remains noninteractive.

The platform-installed `workspace.bootstrap` supervisor alone may create bounded agent children through `POST /api/internal/jobs/:job_id/tasks`. At `modules.invoke` the API binds its random capability to module/version/hash, command task/attempt, org/workspace/job, current owner/lifecycle generation and VM/epoch; the typed graph and limits are Agent API §6.6. The supervisor holds the capability privately and uses a private HTTPS client through the dispatcher-authenticated host platform broker for that exact API route. The broker forwards only that method/path to the configured control-plane origin with the scoped capability, never a generic workspace-token injector or arbitrary destination; direct guest control-plane egress is denied. The transport is inaccessible to provider/repository endpoints. Repository scripts/providers/terminal inherit neither it nor privileged descriptors; client IDs cannot retarget it. Trusted runtime/control has a separate UID, private state and protected proc access; repository commands run unprivileged without sudo or rootful Docker sockets. Allowed images must support the boundary; builds use rootless Docker.

**Host-enforced egress.** Linux MVP uses nftables OUTPUT filtering on an exclusive host UID assigned to each incarnation's passt process. Worker & Host allocates that UID with the slot, installs rules before passt can create network sockets or the VMM is admitted, and verifies their policy digest. The optional shared UID/cgroup hooks in retained `backend/g5d-isolation/src/isolation/passt.rs` are reuse points, not existing enforcement. Repository processes cannot choose the UID or receive NET_ADMIN. Reap passt and close its sockets before deleting rules/reusing UID or proxy port; stale conntrack/rule state cannot authorize the next incarnation. A missing capability, rule-install failure or policy mismatch is `boot_failed(egress_unavailable)` before guest execution. No process fallback satisfies this production gate.

The resolved `VmSpec.egress_policy` is `{version, digest, allow:[{ipv4_cidr, protocol: tcp|udp, ports:[...]}]}` from the registered org `workspace_egress_policy` config; org admins edit bounded explicit destinations, with default empty allow. Worker & Host owns validation/compilation, and platform deny rules cannot be overridden by an org grant. Platform host configuration pins the IPv4 DNS upstream and passt binary; repository files and workspace settings cannot select them. CIDR/port rules authorize destination tuples, not hostnames. Domain-to-IP-set policies are deferred; DNS answers and redirects must each pass the destination check. Provider and internal-Git traffic use their separately scoped brokers. Package registries need explicit approved destination tuples, never an arbitrary-egress fallback.

Rules name both guest addresses and the host socket destinations after passt translation. Guest `169.254.1.2:<own_proxy_port>` maps to the exact host `127.0.0.1:<own_proxy_port>` TCP listener; allow only that tuple for this UID, never sibling ports. Guest DNS `169.254.1.1:53` UDP/TCP maps only to the platform-pinned resolver's exact IPv4:53 tuple. Pin a passt build supporting explicit `--dns-host <resolver-ip>` with `--dns-forward 169.254.1.1`, keep `-4` and disable search-domain inheritance; validate its actual behavior at the selected binary before admission. The [upstream passt manual](https://passt.top/builds/latest/web/passt.1.html) documents these mappings, but is not proof for a shipped binary. Port 853 and alternate resolvers are denied in MVP.

These two translated exceptions precede the deny set; no other host-loopback endpoint is allowed. Deny remaining `169.254.0.0/16` (including metadata 169.254.169.254), `127.0.0.0/8`, host/sibling/control-network addresses, multicast/broadcast and IPv6. Other private/VPC and public destinations default-deny unless a bounded org tuple explicitly allows them; protected host/metadata denies still win. Apply the same destination checks to every new connection, including DNS aliases and redirects. Conntrack marks bind allowed flows to the incarnation: allow replies only for those flows or the exact host-initiated dispatcher/PTY/HTTP forwards registered by the supervisor. Do not add a blanket established-flow exemption that retains revoked or previous-incarnation authority. Purge the incarnation flow marks before UID/port reuse; relay replies must still pass the real fs/PTY/preview tests. The own-proxy network exception still requires its private proxy secret: a raw repository request cannot gain dispatcher authority by reaching the port.

P4.4b adds `backend/g5d/tests/workspace_vm_egress.rs` and strict `workspace-vm-egress` in `infra/ci/cloudbuild-ci-e2e.yaml` (both new implementation targets), after `setup-kvm-libkrun` and runtime staging; its explicit result feeds `assert-ci-status`. It boots real libkrun/passt with private fixture roots and fails on missing KVM, passt pin or nftables support. Existing skip-capable `isolation-backends`/docker-ci1b are not substitutes. Probe approved destination/DNS/own proxy success, unauthenticated proxy refusal, metadata/other link-local/host/sibling/direct-unapproved/DNS-alias/redirect/IPv6 denial, install failure and UID/port reuse. P4.12 repeats the own-proxy cases with the real credential broker. Local docker-ci has an explicit required-security target with the same no-skip rule; P9.1 applies it to self-hosted Linux. macOS development may run a clearly marked local test backend with synthetic credentials only; production grants/VM placement are refused until an equivalent kernel boundary is implemented and separately verified. A self-reported capability string cannot waive enforcement.

Model routing uses the shared session tag for accounting, never provider selection; all sessions use the current owner's credential/gateway. Host grant resolution is the scoped `grants.resolve` ctl path; same-owner rotation swaps a full generation atomically. Workspace-token renewal swaps host proxy values before dispatcher installation. On upstream 401, only proxy-attached credentials may trigger single-flight refresh at most once per grant per 60 seconds, backoff to 15 minutes with 5-second timeout; suppression surfaces the original error.

MVP Git grants name the exact canonical origin/repository and upload/receive-pack operations for internal Git only. External publication remains explicit control-plane authority; later private-dependency grants are upload-pack only. Reject ambiguous encoded paths, other repositories, non-Git endpoints and redirects; strip guest Authorization/cookies on credential-injected routes. No host-wide SCM injector or guest `gh` write path is enabled.

Typed incarnation credentials admit only dispatcher lifecycle/receipt/harvest/event/session operations. The bootstrap capability adds only the exact bounded child-creation route. User/admin/org/workspace-create/transfer, arbitrary other-workspace and generic provider platform-write routes reject both. Human user/device-flow credentials remain separate.

### 6.6 Dispatcher and the Workspace Runtime API

Boot: mount `/work`, create `/home/agent` and `/var/lib/g5d`, restore (§5.5), start the runtime listener on the guest port with the per-VM listener token, load the module catalog, start the file watcher and the port scanner, open the event journal, report `runtime.ready(vm_id, epoch, module_catalog_version, dispatcher_contract_version)`.

The **Workspace Runtime facade** in the control plane is the only client that opens VM channels through a host, and only after the lifecycle service has made the incarnation current; every other platform system (Agents above all) calls the facade. Every request through it is bound to a `workspace_id`, the expected `vm_id`, an actor or grant, a deadline and an idempotency key.

**Workspace Runtime API** (live methods use JSON-RPC on the `rpc` stream; events are journaled). Workspace status is the separate control-plane `GET /workspaces/:id/vm` read composed from durable state/last host report and always makes zero guest calls:

| Surface | Methods | Caller | Contract |
|---|---|---|---|
| Files | `fs.list`, `fs.read`, `fs.stat`, `fs.write(path, content, encoding, expected_hash)`, `fs.delete(path, expected_hash)`, `fs.rename(from, to, expected_hash)`, `fs.watch` → `file.changed` | current-owner editors and file tree through the facade | attached, admission-open VM only; non-owner browsing uses Git, never this surface; mutation preconditions prevent a silent overwrite |
| Terminal | `terminal.open(cols, rows)`, `terminal.write`, `terminal.resize`, `terminal.close`; bytes on a `pty` stream | the workspace owner | the user's escape hatch; never a platform-extension mechanism |
| Modules | `modules.list`, `modules.describe`, `modules.invoke(exec_id, module_id, version, operation, input, grant_id)`, `modules.status`, `modules.cancel` | platform features through the facade | the sole execution and extension path; callers cannot supply `argv`, environment, cwd or signal targets |
| Ports | `ports.list`; `port.opened`, `port.closed` events | current-owner Ports panel | observes listeners; starts nothing; non-owner relay/list access denied |
| Workspace status | `GET /workspaces/:id/vm` (control plane; no dispatcher RPC) | the workspace UI, support, operators | lifecycle state, current or last `vm_id`, placement, lease freshness, the last receipt with a freshness label; when stopped, only durable and last-reported state, never a live claim, and never a wake |
| Runtime inspection | `runtime.inspect.summary` | current owner or separately scoped operator support grant | dispatcher, image and catalog identity, boot time, uptime, resource pressure, mounted roots, port summary, fixed health probes |
| Module diagnostics | `modules.logs(exec_id, cursor?)`, `modules.events(exec_id, cursor?)`, `modules.history(filter)` | current owner or separately scoped operator support grant | bounded, redacted logs and structured events; no raw host processes |
| Diagnostic bundle | `diagnostics.capture(profile)`, `diagnostics.probe(name)` | support grant; owners for safe profiles | versioned redacted bundles and declared read-only probes (`workspace-integrity`, `runtime-health`, `port-connectivity`, `module-catalog-integrity`); no caller-supplied shell command |

Non-owner workspace status and module/task history endpoints serve sanitized durable control-plane projections without invoking the VM. A workspace read invite is not an operator support grant; operator access remains separate, scoped and audited and never grants a non-owner client terminal. Owner/live routes check identity on every request and stream admission, and revoke streams and cached live content on ownership/access changes. Never fall back to live data on a Git read miss.

**Private control-plane protocol**, used only by the facade, the lifecycle service, the host and the dispatcher: `runtime.ready`, `lease.renew`, `health`; `events.replay(exec_id, from_seq)`, `events.ack(exec_id, up_to_seq)`, `outcomes.pending()`; `session_files.restore`, `session_files.harvest`; `modules.input.respond(workspace_id, expected_vm_id, expected_epoch, task_id, attempt, exec_id, request_id, provider_request_id, response_digest, validated_response, idempotency_key=request_id)` for an owner-authorized response to a live native provider request (§8.4); `modules.background.end(workspace_id, expected_vm_id, expected_epoch, task_id, attempt, exec_id, request_id, idempotency_key=request_id)` for the owner's End of a live Claude background wait (§8.3); the admission barrier (`admission.close` returns when in-flight mutations finish; `admission.open`); `workspace.flush` (§5.4).

**Explicitly absent:** `proc.spawn/signal/wait/list` (a private runner used only after module resolution), `git.*` (native git for agents, the git service for refs and policy, `workspace.changes` for the UI projection), `agent.run_turn` (the `agent.turn` module), `preview.*` (the `workspace.preview` module), `checkpoint.*` and periodic checkpoint events (agent-driven persistence plus `workspace.flush`), arbitrary diagnostic shell execution (fixed probes and bundles).

Concurrency: every process uses the same workspace root and the same checkout of each member repository, all on the shared workspace branch name. There is no worktree, branch or lock per task. Concurrent edits to one file have lost-update semantics: the last writer wins and git shows only the final content. Git raises a conflict only at rebase or merge time. Agents are told (the profile says so), and the UI shows a notice when more than one execution is running. Nothing stronger is enforced.

The [Workspace VM API file contract](workspace-vm-api-v9.md#21-file-fields-and-confined-mutation) is authoritative for hash, create-if-absent, encoding, 32 MiB decoded payload bound and descriptor-relative path confinement. `workspace.changes`/diagnostic service calls use `(kind=operation, operation_id, attempt=1, vm_id)` rather than synthetic task rows; retries reuse that ID, and journal/cancel/audit semantics match task invocations. They count against the same bounded-execution slots as agent and command tasks, subject to their declared catalog cap. If unavailable, return explicit busy/queued state; a Save association check must not wait indefinitely or bypass admission.

### 6.7 Declared modules

Every platform-initiated executable unit is a declared module invocation. A module declares: a stable `module_id`, a semantic version and an immutable manifest hash; named operations with typed input, output and event schemas; a pinned entrypoint and a lifecycle class (`bounded_run` or `service`); limits (time for bounded runs, CPU, memory, disk, concurrency, output and log size; preview explicitly has no wall-clock cap or bounded-work concurrency charge); the minimal capabilities it requests (workspace read or write scope, bounded port allocation, network egress policy, git operation scope, provider-turn access); and its observability (health probes, diagnostic profile, event kinds, redaction policy). The dispatcher resolves the immutable catalog entry, validates the input, intersects the requested capabilities with the control-plane-issued `grant_id`, and only then uses its private runner. A manifest requests capabilities; it never grants them. The runtime image and the module catalog are hash-pinned; a workspace configuration may select or configure an installed module but cannot add code or privilege. Each invocation is auditable as `(workspace_id, vm_id, exec_id, actor, module_id, version, manifest_hash, grant_id, input_digest, capability_grant, outcome)`.

`modules.invoke` is idempotent on `exec_id` (tagged task or operation identity; Agent API §6) and returns a disposition: `started`, `already_running`, `already_finished(outcome)`, or `cancelled` (a cancellation disposition exists for this identity, §7.5). Module events and terminal outcomes use the dispatcher journal, ordered replay, acknowledgement and the incarnation fence.

| Module | Owner | Class | Operations |
|---|---|---|---|
| `agent.turn` | Agents | bounded run | `run(AgentTurnInput)` → events `AgentTurnEvent`, outcome `AgentTurnOutcome`; declared live `input.respond` channel for correlated native responses (§8.3–§8.4) and `background.end` channel for the owner's End of a Claude background wait (§8.3) |
| `workspace.changes` | Workspace | bounded run | `get` (the normalized association, dirty, ahead/behind, conflict projection); `push`; `update` (fetch and rebase each selected repo onto its own base branch; refused when dirty); `switch_back` |
| `workspace.preview` | Workspace | service | `start(profile)`, `stop`, `status` (§6.8) |
| `workspace.bootstrap` | Workspace | bounded run | `run` (deterministic workspace setup; platform supervisor delegates a bounded agent-child graph using the exact scoped route/capability in §6.5 and Agent API §6.6; scripts inherit no authority; the capability is post-MVP, P4.12: in the MVP the call carries the incarnation token and the API checks that the caller owns the running bootstrap task) |
| `workspace.diagnostics` | Workspace | bounded run | `capture(profile)`, `probe(name)` |

The dispatcher core (listener, journal, module runtime, admission, flush, restore) is edited only for defects once it ships; features arrive as modules and as versions of modules.

### 6.8 Preview

A Preview button creates a durable **task of kind `preview`**, with `created_by` recording the launching user, and dispatches `workspace.preview start(profile)` through the same task path as other types (§7.3). It appears in the workspace task queue and timeline from `queued` through its terminal state, with launcher, service status and Cancel. The command comes only from `.g5/preview_profiles/<name>.yaml` or the `preview:` block of `.g5/workspace.yaml`; a reader cannot supply arbitrary shell, environment, module, credentials or capability grants. The task runs as a supervised service, remains `running` while the preview serves, and is not marked successful merely because a port is ready.

**Access and identity.** The current workspace owner alone may start, replace, cancel or open the live preview. The Preview panel, task queue, product API, `g5d preview`, generic task cancellation and module grants use the same owner check; caller-supplied kind or launcher identity cannot bypass it. Non-owners see permitted durable task status/history and a Fork to preview action. A stopped owner's preview action is explicitly Start workspace and preview; it first records owner Start intent and waits for attachment. Status reads and cancellation never wake compute. The process uses the incarnation owner's workspace identity and secrets. `created_by` remains provenance, not an enduring authorization grant after transfer.

**One active preview per workspace.** A second start replaces the current preview regardless of who launched it. The start/replacement operation is serialized per workspace and idempotent by request key: durably cancel the previous queued/running intent, deliver its cancellation disposition and wait for its process to stop (or its incarnation to be lost) before launching the successor. Concurrent starts choose one current intent; stale readiness, exit, cancellation or port events are fenced by task/attempt/incarnation and cannot change the successor. Never run two preview processes during a slow or disconnected cancellation. Cancelling an already terminal task is idempotent and cannot cancel its replacement.

**Service lifecycle.** Preview consumes no workspace bounded-work concurrency slot and has no wall-clock limit; host VM capacity/quota and module resource limits still apply. An admitted owner HTTP request or new stream/WebSocket upgrade counts once at the API relay, coalesced every 10 seconds into last_activity_at. Existing socket bytes/keepalive frames and denied requests are not activity. Use the org idle default with a workspace override. An idle service’s existence alone does not keep the VM awake. Cancel, replacement or VM stop terminates the service and records the reason on its task; unexpected service exit is a terminal failure. Loss settles even an unconfirmed preview start. Preview has no automatic retry or successor across process failure, VM loss, stop, transfer or resume; the user starts a new preview task explicitly. A preview alongside an owner’s task therefore does not block task scheduling or idle reclamation once other activity ends.

**Tracked-file contract.** A preview must not modify tracked files. G5 does not enforce this in the MVP because the command comes from the repository’s profile; a tracked change appears in Changes and is captured by a flush. A discard-on-write overlay is a later hardening option. A rebuild may stomp the owner’s running app; this remains a limitation of the shared owner workspace. Forking gives separate execution.

The browser reaches the preview through the API relay over the host tunnel (`http` streams, one per TCP connection) at `/api/v1/workspaces/:id/preview/:port/*`, with relay code carried forward from `routes/preview.rs` and target resolution keyed by workspace, current preview execution and port. The MVP serves the preview as today, owner-only and keyed by the preview task instead of the job: a per-preview subdomain under the platform domain when the preview host suffix (`G5_PREVIEW_HOST_SUFFIX`) is configured, with the single-use handoff ticket, the `__Host-g5_preview` cookie and CSP, and the path relay otherwise. Preview shares the platform's registrable domain, as in the original; this is accepted for the MVP. Current ownership and incarnation are enforced when opening/reopening the relay and on ownership revocation; existing connections close at stop/transfer. Tickets are owner/session/workspace/incarnation scoped and never grant terminal or cross-workspace access. Non-owner readers cannot use the relay even when a preview already runs. Ports opened by the owner’s agents appear in owner-only Ports and use the same owner-authorized relay.

**Post-MVP (P8.13).** The ticket cookie is host-only on a per-workspace/port origin on a separate registrable domain from the platform; isolated origin is mandatory. Missing isolated-origin configuration fails 503 PREVIEW_ORIGIN_UNCONFIGURED, with no shared/self-hosted same-origin HTML fallback. The API entry route only redirects/bootstraps; platform cookies never reach previews, and API CORS/CSRF/Origin plus postMessage checks deny preview-origin platform authority. P5.1 owns browser probes in iframe and new tab. Ticket cookies are host-only, Secure, HttpOnly and SameSite=None; embedded preview uses Partitioned cookies in supported browsers. The handoff redeems once for the authorized preview origin without exposing platform cookies. Verify successful owner rendering in the supported-browser iframe matrix as well as denial probes. If the browser cannot retain the partitioned embedded ticket, show an explicit Open preview in new tab action using a fresh owner-authorized top-level handoff; do not silently relax cookie/origin isolation or fall back to platform-origin HTML. Tests cover iframe and new-tab positive load, unsupported embedded-cookie fallback, stolen/expired ticket refusal and platform-cookie exclusion.

Removed: `job_preview_sessions`, boot generations, `preview_reaper`, the `preview_vms` registry, chat-attach listener, token and host drive, and the separate per-task preview VM path. Preserve preview as a task kind and retain or adapt existing preview launch/task-queue UI until the replacement is working. A legacy preview job wrapper may be removed only after its launch, status, cancellation and history consumers use the preview task; deleting the feature/type from the task queue is prohibited. Agent and app share the workspace VM.

Preview serving readiness is separate from task execution: confirmed started makes the task running; its configured port.opened or declared health probe makes the relay serving. Before that, and after port.closed without process exit, return 503 PREVIEW_NOT_READY and show not-serving without completing the task. Incarnation loss terminalizes all preview intents bound to its start authorization, including a not-yet-invoked replacement; preserve an already-committed cancellation, otherwise fail with vm_lost. A later independently authorized fresh Start is not old demand and is not swept.

### 6.9 Terminal

A browser terminal (xterm.js) over a `pty` stream after `terminal.open`, gated by current workspace ownership (an org admin takes ownership first); the shell runs as unprivileged repository uid 1000 in `/work` with only restricted broker configuration and explicitly allowed build secrets. It cannot read trusted-runtime credentials, inherit privileged descriptors, use sudo or obtain a rootful Docker socket (§6.5). The PTY manager and the multiplexer exist today; the UI panel and the channel are new. Terminal activity counts as VM activity. Terminals are not recorded or audited in this iteration. **Post-MVP (P4.12: the restricted broker configuration; P8.11: the trusted-runtime credential and rootful-Docker rules).** In the MVP the shell gets the module environment as today, with the task secrets and the platform token.

### 6.10 Fleet, placement, drain and rollout

Placement filters by exact org and configured region. Org configs `worker_host_region` defaults explicitly to the deployment region and `max_running_vms` to 10 active starting/running/stopping VMs. The MVP keeps the fallback-region basket for stockouts, as in the original. MVP pools are statically operator-provisioned per org, with zero capacity until provisioned. Automatic scale-out/in and cross-org pooling are deferred. API quota and host slot/boot reservations are separately atomic; capacity waiting uses the durable start intent (§5.8). **Post-MVP (P8.14).** No silent cross-region fallback.

**Hosts** are API-provisioned GCE instances, self-hosted Linux machines (including the Azure canary lane), or macOS dev hosts. A host is a set of equal-size VM slots (`G5D_HOST_MAX_MICROVMS`, VM CPU and memory from the host configuration), not a task pool. The reconciler (provisioning → ready, orphan sweep, `unreachable` after three missed heartbeats) stays. With the 24 h host JWT, cloud hosts are rotated before expiry, so each workspace on a host gets one graceful teardown a day with the nudge and the flush (accepted for the MVP; P8.10 removes it). **Post-MVP (P8.10).** There is no maximum host lifetime: a host is drained only for an upgrade or by an operator, so a long-running workspace is never interrupted by a calendar.

**Placement** is a control-plane decision; the host only accepts or refuses. In order: a host in the org's region with a free slot that still holds this workspace's retained root; then any host in the region with a free slot; then `no_capacity`, surfaced to the user as `queued_for_capacity` with a position and retried by the Workspace placement reconciler against the durable start intent. Org quota is `max_running_vms`, enforced before `vm.start`. A host that answers `slot_unavailable` despite the registry's count is authoritative and the control plane re-places; `workspace_busy` means the previous incarnation of the same workspace has not exited on that host yet.

**Drain and rotation.** Rotation is drain and replace: provision the replacement first, send `host.drain`, then for each VM run the stop sequence with reason `drain` (nudge, deadline, flush, release) and `vm.stop`; a VM whose flush fails is retried with backoff until the drain deadline, after which the teardown proceeds and records the loss; `host.drained` is followed by instance termination.

**Rollout of a new version.** Product versioning is per module and per component, with feature flags in `configs` for behavior that must switch independently of a deploy. The order is fixed by the version negotiation: the control plane deploys first and accepts the current and the previous host protocol version; hosts are replaced by drain-and-replace with the new runtime image; workspaces pick up a new VM image or dispatcher by a rollout drain (per workspace: nudge, deadline, stop sequence with reason `rollout`, release, and a resume with the new image on explicit owner Start/Resume, or a continuation only under still-valid recorded current-owner drain/rollout authorization). An attempt interrupted by the rollout may continue after resume as a new attempt of the same logical task, preserving its session, job and dependencies; its input records the interruption and continuation intent (§7.2). Workers may be at most one version stale; the QA project exercises the sequence before production.

Internal authenticated `/metrics` exports bounded status/reason metrics for host reachability, slots, boot latency, proxy refusals/reconnects, flush latency/failures, unflushed loss, stopping/cleanup age, capacity queue, attempt outcomes, native-request timeouts and receipt verification. Each feature PR owns its failure-path metric/test; do not place workspace/user IDs in metric labels. P4.13 wires alerts for unexpected lease kills/loss, integrity/spec failures, hosts unreachable over 60 seconds, and work beyond recorded stop/cleanup deadlines. ## 7. Task lifecycle (Agents)

The 2026-09-18 MVP scope decision defers the dedicated returned-results workflow (§5.9). Every retained task follows the ordinary output, completion and dependency rules below; there is no result-specific task or lifecycle exception.

### 7.1 Model

```
tasks(id, org_id, workspace_id, job_id NULL, kind agent|command|preview,
      status queued|running|waiting|succeeded|failed|cancelled,
      spec jsonb,        -- requested policy/defaults, initial input origin/template revision, limits, retry/continuation policy
      outcome jsonb,     -- final logical task result only; attempt outcomes are separate
      attempt int, vm_id NULL, epoch NULL, start_confirmed bool, -- current-attempt caches except selector
      chat_session_id NULL, continuation_reason NULL,
      hold_reason NULL, created_by, created_at, started_at, ended_at)

task_attempts(org_id, task_id, attempt, vm_id, epoch, start_confirmed bool, policy_snapshot_ref NULL,
              started_at, ended_at, outcome,
              reason exit_code|provider_error|vm_lost|timed_out|cancelled|interrupted|suspended,
              acked_event_seq bigint, PRIMARY KEY (task_id, attempt), UNIQUE (org_id, task_id, attempt),
              FOREIGN KEY (org_id, task_id) REFERENCES tasks(org_id, id))

task_dependencies(org_id, workspace_id, task_id, depends_on_task_id,
                  PRIMARY KEY (task_id, depends_on_task_id), CHECK (task_id <> depends_on_task_id),
                  FOREIGN KEY (org_id, workspace_id, task_id) REFERENCES tasks(org_id, workspace_id, id),
                  FOREIGN KEY (org_id, workspace_id, depends_on_task_id) REFERENCES tasks(org_id, workspace_id, id))
-- UNIQUE tasks(org_id, id) and tasks(org_id, workspace_id, id); reverse index (depends_on_task_id, task_id)

jobs(id, org_id, workspace_id, kind, status (derived), spec jsonb, created_by,
     max_concurrency, created_at, ended_at)          -- optional orchestration over logical tasks

task_events(id bigserial, task_id, attempt, vm_id, seq bigint, ts, kind, payload jsonb,
            UNIQUE (task_id, attempt, vm_id, seq))

provider_requests(id, org_id, task_id, attempt, provider_request_id,
                  kind question|permission, tool_name, payload jsonb, display jsonb,
                  status pending|reply_pending|responded|invalidated,
                  response jsonb NULL, response_author_id NULL, response_deadline_at,
                  created_at, ended_at NULL, end_reason NULL,
                  UNIQUE (task_id, attempt, provider_request_id),
                  FOREIGN KEY (org_id, task_id, attempt) REFERENCES task_attempts(org_id, task_id, attempt))
```

There are exactly three task kinds. Every `agent` task has a non-null session and invokes `agent.turn`. Human chat supplies typed input; a workflow supplies a rendered, versioned template as initial input. Both then use the same inbox, transcript, questions, permission policy, provider session files, turn adapter and task timeline (§8). The existing table names `chat_sessions`, `chat_messages` and `chat_session_files` are shared storage for every agent workflow, not a separate chat execution model. A `command` task invokes `workspace.bootstrap`; `preview` remains a service task with owner-only start/cancel, no bounded-work concurrency charge, no wall-clock timeout and no auto-retry.

A task is the stable logical unit that dependencies and jobs reference; an attempt is a provider/module execution. An interrupted, suspended or retryable-lost attempt does not terminally fail its logical task while a continuation remains eligible. A continuation increments `attempt` on that same task, with the same session, `job_id`, incoming dependencies and outgoing dependents. A conversational follow-up after terminal completion creates a new `agent` task in the same session; it does not reopen a completed dependency or silently join the old job. Job kinds remain profiles (`uplift`, `downlift`, `sync`, `explainer`, `agent_review`, `custom`); a session/task needs no job.

`provider_requests` projects native questions and process-bound approvals and freezes their accepted replies. Confirmed deferred questions retain their native tool identity across execution end (§8.4); there is no replacement questionnaire engine, `successor_task_id` or provider-independent polling tool. Historical `task_questions` content is preserved as read-only history during migration; old actionable rows are closed explicitly before retiring that engine.

Only `TaskService::apply` changes task/attempt lifecycle fields. `tasks.attempt` selects the current authoritative `task_attempts` row; its `vm_id`, `epoch` and `start_confirmed` task columns are transactionally maintained caches, never independent authority. Attempts own immutable VM/epoch/policy binding and start evidence. `continuation_reason=interrupted|vm_lost|suspended` is non-null only when the prior attempt ended and that nonterminal task is eligible for another attempt; `status=waiting` plus `hold_reason` blocks it, while `status=queued` and valid admission permit dispatch. Set the reason when settling a continuable attempt; clear it atomically when the next attempt is admitted or the task terminalizes. No `continuation_pending` boolean is stored. Workspace Start authorization comes only from current-owner, lifecycle-generation-bound `start_intent`; a task hold is a reason to display, not another workspace authorization flag.

`task_dependencies` is the only dependency authority; a compatibility `depends_on` list is derived, never another writable array. Composite FKs enforce one org and workspace for both endpoints, with the matching unique task key and ordinary RLS. Reject self edges, cycles and missing endpoints; serialize edge creation/validation with admission, and freeze a task's incoming edges once its first attempt is admitted. Prerequisite deletion is restricted while referenced, so deletion cannot silently make work runnable. Retention removes dependents/edges in a safe order. Backfill valid legacy arrays and quarantine/report invalid edges before cutover; update every readiness/cascade/cancellation/import consumer, then retire the array. Optional jobs and jobless DAGs use the same rules; stable logical task IDs retain all edges across attempts.

Canonical task columns, hold_reason values and setter/clearer rules are specified in [Agent API §2.2.1](agent-api-surface-v9.md#221-canonical-task-and-attempt-state). TaskService is their only writer. MVP dependency_failure_policy is fixed fail_dependents for jobs and jobless DAGs; reject other configured policies. A live native wait has no hold_reason; queued_for_capacity/queued_for_slot/dependencies are derived display reasons, not new persisted states. P4.1 stages target task fields/statuses beside legacy fields; P4.6 writes the six target statuses and P7.1 performs final historical cleanup.

### 7.2 State machine

```
queued ──invoke intent, then start confirmation──► running
running ──native provider request pending──► waiting (live attempt)
waiting (live) ──all native requests delivered/settled──► running
running | waiting ──continuable attempt ended──► queued or waiting (no live attempt; held)
waiting (held) ──authorized Continue/Resume──► queued (same task, next attempt)
running ──final logical success──► succeeded
running | waiting ──non-continuable failure / exhausted retry──► failed
queued | running | waiting ──owner cancel──► cancelled
```

Six states, one writer: `TaskService::apply(event)`. Persist both task state and attempt state; `waiting` is explicitly labeled as live native input or held continuation; a held task has no live provider process and releases no dependency. `running` is recorded before invoking, but counts as execution only when start is confirmed (§7.5). The frontend must not imply that a held task still has a running process.

- **Dependencies and jobs.** Only final logical `succeeded` satisfies a dependency. A completed process with an interrupted/suspended outcome cannot release a dependent. Final failure/cancellation is propagated through the MVP fail_dependents policy; no dangling permanent wait. Job aggregation includes held logical tasks as unfinished. Cancel cascades to the logical task and its pending continuation under one lock.
- **One unfinished task per session.** All entry points serialize the shared session inbox and permit at most one nonterminal logical agent task and one active attempt in it. New input waits behind live or held work; no-process status cannot bypass a hold. A job/template and a human message cannot launch two providers against one session concurrently. Distinct sessions may run concurrently in the shared workspace checkouts.
- **Owner authorization.** The current owner authorizes user-initiated work and answers native requests. Workspaces/TaskService and the trusted declared bootstrap module may create scoped child tasks under that recorded owner authorization; provider/repository shell descendants cannot (§7.4). Readers create/cancel no source task kind, including preview. All dispatch/continuation paths honor transfer/admission and the current generation-bound `start_intent`; queued work never supplies Start authorization. Each attempt resolves the current owner's account, never a former owner's account.

### 7.3 Dispatch path

Human message send and workflow/template launch both persist a session input, then create its `agent` task with optional `job_id`/dependencies when that session has no unfinished task. Inputs behind live or held work stay queued; an explicit Continue reuses the unfinished task rather than creating another. `POST /workspaces/:id/tasks` validates the kind and shared session contract. The dispatch loop runs every 2 seconds and on demand:

1. Select eligible queued logical tasks whose dependencies are finally satisfied, excluding transfer/Start-required holds and sessions with an active attempt.
2. If their workspace is stopped/failed, require recorded, current-owner Start/Resume intent (or a still-valid drain/rollout continuation authorization) before `workspace.runtime.ensure`; otherwise hold and offer Resume. An eligible queued task alone cannot authorize boot. Expose `queued_for_capacity` for an authorized attach. Starting/stopping workspaces wait for lifecycle progression.
3. Lock the task and session. Reserve the shared inbox input/revision or persisted continuation input, resolve the current-owner account and freeze the explicit policy for this attempt, increment `attempt` only for a new execution, and persist authoritative attempt `vm_id`, `epoch`, `start_confirmed=false`, select it through `tasks.attempt` and update task caches/status `running` atomically.
4. Invoke `agent.turn`, `workspace.bootstrap` or `workspace.preview` through the facade. Apply `started`, `already_running`, `already_finished` or `cancelled` dispositions without inventing a second attempt.
5. Re-send an unconfirmed start with the same `exec_id` only on its current incarnation. On completion, atomically persist the attempt, transcript and logical task/continuation decision; only then consider dependents or next session input.

A preview uses its one-active-preview gate. Every agent and command invoke intent reserves one workspace bounded-execution slot until definitive refusal or terminal settlement; preview alone is exempt. Workspaces resolves bounded_execution_slots (default 16, `g5.agents.admission.default-slots`, capped by org policy) and the dispatcher enforces it. Module catalog concurrency and jobs.max_concurrency cap fan-out further; extra eligible tasks show queued_for_slot, distinct from placement queued_for_capacity. Every bounded module has declared CPU/memory/time/output/log/concurrency limits (Agent API §5). Both honor lifecycle admission. Native answer delivery targets a live attempt; it never calls `ensure`. Explicit Continue/Resume may create dispatch demand for a held task. Uplift bootstrap remains a `command` task whose orchestration creates ordinary `agent` tasks with shared sessions.

### 7.4 Jobs and dependencies across continuations

Jobs orchestrate logical tasks and derive status from them; they do not own a separate agent runner, permission shortcut or chat-less session model. Child sessions may run concurrently up to `max_concurrency` in the same member-repository checkouts. Every continuation remains on its original task/node, preserves `job_id` and both sides of the dependency graph, and reuses the same session transcript. A downstream task waits through a native question, held suspension, rollout continuation and retryable VM loss, and becomes eligible once when the logical prerequisite finally succeeds. Jobs may be cancelled; there is no rollback or separate job-merge task. Each agent commits/pushes its own changes and resolves native Git conflicts. Agents may produce reviews, explanations and other output in ordinary shared conversations and artifacts. The dedicated returned-results workflow is deferred (§5.9); ordinary forks do not acquire a special review lifecycle or completion barrier.

**Bootstrap delegation.** A platform-shipped `workspace.bootstrap` supervisor, acting for the owner-authorized command/job, alone may call the narrowed `POST /api/internal/jobs/:job_id/tasks` graph operation. Its API-minted `modules.invoke` capability is bound to module hash, command attempt, job/workspace/org, owner/lifecycle generation, VM/epoch, exact route and graph caps; provider/repository subprocesses never receive it. Its private HTTPS client uses the dispatcher-authenticated host platform broker for that exact POST route and scoped capability, with no generic token injection or direct guest control-plane egress. Agent API §6.6 defines `BootstrapTaskGraphV1` (the retained typed analysis-node payload), saved job-profile/policy validation, same-workspace edges, the implicit bootstrap prerequisite, atomic idempotent job receipt and refusal behavior. This is trusted service orchestration, not a provider tool bridge or permission to create arbitrary workspaces. Generic provider-initiated platform writes are deferred beyond MVP. **Post-MVP (P4.12: the invoke-bound capability and the broker route).** In the MVP the supervisor calls that route with the incarnation token, and the API authorizes it by the token and by its existing check that the caller owns the running bootstrap task, re-keyed from worker to incarnation; P4.2b lands the capability plumbing as planned and P4.8 removes it. The typed graph, its receipt and its caps stay.

### 7.5 Dispatch and event contract

- **Execution identity.** `exec_id` (tagged task or operation identity; Agent API §6). Task identity stays stable across continuations; a fresh execution gets a new attempt and its own sequence space. Invocation retries keep the same identity.
- **Two-phase start.** Persist the invocation intent before sending it. Idempotent dispositions distinguish started/running/finished/cancelled. A missing confirmation is not evidence that no process ran.
- **Durable cancellation.** The dispatcher keeps a cancellation/finished disposition for the incarnation independently of journal pruning. A late invoke returns the disposition without spawning. Logical cancellation and continuation creation share a lock in the API.
- **Journal and replay.** Per-execution events under `/var/lib/g5d/journal/<exec_id>` have monotonic `seq`; insert-ignore on `(task_id, attempt, vm_id, seq)`, cumulative acknowledgements and ordered replay prevent duplicate transitions. An old attempt’s event may fill history but cannot mutate current state.
- **Outcome versus logical completion.** One C3 settles each attempt. In the same API transaction, update its assistant output and either finalize the logical task or set a held/queued continuation. Keep `tasks.outcome`/`ended_at` terminal only for real logical completion. No failed parent plus independent successful successor may bypass a job dependency.
- **Native responses.** Persist the owner’s response intent before dispatch; bind it to the immutable attempt, request ID, native request ID and accepted response digest. The live adapter serializes writes and records delivery evidence. Replaying a UI/API intent must not write a duplicate native control response. If delivery cannot be established, preserve uncertainty and do not claim provider consumption or blindly replay it. Confirmed deferred-question restoration binds the frozen answer to the saved native tool under §8.4.
- **Reconciliation.** On reconnect, replay journals and resolve start/cancel/response dispositions for the same live process. Confirmed executions missing from the dispatcher become lost; tasks already cancelled cannot continue. Response deadlines invalidate/reap live waits; ended attempts invalidate outstanding requests. Continue only through the stored logical-task policy and owner hold.
- **Shared transcript.** Every agent workflow uses `chat_messages` plus `task_events`, with `session_inputs` as the pending-input authority. Transcript status and attempt/task settlement commit together; repair stranded pending rows from those authorities. Provider-native request cards are timeline projections, never a second completion authority.

These existing `chat_*` names now hold every agent workflow’s shared conversation. The schema uses retained physical names: `agent_provider`, `provider_state` (including provider/model settings), `message_index`, `artifacts` and token counters; attachment rows stay in `chat_attachments`. Do not add duplicate logical aliases `provider`, `index`, `attachments` or `usage`. `provider_session_id` is a dedicated nullable native-session handle added/cut over explicitly by P4.1/P4.7, not a second provider-settings authority. Normalized metering belongs to `usage_records`. Human chat creates initial typed input; a workflow renders its template and persists the exact input, template revision and resolved policy before launch. Thereafter both use the same session/inbox/adapter, may receive owner follow-up input, and expose the same history and timeline. Tasks have optional orchestration, not a second session system. One nonterminal logical agent task per session protects provider-session continuity, including a task held without a running process; at most one attempt may run for that task. New input remains in the session inbox behind running or held work and cannot bypass a hold by creating a second task. Different sessions may run concurrently.

Only the current owner sends/edits/withdraws input or changes session policy. Readers see the same history; chat-history search remains a Postgres feature and never depends on removed workspace search. History survives VM deletion. Transfer preserves transcripts, sessions and logical tasks, but new attempts use the new owner’s account after the explicit resume gate. Native request cards survive as history; live request authority does not survive the originating process.

`session_inputs` owns the mutable FIFO queue, exact content/attachment references, revision, provenance and reservation state; `chat_messages` owns delivered input history and streaming assistant/tool output. Queue order is `input_index`, transcript order is `message_index`, both allocated under the session lock. A journaled `input.accepted` atomically inserts the delivered user/system transcript row with `id=input_id`, sets its unique `input_id` link, freezes that accepted content, marks the matching input generation delivered and allocates its transcript index. Assistant events for the attempt apply after acceptance. Replayed acceptance returns the same row; a late prior-generation acceptance may add factual history but cannot settle a newer reservation. Unknown/withdrawn inputs do not enter provider fallback until positive acceptance evidence exists. The queue/timeline UI combines these projections without copying queued content into the transcript. Add `chat_attachments.input_id` for queued attachments and set their existing `message_id` link in that acceptance transaction; never create a second attachment body. Same-org/session constraints bind input, message, task and attachment links. Existing delivered history remains in place during migration; only genuinely pending input is backfilled into the queue. Chat fork/carry copies delivered transcript, not another owner's mutable queue. The linked transcript row has `CHECK(input_id IS NULL OR id=input_id)` and same-org/session ownership; `input_id` is unique. The acceptance transaction compares exact frozen revision/content/digest before reuse. Input rows and accepted message content become immutable after acceptance; only delivery audit may gain factual late evidence. Forked historical messages clear `input_id` rather than linking a different session's queue. Pending queue input and delivered transcript are separate API lists merged for presentation, so repeated acceptance cannot duplicate a visible human message.

**Inbox.** Persist a `session_inputs` row before dispatch. Queued input may be edited or withdrawn until reservation freezes a revision for one execution. `input.accepted` is journaled only after the adapter successfully hands the reserved prompt to its provider transport, not on module start: Codex receives prompt plus EOF; Claude receives the initial stream-json user frame while stdin stays open for native protocol replies. This records transport handoff, not proof that every downstream model side effect occurred. A pre-handoff failure releases the reservation; loss after an unacknowledged handoff is `delivery_unknown` and reconciles from the same-attempt journal/outcome before any retry. Do not promise exactly-once model side effects across an ambiguous VM loss. Delivered revisions remain transcript truth, withdrawn rows remain audit only, and session inputs are processed in FIFO order. General mid-turn human steering remains deferred; native control responses are a separate protocol channel, not a new user turn.

Each attempt reserves exactly one input row; queued rows are never coalesced. Missing acceptance evidence stays delivery_unknown, holds the task with that reason and excludes the row from fallback history. The owner explicitly authorizes possibly duplicate redelivery (same id/revision, delivery_generation+1), or cancels with uncertainty audit preserved; ordinary Continue cannot choose silently. On eligible next-attempt admission TaskService creates one system-authored continuation input row, atomically with the new attempt, reserving it as the sole input. Agent API §8.3 defines its reason/prior-identity content and fixed provider rendering; a delivered original prompt is not replayed. A stopped/draining system nudge is a separate notice carried by system_notice_ids in a later reservation/preamble, not another task or an extra ordinary prompt.

### 8.2 A shared agent turn

1. Human send or workflow launch persists a session input and creates an `agent` task only when the session has no nonterminal logical task. Further input remains queued behind running or held work. Only explicit owner Continue/Resume clears a hold on unfinished work and uses the same logical task; the absence of a provider process alone never admits another task. Once the prior task is terminal, the next input creates a new task in that session.
2. Dispatch reserves the input, resolves explicit policy/current-owner account and invokes `agent.turn` with the execution and session identities.
3. The adapter restores session files, launches the direct provider CLI, hands off the frozen input and journals acceptance and provider events into the common timeline.
4. Claude native `AskUserQuestion` and policy-governed approval requests become live `provider_requests` cards. The owner’s response returns over the native CLI control protocol. Codex MVP never exposes an interactive question/approval callback or custom MCP substitute.
5. On result/EOF/exit settlement, harvest session files and emit exactly one attempt outcome. TaskService atomically persists ordinary output and decides final logical completion or same-task continuation. No provider process remains between attempts; the shared session persists independently.

### 8.3 The `agent.turn` module and provider adapters

Agents owns this module; Workspace hosts it. C1 is command/lifecycle control, C2 is an ordered non-terminal event, and C3 is exactly one terminal outcome per execution. Invocation dispositions, native response commands and process-exit facts are C1. Transcript deltas, native question/permission observations and usage are C2. C3 settles the attempt, while TaskService separately decides whether the logical task is finished (§7.5). Provider terminal-looking frames remain candidates until the adapter verifies result, EOF and exit status; an unknown variant cannot imply success.

### 8.4 Native questions, approvals and request lifetime

[Agent API §8.2](agent-api-surface-v9.md#82-native-request-projection-and-reply) owns the native request, reply and restoration contract. The shared `provider_requests` projection and outbox retain the first valid answer with an immutable request ID and digest. Identical retries return delivery state; conflicting answers fail. The API validates question and selected-option positions against the stored structure, and the adapter reconstructs original native keys and labels from private native input. Public display and journal text remain redacted; accepted answers and raw provider session files are not exposed through reader routes.

A question has no automatic response deadline. Confirmed Claude PreToolUse deferral preserves its pending tool in the native session JSONL, ends the provider attempt and holds the same logical task without releasing dependents. Workspace Stop, VM replacement, transfer and elapsed time preserve that unanswered question. Explicit turn/task cancellation or provider withdrawal closes it. Start and unrelated messages do not bypass the hold. Background work keeps its live callback; only confirmed deferral is marked restorable.

The current owner answers on ready attached compute. Agents freezes the answer and reserves native resumption; the adapter restores the existing private bundle, matches the saved tool-use ID and replies through the fresh callback without sending a replacement user prompt. An old process-specific control ID is never reused. Missing or mismatched native state fails explicitly, with no regenerated question, transcript rewrite or generic answer-message fallback. Answering never starts a VM. Permission requests retain their live-execution fence and 15-minute default deadline, shortened by policy and attempt limits; they cannot approve an action in a later execution.

Only journaled `provider_request.replied` with exact native transport-write evidence settles delivery. For a restored question, the current immutable reservation binds the original question and accepted answer; one transaction settles that source question and the current input. A complete write is not provider acknowledgement. Partial or uncertain writes never authorize blind redelivery. Owner, cancellation, transfer and execution-loss transitions share the same task/workspace serialization boundary.

### 8.5 Provider session files in Postgres

Provider session state must survive VM loss and be independent of any VM. It is stored only in Postgres, in `chat_session_files`, and lives on the VM as a cache outside every working tree: Claude under `CLAUDE_CONFIG_DIR=/home/agent/.claude` (`projects/<escaped cwd>/<session id>.jsonl` and `<session id>/subagents/*`; `cwd` is always `/work/<root_path>`, so the project key is deterministic across incarnations); Codex under `CODEX_HOME=/home/agent/.codex` (`sessions/YYYY/MM/DD/rollout-<ts>-<session id>.jsonl`). After every turn, and again in the stop sequence, the module harvests files whose sha256 changed and upserts them (raw decompressed bytes in Postgres, zstd on the wire only, 128 MiB per file, tagged with the harvesting `vm_id` and `epoch`; a harvest from a non-current incarnation is rejected, so an older transcript never overwrites a newer one; `session_manifest_generation` increases with every accepted harvest). Before a turn that resumes, if the files are absent on the VM, the module restores them first. If Postgres has nothing for that session, or the CLI refuses the restored session before any frame, the module starts a new provider session and prefixes the prompt with a history built from delivered transcript rows, then records the new `provider_session_id`. Nothing about sessions is flushed into git, and no session file can be captured by a flush or a native `git add`. The bundle is opaque to Workspace and Worker & Host. Deferred native answers require their saved pending tool and are excluded from delivered-history fallback (§8.4).

A partial/over-cap/failed latest harvest records session_files_state=persist_failed on its attempt/session generation and a visible session_files_persist_failed notice. A fresh incarnation must never restore older stored files as though current: use a new provider session and delivered-history fallback. Deterministic cap/format failure can be durably marked unrestorable; transient upload/outcome/journal failure follows the stop-reason abort/deadline policy. Raw provider artifacts remain supervisor-only and byte-exact, never reader-visible. Agent API §6.5 names the P4.5 session-file routes/fences used by P4.11; stale incarnations cannot publish manifests.

### 8.6 Fork and carry

Forking a chat copies `chat_messages` up to an index into a new session with `provider_session_id = NULL`; the first turn starts a fresh provider session with the history. Creating a workspace with "carry chats" does the same per selected session into the new workspace owned by the caller. Readers fork chats only into a workspace they own; they cannot create or mutate a session in someone else’s workspace. Provider-native session forking is not used.

## 9. Documents and editing

### 9.1 Reads

`GET /workspaces/:id/files/*path`, file-tree/Changes routes and docs/ontology content wrappers share one authorization and source resolver:

| Caller / state | Repository source | Marker |
|---|---|---|
| current owner, attached running VM | `fs.read/list/stat/watch` through the facade | `source: live`, current `vm_id` |
| non-owner, any VM state | selected complete flush snapshot in internal Git; otherwise branch head | `source: flush` or `committed`, OID and capture time |
| owner, no usable attachment (including starting/stopping/failed) | same durable Git fallback | `source: flush` or `committed`, OID and capture time |
| base workspace, any reader including owner | existing protected/default Git refs | `source: committed`, OID |

V9 deliberately preserves the existing last-complete-receipt fallback; Git-only does not mean branch-head-only. A later branch push may be newer than the receipt: label the default snapshot and offer an explicit committed-branch view, without implying that a receipt is the current live tree. Pin source/OID for each tree/content/diff/projection view so responses cannot mix versions; after a refresh resolve and label a new vector. Git misses or unavailable projections do not fall back to VM reads. Non-owners cannot request a live refresh or flush. Git-only readers therefore do not see newer unflushed edits.

Reads never attach. Durable Git/metadata reads never extend a source VM's activity timer; attached-owner live file RPC may count as interactive activity under §5.8. Access is checked per request and stream admission. Owner live responses/caches are keyed by owner authorization and incarnation, not only workspace/path; stop, transfer and revocation close streams and invalidate that client's live caches before any read-only rendering. Non-owners receive ref/projection invalidation hints to refresh durable Git, never `fs.watch` content or source-VM events. Flush docs/ontology views render from the pinned tree through `CommittedRepoReadView::from_historical`, never branch projection rows. Committed views use projections only when `projection_state.applied_oid` equals the selected OID in the same database read snapshot; otherwise render from Git with a lag marker. A flushed Changes view uses the receipt's dirty set; committed view has no live dirty set.

Chat history, persisted task timelines and PR metadata remain authorized Postgres reads. The Git-only rule concerns repository content and source-VM access, not a migration of all platform metadata into Git. Live ports/preview relay, runtime inspection and live module logs remain owner-only (§6.6–§6.8); separately granted operator diagnostics are not a workspace-reader capability.

### 9.2 Writes and attachment

All client editors, uploads, delete/rename and execution controls require current ownership and a running, admission-open attachment. An unattached owner sees read-only content and Resume/Start workspace; a non-owner sees Fork to edit/run. Save never ensures or boots compute. `PUT /workspaces/:id/files/*path` carries `expected_hash` and `expected_vm_id`; return `WORKSPACE_NOT_RUNNING` before any VM call when unattached, `WORKSPACE_STOPPING` during teardown and a stale-incarnation conflict if attachment changed. An explicit Start may queue for capacity; editing stays disabled until ready, and the editor reloads live content before accepting a mutation so an old Git snapshot cannot overwrite restored work.

On an attached VM, revalidate owner/incarnation, check the association (`workspace.changes get`, §5.7) and call `fs.write` with the same expected incarnation and hash. A hash mismatch returns 409 and current content, with reload-or-overwrite offered only to the owner. Upload follows the same authorized, confined VM path, mutation barrier and overwrite/version policy; it does not implicitly commit. Delete/rename and any document wrapper follow the same boundary. Agent writes reach owner editors through `fs.watch`; editors without local changes reload, while dirty editors show changed-on-disk. A stop/transfer during an edit cannot replay an old pending Save after Resume under a new incarnation.

Changes retains diffs/status and owner Push for existing commits, plus update/association controls after attachment. Remove Commit and its dialogs/shortcuts, `workspace.changes commit`, all UI/API commit convenience handlers, Flush now and any public manual-flush route. Agents control native commit/push cadence. Save/upload, job launch, PR creation and lifecycle flush never invoke a hidden user commit. User-originated receive-pack requires the attached owner (§5.3); shutdown/fork flush and authorized server ref operations retain their service authority. The implementation waits for the real VM write facade before replacing CRDT Save; no interim server-commit path is added.

### 9.3 Editors

Monaco and the block-style spec editor keep their UI but bind to local document state with Save (Ctrl+S) and optional autosave-on-blur, instead of a Yjs text. Editing is enabled only after the owner attaches (§9.2); uploads obey the same rule. The meeting favored autosave but did not settle its default/cadence, so v9 retains explicit Save with optional autosave-on-blur rather than asserting a new always-autosave requirement. The structured question editors and explainer views follow the same pattern; the question-document view that already renders without Yjs is the template. Comments anchor to `(path, line, line hash)`. There is no presence and no co-editing; because all writes go through one Save API, a document-only CRDT can be added later without changing persistence.

A line comment anchors the actual viewed bytes with `(repo_id, path, base_commit_oid, content_hash, line, line_hash, context)`; `comment_index.commit_sha` remains the base commit and `origin_branch` a label. A dirty buffer is not falsely identified by HEAD alone. `content_hash` is the same byte/blob hash as the file contract; context is a bounded surrounding-line excerpt. Equal content uses the recorded line only after hash confirmation. Otherwise try retained hunk mapping when applicable, then a unique hash-plus-context match within ±20 lines. Missing or ambiguous matches render an orphan/ambiguous marker with the original anchor; never silently choose the nearest duplicate. Reader rendering uses its pinned source, not the owner’s live buffer. P2.2 adds fields via append-only migration and carries the create/render contract end to end.

### 9.4 Projections and convergence

`docs` and `ontology_nodes` remain projections of git files; workspace search and its embedding/index projections are removed. The event bus is a non-durable fan-out and a ref can be updated immediately before a crash, so projections never depend on an event: each records the OID it was computed from per `(repo_id, ref)` in `projection_state`; a convergence loop at API startup and every 60 seconds lists the authoritative OIDs of every workspace branch, every protected branch, compares them with `projection_state`, re-projects what differs and removes rows for refs that no longer exist. `branch.updated` and `flush.completed` events trigger the same work early. PR `head_sha` and `workspace_repos.head_sha_cache` are projections under this contract.


### 9.5 Workspace search removal boundary

Remove workspace search end to end: the global/workspace search box, result panels and navigation/shortcuts; workspace search endpoints and clients; text/vector/embedding search indexing, reindex queues/workers and scheduled jobs; search-specific tables, columns, indexes, settings, provider credentials/configuration, feature flags and events; search-only tests, fixtures, benchmarks, seed/backfill/reindex tools, commands and deployment wiring. Remove APIs and consumers together; an inert control, empty endpoint or permanently disabled worker is not removal. Applied migrations remain immutable; drop search-owned data with forward migrations after its writers/readers retire.

Retain chat-history search over session messages, editor Find, and agent-local code search such as `rg`, native provider tools and permitted unrelated MCP tools. Retain document/ontology projections, their convergence/rebuild work and shared infrastructure they still consume. Classify each indexer/embedding dependency by its actual consumers before deleting it; a process named `g5-api-indexer` must be split or retained for document/ontology projection work if that work shares it. The search feature cannot remain reachable through an ontology endpoint or legacy client alias. Search removal does not remove docs/ontology reads, graphs, grounding or chat history.

The convergence loop enumerates only managed/protected branch heads. Flush completion invalidates source caches; it does not project snapshot refs into single-version `docs`/`ontology_nodes` rows. P4.5 moves its legacy mapping join to `workspace_repos`; P2.1 guards every projection read by selected OID. Provider-backed source entries include `{repo_id, ref, oid, source, captured_at, mirror_observed_at?, mirror_state?, receipt_id?}` and display staleness from the observation timestamp, not the time the API happened to read a frozen mirror.

## 10. Governance

Governance stays in the design and is built the week after the MVP milestone; nothing in the MVP may block it (§13).

### 10.1 Protected refs

`repos.protected_branches` holds the default branch and any branch a base workspace tracks. Receive-pack denies every network push to those refs (§5.3). At repo connect time the API reads the provider's branch protection for the default branch and warns when G5 approval rules and provider rules disagree. Both gates apply.

### 10.2 Pull requests

```
pull_requests(id, org_id, workspace_id, repo_id, source_branch, target_branch,
              status open|merged|closed, head_sha, title, body,
              provider_pr_number NULL, provider_pr_url NULL, published_sha NULL,
              merge_op_id NULL, merge_state NULL|pending|provider_merged|applied|failed,
              merge_source_sha NULL, merge_target_sha NULL, merge_result_sha NULL,
              merge_error NULL, created_by, created_at, merged_at, merged_by)
```

Created by the current owner from the UI or authenticated user laptop CLI with `g5d pr create` (the later P6 surface); a reader or non-owner admin must fork or take ownership first. Creation reads the source OID from the internal branch at that moment, publishes the branch to the provider at that OID and records it as `published_sha`, and opens a provider PR when the repo has a provider; the provider PR is a mirror for external reviewers, not the source of truth for merging. A PR is created from the existing internal branch OID. If `workspace.changes get` reports dirty or unpushed state, refuse creation with a clear not-ready result and show that the agent must finish its checkpoint/push; an owner may use retained Push for already-created local commits. Do not offer Commit and push all, silently commit, or publish a flush snapshot onto the branch. The agent commits/pushes before the owner creates the PR; a flush is not PR publication. Provider-initiated platform PR writes are deferred (§11.1). `head_sha` is a projection of the source branch (§9.4); every decision and the merge operation use OIDs they read from git themselves.

### 10.3 Approvals

```
approval_rules(id, org_id, repo_id, target_branch, required_approvers uuid[],
               min_approvals int, agent_reviewer_profile NULL, created_by, created_at)

approval_decisions(id, org_id, pull_request_id, source_sha, actor_user_id NULL,
                   actor_task_id NULL, outcome approved|changes_requested, note, created_at)
```

Recording a formal decision is later governance work (P6), using an eligible human approver’s authenticated UI/CLI request with current read access to the source/target PR and the rule-defined approval authority. Each decision is tied to its PR’s `repo_id` and records the exact `source_sha` the approver saw for that repository. That SHA is immutable review evidence, not by itself an approval-validity rule. No new reviewer-request/result linkage or provider-execution approval path is part of the MVP. Ordinary agent review text is conversation output and never an implicit decision. Org-admin rule administration remains distinct from workspace content writes.

**Open approval-validity policy:** A decision records the exact SHA reviewed for each repository. When that SHA still matches the current source SHA, the approval will likely remain valid, provided the other approval requirements are met. A mismatch does not automatically invalidate the approval: additional checks, still to be specified, will determine whether a decision continues to count after a source-head change. Specify those checks for each repository in a multi-repository workspace before implementing P6 merge authorization or its changed-head pass/fail tests. The merge operation still pins its own source and target OIDs for retry and provider preconditions (§10.6); those operation inputs are separate from the SHA recorded on a decision.

### 10.4 Roles and login

Org roles `owner|admin|member|viewer` and the org visibility/invite read model are kept. `workspace_members` grants read access only; `workspaces.owner_user_id` is the sole human writer. Org admins may read any workspace and transfer ownership to any current eligible same-org non-viewer member, including themselves, but must take ownership before writing. The workspace owner can transfer to any current eligible same-org non-viewer member. Read access includes authorized durable Git/metadata browsing, clone/fetch and forking into a new owned workspace; it excludes all live source VM access and preview operations; the capability matrix in §5.1 governs all routes. Per-user scope grants, workspace permission overrides and workspace mutation policy are dropped. RLS tenant isolation stays. Platform login is GitHub in the SaaS; self-hosted installations add Microsoft Entra (§16.3). `user_scm_connections` keeps GitHub and GitLab repository credentials for publish and PR operations. Operator permissions (who creates organizations) are not part of this work.

### 10.5 Removed

`approval_definitions/configs/requests/statuses/review_runs`, `merge_evaluations`, `agent_approval_handoffs`, `job_merge_runs/artifacts`, `workspace_pull_request_events` and `_provider_repos`, coordinated repo publication, workspace merge / rebase-merge / change-graph services, stages and merge-target columns, the non-GitHub login adapters (Entra returns for self-hosted only).

### 10.6 The merge operation

`POST /pull-requests/:id/merge` is the only path for user-requested protected-ref changes. Repository bootstrap and provider imports are separate API-only paths (§5.2, §5.6); a workspace fork never rewrites an existing protected ref. Merge is a persisted, resumable operation with one identity (`merge_op_id`) and pinned inputs kept until the operation is resolved; a retry of an unresolved operation never re-pins.

1. **Pin.** If the PR has an unresolved operation (`pending` or `provider_merged`), resume it at the step its state indicates; otherwise, under a per-repository lock that also serializes inbound fetches (§5.6), read the source and target OIDs from the mirror and store them with a new `merge_op_id` as `merge_source_sha` and `merge_target_sha`, `merge_state=pending`.
2. **Authorize.** PR is `open`; the caller may merge; evaluate the approval rule using each decision’s recorded repository/reviewed SHA, the operation’s source OID, and the approval-validity checks to be defined in §10.3. A matching SHA will likely leave the approval valid if the other requirements are met. A difference alone does not invalidate it. P6.2 requires the additional changed-head checks before this authorization step can be implemented.
3. **Mergeability.** Fast-forward or clean merge of source onto target, computed on the bare mirror without writing refs.
4. **Provider-connected target.** Republish the source at `merge_source_sha` if `published_sha` differs; call the provider merge API with the expected source SHA; on success record `merge_result_sha` and the durable `merge_state=provider_merged`; fetch the target from the provider into the mirror under the same lock (the mirror never computes its own merge commit for a provider-backed target); record `applied`, `status=merged`, `merged_at`, `merged_by`. An import failure leaves `provider_merged` and is retried. Ambiguous replies are reconciled on retry by reading the provider PR: attribute a remote merge to this operation only if the provider reports the pinned source as the merged head; if the head changed, or it merged at another head, record `failed` for a re-run with fresh inputs.
5. **Local-only target.** Compute the merge commit on the mirror, persist its OID as `merge_result_sha` before touching refs, then in **one ref transaction** (`git update-ref --stdin` with `start`/`prepare`/`commit`) compare-and-swap the target from `merge_target_sha` to the result and create `refs/g5/merges/<merge_op_id>` at the result. On recovery, the receipt ref proves application whatever the target holds now (a later fast-forward or rewrite of the target does not hide it); a missing receipt with a target that is neither `merge_target_sha` nor the result means another writer moved the target before application, and the operation records `failed` for a re-run with fresh inputs. Receipt refs are pruned when the PR closes or 30 days after `applied`.
6. **Failure.** Terminal `failed` is recorded only for a known rejection or conflict before anything was applied. Once the provider has merged, or the receipt ref exists, the operation can only progress to `applied`. There is no rollback because nothing that was applied needs undoing.

PRs may also target another workspace’s branch; those targets are not protected, so the operation follows step 5 and skips the provider. Updating that target requires its current workspace owner’s authorization; source ownership, read access or org-admin status alone does not grant target write access. Recheck the target owner under the target workspace’s mutation/transfer barrier before the ref transaction so an in-flight merge cannot bypass a transfer.

The merge receipt proves this operation's Git transaction applied; it does not prove the target still has that history. If a later permitted rewrite/import removes the result, retain the applied audit and surface current ref divergence rather than reapplying the old operation. Neither present ancestry nor a prewritten merge_result_sha substitutes for the receipt across a Git/Postgres crash window.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Agents forget to push and a host is lost | Profiles say push when a unit of work is done; the nudge before every deadline-bound teardown; the loss is bounded to the last receipt and shown, never silent |
| Two forks pass a name check, or one creates only part of the repository vector | Pending/aborting fork manifests are durable claims. Canonically locked repo rows plus a fresh READ COMMITTED query serialize overlapping exact/prefix names; all-member terminal transitions and late-writer fencing retain claims through recovery. Git proof/CAS and admission prevent a usable partial destination (§5.8). |
| A flush publishes a partial multi-repo cut | Immutable per-flush refs plus a receipt completed only after the API verified every ref; consumers read receipts only (§5.4) |
| A live flush cuts a moving tree | Quiescence: module and file-mutation admission closed and drained, bounded runs ended or interrupted; concurrent writers are recorded, and an exact fork closes terminals/previews with owner consent (§5.4) |
| A message is marked delivered before the provider received it | `delivered` follows the adapter's `input.accepted`, never the module's `started` disposition (§8.1) |
| A native request outlives its process | Retire its process channel; preserve confirmed deferred questions for native restoration, while permission requests end (§8.4) |

Post-MVP: P8.14. |
| A superseded VM reconnects and keeps writing | Incarnation fence at every boundary (including the proxies, post-MVP, P4.12); reconnect kills stale VMs (§6.4) |
| A cancelled start launches after journal pruning | Dispositions are a separate small table retained for the incarnation (§7.5) |
| An unconfirmed start is stranded by incarnation loss | Loss settles every intent bound to the lost incarnation (§7.5) |
| A late native answer restarts cancelled work | Answer delivery cannot wake; invalidate under the same task/cancel/continuation lock (§7.2, §8.4) |
| Two attempts on one VM collide in the timeline | Event keys and watermarks carry the attempt (§7.5) |

| A crash between a command and its outcome | Two-phase invocation, journaled events, retained outcomes, reconnect reconciliation (§7.5) |

| Backups restore a database whose git objects are gone | Backup barrier across Postgres and the git store (§16.4) |

| Codex exec lacks native interactive input | Noninteractive MVP policies only; no question/approval UI or MCP fallback; scheduled stdio app-server migration (§17.2) |
| A non-owner reaches preview or another live source route | Owner checks across task/CLI/module/relay and Git-only routing across all read siblings; close streams on revocation |


| A preview modifies tracked files | Profile contract only in the MVP; Changes and flush expose/capture the edits; a discard overlay is deferred |
| The owner is unavailable | An org admin transfers ownership; live pairing requires transfer or a fork |
| A transfer changes the owner before old work stops | Persisted stop barrier, flush, host exit/release, then atomic owner/audit commit; abort on flush failure |
| A provider process never exits | No default time limit after input acceptance (§8.3); the owner's Stop or Cancel (SIGINT then SIGKILL), an explicitly requested wall-clock limit, `max_turns`, the output bound, or a VM stop including daily host rotation on cloud hosts |
| Session-file restore fails | Ordinary turns reconstruct from delivered history; a deferred native answer fails explicitly without a replacement prompt (§8.4–§8.5) |
| Several agents in one folder overwrite each other | By design; agents are told; the UI notices |
| Owner force-push discards an unseen commit | Profiles require `--force-with-lease`; only laptop-versus-VM races can hit it |
| Approval, publication and merge drift apart | One pinned source OID; provider merge with expected SHA; receipt ref for local merges (§10.6) |
| An event is lost after a ref update | Projections converge from authoritative OIDs (§9.4) |

Post-MVP: P8.14. |
| Isolated preview required but not provisioned | Accepted for the MVP as in the original: preview shares the platform's registrable domain, on a per-preview subdomain with the single-use handoff ticket, the `__Host-g5_preview` cookie and CSP when the host suffix is configured, and on the path relay otherwise (§6.8). Post-MVP: P8.13. |

## 15. Validation

The Rust end-to-end crate and the Playwright flows are pruned per removed feature and extended per PR with tests that fail without the new behavior and exercise the production boundary. Beyond draft 6's list, which stays in force where the mechanism is unchanged, this draft requires:

- **Workspace mapping and fork:** onboard multiple repositories with different protected/default source names and fork them into one workspace whose branch name is the exact user name in every member repo; reject an existing name in only the second/code/docs/provider repo with no destination refs created and a different-name field error. Test Git-invalid names and prefix conflicts, two concurrent forks with partially overlapping member sets, duplicate requests, changed source membership/access, crash after each member ref transaction and before workspace publication, resume/rollback of partial creation, and cleanup refusal if a created ref changed. No suffix or existing-branch adoption is permitted. Test direct user/incarnation push creation, missing-ref ensure/restore, rename/member-add and legacy create/clone paths cannot bypass fork; Fork and preview/chat use the same operation. Initial provider publication refuses a remote branch created after preflight.
- **Fork claim concurrency:** real independent database connections race overlapping `{A,B}`/`{B,C}` member sets, exact and slash-prefix names, and duplicate idempotency keys (a matching unfinished retry resumes itself; changed input fails; terminal replay does not require deleted historical repos). A waiter must observe the first committed claim in its post-lock query; disjoint sets and nonconflicting names remain allowed subject to existing workspace-name rules. Restart after claim commit/before Git, partial create, failed/ambiguous cleanup and delayed mutation after abort cannot lose or recreate a claim. Verify private-workspace claims still exclude conflicting requests without leaking private metadata; repository delete/import/bootstrap refuse conflicts; deletion that wins before repo-lock acquisition causes admission to reject the now-incomplete member set. No reservation table or timeout-based release is required.

- **Flush and receipt:** a shutdown flush of a two-repository workspace whose second push fails, and separately whose receipt commit fails, leaves the previous receipt as the restore point after a deadline-bound teardown and a cold resume, and the retained refs still resolve; an owner-authorized fork of a running workspace while an agent updates two related files is refused or interrupted per the quiescence rule and the fork restores a stable tree; a Save admitted just before a fork flush and released while the capture runs is waited for and the cut is consistent, also for delete and rename and across two repositories; both admissions reopen after a refused and after a failed live flush; a user stop whose flush fails leaves the VM running with admission reopened; a drain whose flush fails proceeds at the deadline and records the loss; pruning keeps the two newest complete receipts and their objects; a receipt whose ref the API cannot verify is never completed.
- **Restore:** committed-but-unpushed commits on a clean tree restore with the branch ahead of origin; local commits plus dirty edits restore both; a tracked file matched by `.gitignore` with a dirty edit is captured and restored, including a same-second same-size edit; a warm root whose file contents changed after the last receipt with the same `HEAD`, dirty paths and sizes attaches with exactly the content a cold attach gives; provider session files are never captured by a flush or a native `git add -A`.
- **Host protocol and lease:** hello, accept and reject with an unsupported version (the host self-drains and keeps its VMs); a `vm.start` whose result is lost is resolved by the inventory; a `vm.event exited` survives a tunnel drop; an unrenewed server-side lease expires and marks the row failed, and a replacement is placed only after; a command delivered after its deadline is refused; a stale incarnation is refused on every command and stream, while a draining one is accepted; two incarnations of one workspace on one host are refused with `workspace_busy`; `vm.stop` for a superseded `vm_id` the host still runs stops it and frees the slot while `vm.start` and stream opens for it are refused; the row stays `stopping` until the host's exit and a lifecycle restart after `vm.stop` re-sends it and then releases; a restart of the workspace right after a stop never sees `workspace_busy`. **Post-MVP (P8.14, P4.12).** A delayed renewal reply followed by a partition expires the host before the server grant, the proxy refuses traffic and a replacement is placed only after (P8.14); a stale incarnation is also refused on every proxy request (P4.12).
- **Credentials:** after transfer the next dispatch uses the new owner's key; the old incarnation's token is rejected at every boundary.
- **Post-MVP (P4.12).** **Proxies:** every session uses the incarnation owner’s provider account, never a session creator or preview launcher; an untagged request or missing owner grant is refused; tags meter usage without selecting another user’s credentials; same-owner key rotation takes effect on the next request; no credential appears in provider environments; after transfer old grants fail and new-owner turns bill the new account; internal git pushes succeed without a token in the provider process.

- **Modules:** `modules.invoke` returns the right disposition for started, running, finished and cancelled identities; the module input cannot carry `argv` or host paths; a module exceeding its limits is stopped with a definite outcome; catalog integrity is probed.
- **Dispatch and events:** loss before delivery and after spawn with lost reply settles each attempt; same-incarnation idempotent retry; durable cancel followed by delayed invoke never starts work. Test `A → B` dependencies through A’s live native question, held suspension, drain/rollout continuation, retryable loss and cancellation: task/session/job identity stays fixed, B waits until final A success and dispatches once. Delayed old-attempt events/acks cannot mutate the current attempt. Job aggregation never completes while a child has a pending continuation.
- **Native questions and permissions:** pinned Claude initial stream-json input plus native `AskUserQuestion`, multiple options, answer, permission allow/deny, duplicate reply, malformed/wrong ID, timeout, cancellation, lost acknowledgement, process exit and transfer races. A live answer travels through native control response; stdin remains open only for protocol traffic. Ended process-bound requests are read-only history. Confirmed deferred questions have no automatic expiry, survive Stop/Start and transfer, and deliver through the restored native callback without a replacement prompt; test the same tool ID, mismatches, answer-versus-Stop and atomic reply/input evidence. Answers never wake compute, and unanswered questions block ordinary Continue and queued messages. Codex MVP rejects interactive policy, registers no custom ask-user tool and treats prose questions as ordinary output. Later app-server stdio gates cover native requests/approvals and thread/turn resume before enabling them.
- **Removal boundaries:** workspace search UI/shortcuts/routes/index workers/embeddings/data/settings/tools/tests are gone; retained chat-history search, editor Find, agent-local search and docs/ontology reads/convergence still pass. Commit UI/API/module operations and Flush now/manual flush endpoints are absent, and `explicit` requests are rejected; shutdown/fork still restore uncommitted work without advancing the working branch. Unrelated MCP registrations and tests remain.
- **File writes and attachment:** no-VM Save/upload/delete/rename and user receive-pack are rejected without boot; owner explicitly resumes cold, editor reloads, then matching association/hash succeeds. Test mismatched branch/hash, stale incarnation, stop/transfer between authorization and mutation, stale queued Save, and sibling docs/ontology routes. Non-owner writes are denied regardless of VM state.
- **Shared sessions and inbox:** typed human and templated workflow starts both create `agent` tasks using the same tables/adapter, explicit policy and transcript. Same-session launches serialize across both live and held tasks, so a queued message cannot bypass a hold; distinct sessions run concurrently. Input can queue/edit/withdraw until frozen; transport acceptance differs correctly for Codex EOF versus Claude open control stdin. Pre-acceptance failures requeue; uncertain handoff is labeled and reconciled without claiming exactly-once model side effects. After terminal completion, follow-up creates a new task in the same session. Transfer rebinds credentials for all origins without an origin-based permission escalation.

- **Governance:** PR creation refuses dirty/unpushed state without Commit and push all, hidden commit or flush-to-branch publication; existing-commit Push and agent checkpoint work. Preserve OID-pinned approval and local/provider merge recovery, including a target advanced after the operation receipt.
- **Backup (self-hosted phase):** a workspace deleted or rewritten during a backup is either wholly in or wholly out of the restored installation; every restored receipt resolves to retained objects.

### 16.2 Self-hosted installations: what is retained

The self-hosted control plane on pre-provisioned VMs is a retained deployment target. The bundle under `infra/self-hosted/` (installer, Compose stack with `postgres`, `db-migrate`, `g5-api`, `g5-api-indexer`, `edge`, and the worker service, the `just` operator runner with `setup`, `up`, `logs`, `backup`, `restore`, `upgrade`, `down`, the license and registry-token flow, TLS overlay, starter repositories), the worker-host installer (`install.sh --worker-host`, `g5-workerhost.sh`, which runs the host container with `/dev/kvm` and `G5D_GUEST_HOST_ALIASES` / `G5D_GIT_HTTP_ALLOW_HOSTS`), the Azure canary workflow (a VNet with a private DNS zone so the worker VM reaches the control plane at its private address, a nested-virtualization worker VM, backup and restore, down and up, upgrade), and the bundle contract tests are all on `main` and byte-for-byte the original G5 assets apart from the GitHub-only login change and, since 2026-10-09, the Redis removal (G5Labs/G5-Lean#405). `SELF_HOSTED=true` and `ENABLE_CLOUD_FEATURES=false` keep the SaaS-only routes off. The general deployment target remains. Search-specific services, worker duties and configuration are removed by the search-removal MVP gate across SaaS/dev/self-hosted manifests; shared document/ontology projection duties remain available. The later self-hosted phase brings the remaining bundle to the workspace-VM model.

### 16.3 Gaps against this design

| Area | State on `main` | Gap | Phase |
|---|---|---|---|
| Worker host on a pre-provisioned VM | `g5-workerhost.sh` starts a per-task worker container with poll and claim | The container must run `g5d host` with the `ctl` tunnel, slots, retained roots and the host proxies; the registration token flow stays; the Compose stack's in-box worker service becomes a `g5d-host` service with `/dev/kvm`; production workspace execution requires KVM and the enforced host egress/process boundary; remove the old acknowledgement-based process fallback. These are scheduled as a later phase (§13) and change nothing in the MVP's design.

### 16.4 Backup consistency

Postgres rows and git objects describe one state only when they were captured under one barrier. Restoring a database snapshot next to a git store captured later can name receipts, branches or merge results whose objects were pruned or rewritten in between; projection convergence cannot recreate missing objects. The barrier above makes both stores quiescent for the window; the alternative of pinning the ref set at the database snapshot and retaining it through the backup is the implementation-time choice if the window is too long for large stores.

## 17. Implementation-time choices, deferred items, open questions

### 17.1 Implementation-time choices

- The journal file format, the disposition table's storage and the disk budget on the VM; the event payload shapes for `branch.updated`, `flush.completed`, `file.changed`.
- `quiesce_secs`, the retry and backoff schedules for flush pushes, receipt completion and merge imports, and the default drain deadline.
- Native-response deadlines, bounded protocol buffers and response-delivery reconciliation; zstd level and caps for session files. Unrelated MCP tools retain their own ordinary tool timeouts.
- The `configs` shape for feature flags; whether `projection_state` is one table or a column set on each projection.
- Retained-root retention as a fixed value or an org setting (default 24 h); one version number or two for the host protocol and `VmSpec` (default: two).
- Whether the passt door can be mapped to a per-VM host address so the proxy secret becomes defense in depth only. This choice is post-MVP and belongs to P4.12.
- Crate consolidation targets; the list of `.g5/` runtime subdirectories in the excludes file.

### 17.2 Deferred items

- **Generic provider-initiated platform writes.** Provider/MCP/shell PR/task/platform mutations require a separately scoped authenticated transport proposal; they are not an MVP gate. Trusted dispatcher lifecycle and the bounded platform-shipped bootstrap graph operation remain specified service paths. Ordinary owner UI/authenticated laptop CLI are separate.
- **User-erasure and Git-history policy/automation.** Workspace + Platform own a decision and scoped follow-up in P8.8 security audit before an erasure feature is enabled. Decide retained organization Git authorship/content, private provider artifacts and backup/retention behavior explicitly; rewriting an author ID is not erasure. Existing owner-departure/demotion guards and tenant resource offboarding remain required.

- **Codex app-server migration (scheduled later phase).** P3.7 moves the adapter to `codex app-server` over stdin/stdout for native questions and approvals, with generated-schema/pin probes, owner-authorized replies, shared session/continuation semantics and transport-loss gates. MVP remains `exec --json` without interactive input or fallback.
- **Session-resident Claude process** behind `agent.turn` (steering, in-band interrupt, live model and permission changes), with the gates of §8.7; the Claude Agent SDK stays unused.
- **Document-only CRDT** for real-time co-editing behind the Save API.
- **Org-level read-only provider grants** for private git dependencies, and the `gh` credential path with a per-VM CA.
- **Secret files and secrets-manager integration** beyond environment variables. Per-user task-secret isolation within one workspace is unnecessary under the single-owner model.
- **Preview write isolation** through a disposable overlay that discards preview writes.
- **Multi-replica API**: moving the tunnel registry and event bus to a shared store with a centralized lease (amended 2026-10-09: Redis was removed, G5Labs/G5-Lean#405; the multi-node design is G5Labs/G5-Lean#402).
- **A CI service outside workspaces** (a read-only clone of the workspace answering API calls at a git version).
- **Snapshot of the tree to object storage** as a mitigation for flush failure.
- **Dedicated review/explainer workflow and advanced fork products.** Reviewer requests, automatic children, source-versioned returned results/replies/API/CLI/UI, special producer capture/publication and completion cleanup are outside the backend-refactor MVP and have no implementation PR in this plan. Ordinary collision-checked workspace forks, shared conversations, task history and manual authorized collaboration remain. Future scope requires a separate product decision.
- **Transfer preserving a live VM for debugging.** Discussed and deferred; no admin flag or security bypass is introduced.
- **Host-side credential custody (P4.12).** Host-held provider keys, the per-VM `g5-llm` listener, the git and platform brokers, the bootstrap capability, `credential_grants` with `grants.resolve` and `vm.grants.update`, and request-id metering; see the [MVP scope amendment](v9-mvp-scope-amendment.md) §6.
- **Host registration exchange (P8.10).** The one-use registration exchange, the renewable host credential, credential generations and the runtime identity hash; see the [MVP scope amendment](v9-mvp-scope-amendment.md) §6.
- **Guest egress enforcement, network mode and runtime process isolation (P8.11).** nftables per-UID egress with the org egress policy, passt as the only network mode with pinned DNS, and the separate trusted-runtime UID with rootless Docker; see the [MVP scope amendment](v9-mvp-scope-amendment.md) §6.
- **Git object views (P8.12).** Authorized object views, scoped receive-pack, view budgets and the host-only git-view artifact; see the [MVP scope amendment](v9-mvp-scope-amendment.md) §6.
- **Preview origin isolation (P8.13).** Preview on a separate registrable domain, `PREVIEW_ORIGIN_UNCONFIGURED` and removal of the same-origin fallback; see the [MVP scope amendment](v9-mvp-scope-amendment.md) §6.
- **Operational policies (P8.14).** The host lease timer and the deploy guard, image and fleet policy, configuration authority, retention, admission bounds, GC and the backup barrier; see the [MVP scope amendment](v9-mvp-scope-amendment.md) §6.

### 17.3 Open questions

- Confirm the reading of the ontology decision in §2 (developed without the gate and outside the MVP acceptance, code retained).
- Whether general mid-turn human steering or a session-resident Claude process is useful after the native one-turn control protocol ships; native question transport is already decided, not an open question.
- Agent-initiated workspace creation as a way to attach compute (not offered here).
- Share-link presentation and discoverability within the org read-access model; ownership transfer semantics are settled in §5.8.
- Autosave default/cadence; v9 retains explicit Save and optional autosave-on-blur until decided.
- Delivery grouping and development mocks at the execution-plan checkpoint (§13); neither changes production acceptance gates without a new decision.
- Validate the documented v9 defaults (durable snapshot selection, ordinary lifecycle defaults) with UX/implementation evidence; their current contracts are explicit in §5.9 and §9, not unspecified placeholders.
