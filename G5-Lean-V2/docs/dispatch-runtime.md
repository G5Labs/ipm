# Workspace dispatcher runtime

`g5d dispatch` runs the guest file, port, terminal, inspection and private lifecycle surface, plus the declared-module runtime: the pinned catalog, `modules.*` invocation with durable dispositions, the per-execution event journal with replay and acknowledgement, the native-reply delivery primitive, module diagnostics, and the built-in `workspace.changes`, `workspace.bootstrap` and `workspace.diagnostics` modules. The authenticated host connection is its sole caller; the control-plane Workspace Runtime facade performs current owner authorization before routing requests through that host. This crate is not a VM isolation backend.

## Startup configuration

The host supplies these environment variables. Missing or malformed required values fail startup. Tokens are omitted from configuration debug output and are never written into the installed Git configuration.

| Variable | Contract |
| --- | --- |
| `G5D_WORKSPACE_ID` | Required workspace UUID. |
| `G5D_VM_ID` | Required current incarnation UUID. |
| `G5D_EPOCH` | Required positive incarnation epoch. |
| `G5D_OWNER_USER_ID` | Required owner UUID, fixed for this incarnation. |
| `G5D_WORKSPACE_HOSTNAME` | The workspace name as a hostname label (lowercase `[a-z0-9-]`, at most 63 bytes). The guest bootstrap, not the dispatcher, consumes it: it sets the kernel nodename, writes `/etc/hostname` and adds a `127.0.1.1` entry to `/etc/hosts` before the dispatcher starts, so terminal prompts, `hostname` and `uname -n` name the workspace. Absent means the label `workspace`. Refreshed on every start; a rename takes effect at the next start. |
| `G5D_OWNER_GIT_NAME`, `G5D_OWNER_GIT_EMAIL` | Required workspace-owner commit identity. They are host runtime inputs, not session or preview launcher inputs. |
| `G5D_WORKSPACE_TOKEN` | Required workspace JWT. The dispatcher checks its `vm_id` and `exp` after receipt from the authenticated host; signature and authoritative current-custody validation belong to the host/control plane. |
| `G5D_DISPATCH_TOKEN` | Required independent 32-byte listener secret encoded as 64 hexadecimal characters. This is distinct from the renewable workspace JWT. |
| `G5D_API_URL` | Required internal control-plane HTTP(S) origin, without a path, credentials, query or fragment. |
| `G5D_DISPATCH_PORT` | Required nonzero guest TCP port. The listener binds all guest interfaces; this is a private host-to-guest endpoint. |
| `G5D_LEASE_TTL_SECS` | Lease duration, default 60 seconds, range 1–86400. JWT expiry supplies an additional upper bound. |
| `G5D_PTY_REATTACH_GRACE_MS` | Detached browser terminal retention, default 15,000 ms; supplied values are clamped to 100–60,000 ms. Invalid values use the default. Parsed once at dispatcher startup. |
| `G5D_MODULE_CATALOG_HASH` | Required 64-hex SHA-256 pin of `/opt/g5/modules/catalog.json`. The host passes the bundle's `catalog.sha256`; a missing pin, a mismatch, a missing or a malformed catalog fails startup before the listener exists. There is no unpinned mode. |
| `G5D_BOOTSTRAP_BROKER_URL` | Optional HTTP(S) origin of the host's exact-route bootstrap broker (Agent API §6.6). Absent means the `workspace.bootstrap` supervisor cannot submit a task graph and refuses that delegation with `BROKER_UNAVAILABLE`. |
| `G5D_SECRET_*` | Optional additional secret values. Every configured secret value — the workspace token, every renewed lease token, delivered supervisor capability secrets, the listener token and these — is redacted from module logs, events, outcomes and diagnostics regardless of which key carried it, including values split across output chunks. A module's log reader picks up values added while it runs. |
| `G5D_MODULE_UID`, `G5D_MODULE_GID` | Optional unprivileged identity the host provisioned for repository-facing code (`0` is refused at startup: root is never handed to repository-facing children); when set, every non-builtin module process, every built-in git child (including cleanup) and every `workspace.bootstrap` repository step runs under it, while the platform-shipped bootstrap supervisor keeps the dispatcher's identity (and is not dumpable), so a step can neither inspect the capability-holding supervisor nor read dispatcher-private state. `/var/lib/g5d` is traversable (`0711`) so that identity can read the installed Git configuration and excludes, while the journal, watermarks, dispositions and credential helper inside it are owner-only. Without them the guest runs modules under the dispatcher's own identity; the account itself is a VM composition property of the host boot. When they are set, the host hands the materialized `/work` tree to that identity before boot and the dispatcher hands it the provider home (`/home/agent`, mode `0700`) at startup: OCI extraction never preserves image ownership, so nothing else makes those trees writable by the module uid. |

The production workspace root is `/work`, provider home is `/home/agent`, and dispatcher state is `/var/lib/g5d` (`journal/<exec_id>`, `journal/.ack/<exec_id>` watermarks and `dispositions/<exec_id>` beneath it). The declared-module catalog is read from `/opt/g5/modules/catalog.json` in the host runtime bundle mounted at `/opt/g5`; it is exported next to `catalog.sha256` by `infra/docker/Dockerfile.g5d`'s guest-artifacts stage and staged by `scripts/stage-local-worker-runtime.sh` under `runtime/modules/`, never taken from the repository-selected guest image. The host writes `/work/.g5/layout.json` before startup:

```json
{
  "repos": [
    {
      "repo_id": "00000000-0000-4000-8000-000000000001",
      "root_path": "code",
      "git_url": "https://api.example.test/git/00000000-0000-4000-8000-000000000001",
      "branch": "feature-name",
      "base_branch": "main",
      "object_format": "sha1"
    }
  ]
}
```

The layout contains 1–256 member repositories, at most 1 MiB of JSON. IDs and normalized relative roots must be unique; member roots cannot overlap or traverse `.git`, `.g5` or symlinks. Every member uses the same working branch. Each `git_url` must exactly equal the configured internal origin plus `/git/<repo_id>`. `object_format` defaults to `sha1`; `sha256` is also supported for blob hashing. The dispatcher consumes already-materialized member roots and does not create workspace branches or infer owner identity from repository configuration.

## Host wire protocol

The host sends the raw 32-byte listener token first, within five seconds. A wrong or incomplete token closes that connection. Up to 32 pending handshakes are processed concurrently so one silent peer cannot block host authentication. Successful authentication starts `g5_internal_api::stream_mux` framing with the host as initiator. The dispatcher accepts `Rpc`, `Http` and `Pty` streams. The first `Rpc` stream owns live notifications; additional RPC streams serve requests. A newly authenticated connection replaces the old connection and its watches; one accepted before the connection last installed is closed instead, so a probe the host abandoned before reaching ready cannot finish its handshake late and displace the live connection. An `Http` stream starts with a two-byte big-endian guest loopback port, followed by raw bidirectional bytes. Only a scanned listener or a service port declared ready by the preview module is admitted.

An API owner WebSocket opens a `Pty` stream with newline-delimited JSON containing `type: "open"`, dimensions, optional `terminal_id`, optional byte `offset`, and owner secrets. The dispatcher replies with a newline-terminated `opened` control message containing the terminal ID, `reattached`, replay `offset`, and `reset`, or a `rejected` message with a `reason`: `terminal_unavailable` when the identity cannot be attached, or `secrets_invalid` with a `detail` sentence when the owner secrets violate the shared exportable-environment policy (`g5_contracts::types::task_env`: uppercase names that are not platform-reserved, values of at most 64 KiB without NUL, at most 128 entries and 256 KiB serialized; the `open` line is bounded by that budget plus headroom). The API admits the same set before opening the stream and answers the browser with the same `rejected` line itself. Raw PTY bytes follow the control line. The browser sends newline-delimited `input`, `resize`, and `close` controls; a transport close without `close` detaches the session. A reconnecting panel sends the number of output bytes it has displayed. When that offset is still in the bounded replay buffer (4 KiB by default), the dispatcher sends only unseen bytes and the panel keeps its screen. If the offset is absent or no longer retained, `reset` is true and the dispatcher replays the available tail; the browser clears a reattached screen before applying it. Detach retains the PTY for `G5D_PTY_REATTACH_GRACE_MS` before cleanup. `Pty` and `Http` streams use the admission stream slot, separate from the operation write slots, so an idle browser stream does not block a live fork.

### Terminal close reasons

Every terminal close is logged with one of these `close_reason` values:

| Value | Trigger |
| --- | --- |
| `workspace_stop` | The stop RPC shuts down registered sessions, including detached ones. Admission cancellation also closes any terminal opened after the shutdown snapshot; closing an already removed session is harmless. |
| `fork_interrupt` | An interrupting live fork closes terminals through the same two-phase lifecycle path. |
| `connection_end` | Host connection replacement or loss closes attachments still owned by that connection. |
| `drain_timeout` | A connection stream does not finish its bounded drain; the fallback closes only that connection's attachments. |
| `client_close` | The browser sends a terminal `close` control. |
| `stream_failure` | Control parsing, input, resize, PTY read, or opening replay delivery fails. |
| `process_exit` | The shell exits and its PTY reader reaches EOF. |
| `detach_grace_expired` | The transport detached and no new owner claimed the terminal within the configured grace period. |
| `reattach_write_in_flight` | A new owner arrives while the old owner has an interactive write in flight, so that identity is retired. |
| `retiring_retry` | The manager retries a previously failed terminal shutdown before a later registration. |

When the RPC stream opens, the dispatcher emits `runtime.ready` with `workspace_id`, `vm_id`, `epoch`, `module_catalog_version` and `module_catalog_hash` (from the loaded, pinned catalog), `dispatcher_contract_version` (`1`) and `pending_outcomes` (everything `outcomes.pending` would return, counted: journaled terminal outcomes not yet acknowledged plus finished outcomes the journal could not persist, so a reconnecting host that sees zero can safely skip the call).

Every inbound method request carries a `params.context` envelope:

```json
{
  "jsonrpc": "2.0",
  "id": "read-1",
  "method": "fs.read",
  "params": {
    "context": {
      "workspace_id": "00000000-0000-4000-8000-000000000002",
      "expected_vm_id": "00000000-0000-4000-8000-000000000003",
      "expected_epoch": 1,
      "actor_user_id": "00000000-0000-4000-8000-000000000004",
      "deadline_ms": 1800000000000,
      "idempotency_key": "read-1"
    },
    "repo_id": "00000000-0000-4000-8000-000000000001",
    "path": "src/main.rs"
  }
}
```

`deadline_ms` is an absolute Unix time in milliseconds and must be in the future and no more than 24 hours away. The RPC response wait is bounded by that deadline; a file mutation checks it again before entering the filesystem operation. An admitted operation that has already entered filesystem I/O retains its permit and completes its outcome even if the caller times out or disconnects, so admission close still drains it. The idempotency key is required and limited to 256 bytes. Public live operations require the exact configured `actor_user_id`; `runtime.inspect.summary`, `modules.logs`, `modules.events`, `modules.history`, `diagnostics.capture` and `diagnostics.probe` also accept a separate facade-validated `inspection_grant_id` without an actor or lifecycle marker — bounded, redacted reads only, never invocation, cancellation, files, ports or terminal. Private `health`, admission, `modules.input.respond`, `events.replay`, `events.ack` and `outcomes.pending` operations instead require `lifecycle: true` and omit the actor. The lifecycle marker is an assertion over the authenticated host/facade transport, not a public capability or bearer credential. Workspace, VM and epoch mismatches return `STALE_INCARNATION`. Requests without a JSON-RPC ID do not execute operations. Each connection admits at most eight simultaneous RPC handlers, counted independently of background tasks; excess requests return `TOO_MANY_REQUESTS` (429). Completed or cancelled handlers release capacity immediately.

File paths are normalized member-relative paths, confined using pinned member descriptors and no-symlink component traversal. Directory listings omit symlinks and special entries such as Unix sockets; direct reads and stats of those entries return `PATH_FORBIDDEN`. Absolute/parent paths, `.git`, runtime artifacts and symlink traversal are refused. Version conflicts return code 409 and current hash/size, without embedding file content. Create-if-absent and destination refusal apply at the filesystem boundary. Atomic sibling staging protects file replacement from partial writes and avoids modifying other hard-linked files. Native owner processes still share the same tree and retain the design's concurrent-edit semantics. Admitted mutations retain their idempotency outcomes in an incarnation-local cache of at most 1024 entries for five minutes after completion, including through peer replacement. An authorized retry with the same operation, parameters and key returns the recorded result even with a refreshed deadline or closed admission. The context is validated on every retry but excluded from the operation digest; reusing the key for a different operation or payload fails. The drain permit remains held until the outcome is recorded. A refusal before filesystem entry, including an expired queued request, is not cached and can be retried with a refreshed deadline. When all 1024 replay slots are occupied, new mutations receive `TOO_MANY_REQUESTS` (429) with `retry_after_ms` and `limit`; completed replays still work. Unexpired outcomes are not silently evicted: a replayed delete could otherwise remove a newly recreated file with identical bytes and therefore the same expected blob hash. This is explicit bounded backpressure; callers must honor the retry delay.

Native watchers hold directory descriptors, register nonrecursive physical directories and revalidate event parents before disclosing paths. A typed native file removal emits its concrete member path when the parent descriptor still matches; uncertain removals request a rescan. They do not follow symlinks into other roots. Ordinary file creation, deletion, content changes and file renames do not rebuild the directory registration tree. Directory topology changes are coalesced in fixed 25 ms windows; after reconciliation, a subscription rescan covers writes made while new directory watches were being installed. A failed refresh keeps the connection in a degraded state: the dispatcher retries reconciliation after a one-second delay and emits subscription rescan notices for each attempt until coverage is restored, even when no native events arrive from an unregistered subtree. Incoming topology events do not accelerate those retries, and successful reconciliation clears the degraded state. Native callback loss also triggers topology reconciliation. Each native notification emits a given path once per repository and subscription, including when several macOS ancestor registrations match it. Each connection has at most 32 subscriptions and 10000 physical directory registrations; traversal is bounded to 64 nested levels and 10000 entries per directory. Both callback and delivery queues hold at most 256 events. Exceeding initial traversal limits refuses the watch; later overflow, topology errors and unverified paths emit `rescan_required` for the original subscription. Git-ignored product directories remain observable within these bounds; only the declared platform exclusions are omitted.

All other inbound methods return JSON-RPC `method_not_found` (`-32601`), including `workspace.status.get`, `git.*`, `proc.*`, `terminal.*`, `preview.*`, `workspace.flush` and session-file methods. Workspace status belongs to the control-plane `GET /workspaces/:id/vm` surface.

The dispatcher sends a `lease.renew` request around half of the remaining bounded lease with JSON-RPC ID `lease:<seq>` and `{workspace_id, vm_id, epoch, seq}`. The host responds using that ID and `{seq, token, lease_ttl_secs}`. Installation requires an outstanding sequence newer than the last installed sequence, the same `vm_id`, a live current lease and valid TTL/expiry. Up to 128 outstanding departures are retained, so a slow reply remains eligible after a retry is sent; a full window pauses new requests without extending the lease or discarding still-valid replies. Replacing the authenticated peer abandons that peer’s outstanding requests and schedules an immediate fresh renewal, preserving the current token, sequence and expiry; it cannot revive an expired lease. Renewal time is bounded by request departure plus TTL, preventing delayed replies from restarting a full lease. Missing replies are retried without extending custody. Expiry closes mutation admission, rejects live operations and suppresses newly produced file and port notifications; authenticated health remains available. The host relays a renewal only when its `{workspace_id, vm_id, epoch}` is the incarnation the dispatcher connection is bound to and otherwise answers error 409 `STALE_INCARNATION`, which the dispatcher treats like any other refusal; the host still owns VM termination and authoritative lease enforcement.

## Declared modules

Callers name a catalog entry, an operation and typed input; they never supply argv, environment, cwd, signals or an entrypoint. A top-level key from the reserved set (`argv`, `args`, `command`, `cmd`, `env`, `environment`, `cwd`, `working_dir`, `signal`, `kill`, `pid`, `entrypoint`, `uid`, `gid`) in `params` or `input` is refused as `MODULE_CONTROL_OVERRIDE` before resolution; ordinary text values that merely contain those words are fine. Unknown modules and operations, an `input_schema` that does not match the operation's declared id, a malformed `grant`, and — for built-in modules — any input that does not deserialize into the operation's strict typed shape (unknown fields, malformed identifiers, undeclared probe or profile names) are refused before anything is reserved or spawned. `input.respond` is never an invokable operation.

**Catalog.** `bounded_run` entries require `wall_clock_ms`; `service` entries must not carry one; every limit is nonzero. The dispatcher hashes the catalog bytes at startup, compares them with `G5D_MODULE_CATALOG_HASH` (required: production startup always pins and compares; only test fixtures load a catalog without a pin), and reports the loaded hash in `runtime.ready`, `modules.list` and `runtime.inspect.summary`. The `module-catalog-integrity` probe re-hashes the mounted file so later tampering is visible without affecting the loaded catalog.

**Capabilities.** A manifest lists `requested_capabilities`; the facade-asserted `grant` can only narrow it, and an invocation missing any requested capability is `CAPABILITY_DENIED` with the missing names. A grant carrying `preview.service` authorizes `workspace.preview` only. `supervisor_capability` is accepted for the platform-shipped `workspace.bootstrap` only (`SUPERVISOR_CAPABILITY_SCOPE` otherwise) and must bind this exact task identity, module version, manifest hash, VM, epoch, workspace and the route `POST /api/internal/jobs/:job_id/tasks` with a 64-hex secret (`SUPERVISOR_CAPABILITY_BINDING` otherwise). The dispatcher stamps its configured broker origin into the delivered envelope; a caller-supplied `broker_url` is discarded.

**Execution identities and slots.** `exec_id` is the canonical `task.<uuid>.<attempt>.<vm_uuid>` or `operation.<uuid>.1.<vm_uuid>`; any other shape, and any identity minted for another incarnation, is `INVALID_EXEC_ID`. Every decision about an identity — invoke's disposition check and reservation, cancel, settlement — is serialised, so simultaneous duplicate invokes launch exactly once and a cancellation cannot slip between the check and the launch. Every bounded invocation takes the P4.2a admission permit before any slot is reserved (so `admission.close` refuses new module launches with `WORKSPACE_STOPPING` and drains the invocations already admitted) and one of the catalog's `bounded_execution_slots` (`EXECUTION_SLOTS_EXHAUSTED` with `state: busy` when none is free); a per-module `concurrency` limit applies too. Service lifecycles take no slot. The durable `invocation.started` event is written before anything runs; if the journal refuses it, the record, permit and slots are released and the identity is retryable. The validated actor is recorded in that event and in `modules.history`.

**Process runner.** A non-builtin entry runs its pinned entrypoint (`g5d` resolves to the running binary; catalog validation admits only `g5d`, an absolute path inside the read-only `/opt/g5` runtime mount with no `.`/`..` components, or — for built-ins — `builtin:<module_id>`, so nothing resolves through `PATH` or outside the mount; at launch the path is canonicalized and must remain below the canonical mount, so a symlink pointing outside it is refused and the canonical target is what runs) from the workspace root in its own process group, with a cleared environment plus the Native Git environment and `G5D_EXEC_ID`, `G5D_MODULE_ID`, `G5D_MODULE_VERSION`, `G5D_MODULE_OPERATION`, `G5D_WORKSPACE_ROOT`; no platform token or catalog pin is inherited. The invocation record — `{exec_id, module_id, module_version, operation, input, capabilities, supervisor_capability}` — is written once on stdin. JSON lines on stdout become journaled `module.<kind>` events (`kind: "outcome"` is captured as the result; other text is `module.output`); each structured event is held for at most 25 ms (an absolute bound from the moment it was read) so a secret split across the last string of one event and the first string of the next is masked in both before either is journaled or streamed; a trailing fragment that is an unresolved prefix of a secret when the hold expires (or when a frame without any text displaces the held event) is carried (and masked when it is two bytes or longer; a single byte stays as emitted so typed payloads are not mangled), frames without text neither continue nor break a carried chain, every decision (chains and the boundary with the held frame alike) is made on a frame's original text — a held frame's first and last leaves are kept as the module wrote them and rendered once when it leaves, with the union of every masked span: complete secrets in the original (overlapping secrets form one span, in leaves and in stderr alike; a run that keeps matching a self-overlapping secret is one mask and the stderr redactor never retains more than the longest secret's length or rescans what it masked), chain completions and extensions, and secrets spanning a boundary, so a boundary mask never hides a complete secret from the whole-value scan and an untouched leaf, empty ones included, leaves exactly as written — and every match counts at once (a pair that completes one secret and extends a longer one does both; two secrets spanning the same pair mask the union of their spans; every suffix that is a prefix of a secret is carried, not only the longest; a leaf that completes one secret still carries the prefix of another), the set of carried chains is never evicted (each is a distinct proper prefix of a configured secret, so it is bounded by the secrets' total length), literal mask text in module output is ordinary text, event kinds and object keys are redacted like values (a redacted key that collides with one already present is suffixed `#2`, `#3`, … in map order, which is sorted key order), and later fragments — the outcome frame included — that extend or complete a chain are masked, so no sequence of frames reconstructs more than one byte of a secret; stderr is redacted and retained as bounded logs. One wall-clock deadline covers the record handoff, the run and the final pipe drain; output and log bytes are counted as they arrive, so newline-free floods are bounded too. Every module declares `max_output_bytes` except `agent.turn`, whose output has no total cap; one stdout line over 1 MiB (`max_event_bytes`) ends any module's run. Wall clock (`timed_out`), `max_output_bytes`/`max_event_bytes`/`max_log_bytes` (`limit_exceeded`), and cancellation (`cancelled`) each stop the whole process group with a definite outcome; a module that crossed a limit and exited on its own is still `limit_exceeded`. After the module exits, whatever it left in its process group is stopped before settlement, and a pipe an escaped descendant still holds cannot hang the outcome (`failed` with `output_drain_timeout` after a bounded grace, with the readers aborted so nothing is logged after settlement). Built-in modules run in-process under the same wall clock and cancellation: every git child is supervised under the module identity, its output bounded by `max_output_bytes`, its group stopped and its pipes drained under a bound before the permit is released, and an interrupted rebase is aborted by an equally bounded child. Linux applies `RLIMIT_DATA` for `memory_mib`, `RLIMIT_FSIZE` for `disk_mib` and `RLIMIT_CPU` from the wall clock times `cpu_cores`.

**Agent turn execution.** `agent.turn` is the production provider lifecycle. The older `g5d-agent::runner` module now contains only provider wire adapters, event projection and session-file helpers; it has no separate process runner or settlement path. The dispatcher owns admission, cancellation and Linux descendant reaping; its deadline begins before Git input refresh and module handoff. The supervisor owns provider launch, protocol IO, event emission and outcome classification. Its `wall_clock_ms` begins before attachment preparation, native authorization and initial provider write. The effective attempt deadline is the tightest catalog, frozen policy and turn request bound; the dispatcher passes its absolute deadline to the supervisor and allows bounded cleanup and harvest grace after expiry. V1 has no separately requested provider-only timeout. A blocked write or terminal result before EOF cannot extend the deadline or prove success; cleanup has bounded grace after expiry and capacity remains held until reap. An agent turn's output has no cumulative limit (`g5.agents.output-bounds`): every event the supervisor projects is written, the catalog declares no `max_output_bytes` for `agent.turn` and refuses an entry that does, and a runaway turn ends only by Stop or a VM stop. Output is bounded per line and per event instead: provider stdout is assembled one line at a time under a 16 MiB line ceiling, a line past it is discarded to its newline with a `provider_line_skipped` notice, and every recorded event is bounded and masked before the cut (32 KiB inline tool input/output, native request payload and display at the API's 64 KiB per-field limit, 256 KiB final/thought text as serialized, each beside the digest of the full value and a `*_truncated` flag), which keeps it under the dispatcher's 1 MiB event bound. Native control frames waiting for the provider's input (the handshake, hook answers and control-request rejections, which echo the provider's own request id) are held within 1 MiB; the reply that does not fit is dropped, a `provider_control_backlog` notice is recorded and the attempt ends `failed`/`provider_error`. Provider stderr is capped at 8 MiB and the catalog log limit remains in force. `max_output_bytes` in the turn request and policy is retired: the API still sends 64 MiB because a worker from before the removal refuses a turn without it, and a current worker accepts any value, or none, and ignores it. While the API is not acknowledging events the journal keeps every unacknowledged one, so a turn that keeps recording grows it. Claude receives the effective request or policy `max_turns` as a CLI bound; Codex turns with either field are refused before prompt delivery. The optional title call's stdout is capped at 1 MiB and the ontology card at 768 KiB. The log caps settle with `limit_exceeded`; an incomplete initial provider write leaves the reserved input `delivery_unknown` for an owner choice. Replay retains the same invocation identity and already journaled partial events.


**Journal and dispositions.** Every event is appended to `/var/lib/g5d/journal/<exec_id>` with a per-execution `seq`, fsynced (with its directory entry) before it is streamed as a `module.event` notification (`{exec_id, seq, kind, payload, terminal}`), and journal order is stream order. A peer that lags the bounded stream receives `module.events.lagged` and must `events.replay`; from the moment a replay is admitted until its reply has been queued on the connection writer, that execution's live events are held; the release is performed by the forwarder — the only task that writes live events — one event at a time, reserving writer capacity before consulting the gate and enqueuing while the gate is held (so no event is detached from the hold between the gate's decision and its queue position), remembering for the connection's lifetime the highest sequence a reply carried so an event a reply already carried is dropped even when it reaches the forwarder after the release (only a canonical identity of this incarnation takes the hold, and an identity whose replays never carried an event leaves nothing behind), so a held event can never be overtaken by a newer one, a replay admitted mid-release re-takes the hold for the rest of the backlog, a failed reply releases its backlog only after its error response, and overlapping replays release after the last one. `invocation.started` is the first event and `invocation.outcome` the terminal last one: the terminal event closes the journal, so nothing — not even a late `request_gone` reply — is appended after it. An append first restores the file to the last accounted boundary (a torn prefix from a failed write is cut away) and, if the write, the file sync, the directory sync or the closing watermark fails, cuts back again or fences that execution's journal until a restart repairs it, so a failed append can never corrupt a later event or reissue a sequence number. An acknowledgement takes effect only once its watermark is durable, so pruning never rests on state that could be lost; a closing watermark whose terminal event was lost before it became durable is reopened on the next start and the terminal event re-emitted from the retained settlement under the sequence the watermark assigned it, even when every earlier event was already acknowledged and pruned. Settlement redacts the outcome exactly once — that value is what the settlement retains, what the terminal event carries, what status and a retried invoke return, and what the digest binds; no surface rescans it, and recovery re-emits recorded settlements as written — and records the exact outcome before the terminal event — as `already_finished`, or retained alongside an earlier `cancelled` decision without changing it — then journals every delivery disposition that still lacks evidence, then the terminal event; if any of these cannot be written, the terminal event is not journaled and the outcome stays in memory. `events.ack` makes its watermark durable under the same lock as appends and compacts the acknowledged prefix away only when it is at least 1 MiB and at least a quarter of the retained file, when nothing unacknowledged remains (the file is removed, never rewritten) or when the disk budget needs it, so a consumer acknowledging in batches does not rewrite the same suffix after every batch; an acknowledged record still on disk is never replayed again, and a concurrent event can never be dropped; the per-execution watermark under `journal/.ack/` survives a fully pruned journal, so sequence numbers are never reissued. Replay serves bounded pages (`limit`, `max_bytes`, `has_more`, `next_seq`) from a per-execution sequence-to-offset index maintained on append and rebuilt on compaction and restart, so a page costs one bounded read. The host's control connection consumes `module.event` and `module.events.lagged` frames: it forwards no payload but coalesces the execution ids into a content-free `vm.module_events` hint for the control plane, when the control plane enabled hints in its accept. On open, a torn trailing record from an interrupted append is cut back to the last complete record before anything is appended, and the journal is reconciled with the disposition table: a journaled outcome whose disposition write was lost is reconstructed, a cancelled execution whose run never settled is closed with a `cancelled` outcome, an undecided open execution with `interrupted`; a recovery write that fails refuses startup. The 64 MiB disk budget prunes acknowledged prefixes oldest-first and never drops unacknowledged events. `/var/lib/g5d/dispositions/<exec_id>` records `cancelled` or `already_finished` (with the outcome digest) for the life of the incarnation, independently of journal pruning, and the first recorded disposition wins: once an identity is cancelled, `modules.invoke` and `modules.cancel` report `cancelled` even after the run's own outcome was journaled, while `modules.status` still exposes that outcome, also after acknowledgement and restart. If the terminal event or the disposition cannot be persisted, the outcome is kept in memory, reported with `persistence: failed` by `modules.status`/`modules.history`, listed by `outcomes.pending` with `source: memory`, counted in `runtime.inspect.summary.modules.unpersisted_outcomes`, and never evicted. A dispatcher restart within the incarnation settles every execution it did not see finish with a definite `interrupted` outcome before it listens; such an identity is never launched twice.

**Native replies.** `modules.input.respond` only admits the task identity spelled by `task_id`/`attempt` on this VM (anything else is `stale_execution`), only for a module whose catalog entry declares `operations.input.respond`, and only with `idempotency_key = request_id`. Deliveries are serialised with each other and with settlement; the immutable `request_id`/digest/`provider_request_id` binding is reserved before any byte moves (a retry under a different provider request identity is `RESPONSE_CONFLICT`); the delivery itself is owned by the execution, not by the requesting RPC handler, so a deadline or a replaced connection can never leave a half-done delivery unrecorded. `delivered` means the module's control transport took and flushed the bytes; a write the module does not take within ten seconds is abandoned and the channel closed, so `request_gone` is never followed by a late frame. A transport result is acknowledged only once its `input.respond` journal evidence exists: if that write fails the RPC reports `JOURNAL_ERROR`, an identical retry persists the recorded disposition without touching the transport again, and settlement persists any evidence still owed before it closes the journal. The disposition is journaled as `input.respond` before the reply is acknowledged; an identical retry, including overlapping ones, returns `already_delivered` without redelivery for the attempt's lifetime; a finished execution answers `request_gone` without touching its closed journal.

**Internal Git transport.** Repository Git never holds a platform credential. Network operations of platform modules go through a dispatcher-owned loopback smart-HTTP relay: a module operation leases a random 256-bit path (`http://127.0.0.1:<port>/<lease>/git/<repo_id>`) for one configured member for the duration of that operation; the relay accepts only `info/refs?service=…`, `git-upload-pack` and `git-receive-pack`, receives the request body under the lease and a bound — spooled to a private unlinked temporary file, never held in memory, under a shared 1 GiB budget across every concurrent exchange (reserved frame by frame and released when the exchange ends; a request the budget cannot admit is refused with `507`), and forwarded upstream as a sized stream — revalidates the lease and only then obtains the current lease token through the installed credential helper, forwards to the member's configured internal Git URL, follows no redirects and reaches no other destination; revoking the lease abandons every exchange admitted under it — one still receiving its body, one waiting on the upstream, or one still relaying the upstream response. Git sees a plain loopback URL; hooks, filters and descendants inherit nothing. This is the typed authenticated boundary P4.2a deferred; P4.3a's flush reuses it.

**Built-in modules.** `workspace.changes` runs in-process over fixed `git` command lines with the installed excludes file, addressing the internal origin through the transport above and never through the checkout's mutable `origin`. `get` reports, per member, the association (`head`, `on_shared_branch`, `internal_ref_present` and `internal_ref`, `detached_head`, `foreign_head`, `sequencer` markers, `errors` such as `BRANCH_ASSOCIATION_MISMATCH`, `MISSING_INTERNAL_BRANCH`, `DETACHED_HEAD`, `INTERRUPTED_SEQUENCER`, `STATUS_UNAVAILABLE`), the dirty set (`null`, never an empty list, when `git status` could not be collected within the output bound — and `update` then refuses rather than guessing), ahead/behind against the internal branch and against the member's own `base_branch`, and unmerged paths. `push` sends `refs/heads/<shared>` to the existing internal branch only, pinned with `--force-with-lease` to the last observed internal ref so a deleted or concurrently moved branch is refused as `INTERNAL_BRANCH_MOVED` rather than recreated or clobbered, while a history rewritten by `update` replaces that exact value in place; it never stages, commits or creates a branch; `update` is refused for a dirty tree or a broken association and otherwise fetches and rebases onto `refs/remotes/origin/<base_branch>` in place; `switch_back` checks out the shared branch (refusing a name that is not Git-valid before anything reaches `git checkout`), materializing a local tracking branch only from an existing internal ref. There is no `commit` operation. `workspace.diagnostics` offers `probe(name)` and `capture(profile)`. `workspace.bootstrap run` launches `g5d bootstrap`, the trusted supervisor: it reads the invocation record from stdin, runs each selected member's `g5.yaml` `setup.bootstrap` steps (`profile: setup`) through `/bin/sh -c` in the member root with `setup.env`, stdin closed and no capability in reach, streams `bootstrap.step` events, and only after every step succeeded submits an optional `input.graph` (`g5.bootstrap.task-graph/v1`, `tasks` only — `wait_mode`/`wait_for` are refused) as `POST <broker>/api/internal/jobs/<job_id>/tasks` with the capability secret as bearer token. A graph without a capability, a capability without a configured broker, or a failing step ends the run with a definite `failed` outcome and no submission.

## Native Git boundary

Startup installs `/var/lib/g5d/gitconfig`, with exact member `safe.directory` entries written through `g5_scm::native::configuration::install_member_configuration`, the owner's identity and `core.excludesFile=/var/lib/g5d/excludes`. `GitRuntime::process_environment` selects this configuration, fixes the provider homes outside working trees, and carries the owner's author/committer values. `provider_command` starts from an empty inherited environment; later module launchers must add only their declared build secrets and inputs.

Excludes reserve `.g5/cache`, `.g5/runtime`, `.g5/state`, `.g5/logs`, `.g5/tmp`, `.g5/sessions`, legacy `.g5/gitconfig` and `.g5/gitconfig.host`, and `.g5/layout.json`. The `.g5-dispatch-tmp-*` staging pattern is excluded at any depth. Product files such as `.g5/workspace.yaml` and `.g5/preview_profiles/*` remain eligible for native `git add -A`; tracked product edits remain staged normally.

`GitRuntime::credential_for_url(current_token, git_url)` invokes only the installed platform helper with a fixed `get` operation and bounded, generated credential fields. It returns `x-access-token` credentials only for exact configured internal member Git URLs; other routes receive no credentials. Each invocation receives the latest token, with no token stored in the helper file. Only that helper receives the token in its cleared environment. No credentialed Git command factory exists: repository Git can execute hooks, filters and other configured programs, which must never inherit the platform token. Ordinary provider processes and their Git descendants receive neither platform credentials nor the helper configuration. The later P4.3a flush implementation must supply a typed authenticated network boundary that preserves these restrictions, enforces exact internal destinations and disables credential-bearing redirects; that transport is outside P4.2a.

Later API and provider suites build on it; it is not a fake task service. The test-only mutation gate makes close/drain races deterministic. Neither feature is a production process fallback or evidence for KVM isolation.
