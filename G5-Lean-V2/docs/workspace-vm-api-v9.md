## 1. Boundary and workspace authority

The workspace VM is an ephemeral execution environment and working-tree cache. It is not the authority for Git refs, identity, approvals, provider credentials, or durable platform metadata.

**Codex subscription amendment, 2026-09-23.** The single-owner VM may hold an ephemeral owner-scoped credential cache created by native device authorization; it is not durable platform credential authority. Same-owner agent tools share the developer-desktop trust boundary. Ownership transfer must stop and purge the old VM before committing the new owner, never reassign that VM. See [Codex device authorization](codex-device-auth.md) for the turn lifecycle and validation contract. API-key and OpenRouter authentication are unchanged.

| Place | Owns |
|---|---|
| Workspaces control plane | Workspace identity, exactly one `owner_user_id`, org/invite read access, ownership transfer and its audit, lifecycle admission, VM incarnation, flush and restore; ordinary checked fork and source/parent linkage. |
| Git service | Refs, receive-pack policy, workspace-branch ownership, protected branches, provider publication, and merges. |
| Workspace VM | The live working tree, declared modules, provider/agent processes, interactive terminals, and VM-local observations. |
| Workspace Runtime facade | The only control-plane client allowed to open the VM channel. Other platform systems call this facade rather than the host tunnel or dispatcher directly. |
| Agents / TaskService | Durable tasks, attempts, shared `chat_sessions`, queue visibility, cancellation and terminal task transitions. Human and workflow inputs use `kind=agent`; `kind=preview` retains its service lifecycle. The Workspace module supplies the preview execution. |
| Agent or terminal inside the VM | Native shell and Git operations under the workspace owner. These are local capabilities, not control-plane extension APIs. |

**Post-MVP (P8.14: `orgs.access_generation` as the authorization-freshness fence).** MVP behaviour: P4.1 lands the column and it stays dormant; access removal reaches the next request immediately, because membership is read on every check (amended 2026-10-09, G5Labs/G5-Lean#405: the 60-second membership cache that previously bounded this was removed with Redis); open streams and issued tokens keep their TTLs until this fence lands. Authorization freshness uses the existing org row’s `orgs.access_generation`, incremented atomically with membership/role and workspace invite/visibility/owner/deletion changes. This coarse revision fences cached views, tickets and future stream delivery; current authorization is still checked separately.

Every VM request is bound to a `workspace_id`, current `vm_id`, actor or capability grant, deadline, and idempotency key. A stale incarnation is rejected at every execution boundary. `owner_user_id` is fixed for the lifetime of an incarnation; transfer releases that incarnation before changing the owner.

Here, “org admin” means org role `owner` or `admin`. Only active org members with role `owner|admin|member` may own a workspace, fork or receive a transfer; a `viewer` remains read-only (`ORG_ROLE_READ_ONLY`). The owner always has read access. Other read access follows the org model: org admins read all workspaces; other org members read according to `visibility=org|invite_only` and the invite list. A workspace has no list of writers. Its owner alone may save files, use terminals, send/edit/withdraw chat inputs, answer live native question requests, submit or cancel tasks, launch/replace/cancel preview and access its relay, push existing commits, create PRs, record workspace approval decisions, and stop/resume/delete. G5 exposes no user-controlled Commit action; agents make commits through native Git. Invite add/remove and visibility changes are also owner capabilities; admins take ownership before changing them. `created_by` and former ownership grant neither invite administration nor invite-only read access. Eligible readers may fork into a workspace they own. They cannot access the source VM through filesystem, execution, terminal, preview, port, inspection or live log APIs. Their repository-content reads always use durable Git; durable chat/task/PR metadata remains under its own platform ACLs. No reader action wakes or flushes the source VM.

The client is read-only for an owner without an attached healthy VM. Explicit owner Start/Resume admission must complete before editing, uploading or executing; a clearly labeled compound Start workspace and chat/preview/terminal action may record that same intent and wait for readiness. Save/upload, ordinary input submission and history reads never ensure a VM implicitly. Requests revalidate current ownership, VM readiness and `expected_vm_id`; `stopping` or a pending transfer returns `WORKSPACE_STOPPING`; missing readiness otherwise returns `WORKSPACE_NOT_RUNNING`. An attached healthy VM means `workspace_vms.status=running`, open admission and a passing latest private health report no older than the configured freshness bound (30 seconds, sampled every 10 seconds by default). V9 also applies the read-only invariant to user-originated mapped-branch pushes, including laptop receive-pack: Git service authorization requires current owner and running/admission-open workspace, otherwise `WORKSPACE_STOPPING` during teardown/transfer or `WORKSPACE_NOT_RUNNING`, without auto-boot. This is a v9 interpretation of the clarification. Lifecycle flushes and control-plane fork/merge/import retain distinct service capabilities; native Git commands inside the attached VM remain available without shell policing.

Base workspaces remain read-only and have no VM; chat, terminal and preview actions offer a fork into a workspace the caller owns. The connecting user owns the base for invite/visibility administration, with `visibility=org` initially; an org admin may transfer it. Stop/resume return `WORKSPACE_IS_BASE`; delete is refused while the repository remains connected. Ownership does not permit direct content writes to a base workspace.

### 1.1 Member-repository mapping and fork

A working workspace maps to `[(repo_id, shared_branch_name), ...]`, with one checkout per member repository under the workspace root. Every mapped branch uses the same name; there is no per-repository branch-name override. The proposed workspace name is the exact Git-valid destination branch name, without slug/UUID suffixes.

Workspace fork, including fork from a base workspace, is the only creator of new internal workspace branches. All Create/Fork/Fork-and-preview/chat/API/CLI entry points call that same control-plane operation. Before creating any destination branch, it checks every member repository (including connected provider branches) for the name and ref-prefix conflicts. Any collision returns `WORKSPACE_NAME_CONFLICT` and asks the user for a different name; it never overwrites, adopts or automatically renames the branch. A failed verification is not a free name.

Design v9 §5.8 defines durable all-member reservations directly in unfinished `workspace_forks` (`pending` and `aborting`), create-if-absent branch-plus-fork-receipt transactions, idempotent recovery and safe cleanup after partial failure. Fork keys are unique within `(org_id, requested_by, idempotency_key)` and bind a canonical digest of the requested source selector, member set, name and carry options; a different request under the same key returns `IDEMPOTENCY_KEY_REUSED`. Server-resolved OIDs are pinned once, not recomputed during a retry. The provider namespace check uses the repository’s recorded connection credential, fails closed when it is unavailable, and never borrows another user’s token.

The immutable claim is the exact proposed name plus the complete validated member IDs; source/copy/progress fields may be populated later without altering that key. Admission locks existing repository rows in canonical order in a short READ COMMITTED transaction, then uses a separate fresh query over every same-org unfinished manifest for overlapping members and exact/slash-prefix names before inserting pending. Require the locked repository rows exactly match the full same-org eligible member set, so a concurrent deletion cannot leave a partially validated claim. Resolve idempotency before refreshing source inputs: unfinished retries use stored claim keys and resume themselves after locked status/auth checks; terminal retries return recorded outcomes without needing historical repos. Exclude only that proven same operation from conflict checks; changed input still fails. No matching fork rows is not a lock. Server conflict lookup includes inaccessible workspace claims without exposing their metadata. Slow provider/flush I/O follows claim commit outside those locks; source receipt pins follow the established repository/flush lock order. Only pending→completed publication or aborting→aborted verified cleanup ends the temporary claim; pending→aborting permits cleanup only, so a stale creator/finalizer cannot publish after abort wins; timeouts, errors, stalled cleanup and API restart never do. Ref mutation, cleanup and terminal transition recheck current operation state under the same repository/writer barrier, preventing a delayed worker from recreating an aborted ref. Repository deletion and conflicting bootstrap/import writers consult unfinished manifests under that boundary. No separate reservation table is used.

Recovery status is available through `GET /workspaces/:id/forks/:fork_id`; an org admin may request idempotent reconciliation, but may not release a name until create/delete proof verifies every member. Fork proof refs live through settlement, then seven days after completion (or until verified abort cleanup); active operations are never pruned.

The destination is created stopped and usable only after its whole branch/receipt vector commits. Attachment is a separate explicit owner Start/Resume action; creating a child alone never allocates a VM. A reader source vector comes only from the selected complete durable Git receipt or branch heads, without source VM access or flush. An owner may explicitly select a live source fork, using an owner-authorized `reason=fork` flush. Both paths persist and display the exact pinned source manifest and freshness before creating refs. The dispatcher and restore path consume that completed mapping and cannot recreate a missing authoritative ref; native pushes update existing mapped refs only. Base workspaces read existing protected/default refs per repo, whose names may differ; the fork creates the same proposed destination name from that source vector. Repository setup may initialize protected/default refs, but cannot mint a working workspace branch. Per-repo upstream/update targets remain in `workspace_repos.base_branch` and do not override the shared working name. A working-repository member change cannot mint a new branch outside a new checked fork.

**Post-MVP (P8.12).** MVP behaviour: internal git serves upload-pack and receive-pack on the authoritative repository with the repository-level read check and the landed P1.2 policy, and the host keeps its URL-keyed bare cache and materializer. Internal Git and host materialization use the immutable authorized-closure artifact in design §5.3. Its manifest binds org/repo/object format, principal scope, authorization generations and exact root/OID vector; no global alternates or copied whole bare cache is permitted. Scoped receive-pack resolves thin bases/connectivity only from authorized existing objects plus this request’s uploaded objects, then commits authoritative refs after current-authority/CAS revalidation. Host cache reuse requires the same scope/digest under a current incarnation; guest `.git` contains only that validated closure. Cache miss, eviction or pressure cannot widen the scope. P4.3a/P4.4b test private-sibling warming followed by excluded-workspace reads, known-object access, hidden-parent/thin-base pushes and revocation.

**Post-MVP (P8.14: the per-operation rate bounds).** MVP behaviour: the existing rate limiter applies. Control-plane defaults bound amplification: 60 fork operations per org per hour, four pending forks per user, six Resume actions per workspace per minute and 100 queued ordinary inputs per session. Rejections return `RATE_LIMITED` with Retry-After (429); payload caps use 413. Retries of the same operation consume no additional mutation quota. Conditional provider-list caching may reduce traffic but a stale cached absence cannot prove the proposed name is free at fork preflight. Org policy may lower these limits; increasing them requires deployment capacity policy.

## 2. Workspace Runtime API

The live operations below are exposed through the Workspace Runtime facade, never through a direct host or dispatcher connection. The explicitly marked workspace status route is a control-plane read and never opens a VM channel, including for the owner of a running workspace; the dispatcher has no `workspace.status.get` method. The product API performs current owner/read authorization before invoking them; a module capability grant is not a session-scoped provider grant.

| Surface | Methods | Caller | Contract |
|---|---|---|---|
| Files: read | `fs.list`, `fs.read`, `fs.stat`, `fs.watch` | Current owner with attached healthy VM | Live content and `file.changed` events for the current incarnation only. Readers use the control-plane Git read path and never reach this surface. |
| Files: write | `fs.write(path, content, encoding, expected_hash)`, `fs.delete(path, expected_hash)`, `fs.rename(from, to, expected_hash)` | Current owner with attached healthy VM | Editing and upload share this path. Preconditions prevent silent overwrite; admission, association checks and mutations use the same `expected_vm_id`. Save/upload never starts a VM; return `WORKSPACE_NOT_RUNNING` until explicit attachment is ready. |
| Terminal | `terminal.open(cols, rows)`, `terminal.write`, `terminal.resize`, `terminal.close` | Current owner with attached healthy VM | Owner-only interactive shell from the client/web UI. No non-owner attach, read, write, resize or close; no platform-extension mechanism. |
| Modules | `modules.list`, `modules.describe`, `modules.invoke(exec_id, module_id, version, operation, input, grant_id)`, `modules.status`, `modules.cancel` | Authorized platform feature on behalf of the current owner, through the facade | Sole platform execution/extension path. No arbitrary `argv`, environment, cwd or signal targets. No reader preview exception; generic task/job/module paths must enforce the same rule. |
| Ports and relay | `ports.list`; `port.opened`, `port.closed` events; authorized HTTP relay | Current owner with attached healthy VM | No non-owner port discovery or live preview/forwarded-port access, including guessed or previously granted URLs. |
| Workspace status | `GET /workspaces/:id/vm` (control plane, outside VM JSON-RPC) | Any authorized workspace reader | Durable control-plane lifecycle, owner, attachment summary and latest complete flush receipt with source/freshness labels. Does not invoke the VM or reveal live roots, ports or logs to readers. |
| Runtime inspection | `runtime.inspect.summary` | Current owner with attached healthy VM; narrowly authorized internal operational service | Bounded, redacted VM identity, health and resource observations. Workspace read/org-admin permission alone cannot invoke it. |
| Module diagnostics | `modules.logs(exec_id, cursor?)`, `modules.events(exec_id, cursor?)`, `modules.history(filter)` | Current owner with attached healthy VM; narrowly authorized internal operational service | Live or VM-resident diagnostics remain owner-scoped. Durable task history is a separate ACL-checked platform surface; reading it cannot tunnel into live module logs. |
| Diagnostic bundle | `diagnostics.capture(profile)`, `diagnostics.probe(name)` | Current owner for safe profiles; narrowly authorized internal operational service | Fixed declared collectors, never caller-supplied shell. No reader invocation or live-results subscription; stored redacted operational records follow their separate ACL. |

### 2.1 File fields and confined mutation

`fs.read` and file `fs.stat` return `{path, hash, size, mode, mtime, encoding}`. `hash` is the Git blob object ID of the exact bytes using the member repository’s declared object format (SHA-1 for current repositories), not a commit OID or an mtime. `fs.write` requires `encoding=utf-8|base64`; API and dispatcher both enforce a 32 MiB decoded-byte cap before allocation or filesystem mutation, with `PAYLOAD_TOO_LARGE`. The instance capability response advertises the same cap. Upload is this same operation and has no separate overwrite or versioning policy.

For write, `expected_hash=null` means create if absent (`FILE_EXISTS` if present); a non-null hash requires an existing matching file (`FILE_MISSING` or `FILE_VERSION_CONFLICT` otherwise). File delete/rename require the matching hash. A successful write returns the new hash. Conflicts return the current hash and size; content is obtained through the normal authorized read route rather than embedded as an unbounded error payload. Rename never replaces an existing destination. Directory rename requires an existing directory and absent destination; directory delete is allowed only when empty. Mutations and their association/precondition check share the same incarnation and admission lease, and the dispatcher drains admitted mutations before a flush.

Paths identify a member `repo_id` and a normalized relative path. Absolute paths, `..`, `.git` and platform runtime/cache directories are forbidden. Resolve every component relative to the already-open member root using race-safe descriptor-relative traversal (`openat2` beneath/no-symlink resolution or equivalent), refusing symlink traversal; checking a canonical parent then opening it later is insufficient. The client cannot overwrite `.git/config`, escape through a symlink, or target another member root by path spelling. Native owner shell/Git behavior remains separate.

### 2.2 Durable source selection

The repository-content read router uses Git for non-owners regardless of VM state, and for owners without an attached healthy VM. As a v9 draft design choice, the Git source is the last complete verified flush receipt when present, otherwise the branch-head vector. Each response carries `source=live|flush|committed`, repository/OID vector or live `vm_id`, and observation time/freshness. A Git snapshot may include edits captured by an earlier flush but cannot include newer unflushed VM edits. Tree/stat/download, documents, ontology projections and Changes/diff routes use the same selection; reader Changes never promises current dirty-tree state. Cache entries are keyed by source vector and authorization scope; incomplete receipts cannot produce a mixed snapshot. Flush document/ontology views render from the pinned Git tree via the historical read path and never read branch projection rows. A committed view uses a projection only if its `applied_oid` equals the selected OID; otherwise it renders from Git and marks projection lag. The convergence loop projects managed/protected branch heads, not flush refs. Provider-backed committed entries additionally expose `mirror_observed_at`, `mirror_state` and `stale`; fetch failure, missing provider ref, or observation older than three poll intervals is visible. Source selection and response production pin the complete receipt under the flush lock; pruning cannot remove it mid-read. Reads never request a flush or start a VM. Git/durable reads do not extend VM idle time; attached-owner file RPC may count as activity under the existing policy.

**Post-MVP (P8.14: delivery serialized against the org access generation change).** MVP behaviour: access removal reaches the next request immediately, because membership is read on every check (amended 2026-10-09, G5Labs/G5-Lean#405: the membership cache was removed with Redis); open streams and issued tokens keep their TTLs until this fence lands. Opening a live stream and delivering responses revalidates ownership/access and incarnation. Ownership/access changes invalidate source-dependent caches and close filesystem watches, terminal/preview relays, durable metadata subscriptions and live diagnostics streams. Delivery is serialized against the org access generation change: no payload ordered after revocation commits may use an earlier authorization, even if asynchronous stream close has not yet arrived. A former owner's cached URL, tab or pending response cannot retain VM access. The owner may browse the Git fallback during failure, but live editing/execution resumes only after a healthy current attachment. Internal host/lifecycle telemetry remains a service boundary, not an org-reader escape hatch.

Workspace search is absent: no workspace-wide search API, index, embedding pipeline, search database, settings or tooling is exposed by this boundary. Chat-history search, editor Find and an agent's local code-search tools remain; docs and ontology projections still serve their retained product surfaces.

## 3. Declared module runtime

`proc.spawn` is a private dispatcher implementation detail. Every platform-initiated executable unit is a declared module invocation.

| Module declaration field | Requirement |
|---|---|
| Identity | Stable `module_id`, semantic version, immutable manifest hash. |
| Contract | Named operations plus typed input, output, event schemas. |
| Execution | Pinned entrypoint and lifecycle class: `bounded_run` or desired-state `service`. |
| Limits | CPU, memory, disk, output/log bounds and appropriate concurrency/time policy. Preview services have no wall-clock limit and consume no workspace bounded-task concurrency slot. |
| Capabilities | Requested workspace scope, bounded ports, network-egress policy, Git operation scope, provider-turn access and related privileges. |
| Observability | Declared health probes, diagnostic profile, event kinds and redaction policy. |

The dispatcher resolves the immutable catalog entry, validates input, and intersects requested capabilities with the control-plane-issued `grant_id` before using its private runner. A manifest requests capabilities; it never grants them. The runtime image and module catalog are signed or hash-pinned. Workspace configuration may select/configure an installed module but cannot install code or expand privilege. The preview's no-tracked-write rule is a repository-profile contract, not an enforced filesystem isolation guarantee (§3.1).

Each invocation is auditable as:

```text
(workspace_id, vm_id, exec_id, actor, module_id, version, manifest_hash,
 grant_id, input_digest, capability_grant, outcome)
```

`modules.invoke` has a tagged execution identity: task invocations use `(kind=task, task_id, attempt, vm_id)`, while task-less `workspace.changes` and diagnostic calls use `(kind=operation, operation_id, attempt=1, vm_id)`. The facade mints a UUIDv7 `operation_id` per logical request and reuses it on retries; it never invents task rows for Save/status/PR checks. The API mints opaque canonical scalar IDs `task.<task_uuid>.<positive_attempt>.<vm_uuid>` and `operation.<operation_uuid>.1.<vm_uuid>`; both classes use the same idempotency, cancellation, audit and journal rules in the Agent API execution contract. Bounded task-less calls use the shared workspace bounded-execution limit and module-specific caps, like agent/command runs; only preview service is exempt. `modules.invoke` is idempotent on that full identity. Its dispositions are `started`, `already_running`, `already_finished(outcome)`, or `cancelled`. Cancellation records a durable disposition even before a process exists, so delayed invoke delivery cannot launch cancelled work. Dispositions last for the incarnation, independently of journal pruning. Module events/outcomes use ordered journal replay, acknowledgement and incarnation fencing.

| Module | Operations | Notes |
|---|---|---|
| `workspace.preview` | `start(profile)`, `stop`, `status` | Service backing a durable `preview` task; declares its port and relay contract. |
| `workspace.changes` | `get`, `push`, `update`, `switch_back` | Normalized association, dirty/ahead/behind/conflict state and owner-authorized mutations. Push sends existing commits; no manual Commit operation is exposed. |
| `agent.turn` | `run`, live `input.respond` | One Claude or Codex attempt for a shared-session `agent` task through [Agent API Surface v9](agent-api-surface-v9.md), including native provider question contracts. |
| `workspace.bootstrap` | `run` | Deterministic setup and `command` tasks. |
| `workspace.diagnostics` | `capture(profile)`, `probe(name)` | Fixed read-only diagnostic collectors. |

### 3.1 Preview task and service

An owner preview button against an attached healthy VM creates a durable `tasks.kind=preview` row and returns its task identity. A clearly labeled compound Start workspace and preview action records explicit owner Start/Resume intent and the queued preview task together, exposes `queued_for_capacity` and cancellation in the task queue, and waits for readiness before execution; a preview-only request against a stopped workspace returns `WORKSPACE_NOT_RUNNING`. Cancelling during attachment terminalizes the queued task and withdraws its launch demand; delayed readiness cannot launch it. The lifecycle service releases an otherwise unneeded attach under its ordinary cancellation policy without cancelling unrelated authorized work. Dispatch checks current ownership and workspace/branch association on that incarnation, then invokes `workspace.preview start(profile)` with the task execution identity. Task queue and timeline show the launcher's user id, start/stop state and cancellation controls. Preview remains running until cancelled, replaced, failed, or stopped with its VM; module start success is not terminal task success.

Preview task state becomes `running` only after confirmed module start. Relay readiness additionally requires the configured profile port or declared health probe; before readiness or after port closure it returns `PREVIEW_NOT_READY` (503) while the task remains running until exit. Incarnation loss terminalizes bound running and queued/replacement launch intents: preserve an already-cancelled predecessor, fail the unstarted successor with `vm_lost`, and never revive it at delayed readiness. A later independent explicit Start intent remains independent.

Only the current owner may launch, replace or cancel preview, inspect its ports or use the live relay. Authorization uses current ownership plus the stored task identity, never a client-supplied task-kind claim. Generic task/job cancellation, module invocation and relay APIs enforce the same rule. A non-owner must fork and execute in their own child; neither read access nor knowing a relay URL is sufficient.

**Post-MVP (P8.13: the separate registrable preview domain, `PREVIEW_ORIGIN_UNCONFIGURED`, the removal of the same-origin fallback with the legacy path cookie and inline relay, and the QA DNS/TLS and CI test-domain work; P8.14: the access generation in the ticket scope).** MVP behaviour: preview is served as today, on a per-preview subdomain under the platform domain when the host suffix (`G5_PREVIEW_HOST_SUFFIX`) is configured, with the single-use handoff ticket, the `__Host-g5_preview` cookie and CSP, and through the path relay otherwise. Repository HTML/HTTP/WebSocket content is served only on a mandatory per-workspace/port origin under a separate registrable domain. The platform route is an authorized bootstrap/redirect only and never relays guest bytes for any method or WebSocket upgrade; missing configuration returns `PREVIEW_ORIGIN_UNCONFIGURED` (503). Remove the legacy path cookie, relative same-origin URLs and inline relay. Preview tickets are host-only, Secure and scoped to owner/session/workspace/incarnation/access generation, with HttpOnly. Embedded mode uses `SameSite=None; Partitioned` with a proved one-use handoff on supported browser configurations; the retained `SameSite=Lax` ticket alone cannot authenticate cross-site iframe traffic. If embedded ticket storage is unavailable, show an explicit Open in new tab path using the top-level isolated-origin session, never a same-origin fallback. P5.1 proves both modes and the denial of platform DOM/storage/API authority, provisions QA DNS/TLS and CI test domains before enabling the UI, and records the browser support matrix.

One preview may be active per workspace. Starts, replacement and cancellation serialize under the workspace preview/lifecycle admission lock. A replacement records cancellation for the previous task, settles any ambiguous start and confirms the old execution is stopped before launching the new one. Racing starts or cancel-before-start delivery cannot leave two services or restart a cancelled preview. Ambiguous invocation retries retain their task/execution identity. The service designation never authorizes restart after a process failure; unexpected service exit fails the task and needs a new explicit preview start. Stop/transfer holds admission closed, so a preview cannot wake or launch during the lifecycle barrier.

Preview runs under workspace identity using workspace secrets and the current owner's provider context if needed; `created_by` is launch audit, never credential selection. The selected command comes from the repository's preview profile and must not modify tracked files. G5 does not enforce that contract in v9: any tracked changes appear in Changes and are included in a later flush. Discarding writes with an overlay is future hardening.

Preview does not consume the workspace's bounded-task concurrency slot, has no wall-clock limit and never restarts automatically after stop/resume, transfer, VM loss or rollout. A fresh explicit owner preview start creates new demand against an attached healthy VM; no queued preview automatically wakes a stopped or transferred workspace. Only an authorized owner HTTP relay request or WebSocket open counts as preview activity (updates debounce at most 10 seconds); idle WebSocket keepalives, service output and unauthenticated probes do not count; a running preview process alone does not disable the org idle timeout or its workspace override. This removes dedicated preview VM/session/attach machinery, not the `preview` task kind or the task-list cancellation surface.

### 3.2 Shared agent task lifecycle and live questions

Human chat input and templated workflow input both enter the same `chat_sessions` lifecycle and dispatch `tasks.kind=agent` through `agent.turn`. Input origin is typed provenance, not a separate execution engine or permission policy. The server records permission policy explicitly, independently of whether the input came from a person or a workflow. The Agent API companion owns the field-level contract.

One nonterminal logical agent task occupies a session, even while held with no provider process. New session inputs remain queued behind it; explicit owner Continue/Resume or acceptance of the pending native answer clears the corresponding hold. A continuation retains the same logical `task_id`, session, dependency edges and job grouping; each new process gets a new attempt and `exec_id`. A waiting or interrupted attempt does not complete the task or release dependent work. Dependencies unblock only on the logical task's final `succeeded` state; final failure or cancellation follows the existing dependency failure/cancellation policy without pretending success. Preview remains a separate service task and does not inherit agent continuation behavior.

Claude's direct CLI emits native `AskUserQuestion` requests into the timeline. The current owner answers through its native stdin control protocol, either on the live callback or after restoring a confirmed deferred question from the saved native session on attached ready compute. MVP Codex `exec --json` has no interactive-question transport and no custom MCP fallback; a later App Server stdio adapter supplies its native interactive path. The provider adapter owns native framing; the facade exposes only its declared `modules.input.respond` channel for validated, owner-authorized replies to a live attempt, never arbitrary stdin or a new host RPC. Unrelated MCP tools remain available.

Native questions and permission requests are projected into `provider_requests`, keyed by `(task_id, attempt, provider_request_id)`, with states `pending|reply_pending|responded|invalidated` as defined by Agents. Ordinary process-bound requests become historical when their execution ends; permission requests retain their deadlines. A confirmed native deferred question has no automatic deadline and retains its original identity and immutable first answer across workspace Stop, session restore and ownership transfer. The current owner answers on attached ready compute, and Agents resumes the saved native session in another attempt and matches the original tool-use identity before writing through the new callback. Explicit turn cancellation closes it; missing or mismatched native state fails explicitly. The Agent API owns current-owner checks at answer acceptance and dispatch, uncertain-delivery handling and settlement. Reading history or submitting an answer never wakes a VM. User stop, idle stop, transfer and unexpected loss require explicit owner Resume before another attachment. Deliberate drain/rollout may continue the same task under previously recorded current-owner continuation authority only while no later stop, transfer or workspace teardown supersedes it; queued demand alone is not wake authority. A deferred question alone does not keep compute awake.

## 4. Private lifecycle protocol

Only the lifecycle service, Workspace Runtime facade, dispatcher, host and provider runner use these reliability operations.

| Protocol | Responsibility |
|---|---|
| `runtime.ready`, `lease.renew`, `health` | Establish VM custody, renew the current incarnation and report liveness. |
| `events.replay`, `events.ack`, `outcomes.pending` | Replay/acknowledge journaled module events and outcomes. |
| `session_files.restore`, `session_files.harvest` | Restore/persist provider session files outside the working tree. |
| `modules.input.respond(workspace_id, expected_vm_id, expected_epoch, task_id, attempt, exec_id, request_id, provider_request_id, response_digest, validated_response, idempotency_key=request_id)` | Deliver an owner-authorized native response only to its live `agent.turn` request; the Agent API companion binds the first immutable bounded response by SHA-256 digest. Identical retry returns its disposition; conflicting answer returns 409. Only journaled delivery evidence settles responded. It neither wakes a VM nor accepts raw stdin. |

### 4.1 Ownership transfer

The current owner may transfer to any org member; an org admin may transfer to an org member, including themselves. A transfer operation carries a durable idempotency key and records old owner, new owner, requester and completion time. Workspaces holds the lifecycle/admission lock from the start through stop/release and the owner/audit transaction.

Transfer uses the stop sequence with `stop_reason=transfer`: close admission, interrupt executions, close previews and terminals, persist attempt outcomes, task continuation state and Agent session state, invalidate process-bound native requests while preserving confirmed deferred questions under the Agent contract, flush with reason `shutdown`, persist required Agent state, confirm host exit, release the incarnation, verify retained-root purge, then atomically change `owner_user_id`, cancel the old owner’s start intents and complete the persisted transfer operation/audit. A stopped workspace skips boot/flush but still verifies retained-root purge before owner change. An ambiguous host stop must be reconciled; it is not permission to change ownership while the old VM can run.

Flush failure aborts transfer, restores admission and leaves the old owner unchanged. Interrupted execution state remains truthful; abort does not silently relaunch a preview. No forced-loss path completes ownership transfer. A retry of a completed transfer returns its recorded result without a second owner change or audit.

Chats, tasks, PRs, queued inputs and question history remain with the workspace. Transfer never wakes a VM or dispatches queued work or continuation attempts. Only the new owner's explicit Resume records a fresh owner/generation-bound start intent before attachment and pending work use their provider account. An agent continuation retains its task/session/dependencies and uses a new attempt; confirmed deferred questions remain answerable by the new owner after native session restoration, while ended process-bound requests remain historical. There is no reader preview wake path or pending-work bypass. Cached file content, old watches and preview/terminal connections are invalidated as access and incarnation change; the previous owner switches to the durable Git view. The previous owner retains only the read access independently granted by org visibility/invites.

## 5. Workspace flush

There is no asynchronous checkpoint task. Agents normally commit and push through native Git. Uncommitted edits and unpushed commits may be lost on unplanned VM loss. The lifecycle service alone invokes `workspace.flush({reason: shutdown|fork, interrupt?})`; no Flush now UI, explicit reason or public flush route exists.

```text
FlushReceipt {
  flush_id, workspace_id, origin: flush|fork_copy,
  vm_id?, epoch?, reason: shutdown|fork, source_flush_id?,
  repos: [{ repo_id, branch_oid, local_branch_oid, local_head_oid,
            head_ref, sequencer: none|rebase|merge|cherry_pick|revert,
            snapshot_oid, dirty }],
  concurrent_writers, started_at, complete_at, pruned_at?
}
```

`branch_oid` is the observed internal mapped-branch head; `local_branch_oid` is the local mapped branch even when `HEAD` is detached or on another branch. `local_head_oid` and `head_ref` identify the checked-out content independently. A snapshot commit descends from local HEAD; a clean snapshot is exactly that HEAD. Each member has two immutable refs: `refs/g5/flush/<workspace_id>/<flush_id>/snapshot` at `snapshot_oid` and `/branch` at `local_branch_oid`. The branch ref retains unpushed mapped-branch commits even when they are not ancestors of HEAD. Git does not permit both an old `<flush_id>` ref and a child `<flush_id>/branch`; the two-leaf namespace is the v9 contract.

Before any push, the API creates the `origin=flush` row for the current incarnation and freezes its required member set. The dispatcher retains one `flush_id` and one immutable vector for push/complete retries. Identical existing refs are accepted as no-ops, mutation to another OID is refused. A failed capture that must be recomputed creates a new ID after marking the old attempt failed; no two captures run concurrently. Receive-pack accepts these refs only for the current incarnation and that unfinished receipt, never an unknown ID. Completion requires an exact duplicate-free match of the frozen current member set, both expected refs at their OIDs, commit objects, HEAD reachable from the snapshot, and `dirty=false` only when `snapshot_oid==local_head_oid`. Under the workspace lock, the API atomically sets `complete_at` and `last_flush_id`; an incomplete vector returns `FLUSH_INCOMPLETE_VECTOR` and never replaces the previous receipt. Repeating completion with an identical manifest returns the receipt; a changed manifest conflicts.

Capture closes module and mutation admission, drains admitted writes, and uses a temporary index without changing the real index, HEAD or branch. A shutdown cut follows interrupted executions and closed previews/terminals. A live fork waits for bounded executions up to `quiesce_secs` (30 seconds), then refuses `WORKSPACE_BUSY` unless the owner authorized interruption. An exact fork also closes all listed terminal/preview writers with owner consent; it cannot claim an exact cut while they remain able to write. Readers never enter this protocol. Admissions reopen on completion, refusal or failure.

Snapshot bounds are explicit: default per-file 100 MiB, captured tree 2 GiB, uploaded pack 2 GiB, configurable within the deployment’s storage/request limits. Common untracked build caches are excluded by the platform template; tracked files remain tracked even if ignored. Exceeding a bound returns `FLUSH_TOO_LARGE` with the offending repository/path or pack size. It never silently drops files or manufactures a complete receipt. The implementation preflights the tree and pack before upload; transport limits agree with the advertised pack cap. User stop/delete, transfer and live fork retain the VM on flush failure. Transient idle failures use a five-minute cooldown; deterministic size/proof errors persist the `last_error.flush_block` record/fingerprint/limits/offenders from design §5.4, notify the current owner once per fingerprint, expose operator blocked-age/category state and disable periodic idle retries. After repair through ordinary agent/terminal work or an authorized limit change, an explicit retry of the intended lifecycle action performs fresh preflight; there is no Flush-now control. Only existing authorized deadline teardown or explicit force Delete may release with recorded loss, never an automatic size/idle bypass.

**Post-MVP (P8.14: Git object maintenance serialized behind the repository-write/backup barriers).** MVP behaviour: object reclamation stays with the existing repository GC maintenance. The latest receipt, two newest complete receipts, pending fork source pins and active read/restore pins are retained. Source selection pins before releasing the same lock used by pruning. Incomplete/unknown refs older than 24 hours are swept; failed rows and pruned receipt metadata are retained with `pruned_at` for truthful provenance. An explicitly selected pruned receipt returns `FLUSH_PRUNED`. Ref deletion feeds serialized Git object maintenance after a 24-hour unreachable-object grace, sharing repository-write/backup barriers; loose-object count alone is not a sufficient GC trigger. A fork-copy receipt gets a fresh child `flush_id`, `origin=fork_copy`, `source_flush_id`, null VM/epoch and the source reason. The child branch is at source `local_branch_oid`. Its receipt normalizes local HEAD/head_ref to that child branch and creates a snapshot commit with the selected source tree and child branch parent when those trees differ; otherwise snapshot equals child HEAD. The immutable source manifest retains the original HEAD/tree provenance. Both resulting child refs are verified before the fork publication transaction completes the receipt; copying the foreign source HEAD fields verbatim would violate clean/association invariants. No source VM identity is fabricated.

Restore is authoritative on both warm and cold roots. Abandon leftover rebase/merge/cherry-pick/revert state, force materialize the selected receipt, set the mapped local branch to `local_branch_oid`, then reproduce the recorded foreign-branch or detached HEAD at `local_head_oid`; an interrupted sequencer restores detached with an explicit interruption marker and never replays stale `.git` operation state. Apply the snapshot tree as unstaged edits without moving either retained commit. The child fork deliberately remaps its own HEAD to the newly named branch at `local_branch_oid` and reapplies the selected source tree from its normalized child snapshot; it does not inherit a source foreign branch name or active sequencer. Without a receipt, force checkout the mapped branch at the server-issued `VmSpec.repos.branch_oid` and remove stale nonignored cache content. Warm post-receipt commits, dirty files, stash/reflog and operation metadata are not an alternative durable authority. Association mismatch is reported until the owner/agent repairs it. These rules preserve mapped-branch history and checked-out work separately.

### Lifecycle admission, start intent and stop durability

The control-plane `GET /workspaces/:id/vm` returns durable lifecycle/queue/nudge/last-error state and the latest host observation, never guest data. `workspace_vms.start_intent` is one typed durable record, not a separate queue or table: `{id, kind: resume|compound_start|rollout_continuation, owner_user_id, lifecycle_generation, status: pending|queued_for_capacity|starting|consumed|expired|cancelled|failed, launch_task_id?, created_at, expires_at, attempts, consumed_vm_id?, superseded_reason?}`. The row’s workspace identity supplies the scope. `workspaces.lifecycle_generation` fences replacement consent. Only explicit owner `POST /workspaces/:id/resume` or an already-authorized rollout writes an intent; generic dispatch never creates one. A compound request creates its queued task/input and intent atomically under that route; terminal launch is a transient client action after readiness. The intent binds current owner and generation, expires after 15 minutes before attachment, and is consumed exactly once at `runtime.ready`. Three definite boot/spec failures end it; ambiguous delivery reconciles the same incarnation. Queue order is FIFO by intent creation within the org, subject to quota, and survives API restart. The placement reconciler runs every two seconds and on capacity changes. Status supplies queue position/cancel/expiry, without promising cross-org FIFO fairness.

The explicit workspace Restart operation is retired; `POST /workspaces/:id/restart` returns 404. Owners use Stop and then Start (`POST /workspaces/:id/resume`); Stop alone does not create new start consent.

Admission of a stop intent advances lifecycle generation, cancels older start demand and records the new value as `stop_generation`. An explicitly authorized rollout atomically mints its one successor intent for that same newly advanced generation; release does not increment it again. A later superseding Stop, transfer, deletion, loss or safe explicit supersession advances generation again and cancels older consent. Every asynchronous stop step checks the current operation/incarnation/generation. Queued tasks alone cannot restart a VM. Cancellation of a compound task withdraws its own unconsumed intent; it cannot cancel unrelated later owner consent. After release, only a valid successor start intent permits replacement attachment. Resume need is derived from that consent and lifecycle state; no owner-resume boolean exists.

Admission is evaluated after actor authorization: base restriction; pending transfer or `stopping` (`WORKSPACE_STOPPING`); current running/healthy incarnation (`WORKSPACE_NOT_RUNNING` otherwise); current incarnation admission; then per-operation association/precondition and dispatcher admission. Transfers and stops close the same workspace admission lease and wait for admitted mutations, including laptop receive-pack, to finish before flush/owner CAS. The Agents reservation barrier and dispatcher file/module barrier implement that lifecycle decision; neither independently authorizes a wake. Read/status and durable control-plane action routes do not require live mutation admission.

Deadline-bound stops have a nudge phase while status remains `running` and admission open, with persisted `pending_stop_reason`, `pending_stop_deadline_at`, `nudged_at` and operation ID. The pending deadline ends this phase; it is distinct from `stop_deadline_at`, the flush/harvest deadline set when quiescence starts (default ten minutes, never beyond the host credential safety deadline). The default nudge is 30 minutes, shortened as necessary. Owner Stop/transfer supersedes it. The lifecycle transaction writes one notification for the current owner and system timeline notices for sessions with nonterminal agent work, with queued notice-delivery metadata in `chat_messages.artifacts` and keyed by stop operation (not ordinary `session_inputs` rows); no reader fanout or new task is created. Native CLI turns are not interrupted just to deliver a nudge. The next admitted ordinary input may carry queued notices as a platform preamble under the Agent API `system_notice_ids` contract; undelivered notices are withdrawn when the nudge is cancelled or the VM releases. An API process restart resumes the persisted deadlines without duplicate notices. Operator `capacity` and credential-expiry reconciliation exercise this same path in MVP; fleet orchestration later reuses it.

Stop durable prerequisites include the complete Git receipt, required task outcomes/journal and provider-session harvest. Agents prepare closes reservations and settles executions; final harvest persists the frozen bundles and journal before host stop. Retry transient failures for up to 120 seconds, bounded by the operational stop deadline. User/transfer/idle stops abort if required durable state is unavailable; call Agents abort and reopen admission only if the VM is still known running. Deadline-bound release records exactly which Git/session/event state was lost. An oversized/invalid provider-session bundle may be durably marked unrestorable with a visible notice and delivered-history fallback; this exception does not authorize dropping task events or accepting a stale incarnation. Stale harvest is fenced, never classified as permission to release. After confirmed host exit, Agents stop commit and workspace release commit atomically; a database failure leaves `stopping` for reconciliation. Transfer additionally waits for retained-root purge before owner change and never accepts forced Git/task-history loss.

### 5.1 MVP workflow boundary

Dedicated durable, source-versioned review/explainer returned-results workflows are deferred beyond MVP. The VM contract adds no result-candidate submission/publication, designated producer, request/result/reply storage, special idle policy or task-completion stop. Ordinary owner conversations may review/explain files and retain their normal chat/task history. Checked fork still records parent/source linkage and pinned source vectors; child compute starts explicitly and uses the ordinary lifecycle.

## 7. Design invariants and acceptance

1. Platform execution uses declared modules through the facade under explicit owner Start/Resume admission. Non-owners cannot invoke modules, preview, terminal, live file/inspection/log/port/relay surfaces or source-VM flush.
2. Fork is the only member-branch creation path: the exact proposed name is shared across all members, collision in any repo rejects the fork, and partial creation never yields a runnable workspace. Fork source vectors come from complete verified flush receipts or pinned branch heads; reader forks never call the source VM and completed child creation never boots it. Ownership commits only after the old incarnation is released.
3. Non-owner repository-content reads are Git-only at every sibling surface even while the owner VM runs. Owners without a healthy attachment receive the same fallback and cannot edit/upload/execute until explicit readiness. Durable metadata reads retain their separate ACLs. Source/OID/freshness labels and cache/stream invalidation prevent live-tree leaks across source or owner changes.
4. Owner-only preview tasks are durable, visible and cancellable before/after start; replacement, cancellation, retries and teardown cannot create duplicate active services.
5. Owner-only authorizations are checked at admission, including generic task, chat, file, terminal and Git boundaries. Old-owner requests cannot succeed after transfer.
6. Transfer failure, API restart between release and owner/audit commit, stale invocation replay, answer-versus-process-exit/transfer and explicit resume under the new account require boundary-level regression coverage. A process-bound response cannot reach a replacement process. A confirmed deferred question preserves its original identity and accepted answer across native session restoration; delivery must match that native tool under current-owner authority. Continuation preserves task identity and dependencies.
7. Human and workflow inputs use the same agent task/session path with independently explicit permission policy. Test that interrupted/waiting attempts never release job dependencies, and that Claude native question replies reach only the bound live callback or the matching restored native tool, while MVP Codex exposes no fallback question route.
8. Ordinary forks and agent conversations retain their source link and chat/task history without introducing a returned-results workflow or completion-triggered teardown.
9. Removed Commit, explicit flush, workspace search and custom ask surfaces are absent end to end; Push/Publish, lifecycle shutdown/fork snapshots, chat-history search, editor Find, agent-local code search, docs/ontology projections and unrelated MCP remain. These are implementation gates, not claims that implementation or deployment has passed them.
