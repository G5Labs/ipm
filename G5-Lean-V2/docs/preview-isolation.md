# Preview isolation

Previews are served only from per-preview hosts: with `G5_PREVIEW_HOST_SUFFIX` configured, the preview session endpoint returns a single-use handoff URL `https://<task-id>.<suffix>/?__g5_preview_ticket=…`, the handoff exchange sets the origin-scoped `__Host-g5_preview` session cookie on that host, and the relay serves the application there. The platform origin never serves preview content, sets no preview cookie and accepts none: an authenticated GET/HEAD on `/api/v1/preview/<task>/` redirects to the preview host with a fresh handoff ticket, every other method answers 405, and browser requests with `Sec-Fetch-Site: same-site` or `cross-site` are refused with 403 before any of that. Those platform-path responses carry `Cache-Control: private, no-store`.

Without a suffix the platform keeps running and previews are unavailable: the session endpoint and the preview re-auth route answer `503 PREVIEW_ORIGIN_UNCONFIGURED`, which the preview control shows. Preview tasks still start, stop and record their outcome. Subdomain mode requires an HTTPS platform origin, a registrable platform domain, a suffix on the same site, and wildcard DNS and TLS for `*.<suffix>` pointing at the API (through the ingress or edge, which route those hosts to the API for every path). Plain-HTTP localhost development therefore runs without previews; the CI stacks and the self-hosted bundle run subdomain mode like production (`infra/docker/caddy-ci-tls.caddyfile`, `infra/self-hosted/Caddyfile.tls`).

The relay strips upstream `Clear-Site-Data` from HTTP and WebSocket handshake responses because its `"cookies"` directive affects the whole registrable domain. It allows app-issued cookies after removing every `Domain` attribute and rejecting malformed, invalid UTF-8, or G5-reserved cookies (`g5_`, including `__Host-` and `__Secure-` variants), so apps can establish server-issued sessions on their own preview host. G5's own handoff and ticket-renewal cookies are issued by the platform after that boundary. Platform credentials never reach the application: platform bearer tokens and the preview ticket cookie are stripped from forwarded requests.

Isolated-host WebSocket upgrades require exactly one `Origin` matching that preview's HTTPS origin. Missing, opaque (`null`), duplicate, and sibling origins are rejected before a connection to the app is opened; a page on another preview host cannot open a WebSocket to the target with the target's cookies. As defense in depth, the cookie-to-token exchange on `POST /api/v1/auth/refresh` is origin-checked: a request that names a browser `Origin` must name the platform origin or a CORS-allowed origin, `Sec-Fetch-Site: cross-site` is refused, and an exchange authenticated by the `__Host-g5_refresh` cookie returns only the JWT, never the refresh credential. A page on a preview host therefore cannot turn the owner's cookie into tokens even though the browser attaches it on the same site.

Secure deployments use `__Host-g5_refresh` and `__Host-g5_github_app_pkce`, each with `Secure; HttpOnly; SameSite=Lax; Path=/` and no `Domain`. Browsers refuse parent-domain or narrower-path writes to these names, preventing a preview from planting another account's refresh credential or GitHub App attempt cookie. A custom `G5_REFRESH_COOKIE_NAME` also receives the host prefix unless already present; `preview_refresh` becomes `__Host-preview_refresh` and remains permitted through an outer G5 preview relay. Secure startup refuses `g5_github_app_pkce`, `g5_oauth_login`, `g5_oauth_scm` and their `__Host-` forms as refresh names because they would overwrite authorization-attempt cookies at the shared root path. Credential-cookie readers reject duplicate occurrences across all Cookie headers, even identical or empty duplicates, and empty or undecodable selected values. Unrelated cookie bytes, including non-ASCII app data, cannot block a valid credential or hide another occurrence.

The secure cutover accepts only the protected names. Existing browser sessions sign in at their next renewal, and in-flight GitHub App attempts restart. Replacement and clearing responses expire the former host-only cookies at their old paths; planted parent-domain cookies can remain but are never accepted. Existing access-token lifetimes and explicit body-token clients are unchanged. Plain-HTTP development retains the unprefixed names and original paths (`/api/v1/auth`, `/api/v1/github-app`), and cannot use secure-prefix names with `G5_COOKIE_SECURE=false`.

This does not provide full site isolation: preview hosts share a registrable domain with the platform, and the embedded preview's `SameSite=Lax` cookie flow and startup validation require that arrangement. Preview page JavaScript can still set a `Domain` cookie on that shared registrable domain (SEC-M43); rewriting server-issued cookies does not remove this residual. Moving previews to a separately controlled registrable domain remains later work.

## History

Until 2026-10-13 a platform-origin path relay served previews when no suffix was configured. From 2026-09-29 (PR #221) its responses carried an enforcing `Content-Security-Policy: sandbox`, cache suppression and service-worker retirement headers so that repository content could not run on the platform origin. That mode and its browser-cleanup headers were removed with issue 488; an installation that served platform-origin previews before 2026-09-29 and never ran the PR #221 rollout should still clear affected browser profiles' site data for the platform origin, because headers cannot repair a service worker registered before that date.
