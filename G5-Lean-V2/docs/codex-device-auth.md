# Codex subscription device authorization

Codex ChatGPT subscription turns use native device authorization inside the workspace's owner-bound microVM. API-key and OpenRouter routes are unchanged and do not invoke login. This replaces credential-file upload/copy and browser callback login; `CODEX_AUTH_JSON` remains rejected and scrubbed, never materialized. The obsolete `run-codex-live-validation.sh`, which required copying a laptop credential and referenced removed browser specs, is retired; use the checks below.

## Turn lifecycle

1. Dispatch freezes the provider route and arms a subscription-only `checking` gate on the task attempt before invoking the VM module. The VM runs `codex login status` against its explicit `CODEX_HOME` with the file credential store. An API-key login does not count as a subscription login.
2. If not signed in with ChatGPT, the module obtains a VM-local single-login lock and runs `codex login --device-auth`. It extracts the official verification URL and complete one-time code, stripping terminal formatting. Raw CLI output is never put in shared chat events or logs.
3. The owner's chat displays the link, code and a five-minute countdown. Challenge acquisition is separately bounded at 30 seconds; status and control-plane requests are bounded at 15 seconds. The CLI's advertised code validity can be longer than G5's wait.
4. A successful CLI exit must be followed by a successful ChatGPT login-status check and a current-attempt `ready` acknowledgment before the original prompt is sent. Prompt acceptance is recorded only after provider delivery.
5. Five-minute expiry ends the turn with “Device-code authorization timed out. Send any message to retry.” A new human message in the same chat queues behind the original prompt, as a follow-up on any running turn does: the checking/waiting attempt keeps its challenge, deadline and reservation, and the gate never learns of the message (`g5.chat.login-before-prompt`). After login the original prompt runs, then the queued messages in order, each with its own launch choices; they stay editable and withdrawable until reserved. Ready takes the task lock and enqueue takes the session lock then the task lock, so both succeed in either order.
6. Failure, the owner's Stop and VM loss before readiness end the turn without creating a provider continuation or uncertain delivery. Chat retains the failed input and a static explanation, and the messages queued behind it start the next turn, where each resolves its own route (including another sign-in if the cache was lost). Process-group cleanup kills login descendants. Another chat encountering an in-progress login ends with a clear retry notice instead of starting a second login. The `superseded` phase and its notice remain readable for attempts that a new message cancelled before this rule; nothing writes it for new attempts.

## Ownership and storage

The CLI owns token creation and refresh in the VM's `.codex/auth.json` (file mode `0600`). Tokens never go to the control plane and are not part of the harvested session files. This deliberately uses the same trust model as an owner-managed developer desktop: tools running as that owner can access the owner's local credential. No credential broker or same-user isolation is claimed.

The VM is inseparable from the workspace's single owner. Existing transfer admission stops and releases the old VM before changing ownership; if that cannot complete, transfer remains pending. The login lives in `/home/agent` on the VM's own disk, which the host deletes when the VM exits, so the new owner starts a new VM and signs in independently. This cache is not durable platform credential authority, and it can be lost on VM replacement.

Only the live owner-incarnation token can update the gate. Only the current workspace owner can read the challenge through the authenticated, `no-store` session endpoint. The short-lived code is encrypted at rest on the attempt, cleared when no longer waiting, and excluded from shared events and transcripts. Collaborators can see static failure text but not the live code. The UI hides stale or expired codes, including after a network failure.

Device authorization must be enabled for the ChatGPT account/workspace. See [OpenAI's authentication documentation](https://developers.openai.com/codex/auth/). The shipped Codex CLI pin supports `login --device-auth`; pin upgrades must preserve the documented output parser contract or update its fixtures.

API-key turns explicitly pass the existing local proxy's placeholder as `CODEX_API_KEY`, ensuring a cached subscription login cannot take precedence. The proxy still supplies the configured real API/OpenRouter key. This uses the CLI's documented [per-invocation API-key override](https://developers.openai.com/codex/noninteractive/#authenticate-in-automation); no API-key login command or credential-cache overwrite is involved.

## Validation

Rollout requires the updated control plane, migration 019, and the updated VM runtime image. Restart existing workspace VMs onto that image before testing subscription login: running VMs retain their old strict `agent.turn` parser and cannot perform this new flow. Non-subscription dispatch deliberately keeps the previous provider wire shape, so existing API-key, OpenRouter and Claude turns are not forced onto the new auth protocol during rollout. Deploying only the control plane does not enable device authorization on an already-running VM.

The native module must also retain the host-owned runtime loader environment after dispatch clears inherited variables. Linux guest binaries load their staged shared libraries from `/opt/g5/bin`; this path is restored independently of task secrets. Without it, `g5d agent-turn` can exit before reading its invocation (`control_channel_closed_at_start`), which surfaces as interrupted authorization even though Codex login never started. Startup failures retain bounded, redacted stderr and an exit code for diagnosis. Dispatcher integration tests deliberately do not inject loader paths as task secrets.

The full-stack preview runs its worker in local process mode. Its staged tool launchers must execute the installed paths directly: the worker-image Codex wrapper locates its npm closure relative to its own invocation path. Symlinking that wrapper into `runtime-process/bin` makes even `login status` fail with `MODULE_NOT_FOUND` before a challenge can appear. `worker-host-env.sh` stages executable forwarding launchers for host tools while retaining the host-build symlink for `g5d`.

Focused checks cover the real HTTP gate and task lifecycle (`api_task_lifecycle::codex_device_auth`), actual dispatcher/module subprocess delivery and cancellation (`dispatch_modules::codex_device_auth`), short-duration timeout and CLI failures (`g5d-agent` unit tests), and the owner chat card (`CodexDeviceAuth.test.tsx`). Retained transfer tests prove that the old VM is stopped and released before the transfer completes, and that the new incarnation gets its own credentials. Fake-provider login supports success, wait, disabled, failed and malformed modes; credentials are synthetic.

Local live verification on 2026-09-23 (Pacific time), using the rebuilt guest runtime and pinned Codex CLI 0.153.3: Chrome at `localhost:3000` displayed a real device challenge from the demo microVM and remained waiting for sign-in. Sending another chat message cancelled the first module, persisted `codex_auth_superseded`, cleared its stored challenge, and displayed a different challenge for the replacement turn. That cancellation observation is historical evidence for behavior replaced on 2026-11-09 ([G5Labs/G5-Lean#1189](https://github.com/G5Labs/G5-Lean/issues/1189)): a message sent during sign-in now queues behind the original prompt. The account login and post-login provider response were intentionally left for the owner; these observations do not establish authenticated completion. The loader follow-up passed 28 dispatcher integration tests, 85 dispatcher unit tests, 39 shared-runtime unit tests, the host loader-override regression, formatting, diff checks, and scoped Clippy with warnings denied.

Before release, run these live acceptance steps on the exact deployed candidate; hermetic tests are not proof of a real OpenAI login:

1. On a fresh owner VM, choose Codex subscription and send a prompt. Complete the displayed device challenge in your browser; verify that the original prompt runs once and a second turn needs no login. Never upload or copy a laptop's `auth.json`.
2. On a logged-out VM, allow the five-minute timer to expire. Confirm the code disappears, the turn ends, and any new message offers a fresh attempt.
3. While waiting, send two more messages. Confirm the same code and countdown stay (one authorization card, also after a page refresh), the messages appear in the queue, and after sign-in the original prompt runs first and the queued messages follow in order. Confirm no cancellation notice appears. Then, in a new logged-out attempt, press Stop while waiting and confirm the turn ends with the interrupted notice while a message queued behind it starts the next turn. Also test stopping the VM and disconnecting/reconnecting the chat.
4. Confirm direct API-key and OpenRouter turns work without a device challenge, including after a subscription login in the same VM.
5. Transfer the workspace to a different owner. Confirm the old VM is stopped and released before transfer completes, the old token is refused, and the new owner's fresh VM requires its own subscription login.
