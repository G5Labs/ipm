01 · Uplift

Uplift: recover and refine the intended behavior

StepWhat we do
1. Recover intentRead requirements, decisions, code and history. Resolve conflicting sources and list the capabilities to cover.
2. OntologyWrite concise rules for outcomes, permissions, data and workflows, including their exceptions.
3. TLA+/TLC model checkingModel important code paths and event orderings. Check where behavior can violate those rules.
4. Refine and reconstructCorrect vague or outdated rules and improve ontology coverage.
5. FinalizeRemove repetition; record unresolved decisions and code gaps. Keep the ontology readable.

PairSoft also had old ontology to reconcile. A regular uplift can start from documents, code and history alone.

03 / 19

The linked chat progressively strengthened the uplift procedure: confirm actual sources and provisional authority, use backend-only as the default, build ontology and models together, inspect breadth independently, and challenge what a replacement could omit while still complying with the ontology. Human tone, authorship and corrections matter more than a fixed file-type hierarchy.

Known implementation defects can coexist with a completed uplift; unexplored major capabilities or missing required checks cannot. A model link is not evidence that every clause of a feature was checked. Missing external sources remain a limitation on reconstruction confidence. Uplift and downlift are separately invoked workflows.

Source: current ontology-uplift skill; linked chat. This is the refined workflow, not a claim that every early step followed today’s rules.

02 · How modeling works

From an ontology rule to a TLA+ model

Example intent: approval must apply to the exact request content the approver reviewed.

Model elementMeaningPairSoft approval example
StateThe facts that describe the system at one moment.Request status, content version, submission identity, approval result and messages waiting for delivery.
ActionsThe steps that change those facts.Submit, edit during review, approve, recall, and deliver an approval result.
PropertyA rule that must hold for every allowed sequence.An old approval result must never approve new or edited content.
Bounds & assumptionsThe size and environment of the check.One request, two services, a few submissions; messages from different services can interleave.

The property comes from intended behavior. The actions come from actual code—including missing checks. This lets the model reveal a disagreement between them.

04 / 19

RA1 reduces content to a version because equality is what the property needs. It uses one requisition and tenant, with ordered delivery per producer but arbitrary interleaving across services. Failure/retry is separately modeled in DP. These are explicit abstractions and premises, not a whole-program translation.

DP has a unit-of-work model for staging, early saves, external calls, final saves and overlapping attempts, plus a delivery model for outbox, forwarding, a partition shared by two tenants and retention. PO models 16 statuses and the relevant callbacks and commands. The original campaign recorded 749 TLC runs; that includes expected counterexamples and controls, not 749 independent guarantees.

The coverage registry’s 65 features were 39 covered, 16 partly, four planned and six excluded. That denominator is more informative than counting passing configurations. Reproduction corrected claims about natural keys and handler ordering.

02 · Worked example

How TLC generates the stale-approval counterexample

Search the graph of possible states

  1. Start: generate the initial state described by the model.
  2. Expand: apply every action allowed in that state. Each possible result is a successor state.
  3. Check: test the rule in each state; queue new states for exploration and avoid re-exploring duplicates.
  4. Report: when the rule fails, follow the recorded path back to the start. That path is the counterexample.

The failing path · shortened

  1. Submit content A.
  2. Approve A; delivery of the result is delayed.
  3. An allowed edit changes the request to B.
  4. The old result arrives while status is “Awaiting.”
  5. The handler accepts it: B is approved without review.

Code link: the handler checks status but not the result’s version. Runtime replay accepted the old approval after prices changed.

Approvals’ own half was not executed, so this is a partial distributed reproduction, not a live end-to-end deployment reproduction.

The recorded run is RA1_AsBuilt_HumanApprover, TLC 2.19, at Git 2c8a288f. It found 303 distinct states and generated 591 states before reporting OrderBuiltFromReviewedContent violated, with eight states and seven action transitions; recorded elapsed time was 0.9 seconds. Bounds: two submissions, two content versions, a human approver and a non-admin editor. These are counts from this failing run, not a completed state-space exploration or counts of all state/action pairs attempted. Generated states include repeats and initial states. Worker scheduling can affect how much exploration occurs before the failure is reported.

The default search expands the reachable-state graph breadth first. An action can have several allowed choices and therefore several successors. TLC evaluates guards and these choices, remembers discovered states, checks the invariant and records predecessor information for error traces. It does not need an LLM to invent the failing sequence once the model and property are supplied. The agent does supply the model, property, bounds and code interpretation.

The two list deliveries enable the edit window; they are grouped out of the simplified explanation, not absent from the model. The repaired run later completed at 201,078 distinct states with larger bounds of four submissions/content versions; it is a separate run.

02 · Refine ontology

How the ontology changed

RuleBeforeAfter
Approval freshnessAn edit during review starts a new approval cycle.Accept only a result for the current submission and the content reviewed. A relevant edit supersedes that submission.
Receipt quantityA new receipt must respect the ordered quantity and any extra allowed by policy.Before accepting a receipt, add earlier receipts and all new receipt rows for each order line. Reject any total above that line’s allowed quantity.
Outdated receiving ruleA fully received order cannot receive more; receipts must never exceed the ordered quantity.With configured tolerance, allow more receiving up to the policy limit. Later policy tightening does not invalidate past receipts.

Two kinds of improvement: formal analysis made the first rules precise; model review and source reconciliation corrected the outdated receiving rule.

06 / 19

Approval requires both current-submission identity and content freshness. Checking an ID alone is insufficient if changed content can retain it. Conversely, using an aggregate storage version as the review identity can wrongly reject another legitimate approver after one vote changes storage. This precision came from the formal analysis and the review of its invariants.

Receipt caps are transition conditions, not a timeless invariant that every historical total must fit today’s policy. A later stricter policy must not retroactively invalidate processed receipts. Stable line identity survives display renumbering, and all repeated rows contribute to the same addition. The original reproduction accepted three units against an order of two via duplicate rows.

Thirty formal contracts were added in the amendment. No product repair or new TLC run was part of the subsequent structure-only ontology edit. Handwritten generalized proof arguments were not machine-checked TLAPS proofs. The claim is greater precision and bounded evidence, not completeness or exclusivity of discovery.

Source: ontology amendments c4abdb3b and coverage review §3.1–3.2. Approved-line edit exceptions remain scoped; stricter policy is not automatically recovered intent.

02 · The refinement loop

Ontology and model checking develop together

1 · Ontology

→

2 · Code-linked model

Edits, messages, status checks and delayed results.

→

3 · TLC

Challenge the rule

Can any allowed ordering approve content that was not reviewed?

↶

4 · Refine, repair and check again

Clarify submission identity in ontology; record the missing code check; verify the proposed repair and reproduce the failure.

Ontology gives the check its purpose

Business rules and exceptions define “correct.” Coverage review checks for missing outcomes.

Model checking gives the rule precision

States, actions and counterexamples expose missing timing, identities and assumptions.

They are co-developed: ontology guides the questions; formal analysis sharpens the answers. A TLC pass establishes the modeled rule within its bounds.

07 / 19

This slide describes the generalizable lifecycle. The original PairSoft baseline verification derived requirements directly from human-written designs and decisions because the ontology was on a different branch. The subsequent ontology review reconciled that evidence into the ontology. The current uplift skill makes the iteration explicit.

TLC does not prove an ontology complete or establish automatic code correspondence. It exhaustively checks the selected finite model. Source reconciliation, model-action coverage, code links and real-code reproduction remain separate checks. New policy still requires governing authority; a model assumption does not grant it.

  • Initial model checking distills the intended behavior and its states.
  • Agents use design reasoning to propose simplifications.
  • TLC tests alternatives and shows which simpler mechanisms still work.

09 / 19

The broader modular-monolith architecture was proposed before the six initial design models. It should be credited to reasoning about authority, state and recovery. Model checking then provided evidence for specific simplifications. It was especially useful for disproving tempting fixes: cancel whenever Ready still allowed bad traces; guarding only events with the watermark missed old snapshots.

D1 compared removing manager draft editing with remembering every editor and excluding them from review. Both could satisfy independence, but editor history added state and could make the configured quorum unreachable. Removing the capability was a deliberate policy restriction. A tool cannot decide that business tradeoff.

External systems still need durable obligations, deduplication or evidence, and explicit recovery. Consolidating internal services does not make external effects transactional. Tenant serialization trades simpler correctness reasoning for a measured throughput limit.

Source: design handoff; initial TLA design findings D1–D7 and S1–S6. “Minimal” means sufficient for selected outcomes; TLC does not prove global minimality.

04 · From design to implementation

Downlift the minimal design ontology

Turn the selected design into a working core

  1. Write the target ontology: core outcomes, owners, rules, exceptions and deferred features.
  2. Check the design: six concern models; seven design defects repaired; all 44 initial properties hold on the amended bounded design.
  3. Generate Rust and tests: implement the owned commands, then test real API, database and worker behavior.

TLC-derived tests: 19 added scenarios, 27 schedule variants and 102 receipt/correction cycles. Example: commit succeeds but its reply is lost; a retry must not repeat the effect.

Downlift carries the checked design into Rust and tests, including failure and retry sequences.

10 / 19

The initial target ontology had 16 pages and 61 commitments. Design checking added eleven blocks and amended 26. The complete catalog kept deferred functionality separate from the core’s implementation obligations.

The focused test addition extended 25 of 42 proposal families, reused existing coverage for thirteen and left four for future acceptance. Its 19 scenarios were not 19 independent test entry points. They ran through one fixture-owning test with controlled variants. Two source mutations, stale draft protection and source watermark protection, demonstrated sensitivity. The receipt oracle folded raw rows independently rather than calling the production logic.

A later continuation indexed 60 trajectories/403 states with explicit dispositions for environmental actions and repaired counterexample suffixes. This is finite correspondence testing, not an automatic full trace compiler or a formal implementation refinement. A valid repaired system should refuse the first unsafe action, not somehow execute the remainder of a broken trace.

04 · Verify the production code

Verus checks the Rust that makes the decisions

The business-rule kernel has explicit inputs and private state; database and network I/O stay outside.

Contract shape · explanatory pseudocode

transition(state, command, facts)

requires
  valid_state(state)
  complete_inputs(facts)

ensures
  accepted ⇒ valid_state(next)
           ∧ allowed_effects
           ∧ unchanged_unrelated_state
  refused  ⇒ no_business_mutation

The same function bodies execute in production; proof annotations are erased for the normal Rust build.

How the proof was built

  1. Translate ontology and TLA contracts into invariants, guards and effects.
  2. Prove each command and its loops, then the combined transition.
  3. Prove selected business predicates and link protocol steps to kernel commands.
  4. Check valid acceptance and refusal behavior; list trusted premises explicitly.

Initial milestone: 19 commands / 428 obligations.
Later backend and boundary work: 679 obligations, with a scoped trusted base.

11 / 19

The initial business-kernel proof was authorized after local implementation. The work first wrote a proof sketch and prototypes, then refactored the production transition into per-command functions and made relevant predicates verifiable. This was handwritten Rust with checked contracts, not a verified clone that production did not call.

Representative properties include submission/content binding, distinct authorized reviewers, one order per purchase, receipt/correction bounds, effect ordering, command replay and no mutation on refusal. Initial protocol models covered Effects, Fulfilment and Restore; their code links differed in strength and were expanded later. Acceptance completeness was also strengthened later, so do not retroactively attribute all final obligations to the first 428-obligation milestone.

Takeaways · TLA+ / TLC

TLA+/TLC: benefits and limits

What model checking adds

  • Systematic exploration: check all reachable states within chosen bounds, including event orderings and retries that example tests may miss.
  • More precise ontology: make identities, timing and recovery explicit. Counterexamples reveal contradictions and force sharper rules.
  • Guided design simplification: remove a mechanism and recheck the same outcomes and bounds before implementing the smaller design.
  • Better runtime tests: turn failing sequences and valid completion paths into concrete scenarios, instead of relying only on scenarios we think to write.

What it does not guarantee

  • Correct, complete obligations: TLC checks the rules supplied. A missing delivery or recovery rule can leave a real bug unchecked, even with an ontology.
  • Faithful code linking: an LLM can omit a branch, guard or commit boundary. Source links and reproduced traces add evidence; they do not prove that the code follows the model.
  • Every system size: a passing TLC run covers its configured states and assumptions. Larger models may be too expensive to explore.
  • Correct Rust implementation: TLC does not check actual Rust branches, arithmetic or updates against the contract. Verus can prove these properties for the code it verifies.

TLC checks the modeled design. Verus checks specified properties of the implementation. Both depend on choosing the right rules.

The added value is systematic checking of a precise behavioral model. A completed exhaustive TLC run checks reachable states in the selected configuration, rather than only sampled execution scenarios. This does not establish a universal defect-detection advantage over every possible review or test strategy, and there was no controlled whole-uplift trial with and without TLC.

The finite scope here is a limit of the TLC runs used in this workflow, not a claim that the TLA+ language can express only finite systems. TLA+ also supports theorem proving and refinement arguments. TLC can check temporal progress properties when they and the relevant scheduling/fairness assumptions are supplied; it cannot establish that a real provider or scheduler obeys those assumptions.

LLM code linking is a separate abstraction step: branches, error paths, identity checks and transaction boundaries may be omitted or represented incorrectly. File links, independent source review and runtime counterexample reproduction help assess that correspondence, but are not a formal refinement proof. In the original campaign, runtime reproduction narrowed one duplicate-effect claim after a database key was identified. In the later boundary campaign, pause/restore exposed the omitted eventual vendor-email requirement.

Verus adds proofs over the supported executable Rust and its contracts, including data updates and arithmetic. It does not automatically prove that the Rust contracts match a separate TLA+ model; that relationship still needs an explicit argument or proof. The TLA+ and Rust specifications can also share the same mistaken assumption, so ontology coverage and specification review remain necessary.

Verus: benefits and limits

What implementation proofs add

  • Beyond sampled tests: prove verified Rust meets its contract for every allowed input and state, under explicit assumptions.
  • Beyond a separate model: check actual branches, arithmetic and updates. Added boundary proofs connect decisions to loading and persistence contracts.
  • Protection during changes: rechecking rejects changes that violate a proved contract, even when existing tests still pass.

What it does not guarantee

  • Complete intent and proof coverage: ontology requirements must become formal rules and proofs. PairSoft proved many decisions, but not that the full workflow always finishes.
  • Unproved code and external services: SQL was proved against a model, not PostgreSQL itself. Some libraries and provider behavior remain assumptions checked by tests. Eventual completion also assumes workers run and dependencies recover.
  • Production behavior: these proofs do not establish throughput, deployment security or provider availability. Load tests, security review, live qualification and monitoring provide different evidence.

A passing proof guarantees its stated contract under its assumptions. Tests and operational checks still cover behavior outside that guarantee.

The guarantee applies to the code and properties actually verified, for inputs satisfying its preconditions and under its trusted assumptions. Verus uses deductive verification, so these function-level proofs are not limited to enumerating the small configurations used by TLC. Unsupported or excluded code requires separate treatment. A proof is not an independent judgment that the product requirements, preconditions or specification are correct.

The 40-mutation sample contained 22 changes caught by tests, fourteen caught only by Verus, two uncompilable changes and two specification-permitted survivors. One surviving refusal detail was subsequently pinned. These deliberate changes test the checks' sensitivity; 14/40 is not an estimate of real-world bug frequency or a universal detection rate.

PairSoft's recorded trusted base included unproved helpers, assumed specifications, uninterpreted functions and axioms, as well as Verus, Z3 and rustc. Tests covered the declared trusted leaves, but testing them is not a proof of their contracts. The wider boundary work proved selected SQL behavior over pgspec and a commit theorem; PostgreSQL matching that model, serialization and the binding to real handler execution still have their own evidence and premises. The whole deployed stack is not proved.

There are two separate coverage checks: do the formal statements express the ontology, and have those statements been proved across the relevant execution? The ontology states progress requirements, but the recorded Verus work did not establish full-system liveness. T8 checked that each reachable state in finite configurations has a path to rest once faults stop; that does not prove every fair execution eventually reaches rest. H15 also exposed a specification error: code and model both required an open tenant to request delivery, and neither had the eventual-delivery property that would reveal the lost obligation.

The remaining unproved components have different reasons: PostgreSQL was represented by pgspec rather than verifying the database implementation; some library operations were outside the supported or selected proof scope; live providers were outside our codebase and tested only through local substitutes in this record. Contract and integration tests check those assumptions without proving them universally. Scheduling, recovery and provider availability must be explicit conditions of an eventual-completion theorem, since application code cannot force an unavailable dependency to recover.

Verus can verify concurrency: shared-state invariants and proof-only ownership tokens connect atomic operations to allowed protocol transitions. Its official counter example proves the result for an arbitrary number of threads. PairSoft also proved transaction-level reasoning under a tenant-guard protocol, with static checks and runtime logs checking that real writers follow it; PostgreSQL implementing the model remains a premise. Safety under interleaving does not itself imply eventual progress. Anvil demonstrates liveness verification built on Verus using an explicit temporal-logic embedding, an environment model and additional proofs. This was additional proof work not completed for the full PairSoft workflow, rather than an inherent inability of Verus.

H15, lost automatic email during pause/restore, required real recovery tests and a missing progress rule. H17, a rendering performance regression, required A/B measurement. Real-provider conformance and customer deployment qualification remained separate from the local proof record. Security properties also require explicit threat assumptions, verification scope and deployment controls; business-rule proofs alone are not a deployment-security guarantee.
