# Discovery omissions versus false clearance

Every discovery reviewer reported at least two of the seven known material gaps; none
issued a whole-implementation clean report. The main diagnostic counts use explicit,
correctly identified issues, not any positive quality score.

A manual audit of positive assessment passages is preserved in
`discovery-positive-claim-screen.json`. Its keyword screen is an aid, not a semantic
classifier or a complete transcript proof. In the screened passages there is no explicit
claim that the exact missed future-warning exception or changed-default outcome succeeds.
Positive statements about owner/VM gates do not establish those omitted cases.

Several reviewers (including f11, f21, f31 and f33) supported persisted identity/lineage
and three-task progress counts at the supplied API test boundary while missing complete
synchronization scope. Those narrow supported assertions can be true alongside K7. They
must not be converted into a full progress-alignment pass. Similarly, successful backend
receipt replay after Stop is distinct from whether the frontend parent displays recovery.

Therefore the report distinguishes confirmed detections and omissions. It does not label
every omission a false declaration of correctness, or manufacture a precise per-obligation
false-clear rate from differently scoped prose. Explicit full-workflow false-clean stopping
is measured in the subsequent loop using its required `can_stop` decision. This is a
measurement limit of the discovery reports, and a reason to require exact evidence
boundaries when using qualitative rubric labels.
