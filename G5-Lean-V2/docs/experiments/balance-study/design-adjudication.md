# Design trial adjudication

Six GPT-6 Sol `xhigh` designs were judged against the [frozen protocol](protocol.md), without an overall score. Astra read all six plans before their work logs and selected public trace events, then checked consequential differences against the source contracts. This assessment was **not blind**: condition labels and the previously identified D1 base-transfer problem were known. There is one run per cell and two requests; this establishes examples and mechanisms, not reliability or an average treatment effect. No implementation or runtime behavior was tested here.

Inputs were frozen at `1738018cad0cb411a31f4c52539e2cf9f2443bd9`. Later base-transfer, legacy-guard and control-plane-admission clarifications were not available to these workers. Initial plans, work logs, patches, public traces and token metadata remain in the run archive (local run record `../runs/2026-09-28-balance-study/`). N had source/documents; O additionally had ontology and metadata; H had ontology and its required planning workflow, without application source/documents. These are different information/workflow bundles.

## Governing adjudications

**Base transfer is an inherited implementation gap, not an allowed new prohibition.** [VM API §1](../../workspace-vm-api-v9.md) line 34 and [main design §5.2](../../lean-backend-design-v9.md) line 289 expressly permit an org administrator to transfer a base workspace. The request restricts *offers* to non-base and preserves administrator immediate transfer. Current `workspace_vm_service.rs::transfer` calls `stop` (line 1575); `admit_stop` rejects `is_base` before the absent-VM case (line 2638). Reading only the transfer method's unused selected column does not establish the effective path. N/O propose codifying the existing mismatch; no new executable regression was observed. H's initial ontology patch (local run record `../runs/2026-09-28-balance-study/d1-h/initial/ontology.patch`) changes `g5.story.transfer-responsibility` to “transfer of a non-base workspace,” despite its plan's unqualified preservation language. That is a consequential narrowing/coverage omission rather than proof of an explicit blanket ban. The base-specific admin grant does not, by itself, establish an *exclusive* admin-only rule against an ordinary current base owner; these trials need not resolve that separate ambiguity to preserve the established administrator path.

**Legacy refusal must not become a ban on ordinary held work.** Main design lines 453 and 1131 restrict retained legacy execution outside common stop coordination, then narrow/remove that gate as producers migrate. Ordinary current tasks may be held by safe Stop and retained across transfer (lines 449–451). None of the D1 plans explicitly reverses this, so missing enumeration is not a demonstrated defect. Nevertheless T4 remains only partial handoff evidence: retaining “safe transfer” is weaker than naming this important legacy-versus-current distinction. H had the legacy heading and provenance available, but its self-review did not expose the body wording's lost qualifier.

**D2 stopped submission is a consequential policy departure requiring reconciliation.** The request's “no automatic VM start” is satisfied by all three plans, but it does not alone authorize all stopped-workspace writes. [Agent API §2.1](../../agent-api-surface-v9.md) lines 37–41 and VM API lines 30–32 require attached-owner admission for new execution controls/ordinary input; explicitly recorded compound Start is the queued-creation exception. O/H preserve that policy. N's new queued submission while stopped needs a specific, reviewed durable-control-plane exception or a change to its plan. Do not infer that every durable action requires a running VM: reading accepted retry results remains valid, and VM API line 202 expressly separates durable control-plane actions from guest admission. This is a plan/contract mismatch to resolve, not evidence of an unauthorized boot or an executed defect.

**Allocation ownership is the clearest useful retained-knowledge difference.** The frozen ontology's `g5.architecture.allocation_composition` and `g5.architecture.job_owner` require complete TaskService allocation with ChatService session creation inside the caller transaction; metadata warns that current JobService bypasses it. O/H explicitly carry that contract into the retry plan. N specifies atomicity and TaskService dispatch but leaves initial ownership unstated. Current JobService's direct task writes, for example around lines 1065–1090, cannot establish the desired boundary. The ontology conditions preserve a reviewed architectural correction that copying the existing implementation can miss. This supports the usefulness of retrieved intent/metadata; it does not isolate ontology syntax from extra information or show that N would necessarily code the wrong boundary.

**The successful-prerequisite alternatives are compatible.** All three use authoritative old success plus normalized same-workspace task edges, fresh logical identities and an immutable explanatory citation; none fabricates a successful new execution. The normalized-edge contract does not require endpoints to have the same job. Current failure propagation records `dependency_failed` and `dependency_task_id` (`task_lifecycle.rs` lines 3118–3127), supporting O's discovery. Retention restrictions, immutable success identity, cause selection under multiple failed ancestors, source input revisions and projection behavior still require coding checks. N's pinned output references “where applicable” and H's scheduling-only receipt caveat are reasonable compatible choices, not grounds for preferring one schema.

**Bootstrap support is extra scope, not an automatic failure.** The request permits reasonable policy. N/O's agent-only restriction avoids needing to reinterpret a command's instruction and graph-submission receipt. H detects a real duplicate-descendant risk and proposes canonical receipt remapping to handle it; its self-review visibly adds that commitment. It must still establish how an editable instruction maps to a bootstrap specification, how new task-map receipts preserve the bootstrap-success dependency, and what a revised instruction may change when a different graph conflicts. Current JobService can allocate a bootstrap command without a session/input (`job_service.rs` lines 634–641); H's general “fresh sessions/initial inputs” wording therefore needs a task-kind qualification. These are consequential, named source-compatibility checks and a broader design burden, not evidence that H's choice cannot work. “No outstanding human product decision” means the worker selected a policy; it does not close these engineering assumptions.

## What this stage supports

Retain ontology as a compact home for consequential boundaries and known implementation gaps: D2 allocation composition is a concrete useful example. Native source access remains useful for caller authority, notification ACLs, actual failure-cause fields and mismatches in reused operations. Those benefits can coexist; O already demonstrated both without mandatory ontology edits or a separate design-review artifact.

The additional H package produced durable, reviewable proposed commitments and explicit assumptions, and caught useful replay/bootstrap issues during self-review. It also spent more work on ontology maintenance, still narrowed an existing exception, and introduced a larger bootstrap compatibility problem. No unique correctness advantage of the full package over O is established here. Source-free planning should not certify reused behavior, and polished links, metadata pairing or a “reviewed” label must not turn assumptions into evidence.

Before implementation comparison, freeze one corrected design and allowed/refused cases for both coder conditions. Carry only consequential unresolved checks, including allocation ownership, accepted-result replay, source-success retention and any selected bootstrap policy. Do not treat a subsequent coding failure as proof that more planning text was needed, or these six designs as sufficient evidence for a broad harness change. Implementation and review trials remain separate stages under the parent's control.
