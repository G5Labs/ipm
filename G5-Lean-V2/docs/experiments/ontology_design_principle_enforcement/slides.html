G5 state machines in TLA+1 / 16
How it works

A model is a list of states and allowed steps

Workspace VM, main steps only. The code allows 11 changes between these states. The 3 rarer ones are not drawn, for example stopping → running when saving fails before the VM is told to stop.

  • States come from the database. A workspace VM is always exactly one of these 5 values.
  • Steps come from the code. Each place in the code that changes the state became one step. This model cites 31 code locations.
  • Rules come from the ontology. For example, a Stop must also cancel a Start that is still waiting in the queue (g5.lifecycle.stop).

How it works

The checker tries every order of events

  1. TLC starts from the first situation, for example "both workspaces stopped".
  2. It applies every allowed step, in every possible order, until no new situation appears.
  3. If any situation breaks a rule, it stops and prints the shortest list of steps that leads there.
Example: the WorkspaceVm check
Limits: 2 workspaces, an org that may run 1 VM at a time, a host with 2 slots, at most 2 starts in total.
1,024,237different situations
~1.5 minto check them all

Across all eight models, the 21 normal checks cover about 19.8 million situations. Normal tests run one order of events each; the checker covers every order within the limits.

Eight helper agents worked in parallel, one per model. Claude chose the areas, wrote their shared instructions, and reran all 21 normal checks (all pass) and all 31 problem checks (all fail as intended).

G5 state machines in TLA+6 / 16
highHostVm

A stopped VM can keep running after its slot is freed

  1. The host starts booting a VM for workspace A.
  2. A Stop arrives while the VM is still booting.
  3. Boot finishes anyway. The host deletes its record of the VM (workspace_vm.rs:349), then sends the kill (:351) without checking the result.
  4. Until the kill completes, the VM is alive but its slot counts as free. A start for workspace B passes the slot check (:283): 2 VMs on a 1-slot host.
11steps to free the slot early, with no failure, only timing
16steps to run 2 VMs on a 1-slot host
"Retain the VM handle, port, slot and workspace exclusion until child reap or valid independent exit proof, including failed boot/cancellation."g5.runtime.custody

The ontology's history already records this risk as R01, for the case where boot clean-up fails. The model shows it also happens when nothing fails.

G5 state machines in TLA+7 / 16
highWorkspaceVm

Stop does not cancel a Start waiting in the queue

  1. The user presses Start. The Start waits in the queue, for example because the org is at its VM limit.
  2. The user changes their mind and presses Stop. The code sees the VM is already stopped and answers "already stopped" (workspace_vm_service.rs:2685). The queued Start stays.
  3. A slot frees up. The queue job (:2100) starts the workspace the user just stopped.
3steps. No existing test covers this case.
"This fencing also applies when compute is already stopped but Start remains queued."g5.lifecycle.stop

highTaskLifecycle

Cancelling a running agent task can be lost

  1. An agent task is running. The dispatcher restarts, so the attempt ends as interrupted.
  2. Before that result is recorded, the user presses Cancel. The task still shows as running, so the code only sets a "cancel requested" flag.
  3. The result is recorded. For interrupted, the code moves the task to waiting and ignores the flag (task_lifecycle.rs:3600).
  4. The user presses Continue, or the VM restarts. The flag is cleared and a new attempt runs.
9steps. The same happens when a question to the user times out. Command tasks are not affected.
"Cancellation forbids continuation of that task."g5.agents.lifecycle.cancel

highWorkerHost

Deleting a host can remove it while a VM lands on it

  1. An admin deletes host h1. The code counts h1's VMs, finds 0 (worker_hosts.rs:1118), and does not lock the host.
  2. At the same moment, workspace w1 is placed on h1 and saved.
  3. The delete goes on and marks h1 terminated (worker_host_service.rs:824) without counting again.
  4. w1 is now recorded on a host that no longer exists.
5steps
A VM is never left on a removed host.rule we wrote for this model

Fix checked before coding it: count again just before terminating. With this fix, plus one for a related drain race, the rule holds across 8.6 million situations.

G5 state machines in TLA+10 / 16
medium

Two ways work gets stuck

TaskLifecycle

A task that depends on a failed task waits forever

  1. Task 1 is cancelled. Tasks already waiting on it fail with it.
  2. A new task 3 is created that waits on task 1 (job_service.rs:811). Nothing checks that task 1 already failed.
  3. Task 3 waits for a success that cannot happen. It stays queued until someone cancels it.
"As an owner, I can see downstream work fail when its prerequisite permanently fails."g5.story.dependency-failure · 2 steps
WorkspaceFlush

A failed save blocks every later Stop

  1. The user presses Stop. The system opens a save record and starts saving the workspace's Git state.
  2. The save hits a temporary error. After its retries the Stop gives up, but the save record stays open.
  3. Every later Stop, idle stop or fork needs a new save record. Only one may be open, so each is refused, until the VM dies or its lease runs out.
"Freeze one flush ID and repository vector across capture retries."g5.git.flush.identity · shortest case 6 steps

3 · Code and ontology

How we used the code and the ontology

The code: what can happen

  • The states, from the database. Example: stopped, starting, running, stopping, failed.
  • Every step and its conditions. Example: an "exited" event only counts if its VM id is the current one. About 220 locations cited.

The ontology: what must be true

  • 25 different rules used. WorkspaceFork alone used 9, such as g5.fork.names.collision.
  • It decides who is wrong. When code and ontology disagree, the project treats the code as wrong.

4 · Was the ontology useful?

Yes, as the source of the rules

Where it helped
  • Rules with exact wording. 11 of the 18 problems break a written rule, such as "Cancellation forbids continuation of that task."
  • A known risk to aim at. Risk R01 pointed at the VM clean-up path, where the most serious problem was.
  • A name for each problem. Every finding cites one rule ID, so a reviewer goes from rule to steps to code line.
Where it fell short
  • No list of states. Real database values such as reply_pending and queued_for_capacity never appear in it.
  • Missing decisions. If Cancel and Success arrive together, which wins? No rule says. The code lets Success win.
  • Unclear conflicts. A clean-up for silent hosts can never run, and nothing else removes unreachable hosts. Which is intended?
  • Rules kept elsewhere. Most save (flush) rules live in the v9 design document.

Wrap-up

Limits and next steps

Limits

  • Small limits, for example 2 workspaces, 2 hosts or 3 tasks. A pass means no problem within those limits.
  • The models are written by hand from the code. When a cited line changes, the model needs updating.
  • No problem has been reproduced on a running system yet.

Next steps

  1. Turn each failing sequence into a test that fails before the fix. Start with the VM that keeps running and the Stop that ignores a queued Start.
  2. After each fix, rerun that problem's check. It should now pass.
  3. Add state lists and the missing decisions, starting with Cancel versus Success, to the ontology.
