# Evaluation appendix for the three ontology-skill candidates

Status: prepared; no trial or application check has run under this appendix.
The [candidate briefs](ontology-skills-pr-candidates.md) supply the tasks. This ordinary
document defines evaluation; it is not a skill or permission to launch agents, implement
the candidates, or use external resources.

## Questions and limits

Measure whether governing ontology and explicit design review improve known-gap closure:
contract selection, design completeness, implementation conformance and total effort.
All three gaps were already diagnosed during uplift. Existing metadata and investigations
contain repair hints. Report guided closure separately from independent defect discovery.
A later genuinely new requirement would be needed to evaluate transfer to unseen design work.

Use stale Save first to exercise routing, allocation ownership next for architectural
value, and conversation recovery last for richer planning. A single run is a case study;
report individual repeated runs and variation before generalizing to a reliable benefit.

## Comparison conditions

Choose the comparison before preparing workers. Keep requirements, governing facts,
models/settings, tools, available time, source, environment and evaluation identical
except for the declared context treatment.

| Condition | Worker context | Question it answers |
|---|---|---|
| A: matched ordinary documents | Request and a concise ordinary-document packet containing the same governing facts; native planning, coding and review | Baseline for representation/retrieval, not a claim about every organic documentation workflow |
| B: ontology | Same facts in governing ontology, format/structure guidance and a planning handoff; no prescribed design-review pass | A versus B measures the ontology representation and workflow treatment |
| C: ontology plus design review | B plus the shared design-review guide and explicit planning review | B versus C isolates the additional planning review treatment |
| P: practical local workflow | Normal maintained skills, ontology metadata and authorized project memory | Measures useful guided delivery with accumulated knowledge; report separately from A/B/C |

For A/B/C, omit implementation percentages, known-gap footers, uplift investigations,
historical solutions and evaluator answers from every worker packet. Preserve governing
scope, exceptions and provenance needed to interpret a rule. Give A all the same
governing facts, including any prescribed ownership; do not make its task harder by
withholding policy. Reviewers receive equivalent governing obligations in each condition.
Keep the post-implementation review method/budget equal when comparing B and C.

Create a condition-specific instruction packet for an authorized trial. A/B intentionally
vary the normal local workflow; record that override instead of claiming to use the
ordinary profile unchanged. In B, supplying the full ordinary authoring/planning skills
would reintroduce their design-review instructions. Supply the permitted format/structure
references directly. Keep coding native in every condition; introduce no generation skill.

Source-free planning cannot open code or code-linked evidence. Reading a source-derived
gap from a footer still supplies implementation knowledge, even without opening code.
In P, record that knowledge as an allowed treatment. Do not call it independent discovery.

## Freeze before the run

Save one run manifest beside its artifacts containing:

- Run ID, condition, candidate, assigned scope, model/settings and resource budget.
- Source commit plus exact tracked diff and selected untracked inputs; hash the assembled
  source and ontology snapshots. A commit alone does not capture this dirty checkout.
- The exact request, fact-equivalence map, governing contracts, skill/reference bytes,
  metadata/memory policy and all worker/evaluator packet hashes.
- Tool access, effective AGENTS/CLAUDE instructions, discovered skills, hooks and memory;
  check inherited home/parent instructions as well as repo files.
- Separate checkout/database per implementation; named disposable dependencies and no
  implicit fallback to development services. Record unavailable integrations explicitly.
- Frozen criteria, applicable members, fixtures/fault points, required evidence,
  weights and execution commands after evaluator preflight against the selected source.

Before dispatch, confirm the recorded code gap still exists and the intended checks can
distinguish it. Retain a baseline receipt. A fixed candidate needs a new frozen case or
an explicit no-gap result, not a claim of repair. Evaluator source inspection and fixture
preparation are separate from source-free planning; do not send their diagnoses to A/B/C.

Use fresh worker contexts for compared runs. Verify actual access restrictions: putting
workers in another folder does not hide `.g5/uplift`, parent instructions, Git history,
other solutions or evaluator tests. Sanitize/isolate the permitted material and record
any contamination. Additional agents require explicit authorization. Preserve the local
human implementation handoff when applicable; record human edits/wait time in condition P.

Planning may choose an algorithm or API shape where the frozen request allows alternatives.
Evaluate its declared choice against common properties; do not impose an undisclosed
preferred solution. Resolve missing product policy equally for all conditions before
dependent implementation. Keep the original input and any amendment as separate evidence.
Distinguish inherited baseline defects, intended gap closure and new regressions. Set the
repair scope before running; an unrelated inherited defect must not silently expand the
task. Retain its evidence and scope label when reporting absolute conformance and changes.

## Frozen obligation ledger

Version 1 has eight equally weighted obligations per candidate. Each row is one criterion,
even when it has several providers, entry paths or failure cases. Freeze its applicable
members during evaluator preflight; do not inflate points by counting payload permutations.
All criteria are planned and unexecuted here. Exact commands and fixture paths are populated
only after the source snapshot and disposable environment are selected.

### Conversation recovery

| ID | Obligation / discriminating cases | Required evidence |
|---|---|---|
| F01 | Missing and refused native restore enter fresh-session fallback for both supported providers | Exercise each real adapter with captured local provider transport; inspect received context |
| F02 | Successful native restore retains its normal path; incomplete latest bundles cannot be selected as current | Restore selection trace and complete/incomplete generation cases |
| F03 | Undelivered uncertain/withdrawn/auth-failed input stays out; exact late acceptance makes prior unknown/withdrawn input eligible | Construct durable delivery histories and verify the selected context; withdrawal without proof is a negative control |

| F06 | Freeze evidence cutoff and prompt bytes/hash; identical retry is stable and later evidence affects only a later reservation | Race late acceptance against reservation, retry the same reservation, then reserve a later attempt |

### TaskService allocation

| ID | Obligation / discriminating cases | Required evidence |
|---|---|---|
| A01 | TaskService owns validation and writes for task/initial-input allocation, beyond a forwarding wrapper | Trace callers through the owning operation to protected persistence; inspect exposed raw writers |
| A02 | New sessions use ChatService's owning operation in the same caller transaction; existing sessions retain their identity | New/existing session cases, ownership trace and caller rollback |

Runtime checks must exercise the relevant implementation, transaction or editor boundary.
Local capture transports may replace an external provider but do not establish that
provider's remote behavior. A mock transaction cannot verify A03/A04. Classify unavailable
dependencies as unexecuted/environment failures; retain the actual failed command/output.

## Scores and measurements

For new trials, report demonstrated outcomes/defects, evidence coverage and effort
separately. The historical eight-row scores below remain reproducible diagnostics;
they are not calibrated quality grades or the primary basis for a winner. Validate
each expected behavior against the governing contract, including its scope and allowed
variants, before treating a failing assertion as a defect. Evaluate composed user
journeys across existing and new components. Keep ambiguous requirements separate from
failures; preserve explicit corrections to invalid evaluator judgments. See the
[Experiment 7 adjudication](ontology-evaluator-adjudication.md).

Keep an evidence row per criterion with governing block IDs, inventoried members, expected
outcome, actual result, source/check receipt and remaining limits. Judge the saved plan
before source inspection for specification clarity; judge implementation separately.

| State | Specification points | Implementation points |
|---|---:|---:|
| Supported | 1: clear governing outcome and material cases | 1: all applicable members satisfy the declared evidence requirement |
| Partial | 0.5: useful rule with a material ambiguity or omitted case | 0.5: concrete support for a subset; remaining members/evidence incomplete; no known material violation |
| Absent/contradictory or violated | 0 | 0-F: a demonstrated violating member or required control absent |
| Unknown/unexecuted | 0-U | 0-U |

For each axis, `score /10 = 10 × sum(points) / applicable criteria`. Default denominator
is 8 per candidate, weights 1. Any genuine N/A requires a predeclared reason and the same
scope in compared runs; unknown is never N/A. Report exact sums, supported/partial/0-F/0-U
counts and limits. Keep specification and implementation denominators explicit and do
not subtract unlike scopes. A material counterexample makes its criterion 0-F despite
passing siblings; report critical violations beside the score. Scores are scoped diagnostics.

Also report:

| Measurement | Definition |
|---|---|
| Case execution | Cases executed at the required boundary / frozen applicable runtime cases; report setup failures separately |
| Case acceptance | Cases satisfying the property / executed cases, with violated and inconclusive counts |
| Owner conformance | Allocation paths using complete owning operations / inventoried allocation paths; list bypasses |
| Public surface and locality | Added public operations with justification, responsibility owners touched and remaining raw writers; fewer files alone is not better design |
| Review value | Initial material findings, confirmed corrections, new regressions and residual findings; count shared causes once |
| Trigger adherence | Eligible workflow phases with an observed contract selection/review artifact / assigned eligible phases; instruction text alone is not execution |
| Cost | Planning, coding, review, repair and reconciliation wall/active time and available token/tool cost; preparation and human time separately; unavailable telemetry is unknown |

Footer percentages remain orientation estimates. Do not average them or treat clearer
ontology text as improved implementation. Keep the initial fixed ledger and later
discovered cases separately, even when the latter reveal serious new defects.

## Review checkpoints and reporting

1. Save the initial design, selected-principle trace, ontology diff and unresolved choices.
2. Save the first implementation snapshot and acceptance results before review repairs.
3. Record whether review is self-review or independent. An independent reviewer gets the
   request, governing design/contracts and implementation, without author explanations,
   prior findings or private evaluator answers. A fresh context is required.
4. Freeze initial findings, then allow authorized repair. Retain amended designs and
   later discoveries; never overwrite the original delivery result with its repaired score.
5. Report original and repaired scores, regressions, remaining gaps, cost and contamination
   per run. Include structural/inspection/runtime evidence separately. Do not report a
   plan, copied skill or passing harness test as an executed application result.

Keep all run outputs in new isolated run directories with the manifest, packets,
plans/diffs, pre/post repair patches, criterion/case ledger and raw receipts. These are
evaluation artifacts, not additional mandatory reports for ordinary coding.
