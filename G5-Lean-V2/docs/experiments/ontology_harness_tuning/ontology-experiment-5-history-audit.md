# Experiment 5 — audit of both agent histories

## Scope and conclusion

This audit revisits the complete available public-action timelines of both workers, their tool requests/results, initial and final artifacts, supervision messages and the supervisor's experiment history. It covers 207 ontology events and 138 plain events, including 190 and 126 tool-call events respectively. Those counts include orchestration calls; a single call can contain several shell commands. Public messages and observable actions support the findings below; explanations of attention or anchoring are hypotheses, not access to private reasoning.

Both frozen candidates remain unchanged: ontology `33e39619c8f4e4cfe1b4483da63dd5017be3dddc`; plain initial `afe18c47df129b6ae836ac1b3bde9fca67a5fae8`, final `b52d0c7c361a7d765b1af7b5ff1727bc3612277d`. This audit did not run new tests or change the ontology/harness. Behavioral verdicts use the previously retained executed checks; additional observations about test strength and the review process are identified as inspection.

**The two ontology-only final failures are concrete, tractable integration mistakes. They are not evidence of a problem intrinsically beyond agent reasoning.** Plain handled one during implementation and the other during generic self-review. The ontology worker had the relevant deadline policy in its tool results and still left the incompatible policy in place. For the notification defect, it failed to inspect an alternate terminal-state writer. The main weakness was translating stated obligations into the right source investigation and discriminating checks.

Ontology helped express required behavior and supported several useful repairs, but this run does not establish that it caused better code. More general principles would mostly repeat existing guidance. The strongest changes would be a few precise domain distinctions and a review mechanism that makes critical, unverified promises block a claim of implementation completion. That mechanism still needs judgment: an agent can write a weak test or an incomplete caller inventory.

## Two failures that particularly matter

### Ordinary deletion inherited authority to lose data

1. At **16:28:32**, O025 returned both the host trigger's unconditional `drain` reason and Stop branches that call `permits_deadline_loss()` and `record_unflushed_loss()`. O031 returned the enum's lossy variants. O070 even returned a reference to an existing expired-drain Stop test.
2. At **16:44:30**, the worker's new admission test failed because it expected `stopping` but received `running`. O116 then retrieved the actual definition: `Drain` permits deadline loss and is admitted through a deferred nudge.
3. At **16:44:44**, O117 changed the assertion to `running` and required `pending_stop_reason = drain`. That can correctly describe admission, but it does not establish compatibility with ordinary deletion's safety requirement.
4. At **16:47:37**, O133 described the nudge as confirmed existing lifecycle behavior. The final review honestly disclosed that full capture/Stop completion was unexecuted. The unchanged deadline policy nevertheless contradicted the approved design.
5. Plain read the same policy at **17:49:19–24** (P022–P023) and at **17:49:33** changed operator deletion to use the non-loss `User` policy (P024). Its shared before/after-deadline probes passed.

The ontology already required failed work retention and said authorized deadline loss did not itself grant force deletion. Its existing policy-sharing principle also required equivalent caller semantics. Therefore this is chiefly **failure to apply available knowledge and validate reuse**, with room to make the lifecycle authority distinction more explicit at its canonical owner. It is not simply missing documentation.

### A host notification bypassed cloud termination

The new ontology correctly required provider proof for occupied/forced deletion. However, an unchanged `host_drained` callback could write `worker_hosts.status = terminated` after local custody cleared. The new registry path selected draining rows, so that callback removed its work before provider teardown. The retained probe observed termination with zero provider termination calls.

Ontology inspected `host_control_state.rs` for VM force-settlement behavior (O095), but did not establish the notification's terminal-state semantics. Plain's generic review read this callback at **17:56:11** (P090), recorded the issue at P091 and repaired it at P094. That is direct evidence that a focused alternate-writer inspection could have found the ontology defect. No real-cloud experiment or difficult concurrency reasoning was necessary to expose it.

## Recommended priorities

1. **Apply semantic authority at the call boundary.** A compact lifecycle policy table should distinguish ordinary removal, force and scheduled maintenance; coding must validate the actual chosen policy before using it.
2. **Require evidence for each critical safety promise.** Record only a few rows: invariant, actual path/consumer, forbidden outcome, executed check and result. Deadline failure, notification-before-cloud and force/provider failure would have been the highest-value rows here. Refuse to equate an unexecuted central check with completed implementation.
3. **Inspect all state writers and shared-helper callers.** Searches must cross module boundaries. Check both the forbidden operation and existing valid variants after adding a guard.
4. **Review whether tests discriminate.** Seeded downstream completion and an unrelated busy-host guard can make tests green while the relevant integration remains wrong.
5. **Reduce reporting overhead and strengthen measurement.** Keep a compact current design, evidence outside production diffs and immutable runtime receipts. Retain separate intent, implementation and verification status; prefer explicit gaps to percentage estimates.

These changes plausibly reduce the observed failure modes. Their reliability benefit remains a hypothesis to test in further paired runs. This experiment supports keeping concise intent and review while making the transition from intent to implementation evidence substantially stronger.

## Overall takeaway

**The missing capability was reliable follow-through from intent to evidence.** The ontology already expressed much of the correct intent; the harness made the workflow visible but did not reliably enforce that follow-through. Adding more prose without changing how critical claims are checked is unlikely to address the observed problem. The two ontology failures were tractable integration mistakes: plain handled one during implementation and the other during generic review. The genuinely harder distributed scenarios remain separate, unverified concerns.
