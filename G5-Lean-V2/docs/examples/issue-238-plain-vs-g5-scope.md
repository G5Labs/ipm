# Issue #238: what G5 added beyond plain

Compared: [plain PR #257, `b50078d0`](https://github.com/G5Labs/G5-Lean/commit/b50078d0ff83d0535312b725c5184e735202d1d2) and [G5 PR #254, `ff55b2e3`](https://github.com/G5Labs/G5-Lean/commit/ff55b2e3ed8ec1c2e2558439f0710b3ff5123ea0). This expands the earlier eight-row summary to **18 distinct mechanisms/work categories**, including newer G5 fixes and verification.

[Original issue](https://github.com/G5Labs/G5-Lean/issues/238): owner Save and acceptance—including new files—commit/push affected files through one reusable file-list function; omit empty commits; remain minimal and production-quality.

**Plain:** callers write files, then share selected-file commit/push. **G5:** one coordinator owns write/recovery/commit/push and retains per-file versions/progress. Both omit empty commits and use the mapped internal branch, existing authority checks and selected-file Git isolation; these are not wholly G5 additions.

**Basis:** **O** = pre-existing ontology; **P** = initial plan or its new ontology, shown only when no O basis is recorded. Links name the relevant rule; they do not imply that it requires every implementation detail. P sections refer to the [original high-level design][initial-plan].

| Dimension | Plain | G5's addition/difference | Needed for code quality? | Required by issue alone? | Contract / design basis |
|---|---|---|---|---|---|
| 1. Save surfaces/triggers | Core flows; JSONL Save missing; HTML Apply also publishes. | Makes Save work in the JSONL editor too. It also keeps the HTML editor’s Apply button limited to saving the file, so applying an edit does not unexpectedly create and push a Git commit. | **Yes:** coverage/preserved behavior. | Save explicit; HTML preservation implied. | **O:** [Explicit Save][explicit]. |
| 2. Shared operation boundary | File-list Git helper groups repositories; writes remain caller-owned. | Gives one coordinator responsibility for the whole action: writing the files, recording progress, committing and pushing. Both Save and review acceptance call it, so each caller no longer has to recover unfinished steps itself. Each action covers one repository; neither design guarantees all repositories succeed together. | Good ownership for the chosen protocol; neither design is atomic across repositories. | File-list reuse explicit; complete recovery coordinator unspecified. | **O:** [Owner operations][commands]. |
| 3. Selected bytes/modes/paths | Staged-blob checks; normal Git staging. | Keeps the exact file contents and permissions selected for the action, instead of later committing whatever happens to be on disk. It captures files without following symbolic links and avoids Git filters changing their contents or directory staging pulling in extra files. | Prevent wrong content/path effects; exact mechanism optional. | Affected-file scope explicit; race safety implied. | **O:** [File confinement][confine]. |
| 4. Native index concurrency | Private index and branch CAS; ordinary index updates. | Locks Git’s staging area while checking and updating it, so a simultaneous Git command cannot have its staged changes silently overwritten. It also records enough information to recover an interrupted update to that staging area. | Preserve native staging; implementation choice. | Production-safety implication. | **P§3:** [Preserve staged state][initial-plan]. |
| 5. Save identity | No durable client Save-action identity. | Gives each new Save its own identifier. Retrying that Save reuses the identifier; intentionally saving again gets a new one, even if the contents match an earlier Save. The identifier helper also works when the application is served over HTTP. | Necessary for G5's replay semantics; browser compatibility fix. | Valid Save implied; nonce protocol unspecified. | **O:** [Action identity][identity]; [recovery][recovery]. |
| 6. Pre-write API intent | Same-content retry; no retained payload store. | Stores the intended file contents, permissions and action progress before changing the files. If a write succeeds but its response is lost, recovery still knows what that original action meant to save, even if someone has since edited the file again. | **Conditional:** protects original-action recovery across uncertain writes/later edits. | Not specified. | **O:** [Recovery][recovery]. |
| 7. Guest Git receipts | Commit/push returned OID; no durable feature journal. | Keeps a progress record inside the workspace VM for the Git steps, including commit and staging evidence. After an interruption or lost response, it checks what actually completed before continuing, instead of blindly making another commit or assuming the push succeeded. | Useful crash recovery; this store is not the only possible design. | Exact durable protocol unspecified. | **O:** [Outcome evidence][outcomes]; [recovery][recovery]. |
| 8. Partial acceptance | Push failure can leave applied changes open. | Distinguishes “the accepted edits are already in the files” from “the commit and push are complete.” If push fails, the UI can show that unfinished state without treating the edits as untouched proposals. Reject and Withdraw are guarded against contradicting changes already applied. | **Yes** to coherent decisions; status policy can vary. | Production-quality implication. | **O:** [Outcome evidence][outcomes]. |
| 9. Pending-work UI | Failure/retry through original flow. | Shows unfinished actions and a retry control in Changes, rather than relying only on the original Save or acceptance error. Pending work remains visible after the workspace stops or ownership changes, so a user can find what still needs attention. | Useful recovery UX; needed for G5's discoverability promise. | Not explicitly requested. | **O:** [Recovery][recovery]. |
| 10. Old-VM decision recovery | No equivalent retained-action settlement. | Can use evidence from remote Git to finish recording an acceptance even when the original VM is gone. When that evidence cannot establish what happened, it leaves a manual recovery path instead of replaying old writes against a different VM. | Prevent stranded decisions; automatic proof path conditional. | Not explicitly requested. | **O:** [Admission][admission]; [outcome evidence][outcomes]. |
| 11. Editor/authority fencing | Mostly inherited editor behavior. | Checks that a delayed Save still targets the VM the editor originally observed. A successful response marks only the submitted contents as saved, leaving newer edits unsaved. It also fences stale cache, Reload and late-response behavior that could replace the current editor state. | **Yes:** avoids stale writes/lost edits; includes inherited-gap repairs. | Safe integration implied. | **O:** [Save][save]; [acknowledgment][ack]; [live cache][cache]. |
| 12. Completed-state retention | No feature history to retain. | Removes stored file contents after completion but keeps completion records separately. Action identifiers never expire by time, allowing old retries to be recognized. Keeping those identifiers forever is a design choice; the cited rules do not establish that indefinite retention is necessary. | Cleanup useful; indefinite identity retention **not proven necessary**. | Not specified. | **O:** [Unfinished proofs][proofs]; [replay window][file-replay]. |
| 13. Input limits | Existing per-file bound; no equivalent aggregate file-list cap. | Rejects actions selecting more than 128 files or more than 32 MiB of combined file contents. These are additional limits on the whole action. The existing ontology allows 32 MiB per file, so it does not explain the new combined limit or the 128-file threshold. | Bounded inputs sensible; exact thresholds **need justification**. | Not specified. | **O:** [Per-file size][size]. |
| 14. Schema/legacy replay | No new database schema. | Adds database migrations 043 and 044 for the new stored recovery state. It also converts older records while respecting database access controls and keeps older retry records usable. This work follows from adding persistent state; whether deployed users needed every compatibility path is not established here. | **Conditional:** necessary if valid prior checkpoint state must survive. | Not specified; consequence of G5's chosen storage. | **O:** [Migrations][migration]; [evolution][evolution]. |
| 15. Admission-capacity retry | Bounded retries too: up to 20 at 100 ms. | When runtime capacity is full before work starts, retries the same action every 50 ms until its deadline. Plain also retries—up to 20 times at 100 ms—so the difference is the timing and deadline policy, not the presence of retry handling. | Useful integration handling; **not G5-only work**. | Reliability implication; exact schedule unspecified. | **O:** [Retryable refusals][file-replay]. |
| 16. Runtime/CI compatibility | Existing operations extended; fixture/platform test fixes. | Registers the new checkpoint operation with the runtime and updates compatibility checks so it can be called through the supported interface. It adds route-authorization checks and repairs a shared reading path exposed during verification. These changes support the chosen implementation rather than add user-facing features. | **Yes** for compatibility of the chosen implementation. | Implementation obligation, not extra product behavior. | **O:** [Module contract][module]. |
| 17. Verification | Five core feature cases across three browsers. | Adds 15 distinct feature scenarios in Chromium and more API, Git and UI failure tests. Plain covers five core scenarios across three browsers. G5 therefore checks more feature and recovery cases, while plain checks those core flows across more browsers; test count alone does not prove better coverage. | Meaningful regression evidence needed; exact volume unproven. | Verification implied; comprehensive E2E was a later instruction. | **O:** [Verification evidence][evidence]. |
| 18. Ontology/review records | No maintained design/ontology. | Keeps written contracts, the implementation plan and a current review so people can trace what the feature promises and why the design changed. The long troubleshooting history was moved out of the feature diff, reducing the material a reviewer must read. | Useful traceability; bulk history not necessary for correctness. | No. | **P:** [Planning/review workflow][initial-plan]. |

**How to read the basis column:** a relevant rule does not necessarily require the chosen mechanism. The initial plan itself cited [design.minimal-mechanism][minimal] and said no queue, scheduler or schema was prescribed. Recovery rules explain the direction of expansion; they do not prove every resulting mechanism economical.

The [public-history causal audit](../experiments/issue-238-ontology-harness-findings.md#7-causal-audit-useful-ontology-guidance-versus-excessive-interpretation) now distinguishes faithful application, agent-selected recovery guarantees, mechanisms made necessary by prior design choices, and unsupported strengthening. In particular, rows 6–10 are not directly entailed in full by their O citations: the approved recovery design and subsequent repairs explain the added work. Rows 1, 8 and 11 contain concrete scope/state defects; rows 12–13 contain unresolved lifetime/limit choices. G5 already had guest receipts and pending retry before the E2E follow-up; API intent/payload storage arrived later.

**Unsupported versus hallucinated:** absence from O/P flags an addition for scrutiny. A later explicit instruction or demonstrated defect can justify it. Without either, mark an unsupported scope/design choice; do not invent a governing contract. The weakest specific justifications here are aggregate limits and completed-identity lifetime. Conversely, having an O/P citation does not rule out overinterpretation: a broad outcome rule can justify a safety obligation without justifying the chosen protocol or its lifetime.

**Coverage/evidence:** this covers material mechanisms and supporting changes found in the pinned diffs, not every line or possible defect. No tests were rerun here. [G5's new live evidence][live-tests] aggregates targeted runs, with three feature cases rerun after the frontend UUID fix; in-flight lifecycle and API-crash gaps remain. The previous statement that the simplified version had no live E2E evidence is superseded. [Detailed comparison/cost history][full-results] retains its earlier revision boundaries.
