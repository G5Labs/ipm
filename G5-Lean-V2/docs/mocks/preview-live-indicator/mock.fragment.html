Preview: live indicator on the trigger, run log in the dialog

Today the only way to learn whether a preview is serving is to open the Workspace preview dialog and look at the Open button's colour. This mock turns the ribbon's monitor glyph "on" while a preview runs, and gives the dialog a run log that names the stage the preview is in and shows what the application printed.

Trigger indicator

  • The trigger reads the same GET /workspaces/:id/preview state the dialog already polls, now also while the dialog is closed (owner with a running VM only; one request per 5 s shared by every mounted trigger, like the VM status poll).
  • States: none (plain glyph), starting (amber, pulsing), serving (green, steady), closing (amber, pulsing), last failed (red, steady, until the next start). Colour is never the only cue: the tooltip and accessible name carry the state, e.g. "Preview — serving on port 3000".
  • A: lights the screen in the state colour (no dot) so the computer looks switched on; starting and closing breathe the fill. B: keeps the glyph and adds a badge like the notification badges. C: swaps the glyph (check mark when serving, slash when failed) so the state survives without colour. Recommendation: A.
  • Pulse is removed under prefers-reduced-motion.

Run log

  • A Log toggle sits beside Close preview; it opens a panel with a stage strip (Queued → Starting → Building → Serving → Closing → Closed) and the run's lines.
  • Source: the preview task's timeline, GET /tasks/:taskId/timeline, which already stores every guest event: invocation.started, each stdout line (module.output), module.preview.ready and the invocation.outcome with exit status, close kind and the stderr tail. Live updates arrive on the task:<id> WebSocket channel, which the client already appends into that cache.
  • The failure notice ("check the Preview task's output") becomes a View log link: the failed task id is still known, so its log opens in place. Today no screen shows a preview task's output.
  • Stage derivation: Queued = task created; Starting = invocation.started; Building = no ready event yet; Serving = module.preview.ready; Closing = the view's closing flag (Close is recorded on the task, not as an event); Closed/Failed = the outcome.

Assumptions to confirm

  • Both the application's stdout and stderr stream as output events tagged by stream (decided 2026-10-20; the guest frames each line and still keeps the last 4 KiB of stderr for the failure outcome). Against a guest older than that change, stderr shows only in the failure tail.
  • Polling while closed adds one light request every 5 s per open workspace page of an owner whose VM runs. Alternative: include the preview state in the VM status response, which is already polled, so no new poll is added.
  • The red "last failed" state stays on the trigger until the next start. Is that wanted, or should it clear once the dialog's notice has been seen?
  • Log lines are capped per entry (the guest splits long lines; the server truncates long content), and the timeline pages at 200 entries; the panel loads the latest page and offers "Load earlier".
