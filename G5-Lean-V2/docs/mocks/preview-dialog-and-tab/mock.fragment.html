Preview: one dialog shell with clear states, and the preview in its own G5 app tab

Issue #786 names two problems with the Workspace preview dialog: its controls mislead (a green but disabled Open, a quiet but active Close, a bordered card inside the dialog shell with a horizontal scrollbar), and Open sends the application to a separate browser tab. This mock renders the dialog in one Modal shell through every lifecycle state, with the run log from PR #693, and shows the preview opening as a top-level G5 tab beside the workspace.

1 · The dialog (Workspace preview): one shell, one dismiss, clear actions

2 · Open preview: a new top-level G5 tab beside the workspace

Dialog: what changes

  • One shell. The content renders straight into Modal (size sm; lg with the log open) with the shell's own padding, border and scroll. The inner w-[min(34rem,…)] bordered card is gone, so nothing is wider than the panel and no horizontal scrollbar appears; the action row wraps on a narrow viewport.
  • One dismiss. The × is "Close dialog" and its hint under the actions says the preview keeps running. The stop action is labelled Stop preview (today "Close preview"), so the two are never confused.
  • Open preview is only green when it can open. Starting and stopping render it on the neutral bg2 surface with full-strength muted text (not opacity on green), with a spinner and the label Starting… (variant A) or the unchanged label beside a lifecycle pill in the header (variant B). Ready: green with the app-window glyph (it opens a G5 tab now, not an external window).
  • Stop preview stays visibly available while starting and serving: an outlined button with full-strength text and a red stop glyph. While the stop runs it shows a spinner and Stopping…, and Open becomes not-ready again.
  • The status line is the one place the lifecycle is spelled out (role=status), so a screen reader hears "Starting the configured application" and "Serving on port 5173 · ready to open" as they change; the stage strip in the log repeats it as steps.

App tab: proposed behaviour

  • Open preview adds a tab to the top-level strip beside the workspace's tab, the same surface and opening path as a workspace opened in its own tab (useWorkspaceTabs, g5.workbench.tabs), and selects it. The workspace tab stays; the person switches between them with the strip or Ctrl/Cmd+Shift+arrows.
  • The tab's glyph is the lit monitor the ribbon trigger already uses (PreviewMonitorIcon), so it is distinct from the phase glyphs; its label is Preview · then the workspace name, so the kind survives truncation, with the profile and port in the tooltip.
  • The tab's page is a slim bar (workspace, profile, port, state pill, Reload, Open in browser, Stop preview) over the application, which loads from its isolated preview origin. The centre panel of the workspace gets no preview tab and no file-style tab.
  • Closing the tab (×) only closes the tab: the preview keeps serving and the dialog still offers Open, which focuses or re-creates the one tab. Stop preview, from the bar or the dialog, stops the application and runs its cleanup; the tab then shows "Preview stopped" with a way back and a way to start again.
  • One preview per workspace means at most one preview tab per workspace; a replacement (Close and start) reuses the tab with the new run.

Assumptions to confirm before implementing

  1. Route. The tab is a route the strip can store and restore, e.g. /:org/:workspace/preview; WorkspaceTab grows a kind: "preview" entry (name + org only, as today, so storage never goes stale). A reload of that route re-mints the session and reloads the application.
  2. Loading the isolated origin inside the G5 page. Previews are served only from https://<taskId>.<preview suffix> with a single-use handoff ticket that sets an origin-scoped cookie (g5.workspace.preview-origin-security, POST /api/v1/preview/session/:taskId). Inside an app tab that means an iframe to the handoff URL; the handoff cookie must then be accepted in a third-party context (SameSite=None; Secure, ideally Partitioned), and the preview host must not send X-Frame-Options / frame-ancestors that refuse the G5 origin. If either cannot be met, the fallback is the bar's Open in browser as today, and the tab shows why.
  3. Application WebSockets (Vite HMR and the like) must keep working from the framed origin; the proxy already requires the preview origin for upgrades, which an iframe preserves.
  4. Stop from the preview tab. The bar's Stop uses the existing cancel route and cleanup; it needs the workspace's preview read (GET /workspaces/:id/preview) from the preview route too, or the tab reads the state the dialog already polls.
  5. #693 coordination. The log region (stage strip + read-only hosted terminal) is taken from that PR unchanged; only the shell around it moves. The log's terminal is the one scroll region, inside the panel's max-h-[85vh] with min-h-0.
  6. Variant A (label swap) is recommended: the cue sits on the control it governs and needs no new element; variant B keeps the label stable for a screen reader at the cost of a second place to read.
