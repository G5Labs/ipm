## Findings saved before sharing

### F1 · P2 · A requested rerun can still report the previous passing result

**Path:** `backend/g5-api-core/src/services/workspace_pull_request_checks.rs:288–295,327–340,374–383`.

The reader treats `filter=latest` check-run conclusions plus unchanged PR SHA as sufficient terminal evidence. GitHub's documented rerequest transition queues the parent check suite and clears its conclusion but leaves the existing check run unchanged until the integration updates it. Consequently a rerequested green run at the same SHA is returned as `pass`; with no other pending work, the CLI immediately exits 0 even though a rerun is queued. The API never reads check-suite status. A same-SHA rerun/new attempt arriving between enumeration and the final head read has the same defect: only the SHA is revalidated.

This violates the current amendment's explicit requirement that a rerun during watch invalidate the corresponding earlier observation, under `g5.governance.pr.checks.revision` and `g5.data.outcome-evidence`. This is an already admitted rerun, distinct from the intentionally unsupported inventory of checks that have never been scheduled.

**Evidence:** [GitHub's rerequest transition](https://docs.github.com/en/rest/checks/runs#rerequest-a-check-run). An isolated Rust probe extracted the production `CheckReader::observe` and helpers, supplied a successful run linked to a suite whose GET response is `queued`, and observed `bucket: pass`; its request trace contains no check-suite request. The production CLI maps an otherwise ready/nonempty/pass-only result to exit 0 (`pr.rs:178–184,548–572`). Source inspection establishes the lack of same-SHA attempt revalidation. This probe is adapter evidence, not a full API/DB admission test or live GitHub evidence.

**Proposed repair:** incorporate current suite/attempt evidence into the terminal decision, preserve check identity across reruns, and revalidate the relevant terminal observations before returning them. Do not require an inventory of unscheduled required checks or add durable monitoring.

**Discriminating regression:** keep PR head A fixed, serve a completed-success run whose existing suite is queued with null conclusion after rerequest, and assert the actual public checks endpoint plus CLI watch stays pending. Then update the run/suite to current terminal success and assert watch exits 0. Also inject a newer same-SHA attempt during paginated enumeration and require old terminal evidence to be discarded.

### F2 · P2 · Redaction rewrites trusted protocol enums and breaks valid check reads

**Path:** `backend/g5-api-core/src/services/workspace_pull_request_checks.rs:158–160,474–489`.

The final recursive redaction walks every string in the assembled response, including G5-owned `availability`, `kind` and normalized `bucket` values. Runtime Config accepts arbitrary secret values (`config_service.rs:850–863`). With a legitimate configured value such as `pass`, an actual passing check's bucket becomes `[redacted]`; `g5d-cli/src/pr.rs:566–572` then rejects the response as an unknown bucket and exits 1. Values such as `ready` similarly invalidate repository availability. Provider text must be redacted, but schema discriminators must remain valid.

**Evidence:** the isolated probe executed the exact extracted production `redact` function against a representative ready/pass envelope with secret `pass`; result was `{"availability":"ready","checks":[{"bucket":"[redacted]","kind":"check_run","name":"[redacted] checks"}]}`. The consumer rejects this enum by direct inspection. This is a behavior defect, not a demand to weaken secret redaction.

**Proposed repair:** redact the provider-controlled content fields before constructing the trusted public result (and redact error/detail messages at their boundary), preserving normalized protocol enums. Keep names, URLs, summaries, text and annotations protected.

**Discriminating regression:** configure a secret equal to `pass` and have provider name/summary contain the same value. Through the public API and compiled CLI, assert those provider text occurrences are redacted, `bucket` remains `pass`, `availability` remains valid and a complete successful observation exits 0. Repeat with a secret equal to `ready`.

### F3 · P2 · An annotation read failure discards already available diagnostic output

**Path:** `backend/g5-api-core/src/services/workspace_pull_request_checks.rs:417–429` (consumer at `344–350`).

The fallible annotation fetch occurs before construction of the details object and uses `?`. If GitHub supplies a useful failure summary/text but its annotation endpoint returns 403, 429, 503, malformed data or exceeds the response bound, the caller replaces the entire details object with only an unavailable message. Already retrieved failure evidence is therefore lost. The agent may need no annotation to repair the error, yet the interface hides its available compiler/test summary.

This violates `g5.governance.pr.checks.details`: requested GitHub-published summaries/text should survive a partial diagnostic failure, with the missing part identified explicitly.

**Evidence:** the isolated extracted-adapter probe served a failed run with `summary: "Compile error: E0308"`, text and one advertised annotation, then returned HTTP 503 for the annotation endpoint. The resulting details had only `availability: unavailable` and an error message; summary/text were absent. No external URL was fetched.

**Proposed repair:** retain and redact output title/summary/text independently, represent annotation availability/truncation/error separately, and preserve the check's failure status. Rate-limit errors must still prevent unbounded polling.

**Discriminating regression:** actual public checks route receives a failed run with summary/text and a failing annotation endpoint; assert summary/text survive, annotation failure is explicit, no secrets survive, and check/CLI failure exit remains 1. Include a successful annotation response as the allowed case.

## Evidence and remaining boundaries

- Isolated files: `/tmp/g5-pr-checks-review-three/{adapter.rs,probe.rs,probe}`. `adapter.rs` was extracted from the current production file beginning at `valid_sha`; only the parent-module header-function qualification was adapted. The harness supplies a minimal query/error wrapper and a localhost provider fixture; production provider normalization, pagination, diagnostics, revalidation, truncation and redaction functions are unchanged. `rustc` reused existing dependency rlibs and wrote output only in the scratch directory. Initial localhost bind was sandbox-blocked; the same probe ran successfully after permitted escalation. It made no external HTTP requests or database changes. These are adapter-level runtime results, not a production public-route test.
- Read the added CLI tests covering field discovery, argument validation, exits, watch and fail-fast/error handling and API tests covering current head, redacted details, permissions/incarnation, limits and multi-repository failures. They do not cover F1–F3. No production tests were changed, and no parallel shared DB/build test suite was started.
- The current adapter queries only `pull.head.sha` and ignores the PR test-merge revision. [GitHub documents separate test-merge versus head statuses](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#conflicts-between-head-commit-and-test-merge-commit). The saved design explicitly left synthetic-merge behavior to protocol verification; no new fixture addresses it. This remains a material scope/evidence question: a merge-only failed status is not surfaced by this implementation. Establish whether the approved “selected PR” read promises those observations and either implement revision-labelled coverage or state this limitation explicitly. Do not silently label merge evidence with the source head. This is recorded separately from definite F1–F3 because the accepted design is explicit about observed-head checks but does not specify merge-ref enumeration.
- GitHub's reference-check endpoint itself limits results to the 1,000 most recent suites; the adapter's local 1,000-entry bound does not prove visibility of older omitted suites if those suites have no visible latest runs. This is another provider-completeness boundary requiring a realistic protocol case or an explicit limit description, not evidence that the added pagination test covers every provider limit.
- Missing production execution evidence: live GitHub/Cloud Build payloads, deployed App grant upgrades, personal-credential checks, cancellation via a real SIGINT, provider 429/timeout behavior and synthetic merge/retry attempts. Existing fixtures generally omit check suite identity/status and do not capture real rerun protocol.
- The four new ontology metadata entries still say unimplemented, and the current design still says implementation has not been verified. Main should update those entries and the amendment after coherent repair and actual test results; this reviewer proposes no meaning change to excuse the findings.

Implementation has the main API/CLI/read-only structure, but F1–F3 remain actionable. Verification is source inspection plus the isolated adapter evidence described above; main's suite results and live deployment evidence are separate.
