## Initial findings

### F1 — P2: successful preflight prose becomes a permanent error and incomplete UI state

Affected delta: `frontend/src/components/workspace/PrepareToShipModal.tsx:290-292` and the new `blockingMessage` error rendering in all three PR components; projection at `backend/g5-api-core/src/services/coordinated_repo_publication.rs:1727-1740` and `1767-1780`.

`blockingMessage` is not currently an error-only field. Both summary queries unconditionally fall back to `pr.preflight ->> 'message'`. `JobMergeService::build_preflight_response` (`job_merge_service.rs:1331-1374`) supplies nonempty messages for successful `FastForwardOrNoOp` and `CleanMergeNoGitConflicts` outcomes too, such as “All repos are no-op, already merged, or fast-forward eligible; existing direct publication can be used.” Consequently a normal successful PR response has a truthy `blockingMessage`; Prepare to Ship always treats it as provider attention, never marks that section done, and the three changed components display successful explanatory prose in error styling. Clearing the provider-failure event after retry cannot clear this value. The new backend assertions that recovered `blockingMessage` is null (`api_workspace_pull_requests.rs:3258`, `4220`, `4418`) also contradict the actual projection for real preflight results.

Required repair: make the supported error projection error-only, retaining actual blocked/conflict diagnostics and provider/automatic failure details, or distinguish the informational preflight message at the consumers without interpreting every message as failed publication.

Regression check: exercise an actual successful fast-forward and clean-merge API response through each UI component, assert no error banner and a completed prepare section; follow an automatic failure with successful explicit Update PR and assert the retry error actually disappears. Fixtures must use the server's real nonempty preflight messages.

Obligations: truthful provider outcomes in `g5.governance.pr.write`/`follow-push`, and authoritative result consumption (`g5.design.authority`).

### F2 — P1: retrying an included completed provider member overwrites its accepted evidence

Affected delta: `workspace_pull_request_provider_lifecycle.rs:581-637` now sends every recorded included/identical member through full `create_or_update_one`, and `:1099-1108` rejects its merged/closed provider PR. The explicit-mode catch at `:652-663` persists that rejection using `record_provider_status`.

Counterexample: a multi-repository G5 PR remains open while repo A's provider PR has merged and repo B still needs work (or local merge/import recovery is incomplete). A is now `SourceAlreadyMerged`/`Identical`. An ordinary Update PR with no title previously skipped A. It now fetches A's recorded provider PR, sees `merged=true`, returns “Provider PR completed during refresh; preserve its merge version,” then catches that error and writes a `failed` provider row. `record_provider_status` (`:2176-2205`) replaces `source_head_sha`/`target_head_sha` from the new candidate and nulls provider head/base evidence when `pull=None`, while retaining the PR number. If A's source has advanced to a commit already present on its target, this repins the accepted provider PR to the newer commit. Even without source movement it falsely downgrades a known merged member to failed. `preflight_one_provider_pr_for_merge` (`:1529-1550`) later compares the overwritten source pin with the completed provider PR's original head, so the new pin can prevent recovery of that accepted merge. The old included-member title path used `update_existing_provider_status`, which retained pins and recognized merged state.

Required repair: preserve completed provider state and accepted source/target/provider evidence in the newly expanded explicit reconciliation path. Admit only an open recorded member to current-head repinning; a completed/closed member must be reconciled or refused without passing through the candidate upsert that overwrites its evidence. Do not require another schema or parallel publication flow.

Regression check: create an actual recorded provider PR, complete it, leave the aggregate G5 PR open with another outgoing member, then call the public Update PR path (also cover `--title`). Test unchanged and newly included source variants; verify accepted pins and merged/provider evidence remain intact, no empty/new provider PR is created, and merge recovery still recognizes the accepted member. Cover provider completion racing the lookup too.

Obligations: current amendment's explicit protection of accepted merge pins, `g5.governance.merge`, `g5.governance.merge.effects`, and `g5.architecture.recovery`. This finding concerns the newly expanded included-member path, not unrelated existing merge redesign debt.

### F3 — P2: a local-only preflight refresh erases an unresolved automatic provider failure

Affected delta: the new latest-event projection at `coordinated_repo_publication.rs:1728-1730`/`:1768-1770`, together with removal of pending/error state and the reduced `needs_push_refresh` predicate (`workspace_pull_request_create.rs:649-664`).

An automatic provider failure is recorded as `provider_failed`. The query reads only the latest event of any kind. The incoming PR list's existing “Refresh local preflight” action calls `routes/workspaces.rs::refresh_workspace_pull_request` (`:5541-5581`), which performs no provider synchronization but records `refreshed` via `refresh_pull_request` (`coordinated_repo_publication.rs:1295-1330`). That immediately hides the automatic failure and its manual retry instructions even though the provider operation has not recovered. With an existing provider row, its mismatch may later trigger a new failure, but the user-visible failed state is still falsely cleared in between. With no recorded provider row (for example a previously local-only PR gains its first outgoing remote member and automatic provider creation fails before recording a row), local refresh advances the heads, `provider_mismatch` is false, and further maintenance sees no work: the failure and recovery action stay hidden until a user independently chooses Update PR.

Required repair: an unrelated local evidence refresh must not settle a failed provider-publication outcome. Derive disappearance from successful completion at the provider/publication owner while continuing to use existing history/outcome storage. The design refinement saying “successful refresh/provider events supersede it” should distinguish complete publication from the local-only refresh operation.

Regression check: induce an actual automatic provider failure; invoke the public target-side `/pull-requests/:id/refresh` endpoint; verify the actionable failure remains in source and target summaries until the public Update PR flow successfully reconciles it. Include a first-provider/no-recorded-row case as well as an existing provider row.

Obligations: `g5.governance.pr.follow-push` (failure identifies incomplete publication and manual recovery), `g5.design.authority`, and `g5.architecture.recovery.progress`. The user permitted manual retry, not silent settlement of the failure by an operation that never attempted publication.

Additional inspection note (not a separate confirmed defect): event timestamps default to transaction-start `now()` and IDs are random UUIDs. Multiple provider events in one transaction therefore do not have reliable insertion order under `ORDER BY created_at DESC, id DESC`. Any repair continuing to infer a PR-wide result from a single “latest” member event should test mixed member success/failure and rely on aggregate/current outcomes rather than UUID order.
