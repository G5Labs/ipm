## Initial findings (saved before sharing)

### C1 · P1 · Bound failure-record admission as well as publication

`backend/g5-api-core/src/services/workspace_pull_request_create.rs:518` opens the failure-recording scope **after** the new timeout future has completed. The maintenance worker no longer has its outer per-item deadline. `caller.source_db` first calls `scoped_db_for_user_actor_in_org`, whose current-authority admission executes `authz.lock_user_scope_authority` and takes `FOR SHARE` on the owner's `org_memberships` row. The continuation's `SET LOCAL lock_timeout='5s'` is applied only after that helper returns (source_db_for_target lines 168–194).

Counterexample: retain a transaction's conflicting lock on the first PR owner's membership row while that PR has fresh source work. Publication reaches its deadline; error recording immediately retries the same membership lock without any deadline or lock timeout. It can now wait indefinitely, retaining singleton scan leadership and preventing every later PR/organization and every follower from progressing. Before this patch, the worker's 120-second wrapper bounded this entire path.

Governing: `g5.architecture.recovery.progress`, `g5.governance.pr.follow-push`, and the pinned follow-up's bounded error recording requirement. Fix by bounding the complete failure-recording stage including capability/scope acquisition (or setting the applicable lock/statement limits before current-authority admission) while leaving durable inventory available for subsequent retry. Regression: hold membership authority locked beyond a shortened attempt/error-record budget, require the first call to settle and a later organization's PR to refresh before unlock, then release and verify recovery. Existing new deadline test blocks the PR row only and releases it after 1.1 seconds; it does not cover this admission lock.

Evidence: source inspection of refresh owner, maintenance scan, `db/scoped.rs:691–723`, `PermissionService::require_user_scopes_on_conn`, and migration 042's membership `FOR SHARE`. Not runtime-reproduced by this reviewer.

### C2 · P2 · Preserve target-error retry for stopped workspace owners

`frontend/src/pages/WorkspacePage.tsx:10402` gates the new target-error banner on `!workspaceReadOnly`. That flag includes `!ownerHasRunningAttachment`, so a stopped owner never sees the error or Retry. The ReposBar Create PR action is still present for this workspace and disabled because the failed target query yields no choices. Thus the original hidden-error condition remains for an allowed PR-creation variant.

This is not a forbidden operation requiring compute: `WorkspaceRuntime::prepare_pull_request_source` explicitly returns success for `None | Some("stopped")` when no VM incarnation was required; the public UI caller is that variant. `handleOpenCreatePullRequest` also has no running-VM requirement. Use the durable operation's eligibility (for example existing `canManageDurableOwnerState`) rather than live-edit eligibility, or show query recovery wherever the action is visible. Add a stopped-owner query-failure/retry test and verify Create PR becomes reachable without starting compute.

Governing: `g5.governance.pr.write`, `.target`, shared flow/no implicit compute authority, and the pinned follow-up's visible target failure before opening an action. Evidence is actual UI and runtime source; the new mounted test covers only its running-owner fixture.
