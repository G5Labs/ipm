## Raw finding

### R3-F1 — P2: Preserve loaded PR destinations through transient refresh failures

**Owner and governing rule:** `useWorkspacePullRequestTargets` and `WorkspacePage`; main's `g5.workspace.page.refresh` requires loaded content, typed text and last-known controls to remain through transient failures, with a visible stale status. `g5.governance.pr.target` still requires server-owned choices and current server authorization; retaining cached choices for a transient failure does not replace those checks.

**Path:** `frontend/src/hooks/useWorkspace.ts:488–500` maps the query through `toAsyncState`. When a previously successful destination query refetches and returns a network/503 error, that helper returns only `status: "error"` even though React Query retains the loaded choices. `frontend/src/pages/WorkspacePage.ts:6641–6644` replaces them with `EMPTY_PR_TARGETS`; the default target becomes null at line 6662 and the open Prepare to Ship modal is unmounted by line 11504. Its edited description is component-local (`PrepareToShipModal.tsx:223`), so the draft disappears. The Create PR dialog's explicit selected destination is also reset to an empty ID at lines 6697–6708, then to the first default when the query recovers. This can silently change a user's destination after a temporary failure. This path is introduced by the branch's separate destination query and is not repaired by main's retained workspace-detail state.

**Concrete trigger:** Load valid parent/Base destinations, open Prepare to Ship and type a description (or choose a non-default target in Create PR), then let focus refetch or workspace invalidation receive a transient 503. The error banner is visible, but the loaded choices and dependent component state are lost. Recovery remounts the modal with its initial description and resets the selected target.

**Evidence:** A mounted `useWorkspacePullRequestTargets` probe executes the actual hook and real React Query with the API method mocked at transport: first read succeeds, invalidation causes a 503, cached data is asserted still present, then the governing `status === "ok"` expectation fails with actual `"error"`. Run: `node node_modules/vitest/vitest.mjs run --config vitest.config.ts` in `/private/tmp/g5-rebase91-review-three`; one test failed in 65 ms (514 ms overall). Modal unmount/draft loss and destination resetting are source-traced, not yet exercised in a mounted full-page test.

**Proposed repair:** Return `RefreshingState` via the existing `toRefreshingState`, keep the last choices for transient failures, and expose `refreshError` in the destination status/retry UI while preserving initial-error and refusal behavior. Keep the modal mounted and the explicit selection unchanged during a transient refresh. No new retention store or endpoint is needed.

**Regression checks:** At the full page, load destinations, open Prepare to Ship, edit the description, make destination refresh return 503, assert the modal and text survive with stale status and retry, then recover. Separately select a non-default Create PR target and assert it survives the same sequence. Initial failure still disables the action with retry; 403/404 refusal must not reuse the choices. Include a successful refresh removing a target, which should still update valid selection normally.
