# Code review prompt, review loop option and Re-run Verification — request and interpretation

## User instructions (2026-11-01)

- Scope of this PR: "the code-review prompt and UI".
- Code review prompt: "Please do the code review for the current PR. You should identify all requirements of this PR (e.g. initial requirements in project docs, design and plan, the ontology edits and relevant ontology blocks). You should fix everything that you find against the scope of this PR. Note: you do not need to fix any behavior that are not concrete bug fix, or not in the requirements and ontology and are not reasonably inferable. You will do an review and fix loop of [[N]] iterations, each iteration you will start from a fresh session to do the review and fix. In the end, create a very concise review report in the project docs (if there exists one, update it) for what you have fixed and optionally what uncertainty you have."
- "The UI for code review will be the current page of chat with pre-loaded prompt. But at the very top, there is a option: 'Review in a loop with N iterations' the default is 1, and then you should explain. More iterations will have stronger coverage, fix more issues, gain more confidence at the cost of more time and token spent."
- "add a new button in 'Integration Engineering' tab before 'Create PR', called 'Re-run Verification'. Clicking on this will be similar page as code-review, but the prompt is something like 'Please identify all requirements and relevant ontology of this PR, read .agents/guidance/pr_incremental_TLA_reverification.md, follow it to complete the full workflow for this PR's incremental re-verification. If you are genially blocked because of significant gaps in foundation or missing crucial dependency, stop and report honestly. Otherwise, make reasonable assumptions, skip minor blockage, and do not stop until you have satisfy the guidance's completion gate.'"
- "Before this chat, there should be a line of bold text 'This task will build new or update existing formal state machines and run formal verification to check your PR's changes against its requirement and existing codebase's behavior. It will prove strong guarantee for the code behavior and fix hard-to-discover issues on security vulnerability, PR's feature completeness, integration issues of the PR, and any regression risks caused by this PR. Warning: this is very expensive process.'"
- "should be a very low risk feature."
- Follow-up (2026-11-01): "I want an admin config that has a toggle to turn this on and off. If this is turned off the button will not show up in the UI or greyed." Asked whether existing functionality could be reused, then chose: "Greyed", "off by default", and the agent's recommended placement (a Workbench actions section on the Admin page), and added it to this PR's scope.

## Agent interpretation

- The code review prompt is used verbatim, with `[[N]]` filled in from the option ("1 iteration", "N iterations"). Every existing review entry point uses it: ribbon Code review, the review banner's Run agent review, and the seed on arrival at a review copy.
- The verification prompt is the quoted text with its typos fixed ("genuinely", "satisfied", "blockers"). It points at `$HOME/.agents/guidance/pr_incremental_TLA_reverification.md`, because the harness installs guidance in each VM's home, not in the workspace's repositories. The bold notice is used verbatim.
- "At the very top" and "before this chat" mean the top of the fresh chat that the seed opens, above everything else in it. The option and the notice last exactly as long as the seeded draft: they go away when it is sent or emptied.
- The admin toggle reuses the organization-only boolean switches that already back Issues and the external-checks merge policy (organization Runtime Config, written only by administrators, read by members). "Turned off" greys only the Re-run Verification button; it does not stop an agent from doing the same work when asked in other words.
