# Unified Approvals page

Authorized branch: `issue-704-simplify-approvals-page-and-unify-human-agent`.
Source: [issue 704](https://github.com/G5Labs/G5-Lean/issues/704), requested implementation in this workspace.

## Governing change

The existing approval service remains the owner of quorum and human assignment/decision admission; the formal agent service remains the owner of paid execution and frozen retries. The page composes these operations and the canonical review UI. It introduces no batch lifecycle or merge-validity policy.

[Request selection](../../ontology/features/reviews.g5.md#g5.governance.approval.selection) owns bulk/specific semantics. Selection is requirement-first: bulk skips satisfied approvals unless explicitly included and preserves pending coverage; Any-of adds exactly one selected eligible recipient, while agents-only never selects humans. Specific selection includes only checked requirements. Unresolved Any-of choices require named or random resolution, displayed before admission. [Request presentation](../../ontology/features/reviews.g5.md#g5.governance.approval.request-composer) clears a fully accepted previous batch on opening; unresolved/failed operations retain their frozen retry inputs. Bulk selection hides already-covered/satisfied requirements from its primary list and folds skipped/blocked context into a summary. The immutable submission holds resolved recipients, definition versions, notes and per-recipient operation IDs; retries resend only failures with the same inputs and identities. Server owners recheck current authority/prerequisites rather than trusting the picker.

[Agent replay](../../ontology/features/agent_approvals.g5.md#g5.agent-approval.admission-replay) extends retained run records with append-only operation aliases. A workspace/requester/client-ID lock precedes lookup and admission. Each alias binds normalized definition/version/phase/frozen-retry inputs to the admitted run, including when admission reuses an active run. Terminal replay returns that same receipt before any fresh assignment, preventing a lost response from becoming a second paid run. Reusing the ID with unequal inputs conflicts. Ambiguous-commit confirmation must prove the alias and its exact normalized inputs were committed, including when the run already existed. This uses retained review/request evidence and the existing request-slot fence rather than a new operation ledger or coordinator. Existing clients may omit the identity; the unified composer always supplies one.

[Overview](../../ontology/features/reviews.g5.md#g5.governance.approval.overview) presents three equally prominent top-level sections: Approvals Required to merge into the configured parent with Request, Reviews with Start Review, and Configure Approvals Required to merge into this workspace. Alphabetical linked requirements retain each reviewer's latest decision independently of active waits. Each approval's info button reveals its [full request/decision timeline](../../ontology/features/reviews.g5.md#g5.governance.approval.timeline) in place, grouped by reviewer with entries and events newest first; requested or decided approvals absent from the current parent requirements sit below the required list in a Legacy approvals group, collapsed by default. Each keeps its info timeline, including decision-only legacy evidence. The DTO does not distinguish retired requirements from discretionary approvals, so the group states only that the parent does not currently require them. The final configuration section is visible without an Advanced disclosure. Workspace commit/push controls belong to Source Control and are absent from Approvals. A missing merge target is explained without inventing outgoing requirements. This amends the original page layout in response to the human's follow-up.

[Decision evidence](../../ontology/features/reviews.g5.md#g5.governance.approval.evidence) binds reports through their own request/run evidence, never a newer run. A currentness popup compares pushed vectors independently of outcome and merge admission, retaining added/removed repositories and explicit unknown evidence. Captured source and recorded target/base context are identified separately.

The service's retained history includes legacy decisions without request details and multiple immutable decisions on one request. The per-approval read model retains those records as decisions, alongside complete request cards, without synthesizing requests or attaching a newer report. Missing request state is Unknown. Historical-only approvals remain inspectable when they contain decisions even if no request record is retained.

The existing human decision dialog retains captured vectors and session drafts and is placed beside its addressed requirement. Start Review uses the existing fork/open/reopen operation in the Reviews header, retaining a successfully created copy even if VM start fails. Nested/temporary formal workspaces expose no start action. The existing fork owner requires a `workspaces:write` token for creating the caller’s own review copy; hide Start Review for a token lacking that scope while retaining source-reader admission and source ownership checks. This is an existing prerequisite, not authority to write to the source. Target-less workspaces keep incoming administration without an invented outgoing roster.

[Review-item semantics](../../ontology/features/reviews.g5.md#g5.governance.review.items) explain that a published review is a shared review submission (a pushed round or a direct doc/file annotation publication). An open item is one unresolved suggested edit, doc/file review comment or other review item. An overall summary/verdict can be published without individual items; resolving all items also leaves a published review with zero open items. Counts continue to describe the existing publication and item records. [Contextual help](../../ontology/features/reviews.g5.md#g5.governance.review.help) through a shared accessible disclosure owns this explanation and workspace-comment guidance; keep it closed by default.

[General workspace feedback](../../ontology/features/reviews.g5.md#g5.governance.review.comments) belongs to the existing comment owner and has one creation action in the Reviews header, beside Start Review when eligible. Opening it reveals Reviews; the general comment threads remain under Workspace comments. This keeps the sole entry discoverable without scrolling through explanatory text and published reviews, as required by the narrow-layout keyboard journey. Activity links there. Contextual doc/file comments and replies keep their existing content/thread owners. Reuse shared threads and drafts; do not migrate comments or synchronize them into duplicate publication records. The [follow-up chat](../../chat_intent/issue-704/approvals-follow-up.md) is the source for consolidating general comment creation.

GitHub issue comments have a separate external destination. Move their existing composer from Activity to the full Workspace Issues section; the rail and Activity navigate there rather than mounting more composers. Reuse the existing activity projection for admission and pending publications, and refresh it after issue-link changes. Preserve the existing user/workspace/destination draft keys, submission IDs, primary-issue target and unknown-outcome recovery. This split is the agent’s stated default after asking for the user’s preference, not a confirmed human choice.

A shared server-owned inventory projection opens an explicit system capability on the system pool, scoped to the already-authorized organization (avoiding nested acquisition from the request pool) and reads only formal review workspace/VM summary fields after request authorization, with explicit organization and source-workspace audience predicates. Reuse it for workspace and compute inventories rather than weakening private-workspace RLS. Derive identity from the existing review/workspace binding; add no lifecycle or projection storage. Home and Projects label these entries Agent review, route inspection to source Approvals, and offer no live workspace controls. Shared fork-source and merge-target pickers exclude these private inventory summaries. Human review-copy filtering remains unchanged.

The schema-3 rollout uses the existing runtime negotiation: a dedicated `agent.turn` module and a new catalog identity exclude older hosts before paid execution. Preserve the historical formal module for frozen schema-2 retries. API coordinators share durable invocations, so this transition requires nonoverlapping API deployment; the Helm API strategy is Recreate for every replica count. This extends the default single-replica deployment's existing behavior to multi-replica upgrades, trading rollout continuity for absence of incompatible old readers. Recovery follows the existing forward-only deployment policy rather than rolling old readers onto new stored assignments. No separate schema-activation state or compatibility ledger is introduced.
