Question 1 · Upload transcript vs Extract decisions

Today "Upload transcript" stores the file under meetings/ and immediately runs "Extract decisions" over it, so the second menu item is only for a transcript that is already in Project Docs (imported, edited, or re-run). The variants below make that relationship visible. Change the open document in the bar to see the gating.

1A Keep the menu, say what each item does, gate by the open document

Pattern: disabled-with-reason (g5.ui.unavailable-actions), ellipsis marks the item that opens a dialog. For: smallest change, all three paths remain discoverable. Against: the dominant path still sits behind a dropdown.

1B Split button: upload is the button, the rest is the overflow

Pattern: split button, one primary CTA per group (Apple HIG "primary-action"). For: the 90% path is one click; secondary paths stay one click further. Against: the ribbon has no split control today; two hit targets in 68px.

1C One button, the dialog holds both sources

Pattern: progressive disclosure inside one dialog. For: no menu; the user chooses "upload a file" or "use a transcript already in Project Docs" where they see both. Against: Apply accepted decisions needs another home (the decisions document itself, or Analyze).

1D Adaptive button: the label follows the open document

Pattern: context-sensitive primary action (the ribbon already swaps content by phase). For: the right next step is always the visible label: Upload with nothing open, Extract on a transcript, Apply on a decisions doc. Against: a label that changes under the cursor costs predictability; the menu stays for the other two.

Question 2 · Should "Extract decisions" confirm before it starts?

The item is a chat action: it starts the Business Engineering agent on the open transcript, costs compute, and is interruptible from the chat. The guidelines reserve a modal confirm for destructive or irreversible actions and prefer undo for the rest. Each variant below is clickable; the result appears in the stage.

2A Start immediately, name the target in the tooltip, Stop in the chat

Pattern: no confirm, feedback within 100ms (HIG), interruptible. Pairs with 1A gating so a wrong target cannot start. For: zero extra clicks; the chat shows exactly what was sent. Against: a mis-click still spends the first seconds of a run.

2B Anchored confirm popover with the target and the agent

Pattern: lightweight inline confirmation (popover scaled from the trigger, not a modal). For: the person sees the document and persona before any compute. Against: one more click on every run; the guideline reserves confirms for destructive actions.

Extract decisions from meetings/g5-daily-standup-2026-10-22.md with the Business Engineering agent. The run opens in Chat and can be stopped there.

2C Seed the prompt in the composer; the person presses Send

Pattern: preview-then-send; the platform already does this for Review Workspace (handleSeedChatPrompt). For: the full instruction is visible and editable before it runs; no new UI. Against: the template is long, and the composer is a strange place for a fixed template to live.

2D Start immediately with a Stop toast

Pattern: undo over confirm (HIG "undo-support"). For: no friction on the happy path, a 5-second escape on a mis-click without opening Chat. Against: toasts are easy to miss; a stop after the agent already wrote files is not a true undo.
