## Requested outcome and design

A developer runs `G5D_ISOLATION_MODE=process G5D_ALLOW_PROCESS_ISOLATION=1 just dev-up` on a Mac (or a KVM-less Linux box). The native host registers with the local API, and every workspace it boots is a `g5d dispatch` host process group whose modules (chat turns, preview, terminal, bootstrap) are ordinary host processes. The `full-stack` preview profile then runs Docker Compose on the host's own Docker instead of nested inside a microVM. `just dev-up` without those variables behaves exactly as before.

```
g5d host ──resolve once──▶ HostIsolation::{MicroVm | Process}
   │ Process: verify host-native runtime dir, skip image prep/scratch/forward/passt/cache door, hello += isolation:process
   ▼
WorkspaceVmRuntime.boot_prepared ──process spec──▶ ProcessVmLauncher.start
   cmd=[host g5d, dispatch]  env=identity+token+port+G5D_PROCESS_*  root=<workspaces>/<ws>
   ▼                                                     │ per-VM dir <state>/process-vms/<vm>/{home,state,tmp,dispatch.log}
ProcessBackend::spawn_group (setpgid, sole reap waiter) ─┘ handle.vmm_loopback_addr = 127.0.0.1
   ▼
wait_for_dispatcher_ready ── 127.0.0.1:<leased port> ── token ── runtime.ready   (unchanged)
   ▼
g5d dispatch (process mode): RuntimePaths from G5D_PROCESS_*; listens 127.0.0.1; catalog/bin/harness from runtime root;
   modules get G5D_RUNTIME_BIN_DIR + G5_HARNESS_DIR; no uid handoff; Git door on an ephemeral port
```

**Owners and responsibilities.**

- `g5d host` (`backend/g5d/src/cli/host.rs`) resolves the isolation mode once from `G5D_ISOLATION_MODE` plus `G5D_ALLOW_PROCESS_ISOLATION`, and passes it explicitly; the `IsolationManager` is not constructed in process mode, so its environment re-read cannot override the decision. In process mode it validates the host-native runtime directory (`bin/{g5d,claude,codex,node,git,docker}`, `modules/catalog.{json,sha256}`, `assets/harness/AGENTS.md`, plus `bin/{fake-claude,fake-codex,fake-g5-tools}` only when a deterministic provider flag is set; `bin/g5d` must resolve to the running host executable) and skips image preparation, the runtime-separation check (the dispatcher is the host executable by design), the cache door and passt with a logged reason; `G5D_VM_NET=passt` is an error. Slots default to one.
- `ProcessVmLauncher` (`backend/g5d-host/src/runtime.rs`) owns where a process-mode incarnation lives on the host: it derives the per-VM directory from the spec's `G5D_VM_ID`, creates `home`, `state` and `tmp`, writes dispatcher output to `dispatch.log`, refuses any VM-only spec field, builds the child command with a cleared environment, starts the dispatcher as a **session leader** tagged with the incarnation marker (`G5D_PROCESS_INCARNATION=<vm_id>`) through `ProcessBackend`, and writes a durable ownership record (`incarnation.json`: vm id, leader pid, start time) beside the log. The workspace Git socket gets a bounded path: a short owner-only directory under the user's runtime directory (`$XDG_RUNTIME_DIR/g5d`, the macOS per-user `TMPDIR`, or `/tmp/g5d-<uid>`; `G5D_PROCESS_SOCKET_ROOT` overrides), named to the dispatcher as `G5D_PROCESS_SOCKET_DIR`, refused rather than truncated when it would exceed 104 bytes. The dispatcher hands the same directory to its modules, and a real-provider turn binds its LLM proxy sockets there (found 2026-10-13 on the Mac: with the incarnation home as socket directory the turn failed with `path must be shorter than SUN_LEN`, which the fake lane never reaches because it starts no proxy). A stop in either mode tears the whole incarnation down at once with SIGKILL and returns with the waiter's reap receipt; the grace is logged as not applicable. At startup, in every mode, `settle_process_incarnations` reads the records a previous host left, tears down what still runs and proves its exit before `g5d host` reclaims a root or admits work; an incarnation whose exit cannot be proven stops the host from starting.
- `ProcessBackend` (`backend/g5d-isolation/src/isolation/process.rs`) gains `spawn_group`, `spawn_session(cmd, tag)`, `terminate(handle, grace)` and the public `teardown_incarnation`. A session-leader handle stands for the **incarnation**, observed through one census (`g5d-foundation::process_termination::incarnation_census`): every live process group of its session, every live process whose environment carries the tag (`/proc/<pid>/environ` on Linux, `KERN_PROCARGS2` on macOS), and the **unknown** set, same-user processes started no earlier than the leader whose environment could not be read (non-dumpable on Linux, a failed or truncated argument read on macOS). *Amendment 2026-10-13 (Mac run):* macOS 26.5 returns the arguments alone, without an environment, for every platform and hardened-runtime binary read by an unprivileged user (`/bin/sh`, `sleep`, `zsh`, `awk`, Chrome; a cargo-built or CommandLineTools binary stays readable), including processes the incarnation itself spawned, so with the earlier rule no stop on a Mac ever proved exit (the launcher tests reported a dozen stray `sleep` processes of other shells as uncertain). A withheld environment is therefore no evidence either way: the process is a member when its session or parent chain reaches the leader and otherwise not the incarnation's; only a failed or truncated read stays uncertain. A hardened process that left the session and lost its ancestry is the macOS form of the documented limit. Teardown SIGKILLs groups and tagged processes and succeeds only when nothing attributable is left *and* nothing is unknown; an unknown process is uncertainty, never exit proof: a stop reports the unproven exit naming the pids, the waiter keeps proving, and the receipt custody consumes is published only when the incarnation's exit is proven. On Linux the leader also carries `PR_SET_PDEATHSIG`, so a dying host takes the dispatcher with it; detached descendants are settled by the next host from the record. Processes that scrub their own environment remain the documented limit. Default scratch directories are created only when the spec supplies neither `HOME` nor `TMPDIR`; process handles publish `127.0.0.1`.
- `WorkspaceVmRuntime` (`backend/g5d-host/src/workspace_vm.rs`) carries an optional `ProcessHostConfig { runtime_root }`. In process mode `boot_prepared` builds the process spec: command `[host g5d, dispatch]`, environment from `dispatch_guest_env` plus `G5D_ISOLATION_MODE=process`, `G5D_PROCESS_WORKSPACE_ROOT`, `G5D_PROCESS_RUNTIME_ROOT`, the leased host port as `G5D_DISPATCH_PORT`, `G5D_GIT_DOOR_PORT=0` and the host `PATH`, minus `G5D_MODULE_UID`/`GID` and `LD_LIBRARY_PATH`; no extra mounts, port maps, forwards or scratch disk. Validation of the API's spec (entrypoint `/opt/g5/bin/g5d dispatch`, size, catalog pin) is unchanged. The hello advertises `isolation:process` or `isolation:libkrun-microvm`.
- Dispatcher (`backend/g5d-dispatch`): `RuntimePaths` gains `runtime_root` and `socket_dir`; its sources are production guest paths, the test root (test-support builds) and, when `G5D_ISOLATION_MODE=process` is in the environment, the five absolute `G5D_PROCESS_*` paths. The catalog path, the entrypoint containment check, the appended runtime bin on the command path and the listener address (`127.0.0.1` in process mode, `0.0.0.0` otherwise) follow from the paths and mode. Module children receive `G5D_RUNTIME_BIN_DIR` and `G5_HARNESS_DIR`; in process mode they, terminals and previews also receive the incarnation marker and the host's Docker selection (`DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG`, `DOCKER_CERT_PATH`, `DOCKER_TLS_VERIFY`, an allowlist); the guest-only `/usr/local/bin/g5d` symlink and the Linux loader path are stamped only on the guest bundle path. `agent-turn` and `preview-serve` read `G5D_RUNTIME_BIN_DIR` with the `/opt/g5/bin` default.
- Control plane (`backend/g5-api-core/src/services/hosts/host_control_state.rs`): a hello whose capabilities include `isolation:process` is rejected unless `G5_ALLOW_PROCESS_ISOLATION_HOSTS=true`; the dev compose file reads it with a `false` default and `dev-stack-up` exports `true` only when `G5D_ISOLATION_MODE=process` is acknowledged, ignoring any ambient or dotenv value (decided 2026-10-13: the flag is never set by hand). The hosts admin page labels such a host "process (unisolated)".
- Dev wiring (`scripts/worker-host-env.sh`, `Justfile` `worker-host*`): `G5D_ISOLATION_MODE` defaults to `microvm`; `process` requires the acknowledgement, builds the host `g5d` without the libkrun feature (a machine without libkrun can run it; the default build keeps libkrun linked and a flip rebuilds), stages the host-native runtime directory under `.dev/g5d-host*/runtime-process` (symlinks to the host build of `g5d` and to the host's `claude`, `codex`, `node`, `git`, `docker`; the repository catalog and harness; the host build of the fake provider CLIs only when `G5_CLAUDE_CODE_FAKE` or `G5_CODEX_FAKE` is set, found 2026-10-13 when a fake-provider Mac chat turn failed with `fake-claude` absent), skips the Docker Linux staging, the libkrun smoke, codesigning and the DYLD path, and defaults to one slot. The existing mode file restarts a live host on a flip. The dev stack has one configurable identity: `G5_COMPOSE_PROJECT` (default `g5-dev`) selects the Compose project in every `dev-*` recipe and the container names, `G5_COMPOSE_VOLUMES` (default `g5-lean`) the volume names, `G5_IMAGE_TAG` (default `dev`) the API image tag, and `G5_PORT_*` the published ports, with the health wait and the seed script following the same identity. The `full-stack` preview profile (`just dev-up`; named `dev-up` until 2026-10-13) is its own stack: project and volumes `g5-preview-<incarnation marker>`, image tag `preview`, ports 13000/17500/15433/19876, and a bounded `sleep` loop for its lifetime because Apple's `sleep` refuses `infinity`. *Amendment 2026-10-13:* the profile runs `just dev-up`, not only `dev-stack-up`, with `G5D_ISOLATION_MODE=process G5D_ALLOW_PROCESS_ISOLATION=1` exported in its own shell: the preview is the previewed instance's localhost, a microVM cannot nest microVMs but can run that instance's workspaces as processes, and the previewed API (dev compose) admits the host. Close runs `just dev-down`: `worker-host-stop` finds the previewed host's PID file under the checkout's own `.dev/` and the stray reaper scopes by that directory, so the developer's host is out of reach; `dev-stack-down` remains the containers-only teardown. A nested host stamps `G5D_PROCESS_INCARNATION_OUTER` on its dispatchers and the census reads either key, so an outer workspace stop still proves the previewed instance's work gone.

**Consequential choices.**

- *Launcher shape.* `ProcessBackend` is extended with two public operations rather than `g5d-host` growing a second spawner: the reap-receipt channel, the sole-waiter rule and the SIGTERM→SIGKILL group termination are crate-private in `g5d-isolation` and are exactly what custody relies on; duplicating them would be larger and would create a second reap authority. Building the `Command` in the launcher keeps per-VM directories and the dispatcher log where the host state lives.
- *Who tells the dispatcher its paths.* The runtime names the incarnation-level paths (workspace root, runtime root, port) and the launcher names the host-level ones (home, state, tmp); the dispatcher accepts them only when told it runs in process mode. The guest path stays hardcoded, so a VM boot cannot be redirected by environment.
- *API gate.* Refusing the hello of a process host (unless the API was started for local development) is chosen over a per-placement predicate or a UI-only notice: it keeps `g5.runtime.placement` unchanged, is fail-closed for cloud and self-hosted control planes, and matches the existing `G5_E2E_AUTH` dev-only pattern. The admin hosts page shows the host's isolation; a notice on workspace, preview and terminal surfaces is not added, because the owner of a local stack is the developer who set the acknowledgement.
- *Stop semantics and exit proof (found in implementation and review).* A VM teardown reaches every guest process without signalling any of them, and the dispatcher has no shutdown handler of its own because the control plane drains through RPC before it stops a VM. The first implementation sent SIGTERM to the dispatcher's process group: `preview-serve` reads SIGTERM as an owner Close and would have run the profile cleanup a workspace stop must not run (`g5.preview.service.close`), and the preview application, which `preview-serve` keeps in a process group of its own, survived a group kill. The review then showed that a session is not enough either: PTY terminals (`portable-pty` calls `setsid`) and detached applications leave the session, and a dispatcher that exits with work still running must not count as exited. The process-mode incarnation is therefore the session **plus** every process carrying the inherited incarnation marker; a stop SIGKILLs all of it and never applies a grace, and exit proof is published only when nothing of it remains. Processes that scrub their own environment are the documented limit of a host process without a cgroup or VM boundary; the launcher and host-level tests pin the rest.
- *Networking.* Preview and terminal streams already flow through the dispatcher mux, so no port maps are needed. The dispatcher and Git door bind the host loopback only; the Git door takes an ephemeral port so a second incarnation does not collide, but the preview port is the profile's, so process hosts default to one slot.
- *Catalog pin.* The host pins the catalog from the host-native runtime directory exactly as the bundle does; the dispatcher's `g5d` entrypoints resolve to the running executable, so the pinned catalog and the host build stay one artefact.

**Acceptance.** `g5d host` with `G5D_ISOLATION_MODE=process` and no acknowledgement exits with a configuration error naming the acknowledgement; with both it registers, boots a real `g5d dispatch` as a process group, reaches `runtime.ready`, serves a preview profile whose command binds `PORT` through the mux, runs `cleanup_command` on Close, kills the group without cleanup on lifecycle stop and publishes a reap receipt on crash. The cloud startup script and every CI, packer, helm and installer file never emit `G5D_ISOLATION_MODE=process`. `just dev-up` with the default mode is unchanged.

**Risks.** The port scanner reports host listeners to the owner UI on a process host (accepted exposure). A host `g5d` rebuilt while the host runs spawns the newer binary for the next incarnation (host and dispatcher versions can skew until the host restarts; the `worker-host-start` fingerprint restart covers the normal flow). Linux module `RLIMIT_DATA` limits apply to host processes in process mode exactly as in the guest.

## Amendment 2026-10-13: preview up means the worker is attached

The first QA run of the `full-stack` profile (then named `dev-up`; host `cbd4f950`, workspace `0735e646`) measured: checkout 19:50, containers and seed done 20:08 (eighteen minutes of nested image builds), host binary built 20:18 (ten minutes of `cargo build -p g5d --no-default-features` holding two of the VM's four vCPUs, no incremental cache), host registered 20:19, and the first workspace start failed at 20:21 with `materialize workspace repository vector`: the previewed host's data root sits on the VM's virtiofs mount and the scratch disk is ext4, neither of which reflinks.

Decisions, with the user:

- *Readiness.* "Up" must mean a workspace can be opened, for a developer's `just dev-up` and for the profile alike. `dev-up` builds the host binary first (`worker-host-build`, `--jobs` at the core count because one binary links, never an exported `CARGO_BUILD_JOBS`, which would enter the guest's sccache hashes and miss the image's warm cache; signed at once for HVF in microvm mode), runs `dev-stack-up` with `G5_DEV_DEFER_EDGE=1` so the edge, the published port, is not started and a previous edge is removed, starts the host, proves its registration through the API (`scripts/wait-for-worker-host.sh`: a ready, live host listed for the seeded org), then publishes the edge through `dev-stack-up`'s `G5_DEV_EDGE_ONLY=1` phase, which carries the same identity, overlays and secrets and starts the edge with `--no-deps`. Independent review of this change is recorded in [review.md](review.md). The sequence stays sequential rather than overlapping the cargo build with the image builds: both are memory-heavy in a 16 GiB VM.
- *Three profiles (renamed 2026-10-13 for the picker: `full-stack`, `full-stack-no-worker`, `frontend-only`; the earlier names were the just recipes `dev-up`, `dev-stack-up` and the bare `frontend`).* `full-stack` is the whole stack with the attached process-mode host; `full-stack-no-worker` is the containers alone with a containers-only Close, for previews that only need the UI and API; `frontend-only` is the Vite dev server in its mock mode (`VITE_MOCK=true`, the fetch interceptor answers `/api/*` in the browser) on port 15174, off Vite's own 5174 so a developer's dev server on a process host is never collided with or mistaken for the preview, for client-only work, with no stack and no cleanup. *Amendment 2026-10-13:* the interceptor advertises the dev stack's default instance features (`g5_ui_v3`, `top_panel`, `alignment_ui`, `guided_journey`, `provider_accounts`) on top of the test fixture's `chat` and `codex_ui`, because with the fixture alone the QA `frontend-only` preview rendered the pre-v3 workspace page without the layout, phase-bar and action-bar settings; `VITE_MOCK_FEATURES` replaces the set, and unit tests, which use the MSW handlers directly, keep opting into each gated surface.
- *Materialization.* A process-mode host copies the bare cache when the reflink attempt fails as unsupported (`WorkspaceCheckout::with_copy_when_reflink_unsupported`, set by `g5d host` in process mode only), replacing whatever the refused reflink left in the destination first. The fresh-root rule stands; the copy is the developer's own disk and time, and microVM hosts keep reflink-or-fail-loud.
- *Nested limits (found on QA 2026-10-13, preview `ada45e09`, workspace `235253bb`).* The previewed host runs inside the `workspace.preview` module, whose dispatcher caps it at a 4 GiB hard data limit and a 4 GiB hard file-size limit; every chat turn inside the preview then failed at spawn with `Operation not permitted`, because the nested dispatcher asked pre-exec `setrlimit` for the `agent.turn` catalog values (8 GiB data, 16 GiB file size) and an unprivileged process cannot raise a hard limit. A developer's Mac never saw it: its shell carries unlimited hard limits and macOS sets no data limit at all. The runner now reads its own hard limits before the fork and clamps each catalog value to the inherited envelope (`within_inherited_envelope`), logging each clamp with the effective value. No caller is exempt: the hook runs after the child's identity switch (`Command::uid`), and raising a hard limit needs `CAP_SYS_RESOURCE`, so effective uid 0 proves nothing (independent review, round 1). A module nested in a smaller envelope therefore runs bounded by that envelope instead of not at all.

Tests: `scripts/test-dev-up-preview-profile.sh` (both profiles, the deferred edge, the step order of `dev-up`), `scripts/test-worker-host-env-process-build.sh` (job count), the foundation restore test for the copy fallback, the runner's re-executed nested-envelope test (`ulimit -f` lowered, spawn succeeds, cap equals the envelope; the nested run prints evidence the outer run requires, and the test fails with the clamp removed, root included), and the `cli::host` tests.
