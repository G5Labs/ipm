# Organization disk allowances

Implement the owner's disk policy for [G5-Lean#1049](https://github.com/G5Labs/G5-Lean/issues/1049), as corrected on 2026-11-04 by the [sparse disk correction](../../chat_intent/issue-1049/sparse-disk-correction.md). The incident: cold preparation refused a Start with approximately 156.8 GiB free because it demanded two 80-GiB disks. The policy admits a Start whenever available host space is at least V and keeps every VM disk sparse.

The existing organization configuration owner validates H (default 120 GiB) and V (default 80 GiB). The host-record owner resolves H + V × slots and validates overrides under the organization settings lock. Persist H, V, slots and the resolved size together and return them to launchers. Same-host retries and launchers consume this snapshot; replacements resolve current settings and report an incompatible retained override before disturbing the old host. Preserve recorded live capacities on migration and registration. Development and CI fixtures configure their smaller V through the same administrator API before creating hosts. The provider's historically named GB field carries GiB. H only sizes the host disk.

The host supervisor admits a Start when its workspace filesystem has at least the VM's recorded V available, checked once before preparation. The former V + 512 MiB gate, the cold image's second V, the archive multiplier and the bootstrap margins are removed; slot, memory and other checks are unchanged. Private disks remain sparse reflink clones of the pristine template or repository seed, as on main: nothing unshares, preallocates or verifies their extents, and the VMM keeps the sparse disk default. Admission reserves nothing for later writes. The cache door's free-space floor follows the Start gate, now exactly V. Optional repository seed preparation keeps main's free-space gate (every slot's V plus three preparation disks), because nothing else bounds it.

Reuse trusted guest SCM restoration for every production microVM boot, with an optional seed supplying only initial objects. Restore members, reference repositories, personal mounts and complete receipts before hooks and Ready; process-mode development retains its existing materializer. Do not create a duplicate host workspace archive for production boots.

Capacity failures carry available/required bytes and phase through helper exit, command result and durable events. Requeue the same Start intent only after exit-proven cleanup; stale events remain fenced. Invalid images, source corruption and authorization failures remain terminal and distinct. Capacity classification accepts typed local failures or canonical host-written helper stderr, never guest serial or arbitrary image/source error text. A recoverable local capacity failure in optional seed preparation, including its authorized refresh, falls back to ordinary guest restoration after its processes exit; an opaque optional-cache refresh failure may also discard the accelerator without claiming capacity. Explicit authorization, invalid-input and cancellation refusals remain terminal.

Governing commitments: [administrator authority](../../ontology/features/organizations.g5.md#g5.security.org-admin-settings), [host disk sizing](../../ontology/software_architecture/host_control_plane.g5.md#g5.runtime.placement.host-disk), [VM disk rule](../../ontology/software_architecture/host_control_plane.g5.md#g5.runtime.placement.vm-disk), [private block workload](../../ontology/software_architecture/hosts.g5.md#g5.architecture.build_scratch), [materialization](../../ontology/software_architecture/hosts.g5.md#g5.runtime.materialization), [start settlement](../../ontology/software_architecture/hosts.g5.md#g5.runtime.start.settlement), [Git receipts](../../ontology/software_architecture/git.g5.md#g5.git.flush-proof).

Acceptance: settings and authorization; exact minimum, larger overrides and refusal below it; retry snapshots and replacement settings; admission at exactly V and refusal below it; a private disk with virtual capacity V that allocates far less before guest writes and grows with them, on the warm, pinned, cold and seed paths; the cold image case with free space between V and 2 × V; complete source and receipt restoration across the real Linux guest boundary; E2E Start latency back at main's level. Record implemented, tested, deployed and observed evidence separately in the [evidence](evidence.md). Passing tests implies no deployment.

## Correction history

An earlier revision of this design physically reserved V before guest execution: each Start unshared its reflinked template and fsynced it, and an XFS project quota installed at bring-up capped shared data at H, with private-disk project tagging, shared reader leases, pressure-driven reclamation and a candidate-worker qualification gate. Its CI E2E runs failed because every Start copied the template's data ([analysis](evidence.md#ci-e2e-root-cause-2026-11-04)). The owner then rejected physical reservation, including a proposed copy-free variant that still allocated V, and the shared quota. All of that machinery is removed.
