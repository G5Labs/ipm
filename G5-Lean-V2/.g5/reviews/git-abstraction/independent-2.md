## Initial findings (saved before sharing)

### F1 — P1: Create-only pins break the existing provider resolution retry

- **Changed location:** `backend/g5-scm/src/resolution.rs:111-129`, consumed at `backend/g5-api-core/src/services/git_conflict_resolution.rs:200-201`.
- **Evidence:** The new operation refuses every partial pair and every pair whose tips differ. The provider caller does not always create a fresh run ID: `remote_integrations/resolution.rs:31-48` locks the existing `job_merge_runs` row and permits another enqueue when `resolution_task_id` is absent; lines 57-59 pass that same `input.run_id` as the resolution ID. `remote_integrations/merge.rs:2117-2130` supplies the original merge-run ID and newly captured tips.
- **Counterexample:** Initial pinning succeeds, but task enqueue or SQL commit fails. SQL rolls back while Git pins remain. The user explicitly retries after the provider/local branch advances, or after an interrupted pin write left one side absent. The replacement caller still supplies the same run ID, so the new operation returns conflict on every subsequent attempt instead of recovering the abandoned preparation. No committed task exists to reuse. This is an introduced regression, not deferred migration.
- **Existing discriminating regression:** `backend/g5-api/tests/remote_repo_tracking_integration.rs:3371`, `resolution_retry_recovers_after_enqueue_or_commit_rollback_and_remote_advance`, drives the real start endpoint, injects enqueue and deferred-commit rollback, observes retained pins, tests a partial pair, advances both tips, and requires one recovered task and the new pins. Its expected success now contradicts the changed branch above. I inspected this test; I did not execute its shared database/runtime fixtures.
- **Governing:** `g5.architecture.git_ref_updates` expressly permits intentional replacement with expected current values in a checked multi-ref transaction; `git_retry` preserves existing independently governed recovery, with the human choosing the retry. `g5.architecture.commands` requires the reused operation to support the caller's valid variant.
- **Proposed repair:** Preserve create-or-confirm for fresh workspace runs, and expose the minimal checked replacement operation needed by the existing provider owner after it has locked the run and proven no committed task exists. Supply both expected current targets (including absent sides) and reject changed preconditions before mutation. Keep task-present retries immutable. No new tracking tables or automatic retries are necessary. Correct the initial-slice design statement that the live caller only creates fresh IDs.

### F2 — P2: The clear refusal/uncertainty error never reaches the API caller

- **Changed location:** `backend/g5-scm/src/resolution.rs:46-50`, `:77-80`, and `:139-146`; conversion is exercised by `git_conflict_resolution.rs:201`.
- **Evidence:** Non-conflict refusals and commit uncertainty wrap their useful diagnostics in `G5Error::GitError`; `From<ResolutionPinError>` discards the typed distinction and returns that inner error. The live service propagates it to `AppError`. `backend/g5-api-core/src/errors/mod.rs:123-126` calls `G5Error::to_error_response`, and `backend/g5-contracts/src/error.rs:571-577` replaces every `GitError` with code `INTERNAL_ERROR`, message `An internal error occurred`, and empty details.
- **Consequence:** A lock refusal and a possibly partially written pair produce the same public response. The agent/human cannot see the affected refs, uncertainty, or instruction to inspect before deciding to retry. The new test asserts only `Display` text, which is server-side logging evidence, not the caller-visible contract.
- **Governing:** `g5.architecture.git_outcomes`, `git_retry`, `g5.data.outcome-evidence`, and the user's explicit clear-errors requirement. Preserve `g5.security.credentials.redaction`; do not globally expose raw Git errors.
- **Proposed repair/check:** Carry a specifically safe typed operation outcome through the API mapping, with sanitized target/effect/recovery information. Add a test using the real operation's lock-refusal and commit-failure cases followed by the production error-envelope conversion; assert distinct, actionable public outcomes and no secret leakage. Include repository identity at the owner boundary when composing multi-repository resolution.

### F3 — P3: The new production guard rejects permitted test fixtures

- **Changed location:** `backend/g5-api/tests/authoritative_workspace_reader_guard.rs:65-97`.
- **Evidence:** AST traversal applies the `git2` ban to every node and never excludes `#[cfg(test)]` modules or test functions. An isolated harness extracted the unchanged `typed_git_violations` function and supplied `fn ref_oids() {} fn ref_oid() {} #[cfg(test)] mod tests { #[test] fn raw_fixture() { let _ = git2::Repository::init(path); } }` for the migrated projection owner. It returned `maintenance/projection_convergence.rs: migrated owner accesses git2`. The production raw-open fixture returned the same violation.
- **Consequence:** Adding a harmless raw backend fixture to exercise one of these owners fails the architecture suite even though production remains mediated. This contradicts the explicitly permitted exception, rather than detecting a bypass.
- **Governing:** `g5.architecture.git_guard` explicitly exempts tests/fixtures from production dependency checks; `g5.quality.review.guards` requires harmless-refactor calibration.
- **Proposed repair/check:** Skip test-only scopes for the production prohibition while still enforcing production operation presence; calibrate paired production/test fixtures. Do not weaken the production ban or exempt an entire mixed production file.
