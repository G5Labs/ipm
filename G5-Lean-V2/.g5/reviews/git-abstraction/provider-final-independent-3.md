## Initial findings

### R3-F1 · P2 · Preserve outcome and recovery evidence through the PR owner's error bound

`workspace_pull_request_provider_lifecycle.rs:191–198` converts the new `ProviderError` to an unstructured full display string. Its existing persistence/event consumers at lines 2160, 2204, 2239 and 2265 then apply `truncate_provider_message` (line 2490), which keeps the first 500 characters. `providers/error.rs:76–88` puts the provider diagnostic first and the effect/inspection instruction last. A legal long diagnostic therefore removes the distinction between unknown, partial and refused outcomes from the saved/public PR error. The owner's later generic “retry Update PR” suffix does not restore the instruction to inspect whether an unknown create already happened.

**Counterexample:** a single HTTP 503 PR-create response with a 900-character JSON `message` yields `FailureEffect::Unknown` and an inspection instruction from the actual compiled public SCM client; passing that exact result through the current owner's copied formatter yields 503 characters with neither `unknown` nor `inspect current state`. Receipt: `reviewer3/provider_probe.log`. This is a runtime public-client probe plus exact-source owner-formatter probe, not a full SQL/HTTP owner test.

**Rules:** `g5.architecture.git_outcomes`, `git_retry`, `g5.governance.pr.follow-push`, and the plan's requirement to retain useful failure evidence through the existing PR outcome surface. This is an interaction introduced by feeding the new structured result into the old bound, not a request for retry persistence.

**Proposed repair/check:** preserve the effect and corrective-action summary within the bounded owner-facing message (or retain the structured result until formatting), reserving space for request/rate evidence as appropriate. Exercise a long unknown/partial create failure through the real PR owner and assert persisted `last_error`, event and API output preserve uncertainty and inspection guidance, with exactly one create attempt.

### R3-F2 · P2 · Narrow the whole-SCM HTTP exemption to the shared transport owner

`authoritative_workspace_reader_guard.rs:2090–2093` returns no violations for every `g5-scm/` file. Consequently a new private SCM helper can construct and send a `reqwest::Client` request directly, bypassing shared redirect, replay, deadline and redaction mechanics, while every current structural guard passes. The public-surface guard only checks exposed types and cannot protect this private bypass.

**Counterexample:** the frozen guard source was compiled independently with a private `async fn bypass(url: &str) { reqwest::Client::new().get(url).send().await; }`. `provider_http_violations("g5-scm/providers/new.rs", ...)`, `typed_git_violations` and `scm_public_backend_violations` all return empty. The identical source under a new API consumer is rejected. Receipt: `reviewer3/guard_probe.log`; the probe and frozen source copy are alongside it. No shared files were mutated to conduct this check.

**Rules:** `g5.architecture.git_guard`, `github_transport`, `g5.quality.review.guards`, `g5.design.enforcement`; the approved plan specifically calls for rejecting requests that bypass typed clients **or their shared transport**, and operation-specific exceptions rather than whole-file exemptions.

**Proposed repair/check:** allow transport construction/delivery only in the private transport's declared operations, while permitting the typed adapters' owned request DTOs, methods and URL parsing. Add both a private-SCM raw-request rejection and a harmless typed-client/private-helper control. Separately, no current guard implements the plan's provider-name-dispatch restriction; add a calibrated composition exception and a consumer dispatch counterexample, or accurately leave that enforcement obligation open. This second observation is a missing guard boundary, not evidence that every existing provider-name comparison is a defect.

### R3-F3 · P2 · Configured Enterprise PR selection stops at the unchanged repository-identity owner

The new `ProviderEndpoints::select_pull_request` accepts a configured Enterprise origin/prefix, but `workspace_pull_request_read.rs:110–119` immediately filters attached repositories with the unchanged `github_repository_name`. That helper (`auth/repository_credentials.rs:364–394`) accepts only `github.com`, and the credential owner's App path uses the same parser. Thus a valid configured Enterprise PR URL can pass the newly migrated selector and still produce “No matching GitHub repository is attached” before the provider operation; neither numeric selection nor `--repo` fixes an attached Enterprise clone URL.

**Counterexample:** the compiled public selector accepts `https://enterprise.test/org/repo/pull/12` under matching configured endpoints, while the exact current reused helper returns `None` for `https://enterprise.test/org/repo.git`; the public-GitHub control returns `Some("org/repo")`. Receipt: `reviewer3/provider_probe.log`. The subsequent attached-repository rejection follows directly from the inspected filter; no Enterprise database fixture was executed.

**Rules/scope:** `g5.architecture.github_transport` and the approved design's selected-host/Enterprise PR acceptance and reused-operation inspection requirements. The hard-coded identity helper predates this patch. This is an unclosed final-migration acceptance obligation, not a newly introduced public-GitHub regression or permission to weaken repository identity checks. AppState also selects the new PR web base only from optional GitHub App configuration (otherwise public GitHub), rather than a separately named SCM web-base setting.

**Proposed repair/check:** reconcile supported configured repository instances through the existing identity/credential owner, keeping exact-origin authority and login/report separation. Add an actual attached-repository PR read/check test for the supported configured instance and a foreign-origin denial. If end-to-end Enterprise repository support is intentionally outside this delivery, preserve the current limitation explicitly in the design/metadata instead of claiming that the public-client selector test proves the owner outcome; that scope change requires a justified amendment, not silently relaxing valid ontology.
