## Initial findings saved before sharing

### F1 — P2: exact origin comparison breaks the host's canonical cache identity

**Defect.** `backend/g5-scm/src/native/materialization.rs:43–46` now passes the current request URL to `check_remote`, whose `check_destination` requires byte-for-byte equality with `git remote get-url origin`. The host still intentionally maps URLs with and without a trailing slash to the same cache (`repo_cache.rs:111–114`; existing `cache_key_canonicalizes_whitespace_and_trailing_slash` test). A cold call for `/absolute/source/` records that exact origin; a warm call for `/absolute/source` finds the same cache but is refused as a different destination. The opposite ordering likewise fails. The prior warm operation fetched the cached origin and accepted this supported canonical identity.

**Evidence:** an isolated real `git clone --bare /tmp/g5-host-review-1/trailing/source/ …/cache` followed by `remote get-url origin` retained the trailing slash, confirming that Git does not remove the differing bytes. Source establishes the shared key and new refusal. A full public `RepoCache` probe is pending compilation at this initial save.

**Obligation:** pinned host section explicitly preserves cache identity; `g5.architecture.git_locations`, `g5.architecture.compatibility`, and valid-variant preservation under `git_guard`.

**Suggested repair/regression:** let the host's existing canonical identity rule mediate the expected/cache-origin comparison while preserving credential scoping to the actual admitted transport and refusing genuine URL rewrites. Exercise cold then warm `RepoCache::ensure_warm` with both trailing-slash orders, alongside a genuinely different origin refusal. Testing `CacheKey` equality alone misses this integration regression.

### F2 — P2: host error wrapping reintroduces a rejected URL's credentials

**Defect.** The new SCM calls reject a credential-bearing HTTPS URL and redact their target, but `refresh_under_lock` reconstructs `WorkspaceError::GitClone` / `GitFetch` using raw `repo_url: url.into()` at `repo_cache.rs:755–759,773–776`. Those variants' public Display and Debug include the raw URL (`workspace/error.rs:65–69,104–110`). Thus a request such as `https://username:password-canary@example.invalid/repo.git` passes host scheme admission, is safely rejected by SCM before network access, then appears in plaintext in the outer error/log. This wrapper remains on the migrated public cache path, so SCM redaction alone does not establish the migration's guarantee. The raw URL field existed before this migration; the finding is the incomplete redaction boundary of the newly consolidated operation, not a claim that the old implementation was safe.

**Evidence:** source tracing from `validate_repo_url` through `validate_url`/`at_target`, the new adapters, and WorkspaceError Display. The first isolated external runtime harness used an incompatible cached Tokio artifact and failed before invoking the path; that harness result is not redaction evidence. A corrected public-path probe is pending at this initial save.

**Obligation:** `g5.architecture.git_credentials`, `g5.architecture.git_outcomes`, `g5.security.credentials.redaction`, and the plan's explicit credential-free URL/error acceptance outcome.

**Suggested repair/regression:** preserve the already-redacted typed error (with host recovery classification kept in its existing owner), or redact every outer target field before construction. Exercise the actual public cache operation with a rejected URL password/query canary and assert both Display/Debug/public error/log rendering omit it; retain the existing transient-403 recovery tests. This needs no new retry state or replay.
