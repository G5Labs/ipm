## Initial findings

### F1 — P2: Preserve rate-limit evidence in the App-user repository-access check

`backend/g5-scm/src/providers/app.rs:299-301` maps every 403 to `RepositoryAccessError::AccessDenied`, without inspecting the transport's rate-limit evidence. A provider 403 with `Retry-After: 60` and a secondary-rate-limit body therefore becomes an access-denied result and loses its request ID and retry hint. The unchanged `auth/repository_credentials.rs:285-299` translates it into “Your connected GitHub account cannot access this repository. Check your repository access and GitHub App permissions,” which supplies the wrong corrective action to PR creation.

Governing: `g5.architecture.github_transport`, `git_outcomes`, `git_retry`, and the current-access check under `g5.governance.publish.github-author`. The old owner had this classification too; this is an unmet approved transport/error obligation in the newly migrated operation, not a claim that the refactor invented GitHub rate limits.

Demonstration: the exact-source probe `review_probes::demonstrates_repo_access_rate_limit_discarded` serves the configured `/repos/owner/repo` endpoint with 403, retry-after and a secondary-rate-limit message. The operation returns `AccessDenied`. The test ran successfully, proving the counterexample.

Proposed repair: classify rate limits before translating 403/404 into access decisions and return `Failed(ProviderError)` retaining `RateLimited`, status, request ID and retry hints. Preserve plain 403/404 as denied access, 401 as reconnect, successful matching ID as allowed and mismatched ID as repository-changed. Add those discriminating cases; verify the existing credential-owner projection does not tell the caller to change permissions for a rate limit.

### F2 — P2: A body-read failure must not erase an observed 401's reconnect meaning

`backend/g5-scm/src/providers/app.rs:289-300` now waits for the common transport to read the complete body before classifying authorization status. If GitHub sends 401 headers and then its body is truncated or times out, `.map_err(E::Failed)?` propagates a generic provider failure despite `ProviderError.status == Some(401)`. Before this increment, `GithubAppClient::verify_user_repository_access` matched the response status before reading any body for non-200 results. The current credential owner therefore returns service-unavailable instead of its `PR_CONNECTION_REQUIRED` recovery signal for a known rejected user credential.

Governing: `g5.governance.publish.github-author` requires missing/expired/revoked authorization to require connection/reconnection; `git_outcomes` requires preserving established evidence. No fallback credential is used, so this is a recovery regression rather than authorization bypass.

Demonstration: `review_probes::demonstrates_repo_access_401_body_failure_loses_reconnect` serves `401 Unauthorized` with `Content-Length: 100` and one body byte, then closes. The exact-source operation returns `RepositoryAccessError::Failed` carrying status 401, rather than `ConnectionRequired`.

Proposed repair: map preserved status evidence from transport failures through the same endpoint-specific access classification (with rate limits taking precedence where applicable), or make this read return sufficient headers before optional error-body completion. Add a public-path regression for truncated and timed-out 401 bodies; retain ordinary network failure as `Failed`.

### F3 — P2: Returned issue URLs are not bound to the selected provider instance

`backend/g5-scm/src/providers/issues.rs:450-477` accepts `html_url` verbatim and derives `repository_full_name` from any URL with a `/repos/{owner}/{repo}` suffix. `fetch_issue`, search, comments and timeline normalization do not validate these URLs against the grant's configured endpoints. Fixing pasted-reference parsing at lines 1179ff therefore covers only one direction. A configured instance can return an issue whose canonical URL names another instance, and `external_issues.rs:670` forwards that URL as the public canonical issue link. Search's same-name filter likewise accepts a repository URL on another instance if the owner/repository suffix matches.

Governing: `g5.architecture.github_transport` says every accepted issue URL uses the corresponding owner's host. This behavior existed in the moved normalization code but remains an unmet obligation of the new selected-host provider boundary. This finding does not allege that any current request follows the foreign URL or leaks its token.

Demonstration: `review_probes::demonstrates_cross_owner_html_url_accepted` uses API base on the loopback fixture, web base `https://selected-instance.test`, and a valid issue response containing `https://other-instance.test/owner/repo/issues/7` plus a foreign repository URL. `issues::fetch_issue` succeeds and exposes both the foreign canonical URL and `owner/repo` repository identity.

Proposed repair: perform endpoint-aware URL normalization at the typed operation boundary for returned canonical issue/comment/event links and repository URLs, preserving valid separately configured API/web bases, path prefixes, renamed repositories and ordinary issue fragments. Refuse or omit invalid external URLs with a clear response error according to the field's required/optional meaning. Add same-owner positive controls and mismatched origin/port/prefix cases for issue detail and search; exercise the public DTO projection.
