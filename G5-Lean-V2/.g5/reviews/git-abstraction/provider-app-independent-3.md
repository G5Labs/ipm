## Initial findings

### R3-F1 — P2: A secondary rate limit becomes a user access denial

`backend/g5-scm/src/providers/app.rs:299-301` classifies every complete HTTP 403 response as `RepositoryAccessError::AccessDenied` before asking whether the response reports a rate limit. A 403 with `Retry-After: 60` and the secondary-rate-limit message therefore loses status/request/retry evidence. The unchanged credential owner (`backend/g5-api-core/src/auth/repository_credentials.rs:283-299`) turns this into “Your connected GitHub account cannot access this repository. Check your repository access and GitHub App permissions, then retry.” This sends the initiating PR user toward a permissions repair when the provider asked them to wait.

Governing obligations: `g5.architecture.git_outcomes`, `git_retry`, `github_transport` and `scm_provider_client`: retain provider error meaning and retry-after evidence for caller-decided recovery. The old API helper also conflated 403s; this is an inherited behavior left unresolved on a now-migrated operation, rather than a newly introduced authorization policy regression.

Evidence: the isolated public-client executable `/tmp/g5-provider-app-review/reviewer3/probe` called `AppUserClient::verify_repository_access` against a local server. HTTP 403 with the rate-limit headers/body returned `AccessDenied`; the same response with 429 returned `Failed(ProviderError { kind: RateLimited, ... })`. Source tracing establishes the downstream user-facing denial. No actual provider or database was used.

Proposed repair: recognize rate limits before the access-denied status mapping and return `Failed(response.failure(...))` with retained evidence. Preserve ordinary 401, non-rate-limited 403/404, repository-ID mismatch and successful access behavior. Regression should exercise both 403 rate-limit variants (headers and secondary-limit body), ordinary forbidden access, and the credential-owner error projection.

### R3-F2 — P2: Redaction corrupts unrelated request/rate evidence

`backend/g5-scm/src/providers/transport.rs:252-257` treats every suffix matching any nonempty prefix of a selected secret, down to one character, as a leaked secret. `Response::failure` applies that function to complete response headers (`transport.rs:208-217`), although those headers were not truncated. With selected token `0-private-token-canary`, a valid `Retry-After: 60` becomes `6[REDACTED]`. With selected token `token-canary`, the same public probe also changed request ID `scope-rate-test` to `scope-rate-tes[REDACTED]` and “rate limit” to “rate limi[REDACTED]”. These are unrelated complete values, not exposed credentials.

Governing obligations: `g5.architecture.git_outcomes` and `github_transport` require useful, accurate request/rate evidence; `g5.security.credentials.redaction` requires redacting configured values, not inventing a truncated-secret interpretation for every complete string.

Evidence: public-client localhost probe and retained output in `/tmp/g5-provider-app-review/reviewer3/probe.log`; the final run asserts `retry_after == Some("6[REDACTED]")`. The fresh provider-only rlib is newer than every source in the frozen provider module. This finding is independent of F1, reproduced using HTTP 429 so the access-denial branch cannot hide the header.

Proposed repair: distinguish complete response fields from actually truncated diagnostic capture. Redact full selected secrets and credential/URL forms in complete headers; preserve ordinary request IDs and retry values. If partial-secret scrubbing is needed on a bounded/truncated message, apply it using truncation evidence and an appropriate policy there. Regression should preserve `60` and the exact benign request ID while still suppressing full echoed credentials, encoded credential forms and actually truncated secret diagnostics.
