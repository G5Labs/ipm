## Minimal designs and assurance limits

The requested [minimal-design section](../../../docs/code_gaps.md#simplified-minimal-repair-designs)
covers all 20 gap IDs. Each candidate names the existing owner, retained guarantees,
executed comparison or unmodeled decision, and required implementation tests. Existing
invitation rows, report create fences, scope resolution, preview closing state and terminal
host lifecycle often avoid another ledger or recovery queue. These are bounded sufficient
candidates under stated assumptions, not a proof of global minimality or implemented fixes.
Safe unused-repository removal is a scoped capability; in-use detachment remains outside
that proposal. Autoscale, process isolation and notification policy have explicit unresolved
or unmodeled portions.

The [coverage ledger](coverage.md) spans 23 capability groups and separates behavioral
obligations from inspected structural facts. This is broad ontology coverage, **not a
measured code line/branch percentage or proof of the whole application**. Models are manually
source-bound abstractions with finite actors/versions and explicit atomic premises. There
is no machine-checked composition/refinement, deployed database/cloud/browser proof,
physical process-death proof, complete cryptographic/RLS audit or full failure coverage.
Many finite terminal configurations disable deadlock checking or permit quiescence;
only named fairness checks establish conditional liveness. Important remaining areas
include native writers, cache reconstruction/replacement, arbitrary cloud retries,
PostgreSQL interleavings, parser behavior and provider translation. Runtime E2E and restore
drills are proposed, not executed.

The six [clarifications](clarifications.md) retain physical VM uniqueness, per-request
process isolation, existing-user invitation timing, local process scope, Base Make Remote
and viewer collaboration as questions. Provisional choices are not human amendments.
The external-check freshness candidate remains closed against its actual admission-time
policy. Remaining application defects are explicit in the gap report rather than being
used to weaken Ben's requirements.
