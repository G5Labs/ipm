## Findings

### R2-RUNTIME-1 — P1: CloudLinkage excludes the current ready-but-unlinked recovery writer

**Location:** `.g5/TLA_verification/ben-ontology/runtime/CloudLinkage.tla:12–25`; `.g5/ontology/software_architecture/host_control_plane.g5.md:46–49` and its formal-evidence metadata.

`Recover` changes `provisioning/link=0` atomically to `ready/link=1`. That excludes the actual `ready/link=0` state: authenticated Hello independently marks the host ready (`host_control_state.rs:220–228`), and migration `073_repair_live_worker_host_cloud_refs.sql:85–101` overrides the baseline-only recovery guard, allowing attachment to **any non-terminated unlinked row** while preserving its lifecycle state. The retained source binding to `001_lean_baseline.sql:216–236` is superseded. Neither the model nor the inspected manifest includes this current SQL writer correctly.

This matters to the asserted compensation guarantee. After Hello, a delayed bring-up reply can fail its provisioning-only setter, read `ready/NULL` from the ownership query (`bringup.rs:471–525`), and decide to compensate. Recovery can attach the same instance before the later `terminate_instance` call (`bringup.rs:539`). The cloud implementation performs DELETE for the saved zone/name without consulting DB ownership (`gcp.rs:1404–1416`). A bring-up lease does not exclude this schedule: `touch_worker_host_bringup` remains provisioning-only (`001_lean_baseline.sql:1696–1705`), so it stops renewing after Hello, and the recovery writer can act after its 90-second bound. The cloud operation or task can still be delayed; no code establishes an atomic ownership/deletion boundary.

**Executed challenge:** a temporary copy adds independent Hello, allows the bring-up lease to expire after Hello, and changes Recover to attach a live unlinked host without changing its status. With `Fault="none"`, the existing safe configuration fails `NoOwnedCompensation`: `Create → Hello → ExpireLease → Reply(read unowned) → Recover → Compensate`. TLC exit 12, 40 generated / 20 distinct states, depth 7. This is a source-bound finite counterexample, not a runtime reproduction.

**Minimal uplift repair:** bind the effective migration chain; separate host registration from linkage; retain the read/decision-to-external-deletion interval; add the current recovery writer and lease guard. Classify the actual trace as an as-built divergence rather than preserving the existing safety-pass claim. An intended variant must explicitly name the ownership mechanism that prevents recovery/teardown from crossing; do not hide it in an assumed atomic external deletion. Keep valid attachment, ready-host repair, preserved-owned-result and unowned-compensation witnesses. Update the owning block and code gaps without application repair.

Also restore the omitted reconstruction contract under this owner, using the baseline ontology only as corroboration: `20e393c0:.g5/ontology/software_architecture/worker_host.g5.md:38–64` retained ready/draining-host linkage recovery, provisioning-only missing-instance termination, and accepted-insert timeout semantics. Current implementation independently supports these in migration 073, `reconciler.rs:463–625,649–665`, and `gcp.rs:1329–1400`. A pending accepted insert retains its deterministic zone/name and boot image instead of creating a second attempt in another zone; lookup errors/transient states are not confirmed absence. The current one-instance model does not check these omitted obligations, so either extend the relevant concern or retain an explicit open coverage gap.

### R2-RUNTIME-2 — P1: Rotation's model assumes the custody snapshot it needs to establish

**Location:** `.g5/TLA_verification/ben-ontology/runtime/HostRotation.tla:25–39`; `.g5/ontology/software_architecture/host_control_plane.g5.md:44` and scoped formal-evidence metadata.

The model initializes custody once and only decreases it. It has no competing placement writer; `RotationDrain` atomically checks current custody, and `Teardown` checks it again. The normal implementation does not establish those two atomic checks. `WorkerHostService::place` can select any ready, qualified same-region host (including a rotation-paired host), holds its row lock, and writes a new `starting` VM (`worker_host_service.rs:387–455`). Normal `idle_quiesce` uses a single `UPDATE host ... NOT EXISTS(active VM)` statement (`rotation.rs:691–708`), then its caller immediately tears down (`rotation.rs:598–605`). There is no second custody check before the cloud DELETE (`rotation.rs:1025–1046`). The forced lane has a different lock/read sequence and must not supply an imaginary guard to the normal lane.

A concrete missing schedule is: placement locks the host while custody is zero; rotation's UPDATE begins with that snapshot and waits for the host; placement commits the new VM; rotation's update proceeds using its statement snapshot of `workspace_vms`, returns drained, then calls cloud teardown. The default ScopedDb path uses ordinary `pool.begin()` (`g5-authz/src/scoped_db.rs:141`), and no transaction isolation override was found. PostgreSQL explicitly documents that a Read Committed updater can observe the concurrent target-row change without seeing the same transaction's changes to other rows. See [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED). This is a source/SQL-semantics analysis, not an executed database reproduction.

**Minimal uplift repair:** add a real placement actor and distinguish the rotation statement's custody snapshot from committed custody and the host lock. Model normal teardown according to the actual caller rather than adding a fresh custody guard. Then either establish an independently supported exclusion or classify the counterexample as an as-built gap. Retain current ontology intent. A future implementation repair would need to establish a fresh custody decision while holding the admission lock, but application repair/testing is outside this uplift. Until resolved, the current `IdleBeforeNormalDrain` and `CustodyBeforeTeardown` receipts are conditional intended checks, not evidence of this normal-path correspondence.

**Minimal uplift repair:** check monotonic installed sequence using a temporal action property or a sticky rollback monitor; add the sequence control and a positive out-of-order reply witness. Check server duplicate-grant no-extension separately if that stronger claim is retained. Keep code/model safety claims limited to the actual listed properties, and update the runner's expected-property classification for a temporal control if used.
