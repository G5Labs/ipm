## Findings

**CI-G1 — revoked invitations can still grant membership through OAuth automatic acceptance.** `AuthService::handle_callback` reads pending/unexpired matching verified-email invitations without locking them (`auth_service.rs:1080–1098`). It subsequently inserts membership from the captured tuples and updates the invitation by ID without checking pending state or affected rows (`1100–1132`). `OrgService::revoke_invitation` deletes a pending invitation and commits independently (`org_service.rs:1263–1303`). Schedule: login reads pending; administrator revokes and commits; login inserts membership; invitation update matches zero rows; login commits. The membership FK names the organization and user, not the invitation (`001_lean_baseline.sql:8083–8101`). Existing explicit acceptance locks the invitation and checks its current state (`org_service.rs:1033–1150`), but OAuth does not use it. No documented exception permits a revoked invitation to authorize membership. This conflicts with the administrative revocation authority underlying `g5.organization.admins` and `g5.organization.invites`. `Invitation-as-built` produces the four-state counterexample; `Invitation-intended` serializes revocation with acceptance and passes. This is a code-bound concurrency finding, not a PostgreSQL runtime reproduction. Proposed reproduction: block OAuth after invitation SELECT, revoke through the admin API and commit, resume login, assert no membership. The desired linearization rule allows acceptance that wins before revocation; it must not resurrect a revoke that already won.

**CI-G2 — UI preference storage is browser-wide instead of user-and-organization scoped.** Ben's `g5.user.settings` explicitly says org-specific; the retained c1 discussion further specifies `(user, org)` for model, keys, UI. `frontend/src/hooks/useUserSettings.ts:13–14,170–203,258–350` reads/writes the single key `g5-user-settings` and takes no user/org parameter. Switching organization (or another identity using the browser) reuses preferences. This differs from backend `user_configs`, which resolves `(org_id,user_id)` in `config_service.rs:608–625`. `UiPreferenceScope-as-built` demonstrates another scope observing the first scope's choice, whereas tuple-keyed intended storage passes. The finding concerns UI preference isolation, not an allegation that model API keys are in localStorage. Proposed reproduction: set a UI layout in org A, switch to B and verify independent preferences, then repeat with another user on the same browser. No browser reproduction was executed.

**CI-Q1 — immediate membership versus login-triggered invitation acceptance.** `org_service.rs:635–808` immediately creates membership when the invited email belongs to an existing platform user; only unknown users receive a seven-day invitation. Ben says invitations become membership upon login. Treat this as an explicit policy discrepancy to resolve rather than quietly changing the supplied statement. Best-supported provisional intent is Ben's login-triggered flow; alternative is to preserve immediate admin-granted membership for existing users and state that exception. Existing users' automatic addition is directly visible implementation evidence, not a new human approval.

**CI-Q2 — notification settings are described but current UI removed them.** Ben `g5.user.identity` includes notification settings. `useUserSettings.ts:174–188` deliberately drops `notifyTaskComplete`, `notifyAgentBlocked`, and `notifyChannels`; current user profile update DTO only offers display name/avatar (`user_service.rs:110–126`). This is evidence of missing delivery-preference support in the inspected surfaces, but a repository-wide negative is not yet established. Preserve source intent and investigate the remaining settings surfaces before declaring a complete code gap.

**CI-X1 — stale VM release affects chat notices.** Runtime auditor owns the full reachable schedule and model. `task_lifecycle.rs:4020–4079` settles chat notices by workspace only; lost release also cancels queued/waiting previews and settles preview intent without incarnation. `chat_service.rs:690–712` withdraws workspace notices without VM identity. Integrate once with the runtime auditor's finding, rather than duplicating its gap.

### Exact candidate wording for integration

- **CI-D2, revised — `g5.user.login-proof`:** “Platform OAuth login completes only in the browser that initiated its unexpired, single-use attempt and for the requested provider. - **CI-D3, revised — `g5.documents.question-decisions`:** “Project question sets preserve human decisions and distinguish them from agent proposals. A recorded human decision may be changed or cleared only by its author; a person may adopt or clear an agent proposal. Answer changes preserve question identity and wording. A matching retained receipt is an idempotent retry; a conflicting request under that receipt's key is refused. Other commands require the current question revision. A person's answer or set creation uses the selected-file Save operation; agent proposals remain live until explicitly published.
