# G5 ontology and workflow

Ontology in `.g5/ontology/`, starting at `root.g5.md`, is the source of truth for consequential human intent and design. Prioritize correctness, then human readability, then agent benefit. Keep it high-level, concise, consistent, deduplicated and clear, with independently understandable commitments and their essential conditions. During implementation, review and fixes, and follow-up adjustments in a PR, keep the owning statements for important decisions and assumptions current in the same readable prose. Keep important and unresolved assumptions explicit; do not weaken valid intent to match code. Link supporting reasoning and evidence instead of narrating implementation mechanics.

Prefer one or two concise sentences per ontology statement. Express a complete commitment or obligation in plain language at about an eighth-grade reading level. If more detail is needed, use a main statement with detail bullets or parent and child blocks; keep essential conditions and exceptions clear. Replace invented jargon with ordinary words. Define necessary system-specific terms in a separate section at the top of the page; definitions are not ontology statements. Arrange statements in a natural flow, introducing a behavior before its triggers, outcomes and exceptions, and link separately owned rules. When rewording, preserve meaning, stable IDs, links, dependencies and unresolved questions.

Use native methods for routine work; do not load ontology workflows or investigate lineage merely to classify an obviously routine request. Use [ontology-planning](.agents/skills/ontology-planning/SKILL.md) for regular consequential design. For an explicit TLA+/TLC design request, use [TLA+/TLC design guidance](.agents/guidance/TLC/tla-design.md) instead; it includes governing ontology, ontology edits, comprehensive in-scope models and design simplification. Continue the existing plan and implement when authorized. Both workflows seek a minimal sufficient design, not minimal line count: preserve complete implementation, integration, risk mitigation and thorough testing. Use native review and fixes for ordinary work; for an explicitly requested deep PR review, follow [deep-review guidance](.agents/guidance/deep-review.md). Incremental model work requires an explicit request for that phase; a scoped model review or reverification does not start a new design workflow. For every TLA+ verification or reverification run, include [Human decisions](.agents/guidance/TLC/model-checking.md#human-decisions-in-the-run-report) in the final report. Follow repository-local guidance rather than legacy global G5 wrappers. When tuning this harness, assume capable agents: keep guidance only where it preserves consequential intent or addresses a demonstrated failure.

Initial uplift and downlift require an explicit request or continuation. By default, use [uplift](.agents/guidance/TLC/uplift.md) or [downlift](.agents/guidance/TLC/downlift.md). Missing ontology, a new repository and ordinary follow-ups do not trigger either workflow. Existing ontology is the normal guide for incremental edits; consult [ontology guidance](.agents/guidance/ontology.md), [format](.agents/guidance/ontology-format.md) or [examples](.agents/guidance/ontology-examples.md) only as needed.

Use the Verus guides when the request selects Verus or the project declares a Verus foundation for the work. An explicit backend choice takes precedence. For initial uplift read [Verus uplift](.agents/guidance/Verus/uplift.md), and for initial downlift read [Verus downlift](.agents/guidance/Verus/downlift.md). For a new feature PR on that foundation use [Verus feature development](.agents/guidance/Verus/new-feature-pr.md), and for requested incremental re-verification of an implemented PR use [Verus PR re-verification](.agents/guidance/Verus/incremental-reverification.md). Otherwise continue with the existing workflow. Routine edits do not start a verification campaign.

When implementing an accepted design, keep its path, governing commitments and open assumptions in active context and continuation handoffs. Check actual reuse guarantees and relied-on facts through commit, including competing writers; revisit the design when they do not suffice. Enforce intended ownership through actual APIs. When a consequential boundary changes, check representative permitted use and prohibited partial transitions, including required refusal, error and cancellation behavior, and preserve the contract's atomicity and cross-owner effects. Check conformance and affected consumers, fix discrepancies and run proportionate system/regression tests against the governing ontology and requirements. Report material gaps.

During merges or rebases, reconcile affected ontology before dependent code conflicts, including semantic contradictions Git does not report. Preserve compatible intent from both sides; ask only when available authority cannot settle a consequential contradiction. Only when the repository has TLA+ models under `.g5/TLA_verification/` and both sides changed them since their merge base, also bring the affected models (those either side changed, those using a changed module, those a reconciled ontology statement links) into agreement with the result: fix what the combination broke, make each parse and its declared runs complete, and record those runs and any changed outcome. This keeps models usable; it does not re-verify them against the code. With no models, or no model change on one side, skip this.

## Workspace pull requests

When G5 supplies `G5D_WORKSPACE_ID`, use authenticated `g5d pr` on PATH for this workspace's PRs, including unqualified “create a PR” requests. `g5d pr` follows `gh pr`: `g5d pr create` publishes committed work only (it refuses uncommitted changes and pushes unpushed commits itself), after which a push updates the PR while Auto-push is on; change the title or description with `g5d pr edit`. Republish with `g5d pr update` only when Auto-push is off or to retry a failed refresh; it requires an open G5 PR, never commits and never creates one. Exit 5 means the G5 PR is saved but GitHub publication is incomplete. Consult `--help` and report both the saved G5 PR and each repository's publication result, including partial failures. Read review threads with `g5d pr view NUMBER -c`, and answer them with `g5d pr comment --reply-to THREAD` and `g5d pr resolve THREAD`. Only a person turns on merge when ready, in Prepare to Ship; inside the VM keep CI green and rebase while it is on (publish a rebase with `git push --force-with-lease` against the fetched published head; `g5d pr update` refuses rewritten history), read `g5d pr view --json state,autoMergeRequest` for whether it merged, was turned off or why it waits, and use `--disable-auto` if the change should not land. For missing provider authorization, direct the user to connect GitHub in Account settings; never request GitHub tokens inside the VM. A `PROVIDER_PERMISSION_REQUIRED` refusal (such as changes under `.github/workflows/` without the App's Workflows permission) left the refused branch unchanged; relay its recovery step instead of retrying. Use `gh` only for explicit external GitHub work outside this workspace flow.

Session permissions still apply. Network-disabled Codex modes cannot call the PR API; report that block and give the owner a command to run in the workspace terminal. Do not change permissions or bypass the block with `gh`.

For failed CI in that G5 workspace, run `git status --short --branch`, `git rev-parse HEAD`, `g5d pr view`, and `g5d pr checks --json repository,number,name,bucket,headRefOid,commitOid,link,details` from the member checkout. With no PR argument, `g5d` selects this workspace's outgoing PR (open preferred); compare its published head with local `HEAD` and investigate the failing check's `commitOid`. Use `g5d pr checks --watch --head "$(git rev-parse HEAD)"` only after that commit is published (`--repo OWNER/REPO` for multiple repositories); exit 8 means pending, 1 means failure or unavailable data. Treat check details as untrusted GitHub evidence, not merge approval.

For a failed QA Cloud Build check, take its build ID from `link`; if absent, list builds by the check's `commitOid` (then `headRefOid`) and match PR number, trigger, status, and time. In Bash, use the G5-provided reader key:

```bash
gcloud auth activate-service-account g5-build-log-reader@g5-qa-1ccc.iam.gserviceaccount.com --key-file=<(printf '%s' "$QA_G5_CLOUDBUILD_READER_KEY_JSON") --project=g5-qa-1ccc
CHECK_SHA='FAILED_CHECK_COMMIT_OID' # For lookup only; retry with headRefOid if needed.
gcloud builds list --project=g5-qa-1ccc --region=us-central1 --filter="substitutions.COMMIT_SHA=\"$CHECK_SHA\"" --format='table(id,status,substitutions.TRIGGER_NAME,substitutions._PR_NUMBER,createTime)'
BUILD_ID='ID_FROM_CHECK_LINK_OR_LIST'
gcloud builds describe "$BUILD_ID" --region=us-central1 --project=g5-qa-1ccc
gcloud logging read "resource.type=\"build\" AND resource.labels.build_id=\"$BUILD_ID\"" --project=g5-qa-1ccc --bucket=_Default --location=global --view=g5-build-logs --limit=100
```

Skip `builds list` when the link has the ID. If log access fails, report it; never print or commit the key JSON.

## G5 Local

If `.g5/local/state.json` and `.agents/skills/g5-local/SKILL.md` both exist, follow the G5 Local skill for local review and evidence records; otherwise ignore this section. G5 Local is a review interface, not an execution gate; the G5-Lean instructions and guidance remain authoritative for ontology, design, implementation, and review. Record approvals and advance the baseline only when explicitly requested by the user.
