# Incrementally re-verify an implemented PR with Verus

Use when asked to re-verify an existing PR. Respect any review-only, repair or product-baseline limits in the request. Start from the delivered feature, including work predating this session. Use the product’s existing runbook and [playbook](verification-playbook.txt) change gates. Start with its model-to-source reverse lookup and the source diff, including changed source that was never bound. Keep the pre-PR product, the delivered candidate and any subsequently repaired revision distinguishable.

## Freeze the scope and expected outcomes

Pin base and candidate source, original accepted requirements and decisions, ontology, inherited foundation and toolchain. If the foundation's evidence describes a different revision than the pre-PR product, record that mismatch separately from PR changes and do not carry the affected guarantees forward unchecked. Recover the complete PR diff including additions, removals, generated inputs and changes to contracts or configuration. Derive the expected outcomes from governing sources before reading the author's success claims. Use an independent reviewer where available, or a separate pass with its authorship recorded.

Account for the inherited catalog by relevance, grouping unaffected claims with a reason. Start from the obligations and facts each invariant reads, then identify actual producers, competing writers, unchanged callers, storage boundaries and final consumers. Compare that inventory with the modeled actions. File intersection alone misses a newly registered handler or a changed premise in an unchanged caller. Compare the new source inventory to the old one: a disappearing link, rename, registration or new unbound path may reopen an unchanged claim. Use the broader subsystem as the invalidation boundary where discovery is uncertain. Record search limits. For each affected requirement, write down what would distinguish correct behavior, what evidence the baseline had, and what needs reopening. A PR requirement that no inherited model or proof covers is an in-scope obligation, not an inherited gap.

When relying on a sparse or untested reverse lookup for PR selection, calibrate it on a relevant historical diff or a harmless changed fixture, including an unbound writer or changed caller. Derive the expected affected obligations from product behavior independently of the map, then compare them with the obligations the detector reopens. Record missed obligations and unnecessary reopenings. Use the broader subsystem boundary when calibration missed an affected obligation or the PR introduces a dependency pattern the gate has yet to cover. Reuse the calibration while its selection rules and relevant dependency patterns still apply.

## Recheck, diagnose and repair within authority

1. Compare the delivered ontology, proof statement and observed behavior against the accepted rule, including exceptions, units, identity and supported inputs. Exercise differing histories when a model may merge them. Check whether a new limit or refusal removed a legitimate input. Reconcile both successful trajectories and required failures.
2. Apply [Verus verification](verification.md) to each affected function, transition or protocol. Check initialization, abstraction, actual effects, external premises and competing writers. Recheck dependents of changed contracts, trusted ports, stores or providers. Compare product observations at the final reader using the same input as the model. For concurrency or recovery, identify the actual interruption and the exact safety or progress property. Keep a failing design and its witness visible.
3. Attribute each discrepancy using the pre-PR code, evidence or a matched reproduction. Record origin, impact on the PR and repair authority separately. If the baseline already violates the property, test the newly exposed path or effect separately. Reproducing the old failure can hide a new regression. In the normal repair workflow fix PR-introduced or PR-worsened defects and recheck the fix. Report unrelated baseline defects and blocked reliance. In a review-only task preserve the finding and proposed discriminating check. An absent pre-PR field does not excuse a required feature that this PR can implement.
4. Before deferring a repair, identify which accepted outcome is settled, which choice remains and whether its answer can change the local work. Complete work valid under the reasonable answers. Keep outstanding external evidence and genuine owner decisions explicit. Apply authorized fixes to the owning code, models, bindings or ontology and reopen their dependents. When a repair lets a request past a previously failing prerequisite, exercise the newly reachable path to the required outcome before closing it.

## Close on the final revision

Compare every reused receipt with its current inputs using the [foundation evidence rules](setup_foundation.md#execution-evidence-and-reuse). A matching product revision alone misses a changed proof crate or an invalidated premise; an unchanged proof may remain valid while a source-only change invalidates its product binding. Refresh the binding and correspondence checks; change the model only if the modeled rule or its premises changed. Update ontology metadata only when its formal association changes; preserve the human rule or resolve new intent with its owner. Rerun affected proofs, meaningful controls and complete affected native suites on the final candidate. Check the selected targets and actual verdicts. Verify the specific regression at the real consumer and a valid neighboring case. Track the before and after results of repairs separately from pre-existing limitations.

Report the disposition of each PR obligation, new or lost guarantees, fresh and reused evidence, human decisions with their sources, and remaining reliance or repair limits. An expected counterexample confirms the violation for the variant checked. A failing deliberately broken control shows detection. A violation on a reachable as-built path leaves the product requirement unmet.

State separately whether the authorized re-verification work is complete and which PR guarantees are established, conditional, violated or unestablished. Missing required investigation, an authorized repair left undone or a missing required check leaves the work incomplete. A fully investigated defect outside the repair authority can close the review with the product requirement recorded as violated.
