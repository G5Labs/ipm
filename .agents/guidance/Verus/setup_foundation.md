# Hand off a Verus foundation

Keep existing crates, fixtures and product-specific evidence where they are useful. For a new foundation, place the Verus runbook under `.g5/Verus_verification/`. The [G5 foundation guide](../setup_foundation.md) governs the shared ontology and findings presentation. Use the [shared viewer format](../TLC/setup_foundation.md#artifact-paths) for concern manifests and bindings. Publish Verus run rows in `results/viewer-index.jsonl` with the original outcome, assessment, repository-relative receipt path and recorded proof or case counts. Keep existing TLC evidence intact.

## Two links with different owners

- **Ontology → formal contract.** In the canonical block’s [G5 metadata](../ontology-format.md#metadata), use an ordinary relative link to a stable model, action, function contract or other durable formal target. A shared model is fine: make the relevant claim identifiable there. Change the association when the commitment or target changes. Keep source provenance, question and findings references as G5 requires. The block does not maintain implementation locations, role lists, hashes or run-by-run receipts.
- **Formal contract ↔ implementation.** Each project chooses one convention for recording these links and uses it across all models and iterations. Each link identifies the active formal declaration, the production symbol or source range at the pinned revision, and the behavior or role it connects. Include the deciding inputs, writers and consumers needed for the claimed result, including alternate paths that can change it. Distinguish executable-body verification, transcription with native agreement, inspection only, and missing or conditional roles.

### Where to find every model-to-code link

In the project’s Verus runbook, give the complete machine-readable map or the command that builds it from a clean checkout, and say where to edit a link. Collect inline model citations, model/source crosswalks and existing bindings into one view on the pinned production census. Resolve aliases and ranges to named members. Retain each relation’s original evidence, formal target when known, role and scope. A resolved citation or a relation explicitly marked as assumed gives locator reach. For the active subset, the project must register an exact formal claim and a direct or justified shared behavioral role. Review actual support separately, including cases where a claimed decision is supplied as an input. Preserve multiple claims on one member while counting that member once for reach. Keep stale, ambiguous, file-only and out-of-census records visible for reconciliation. Keep production locations on the formal side and edit evidence at its existing owner. Scoring, reverse lookup and stale-evidence checks consume this same view.

Give a worked lookup in both directions. Starting at one real formal claim, show the exact production lines and their role. Starting at that production symbol, list the affected formal claims. Include copyable commands for its proof and distinguishing control, and compare the product observation if available. Include working directory, toolchain and library pins, declared domain, unchecked premises, raw verdict and what a consumer may rely on. Use `implementation-verified` only for a verified shipped body under established premises, never for a transcription; apply the [existing tag rules](../ontology-format.md#metadata). For design-only work, name what will need binding once implementation exists.

## Execution evidence and reuse

Use the project’s own build graph, stable symbols, generated maps, hashes or another economical mechanism. Reuse the [playbook](verification-playbook.txt) approach where it fits: per-slice or per-crate input stamps, scoped verification on change, and broad invalidation when the shared harness or oracle changes. SQL statement generators and PostgreSQL-specific adapters are examples, not prerequisites. The required outcome is a reproducible command that names affected claims/bindings or conservatively marks a wider scope stale; a table of evergreen green links is insufficient.

Decide two things separately: does the **theorem** still follow from the same formal inputs (definitions, imports, trust, tools and configuration), and does its **correspondence** still hold at this product revision (deciding source, callers, alternate writers/readers, adapters, provider or observation)? Discover added, deleted and renamed production members as well as edits to known links. Where dynamic dispatch, generated code or external state makes precise invalidation infeasible, reopen the affected subsystem and record the premise. No per-member hash is required if an existing coarser gate is reliable.

Demonstrate the gate using the old receipt on a changed formal input and on a source-only change that can alter the observed result. The former should reopen the relevant proof; the latter must reopen product evidence even if the theorem is reusable. Show what the gate does with a newly registered writer or equivalent new dependency. Where the map is sparse, use the [incremental impact check](incremental-reverification.md#freeze-the-scope-and-expected-outcomes) to compare selection against the affected behavior. Use disposable fixtures or known diffs. Record fresh versus reused results, the input identities, commands, scope, expected/actual verdicts and witnesses. Rebind and recheck the real operation, changing model or ontology only if the evidence warrants it. Preserve unsuccessful runs. A timeout, omitted target, empty test run or unresolved binding leaves work open. Run complete affected targets on the final candidate; preserve the earlier counterexample and distinguish a repaired candidate from the original.

## Findings and questions

Keep one authoritative pair of findings files. Follow G5’s [shared reproduction rule, format and decision protection](../TLC/setup_foundation.md#findings), [simplification comparisons](../TLC/setup_foundation.md#simplification-comparisons) and [snapshot/check procedure](../TLC/setup_foundation.md#format-checks). For G5 viewer delivery place the pair under `.g5/Verus_verification/`. A legacy TLC-format pair can stay in place until migrated. Preserve entry IDs and owner decisions. Before running the shared snapshot/check commands, set `verification_root=.g5/Verus_verification` in that shell, or the path of the selected existing findings pair. The shared commands preserve this selection. Use the model linker in links-only mode and review verification tags against their precise claims.

Preserve the stable anchor, plain heading, severity/status, original run and protected owner decisions. Link governing blocks back through their metadata. Distinguish a potential problem, a reachable defect, a question of intent and a refuted finding. State what found it and what actually reproduced it, or “none.” For a simplification compare the as-built and proposed designs under the same required outcomes and operating envelope. Use the `Comparison:` line to link the receipts for the two designs and identify any missing run. Use real bounds and state counts only when comparable and available. A proof-unit count is not a state count.

Record unsettled policy in the shared [open questions format](../setup_foundation.md#open-questions). A reachable bug or an open proof obligation needs a policy question only if intended behavior is also unresolved.

For initial uplift, have a reviewer reproduce a representative result and control from the runbook. Report validated, conditional, violated, unestablished and inherited guarantees, decisions with sources, and the residual areas another change cannot rely on. Preserve [reviewed work during regeneration](../uplift-evidence.md#preserve-reviewed-work-during-regeneration); check the product diff, including untracked files, against the frozen baseline.
