## Install and update (03)

### F-INST-1
**Update reports success without running update steps when the update lock is busy.**
- Code: `HandleAllUpdateSteps` takes `lock +^IPM.UpdateLock(name):3` (`src/inc/IPM/Common.inc#L105`); if the lock is
  not granted within 3 seconds it does `return sc` with `sc = $$$OK` (`src/cls/IPM/Storage/Module.cls#L105-L108`). No
  message is printed unless verbose, and then only "Acquiring lock". `%ApplyUpdateSteps` (`Lifecycle/Base.cls#L1923`)
  passes the OK on; the new version is committed (`Utils/Module.cls#L1346-L1351`).
- Intent: `update` help, "Also runs all of the update steps from the current version to the newer version"
  (`src/cls/IPM/Main.cls#L167`). PR #887 lists "Preventing two updates ... at the same time" as out of scope, so a
  guard was not promised, but silent success was not promised either.
- Impact: two concurrent `update` runs of one module (or any holder of the lock) leave the module at the new version
  with its steps not run, and the operator told it worked. The steps stay due (no `TimeStampEnd`), so a later update
  would run them, but nothing prompts that. Statement INST-B71; decision DEC-INST-6.
- Native check: confirmed — `nc-inst-3-update-lock-busy`: with another process holding `^IPM.UpdateLock("update-simple")`, `update update-simple 2.1.1` returned OK after 3.3 s, printed no warning, left the module at 2.1.1 and created no V2 step record (no step ran). `nc-inst-3b-update-after-lock-free`: a second update to the same version, with the lock free, ran the V2 steps, so the steps stayed due.
- Proof: `inst_witness_busy_lock_reports_success` (`models/verus/update_steps.rs`, verified): from an installed module with one due step, the run with the lock timing out ends OK with the new version durable, no step run and the step still due, and that last step is not an L1 step. With the lock granted (premise PL) every step refines L1 (`inst_refines`). Model checks: `inst-explore-refinement-without-pl` fails as expected (41,400 transitions, every one a lock timeout); `inst-conf-nc-inst-3-update-lock-busy` replays the IRIS run. Statement INST-B71 carries F and the refuting observation (`O!:nc-inst-3-update-lock-busy`); the witness is not a P tag.

- **Revision (2026-11-13, decision resolved):** DEC-INST-6 resolved (assumption): a busy update lock must make `update` fail with a clear error (removed PR #887 test TestSimultaneousUpdateFails asserted it; the first lock code said 'quit if we cannot'). The finding **stands (High)**; new statement INST-B81 carries it. decisions/research/inst.md#dec-inst-6--what-should-update-do-when-the-update-lock-is-busy-high

### F-INST-4
**Between registries that offer the same version, the registry created first wins; sort order plays no part.**
- Intent: INST-B4. `SearchRepositoriesForModule` lists enabled registries `order by %IPM_Repo.Definition_SortOrder(ID)`
  (`src/cls/IPM/Repo/Manager.cls#L70`), and `OverriddenSortOrder` exists to set that order (`Repo/Definition.cls#L37`).
- Code: results are collected in `versions(major, minor, patch, sub, repoID, name)` (`Repo/Manager.cls#L148`) and read
  back in subscript order, so for equal versions the registry ID (creation order) decides and the SQL order is lost.
- Native check: found by check #10 — `nc-inst-10b-registry-tie-break` (r2 created first with sort order 2, r1 second
  with sort order 1: `install nc-inst-x` took it from nc-inst-r2) and `nc-inst-10c-registry-tie-break-high` (same, with
  r1 at sort order 3: still nc-inst-r2). In `nc-inst-10-registry-prefix` r1 was both first-created and tied on sort
  order, so it did not separate the two readings.
- Impact: an operator cannot prefer one registry over another for the same version by sort order; deleting and
  re-adding a registry changes which copy installs. Statement INST-B4.

### F-INST-5
**`update -dev` from a registry does not run in developer mode (observed for a filesystem registry).**
- Intent: the update command's `-dev` modifier "Sets the DeveloperMode flag for the module's lifecycle"
  (`src/cls/IPM/Main.cls#L184`); INST-B52 (update -dev sets developer mode on the named module) and INST-B68 (a failed
  update in developer mode is not undone).
- Code: `LoadModuleReference` sets `tDeveloperMode = 0` for a registry that serves directories unless the version is a
  snapshot (`Utils/Module.cls#L128-L136`), and `LoadModuleFromDirectory` replaces `DeveloperMode` with that value for
  every load that is not a top-level install (`Utils/Module.cls#L307-L310`). An update sets `Update`, not `Install`.
- Native check: found by checks #4 and #19 — `nc-inst-4e-dev-update-from-registry` (`update -dev update-simple 2.1.1`
  from an fs registry: OK, module 2.1.1 without developer mode); `nc-dep-19f-dev-registry-update` (`update -dev
  nc-dep-co-p 2.0.0` whose Activate fails: the moved dependency and the parent are rolled back to 1.0.0, as in
  non-dev `nc-dep-19d-rollback-after-dep-moved`). With `-path` the flag works: `nc-dep-19e-dev-path-update-dep-kept`
  (parent 2.0.0/dev, dependency kept at 2.0.0) and `nc-inst-4c-dev-failed-update`. Related, same code path: a plain
  `update` of a module in developer mode clears its developer mode (`nc-inst-7-dev-mode-guard` v5,
  `nc-inst-2-dev-install-then-update`).
- Not run: remote and ORAS registries. By inspection the same override applies there: `LoadModuleFromArchive` calls
  `LoadModuleFromDirectory` with the default override 0 (`Utils/Module.cls#L293-L296`), so only `update -dev -path`
  keeps developer mode.
- Impact: an operator who asks for a debuggable update from a registry gets a transactional one and loses developer
  mode silently. Statement INST-B52.
- Proof: `inst_witness_dev_update_from_registry_rolls_back` (verified): `update -dev` of a non-snapshot version from a registry whose step fails ends with the old version, not in developer mode, which L1 (INST-B68) forbids. With premise PF5 every step refines L1. PF5 now reads: the run has the typed -dev / -nodev, else the developer mode stored on the module; it holds for every folder or `-path` load (the stored mode is modelled, review finding 7) and fails only for registry loads: `-dev` of a non-snapshot version other than a top-level install, and a registry update without -dev of a module stored in developer mode (Main:Install passes DeveloperMode=0, which clears it: `nc-inst-7`, `nc-inst-2`). `inst-explore-refinement-without-pf5` fails as expected (76,348 transitions: install 15,136, update 61,212); `inst-conf-nc-inst-4e-dev-update-from-registry` replays the IRIS run. Statement INST-B52 carries F and `O!:nc-inst-4e-dev-update-from-registry`.
- Contrast (not a defect): with `-path` the stored mode is kept. After `load -dev`, a plain `load` keeps developer mode and seeds nothing, a plain `load` of a newer version with an update package is refused (the guard reads only the typed flag), and a plain `update -path` whose step fails is not undone (`nc-inst-fix-stored-dev-plain-load`, `-load-newer`, `-update-path-fails`, `-update-path-retry`).

- **Revision (2026-11-13, decision resolved):** Part B U17 (decisions/research/inst.md#u17--f-inst-5-for-remote-and-oras-registries): **ORAS run**, remote by inspection. `install nc-a2-o17 1.0.0` then `update -dev nc-a2-o17 2.0.0` from an ORAS registry ended OK at 2.0.0 with developer mode off (O:r4-inst-u17-oras-dev-update, now `O!` on INST-B52); `update -dev` whose step V2.B throws was rolled back to 1.0.0 with no record of V2.A (O:r4-inst-u17-oras-dev-failed-update). The remote client takes the same branch (`LoadModuleFromArchive`, `Utils/Module.cls#L141-L173`, `#L258`). Added from DEC-LOAD-2 (resolved, evidence: a plain command keeps developer mode, only -nodev turns it off): a plain `update` from a registry also clears developer mode through the same lines (`#L309-L310`). The 'Not run' line above is superseded for ORAS.

### F-INST-6
**A class of the update package named V<n><something> hides the step class V<n>; update then reports success without running its steps.**
- Code: `GetUpdatePackageClassList` (`src/cls/IPM/General/Update/VersionBase.cls#L34-L60`) selects every class whose name starts with `<UpdatePackage>.V`, keeps only the digits of the last name piece (`$zstrip(..., "*E'N")`) and stores `updatePackageClassList(classNum) = className`, so a later row with the same number replaces an earlier one. `HandleAllUpdateSteps` then walks the surviving class, and skips it when it has no `GetOrderedMethods` (`Storage/Module.cls#L131-L138`).
- Intent: VersionBase.cls#L1-L2 asks for step classes named `<UpdatePackage>.V#`; nothing forbids other classes in the package. INST-B44, INST-B71 (update runs every step that was due), INST-B76.
- Native check: found by probe `nc-inst-model-class-number-collision` (`validation/logs/65-inst-model-order.log`): with step class `NcInstOrd.Upd.V3` (step A) and a helper class `NcInstOrd.Upd.V3Helper`, `update nc-inst-ord -path .../3.0.0/` returned OK, the module moved to 3.0.0, and V3.A has no record and never ran.
- Proof: `inst_witness_helper_class_hides_steps` (verified): the class list of [V3, V3Helper] maps 3 to the helper, so L1 "every step class is walked" fails. Both models replay the probe. INST-B71 and INST-B76 carry F and `O!:nc-inst-model-class-number-collision`.
- Impact: a module author who adds a helper class named like `V3Helper` or `V3Util` loses the steps of V3 silently; update reports success.

### F-INST-7
**A class of the update package whose name starts with V but has no digit makes every update of the module fail.**
- Code: same loop: for a class such as `<UpdatePackage>.Validator` the stripped number is empty, and `set updatePackageClassList("") = ...` raises `<SUBSCRIPT>` (VersionBase.cls#L51-L52); `HandleAllUpdateSteps` turns it into an error and the update rolls back.
- Intent: as F-INST-6; the error text names an internal subscript, not the offending class.
- Native check: found by probe `nc-inst-model-class-without-number`: with `NcInstOrd.Upd.Validator` added, `update nc-inst-ord -path .../4.0.0/` failed with `<SUBSCRIPT>GetUpdatePackageClassList+15 ... Subscript 1 is ""`, the module stayed at 3.0.0 and no step ran.
- Proof: `inst_witness_class_without_number_fails` (verified): the class list fails, so no step class is walked. Both models replay the probe. INST-B76 carries F and `O!:nc-inst-model-class-without-number`.
- Impact: any class in the update package (or a sub-package starting with V) whose last name piece has no digit blocks all updates of the module until it is renamed.

## Round 4 (decision research, 2026-11-13; decisions/research/inst.md)

### F-INST-8
**An install or load in developer mode seeds no update step, so the next update reruns steps of versions already in place.**
- **Statement(s):** INST-B18.
- **Code does:** Activate seeds the step records only when the command is not an update and the module is not in
  developer mode (`Lifecycle/Module.cls#L122`; the condition reads the stored DeveloperMode). A dev install, or a plain
  load of a module stored in developer mode, leaves no step rows, and `ApplyUpdateSteps` has no version filter
  (`Storage/Module.cls#L114`).
- **Intent says:** DEC-INST-2 resolved (assumption): any install or load that is not an update seeds the steps of the
  version it puts in place, in developer mode too. Sources: `update` help "from the current version to the newer
  version" (`Main.cls#L167`); IPM's test "Seeded update step ... was correctly not rerun on update"
  (`Update.cls#L467`); issue #550. The dev condition came in PR #887 commit b5cb11a17 with no stated reason.
  decisions/research/inst.md#dec-inst-2--should-an-install-in-developer-mode-seed-update-steps
- **Evidence:** IRIS `nc-inst-2b-dev-fresh-then-update`, `nc-inst-2-dev-install-then-update`,
  `nc-inst-fix-stored-dev-plain-load` (0 step rows), `r4-inst-u22-dev-kill-before-record-save` (V1.S1 ran on the first
  update after `load -dev 1.0.0`). Proof of today's behaviour: `inst_refines`, witness
  `inst_witness_dev_install_leaves_steps_due` (models/verus/update_steps.rs).
- **Impact:** a later `update` reruns migration steps written for older versions against data that is already
  migrated; non-idempotent steps corrupt data.
- **Severity suggestion:** Medium.

### F-INST-9
**Install silently replaces a needed module that is in developer mode and clears its developer mode.**
- **Statement(s):** INST-B35.
- **Code does:** the dev-mode guard (`Utils/Module.cls#L109`) needs `pParams("Install")`, which
  `LoadModuleFromDirectory` removes for dependency loads (`#L317-L319`); `#L310` resets their DeveloperMode.
- **Intent says:** DEC-INST-3 resolved (assumption): a module in developer mode is not overwritten by a non-dev install,
  named or needed; install stops and names it. Source: wiki 00.-Concepts Developer Mode (maintainer commit cfacdd8).
  decisions/research/inst.md#dec-inst-3--should-install-refuse-to-replace-a-needed-module-that-is-in-developer-mode
- **Evidence:** IRIS `nc-inst-8-dev-dependency-replaced` (with complex-c 2.0.0 loaded -dev, `install complex-b 2.0.0`
  leaves complex-c at 3.0.0 without developer mode, no message).
- **Impact:** the developer's working copy link (`^Sources`) is lost with no message.
- **Severity suggestion:** Medium.

### F-INST-10
**Update runs every update step of a module it installs for the first time, instead of seeding them.**
- **Statement(s):** INST-B53.
- **Code does:** `Update=1` passes down to dependency loads (`Utils/Module.cls#L308`, `#L316`), so Activate skips
  seeding (`Lifecycle/Module.cls#L122`) and ApplyUpdateSteps runs everything (`Storage/Module.cls#L114`).
- **Intent says:** DEC-INST-8 resolved (assumption): a module first brought in by update is a fresh install of that
  module, so its steps are seeded. Sources: `update` help "from the current version" (`Main.cls#L167`); issue #550.
