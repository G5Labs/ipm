# Findings: package loading (01) and transaction history (02)

Root causes first (playbook 5c: count root causes, not findings).

- **RC-1. The persistent history row is written with ordinary journaled sets.** `%IPM.General.History` lives in the
  namespace database. Its rows are inserted at Init and updated by `%OnClose`/`PersistToTwin` at whatever `$TLEVEL`
  is open. Any row written while a transaction is open shares that transaction's fate. Only the IRISTEMP copy
  (`HistoryTemp`) is immune, and `%OnClose` deletes it. Instances: F-HIST-1, F-HIST-2, F-HIST-3.
- **RC-2. Committed lives only in IRISTEMP until the log closes.** `SetCommitted` writes the IRISTEMP record; the
  durable row learns it only at `%OnClose`. Instances: F-HIST-2, F-HIST-4, F-HIST-7.
- **RC-3. The auto-purge filter quotes its value.** F-HIST-6.

### F-HIST-1
**Dependency history records vanish when the parent load rolls back.**
- Code: `LoadModuleReference` creates the dependency's log (`Utils/Module.cls#L64-L68`) inside the parent's open
  transaction (`#L1195`). Its twin row is inserted there and finalized by `%OnClose` when the method returns, still
  inside the parent's transaction. The parent's rollback loop (`#L1358-L1361`) removes it.
- Intent: `AbstractHistory.cls#L4` "HistoryTemp is stored in IRISTEMP so that history logs are not affected when
  transactions are rolled back due to install/load failure".
- Evidence: O:ipm-dep-parent-fails (parent Activate fails; 1 row: the parent's; `up-dep` was loaded, then undone,
  and left no record). O:ipm-dev-dep-parent-fails shows the row survives when the dependency transaction committed.
  Model: explore-L1-REC-DEP fails without any crash (109 runs outside premises); `g_dependency_records_lost_unless_fixed`
  (load_general.rs) proves every such failure loses them; `g_refines_strict` holds only under premise PD.
- Impact: an operator cannot see from history that a dependency was installed and then undone, or which dependency
  failed (a failing dependency's own record is also lost). Decision: DEC-HIST-1.

- **Revision (2026-11-13, decision resolved):** DEC-HIST-1 resolved (evidence): a dependency record must survive the parent's rollback, keep its own Success and read Committed = 0 (PR #578 TODO and review, wiki 09). The finding stands as a defect; new statement HIST-B32 carries it too. decisions/research/hist.md#dec-hist-1--dependency-records-when-the-parent-rolls-back

### F-HIST-2
**A developer-mode load that crashes while loading dependencies keeps its module record, but history says
Committed = 0 and names no package.**
- Code: the manifest is committed and `SetCommitted` runs at `Utils/Module.cls#L1311-L1313`, but only in IRISTEMP.
  The next `TSTART` (`#L1318`) opens the dependency transaction. On a crash IRIS runs `%OnClose` first, inside that
  transaction (O:env-halt-open-transaction), then rolls it back, so the durable row returns to its Init values.
- Intent: the seed contract and `History.cls` help: "Committed is not the same as successful, because a failed action
  can keep changes, for example in dev mode". The AbstractHistory property comment: "Whether any of the action's
  changes were kept".
- Evidence: O:ipm-halt-dev-crash-in-dependency (`up-dev-parent-crash` installed in developer mode; row
  `load//0.0.0`, committed 0, no end time). Model: explore-L1-COMMIT-SOUND (70 runs, all developer mode with the
  second transaction open); `g_dev_crash_dishonest_unless_fixed` (load_general.rs) proves every such crash violates L1; `g_refines` holds under
  premise PC; control `no-premise-pc` is rejected by Verus.
- Impact: an operator filtering `history find -DCommitted=1` to find loads that left changes misses this one, and the
  record does not say which module. Decision: DEC-HIST-2.

- **Revision (2026-11-13, decision resolved):** DEC-HIST-2 resolved (evidence): once a load's changes are durable its record must read Committed = 1, even after a crash or restart (SetCommitted comment AbstractHistory.cls#L119, issue #1237, PR #1322). The finding stands. decisions/research/hist.md#dec-hist-2--committed-after-a-crash-or-restart-once-a-developer-mode-or-no-transaction-load-kept-changes

### F-HIST-3
**A command run inside a caller transaction loses its history if the caller rolls back.**
- Evidence: O:ipm-load-inside-caller-transaction-rolled-back (0 rows). Model: explore L1-REC-TOP holds only outside
  premise P1. Proof: `g_caller_rollback_leaves_no_trace` (load_general.rs) shows a caller rollback leaves exactly the
  prior state, history included. Decision: DEC-HIST-4.

- **Revision (2026-11-13, decision resolved):** DEC-HIST-4 resolved (assumption): a command may run inside a caller transaction; its work and its record follow the caller. The code matches, so this is **no longer a code defect but a documentation gap**: wiki 09 says history is copied 'outside the transaction' with no caveat for a caller transaction. HIST-N1 now states the allowed behaviour (O and P tags). If maintainers choose option C (write the record outside the caller's transaction), it becomes a defect again. decisions/research/hist.md#dec-hist-4--commands-started-inside-a-callers-transaction

### F-HIST-4
**An operator who answers "Commit" at a crash prompt keeps a half-done load that history marks Committed = 0.**
- Evidence: O:ipm-halt-txn-operator-commits (module `up-halt` installed, class compiled; row committed 0, no end
  time). This is an IRIS terminal behaviour (SYS-D16). Model: explore L1-COMMIT-SOUND and L1-ATOMIC hold only
  outside premise P2. Proof: `g_operator_commit_dishonest` (every such state that changed the module). Decision:
  DEC-LOAD-1. Severity: low.

- **Revision (2026-11-13, decision resolved):** DEC-LOAD-1 resolved (assumption): committing at a crash prompt is an operator error to document; IPM does not guard against it. **Reclassified as documentation** (HIST-N2, LOAD-N2 now state it with O and I). If maintainers choose option B, it is a defect again. decisions/research/hist.md#dec-load-1--operator-commits-at-a-crash-prompt

### F-HIST-5
**Refused and crashed records do not name the module even when IPM read the manifest.**
- Code: `LoadInit("")` (`Main.cls#L2420`); `SetName` runs only after `OBJ.Load` (`Utils/Module.cls#L1293`), after the
  downgrade and update guards (`#L1213-L1222`), which already know `newModuleObj.Name`.
- Evidence: O:ipm-dev-downgrade-refused (row `load//0.0.0`), O:ipm-halt-txn, O:ipm-terminate-txn. Model:
  explore-L1-PKG-NAMED. Decision: DEC-HIST-3 (the property comment allows an empty name).

- **Revision (2026-11-13, decision resolved):** DEC-HIST-3 resolved (evidence): a record of a command that ends must name the module and version once IPM read the manifest; a crash may leave placeholders (wiki 09). **Narrowed** to 'a refused or failed command that ends after the manifest was read is unnamed' (O:ipm-dev-downgrade-refused). Crash records (O:ipm-halt-txn, O:ipm-terminate-txn, restarts) match the docs and are no longer instances (HIST-N4); a URL load whose clone failed never read a manifest (F-LOAD-1). Added from F-HIST-10: a `-DPackage=` filter cannot match a running row because its name lives only in IRISTEMP until close. decisions/research/hist.md#dec-hist-3--must-a-record-name-the-module-once-ipm-read-the-manifest

### F-HIST-6
**History auto-purge never deletes anything.**
- Code: `AutoPurgeOldHistory` builds `filter("TimeStart") = "<='" _ cutoffDate _ "'"` (`History.cls#L173`).
  `ConstructSQLWhere` already binds the value as a parameter (`#L107-L109`), so the quotes become part of the value
  and `TimeStart <= '''2026-10-14 00:00:00'''` matches no row. `DeleteHistoryGlobally` also swallows errors per
  namespace.
- Intent: `config set HistoryRetain <days>` "Enable history auto-purge" (`Main.cls#L840`).
- Evidence: O:ipm-history-autopurge (HistoryRetain 30, record from 2000 not deleted, status OK);
  O:ipm-history-purge-filter-cause (quoted value deletes 0 rows; the same value without quotes deletes 2).
- Impact: history grows without bound although retention is configured; the command reports success.

### F-HIST-7
**A crash between the outer TCOMMIT and SetCommitted leaves Committed = 0 for a committed load.**
- Code: `Utils/Module.cls#L1348-L1350`. Model only (premise P3); not observed (the window is two statements).
  Residual risk; any order of the two writes has a window because IRISTEMP and the namespace database cannot be
  written atomically.

- **Revision (2026-11-13, decision resolved):** Part B U19 (decisions/research/hist.md#u19--graceful-iris-stop-with-an-open-load-transaction): a graceful `iris stop` waits for open transactions to commit and then stops user jobs, so a load that commits during that wait is stopped inside this window. Observed once (wait 120 s): after restart the load was installed and compiled but its record read `load//`, Committed 0, not ended, not finalized (O:r4-hist-graceful-stop-txn-after; the 20 s run is r4-hist-graceful-stop-txn-wait20s-after). This widens F-HIST-7 from a two-statement window to every graceful stop that waits for a load; recorded as an instance of F-HIST-8 on HIST-B11. The DEC-HIST-2 option A fix covers it.

## Round 3 (native gap probes, validation/native-gaps-n2.md; generalized proofs, models/verus/load_general.rs)

- **RC-4. An IRIS instance crash runs no close code and wipes IRISTEMP.** The history design relied on `%OnClose`
  running at every crash. A restart (`iris force`, container restart, power loss) skips it. Instances: F-HIST-8, and
  `g_instance_crash_loses_pending` (no in-process design keeps pending dependency rows across a restart).

### F-HIST-8
**After an IRIS restart, a developer-mode or no-transaction load that kept its changes reads Committed = 0, unnamed,
never ended and never locked.**
- Evidence: O:nc-gap-P1-docker-dev-after, O:nc-gap-P1-docker-notxn-after (module and class kept; row
  `load//0.0.0`, committed 0, finalized 0; SQL can still edit it). Transactional loads are honest after a restart
  (O:nc-gap-P1-docker-txn-after, O:nc-gap-P1-force-txn-after).
- Proof: `g_instance_crash_dishonest_unless_fixed` (any prior state, any dependencies); with the extended fix (save
  the twin whenever SetCommitted runs at $TLEVEL 0) `g_instance_crash_honest_when_fixed`. Explorer and the 35,892-case
  cross-check include instance crashes. Decision: DEC-HIST-2 (the recommended option A now covers this).

- **Revision (2026-11-13, decision resolved):** DEC-HIST-2 resolved (evidence), see F-HIST-2. New instance (Part B U19): a transactional load committed during a graceful `iris stop` also ends with Committed 0, unnamed and unlocked (O:r4-hist-graceful-stop-txn-after, added as `O!` on HIST-B11). Same root cause RC-2.

### F-HIST-9
**A phase that fails through an Invoke's returned status is left open, with placeholder ERROR #00.**
- Code: `Storage/Module.cls#L669`/`#L671` quit the try block on a returned error; only the catch calls `FinalizePhase`.
- Evidence: O:nc-gap-P3-n2-ph-after-txn, O:nc-gap-P3-n2-ph-before-txn, O:nc-gap-P3-n2-ph-compile-txn (all modes).

### F-HIST-10
**`history delete` of a running command's record wins: the command ends with no record.** A `-DPackage=` filter cannot
even match it, because the running row has no package yet.
- Evidence: O:nc-gap-P2-dev-confirm-after-release, O:nc-gap-P2-txn-by-package-after-release. Decision: DEC-HIST-6
  (today: option A).

- **Revision (2026-11-13, decision resolved):** DEC-HIST-6 resolved (assumption): the delete wins; a delete that hits a row locked by an open transaction may fail with SQLCODE -110, which is acceptable. **Reclassified as intended behaviour** (new HIST-B33, HIST-N5; HIST-B1 no longer carries this finding). Round 4 runs: delete during Compile wins (O:r4-hist-delete-in-compile-txn-after-release, O:r4-hist-delete-in-compile-dev-after-release); a dependency row written inside the parent's transaction cannot be deleted until it ends (O:r4-hist-delete-dep-row-txn-after-release, O:r4-hist-delete-dep-row-dev-after-release); in a no-transaction load every delete wins (O:r4-hist-delete-dep-row-notxn-after-release). The `-DPackage=` part moves to F-HIST-5. If maintainers choose B or C, it is a defect again. decisions/research/hist.md#dec-hist-6--history-delete-of-a-running-commands-record

## Round 4 (decision research, 2026-11-13; decisions/research/hist.md)

### F-LOAD-4
**A normal load can fail after its final commit: the command reports an error while every change stays.**
- **Statement(s):** LOAD-B8 (F, with `O!:r4-hist-post-commit-throw-r4h-msg2-txn`; its P tag was dropped). The
  exception is described by LOAD-N4.
- **Code does:** `LoadNewModule` commits (`Utils/Module.cls#L1348`), calls `SetCommitted`, then
  `WriteAfterInstallMessage` (`#L1354`). That calls `%Evaluate` (`Storage/Module.cls#L1833`) and, for text with `{`,
  `%EvaluateMacro`, which compiles `%IPM.Generated.MacroEval`; a `$$$` macro that does not compile throws through
  `$$$ThrowOnError` (`Utils/Module.cls#L2781`), and the catch turns it into the command's status. Other post-commit
  points (inspection, not run): `tmpRepoMgr.CleanUp()` after the load (`Main.cls#L2530`), `Finalize`/`%OnClose`.
- **Intent says:** LOAD-B8 and wiki 00.-Concepts: a failed normal load rolls the namespace back. Premise PM of the
  models (load_general.TRUST.md G7, "nothing fails after the final commit") is false. Source: Part B U1,
  decisions/research/hist.md#u1--can-anything-fail-after-the-final-commit-in-loadnewmodule-premise-pm.
- **Evidence:** IRIS observations `r4-hist-post-commit-throw-r4h-msg2-txn` (command error; module installed; class
  compiled; record success err, committed 1, ended, finalized; all five phases ok), the same for `-notxn` and `-dev`;
  control `r4-hist-post-commit-throw-txn` (message without `{` is never evaluated) and `r4-hist-macro-probe-iserr`.
  The history record stays honest (Committed = 1).
- **Impact:** a script sees a failed load and may retry or roll back by hand while the module is in fact installed.
  Needs an author's manifest with a broken macro in AfterInstallMessage, so rare.
- **Side observation:** a `$$$` macro that fails to compile leaves `%IPM.Generated.MacroEval` defined until the next
  successful evaluation deletes it (`r4-hist-sem2-evaluate-macro-fails`: `macroEvalClassNow=10`; `$$$ThrowOnError`
  at `#L2781` runs before the `Delete` at `#L2783`). Not given its own ID.
- **Severity suggestion:** Low.
