## 07 — Namespace ownership

### F-NSP-1
- **Statement:** NSP-B40 — enable says a namespace is enabled only when the install there worked.
- **Code does:** On the registry path, `EnableIPM` calls `do $system.OBJ.LoadStream(manifest, loadFlag)` and
  discards the returned status, then always writes "IPM enabled for namespace X"
  (ipm/src/cls/IPM/Main.cls#L3885-3886). The local-file path keeps each status, lists failures and throws
  (Main.cls#L3904-3917).
- **Intent:** the help presents `enable` as installing IPM in the named namespaces (Main.cls#L726-760); the
  local-file branch shows the maintainers' intended reporting.
- **Impact:** an install that fails to download, compile or run its installer is reported as a success, and the
  command returns OK; scripts cannot tell.
- **Proposed check:** point `-remote` at a registry whose `zpm` installer manifest fails to compile (or a stub that
  returns an invalid stream); expect an error status and no "enabled" line; current code is expected to print
  "IPM enabled for namespace X" and return OK.
- **Native check:** confirmed — O:nc-nsp-N5-enable-remote-broken. A registry stub (python http.server in the container, Remote repo `nc-nsp-stub`) served `packages/zpm/9.9.9/installer`, a class whose superclass does not exist. `enable -ns NCT -v 9.9.9 -remote nc-nsp-stub` printed the compile error, then "IPM enabled for namespace NCT", and returned OK; NCT still has no IPM (`%IPM.Main:Shell` not callable) and holds the uncompiled stub class. (A first attempt, log 84-nsp-namespace2, died with `<FRAMESTACK>` because the harness's output capture routine was not visible in NCT; harness artefact, rerun in log 85.)

### F-NSP-2
- **Statement:** NSP-B72 — an IPM version need is checked against the IPM in use, even when that IPM is mapped.
- **Code does:** `CheckIPMVersion` reads `SELECT VersionString FROM %IPM_Storage.ModuleItem WHERE Name='zpm'` in the
  current namespace only (ipm/src/cls/IPM/Storage/SystemRequirements.cls#L91-95). In a namespace that reaches IPM by
  mapping, that table has no `zpm` row (module records are namespace data), so the version string is empty and
  parses as 0.0.0 (SemanticVersion.cls#L33-54).
- **Intent:** the error text says "The module requires IPM version X. Current IPM version is Y"; IPM elsewhere
  resolves the effective version of a mapped namespace (`GetIPMVersionInfo`, Main.cls#L984-1013). Fix #1148
  (commit d067a38f) replaced a cross-namespace lookup with the current-namespace query to fix #1114, apparently
  without the mapped case in view.
- **Impact:** after `enable -map -globally` (the README's recommended legacy-like setup), any module with
  `<SystemRequirements IPMVersion=">=x"/>` is refused in every mapped namespace.
- **Proposed check:** in a source namespace with IPM, `enable -map -ns T`; in T, `load` the fixture
  `version-req-test/version-req-satisfied` (IPMVersion="*" passes trivially, so use a copy with `IPMVersion=">=0.9"`);
  expect success; current code is expected to fail with "Current IPM version is 0.0.0" (or similar).
- **Native check:** confirmed — O:nc-nsp-N9-ipmversion-mapped-snap. A module needing IPMVersion `>=0.10.11-SNAPSHOT` loads in USER (local install) and is refused in NCA (IPM mapped from USER): "The module requires IPM version >=0.10.11-SNAPSHOT. Current IPM version is .0.0" (empty version). The fixture proposed above (`>=0.9`) cannot tell the cases apart: 0.10.11-SNAPSHOT is a prerelease, which IPM's rules do not let satisfy `>=0.9`, so it is refused in USER too (O:nc-nsp-N9-ipmversion-mapped).
- **Proof:** `nsp_witness_version_empty_when_mapped` (models/verus/ns_mapping.rs): in a namespace mapped from a source with version 10, `check_ipm_version` reads no version while L1's `version_in_use` is 10. `nsp_lemma_version_read` proves the check correct exactly when the namespace's IPM code is its own (premise OWN); the explorer finds every violation only where OWN fails (M:nsp-explore-version).

### F-NSP-3

- **Code does:** `Version` passes `VersionString` from `%IPM_Storage.ModuleItem` straight to `DisplayModules`, which
  prints it unchanged (ipm/src/cls/IPM/Main.cls#L1593-1597, L1391, L4292). Only `information` strips build
  metadata (`ToStringWithoutBuild`, L4398).
- **Intent:** help text of `version`: "Prints the currently-installed package manager and registry version
  (excluding +snapshot or other build information)" (Main.cls#L685).
- **Impact:** cosmetic; scripts parsing `version` output see `1.2.3+build` where help promises `1.2.3`.
- **Proposed check:** load a module named `zpm-registry` fixture or install a `zpm` build with `+snapshot`; run
  `version`; expect no `+...` suffix.
- **Native check:** confirmed — O:nc-nsp-N10-version-build. A module `zpm-registry` 1.2.3+ncbuild: `version` prints "zpm-registry 1.2.3+ncbuild"; `info` prints "zpm-registry 1.2.3".

### F-NSP-4
- **Statements:** NSP-B23 (the -repos flag also maps the repo settings), NSP-B30 (`enable -community` maps code and repo settings to all namespaces).
- **IRIS did:** from USER, `enable -map -repos -ns NCA,NCB,NCD,NCE`, where NCD and NCE had no IPM: the code mappings for NCD and NCE were added, then "Skipping repository mapping of NCD - IPM not mapped from source namespace." and no repo mapping (O:nc-nsp-N3-enable-map-repos). The same command run again mapped the repo globals and NCD then listed USER's repos (O:nc-nsp-N3-enable-map-repos-rerun). In `enable -community` (N4) the third step likewise mapped code into %SYS and NCT but skipped their repos with the same message (O:nc-nsp-N4-community-step-fails; that run also held the repo lock, which made the other steps fail, but the skip message is this cause).
- **Cause (inspection):** new mappings are added with activation skipped and activated once at the end (`PerformBatchActivation`, ipm/src/cls/IPM/Main.cls#L3698). The repo loop decides with `GetMapInfo` (Main.cls#L3661), which reads the active `%SYS.Namespace.GetPackageDest` (Main.cls#L1636), so a namespace mapped earlier in the same run still resolves `%IPM` to IRISLIB.
- **Why tests pass:** `%IPM.Test.Utils.CreateNamespace` maps the `%IPM` package from the calling namespace (ipm/src/cls/IPM/Test/Utils.cls#L95; seen natively: `ncaMapsFromCreate=pkg:USER` in O:nc-nsp-installer-existing-pkg-mapping), so BatchActivate.cls#L163-190 starts from namespaces that already resolve `%IPM` to the source.
- **Impact:** on a namespace with no IPM, `enable -map -repos` and `enable -community` give code but not shared repos; the operator has to run the command twice. The README's legacy-like setup (README#L78) is not reached in one step.
- **Native check:** confirmed (found by the native checks) — O:nc-nsp-N3-enable-map-repos, O:nc-nsp-N3-enable-map-repos-rerun, O:nc-nsp-N4-community-step-fails.
- **Proof:** `nsp_witness_repos_second_run`: from a local source, `enable -map -repos` on a namespace with no IPM gives it the code but not the registries (L1 says the source's registries), and a second run maps them; the first run violates the defect premise REPOS. `nsp_lemma_enable` and `nsp_lemma_community` prove the intended effect wherever REPOS holds; `nsp_witness_repos_one_run_when_premapped` shows the case the BatchActivate tests take (target already reached by a package mapping). The fine model reproduces the skip lines of N3 and N4 exactly (M:nsp-conf-nc-nsp-N3-enable-map-repos, M:nsp-conf-nc-nsp-N4-community-step-fails).

### F-NSP-5
- **Statement:** NSP-B49 — running the installer in a mapped namespace gives it a local install; the mapping is gone (see DEC-NSP-1, DEC-NSP-2).
- **IRIS did:** NCD got `%IPM` code and repo settings mapped from USER. `install zpm` there was refused (O:nc-nsp-N7-install-zpm-mapped). Loading `IPM.Installer` and running `setup` in NCD returned OK, but NCD's package, routine and repo mappings still point at USER and `%IPM` still resolves to USER's database; NCD now has its own `zpm` 0.10.11-SNAPSHOT record (O:nc-nsp-N7-installer-in-mapped). From USER, `unmap -ns NCD` then said "No mapping found for NCD" and left every mapping (O:nc-nsp-N7-unmap-after-local-install).
- **Re-point probe:** NCX with only a package mapping to USER (as `CreateNamespace` leaves it). After `setup`, iris.cpf still has `Package_%IPM=USER` and gains `Routine_%IPM.*=NCX`; USER's `%IPM.Main` compile time moved to the NCX install time, so the installer's import recompiled IPM classes in USER's database (O:nc-nsp-installer-repoint; same pattern in the first NCC install, O:nc-nsp-installer-existing-pkg-mapping). So `%Installer`'s ClassMapping and RoutineMapping add a mapping only when it is absent; they never re-point one.
- **Intent:** help for `enable -map -globally`: "Namespace-specific installation will override this." (ipm/src/cls/IPM/Main.cls#L743); Installer.cls#L25-29 means to map `%IPM` to the namespace's own database.
- **Impact:** the namespace looks like a source (it has a `zpm` record, `version` lists it without "Installed In") but runs, and rewrites, the source namespace's IPM code; `unmap` can no longer remove its mappings, so both code and repo mappings are stranded (DEC-NSP-1).
- **Native check:** confirmed (found by the native checks) — O:nc-nsp-N7-installer-in-mapped, O:nc-nsp-N7-unmap-after-local-install, O:nc-nsp-installer-repoint.
- **Proof:** `nsp_witness_installer_in_mapped`: the installer in a namespace whose code and registries are mapped from a source leaves both mappings, gives it a zpm record and still runs the source's code, which is neither of L1's allowed outcomes (refused, or independent); afterwards `unmap` no longer lists it. `nsp_lemma_installer` proves the intended local install under premise INST (every %IPM mapping absent or to the namespace's own database); `nsp_witness_fresh_install` is the positive case.

- **Revision (2026-11-13, decision resolved):** DEC-NSP-1 and DEC-NSP-2 resolved (evidence): repo settings are mapped only with code from the same namespace (README#L69, PR #663), and while a namespace gets IPM by mapping IPM refuses to install itself there; the route is `unmap`, then install (PR #485, issue #470). The help sentence Main.cls#L743 is about namespaces that already have IPM. The finding **stands**; NSP-B49 (installer and load refuse), NSP-B78 (no stranded repo mapping) carry it. decisions/research/nsp.md#dec-nsp-2--may-ipm-be-installed-locally-in-a-namespace-that-gets-ipm-by-mapping

### F-NSP-6
- **Statement:** NSP-B41 — unmap removes the IPM code mapping from the named namespaces, and the repo settings mapping.
- **IRIS did:** `unmap -ns NCE,NCA` returned OK and removed the `%IPM` package mapping and NCE's repo mapping, but the `%IPM.*` routine mapping stayed (iris.cpf `Routine_%IPM.*=USER`); in a new process `%SYS.Namespace.GetPackageDest` still gives USER's database, `%IPM.Main:Shell` is callable, and `version` runs in NCA, listing NCA as "Installed In: USER" (O:nc-nsp-N6-unmap-mapped, O:nc-nsp-N6-unmap-recheck-nca, O:nc-nsp-N6-unmap-recheck-nce, O:nc-nsp-N6-shell-after-unmap).
- **Cause (inspection):** `UnmapIPM` calls `RemoveRoutineMapping(ns, "%IPM.*", 1, .rtnChanged)` (ipm/src/cls/IPM/Main.cls#L3998), but that method's third parameter is the routine type, not skip-activation (ipm/src/cls/IPM/Utils/Module.cls#L1707-1720); it then looks for a mapping named `%IPM.*_1`, which does not exist. `RemovePackageMapping` (Module.cls#L1646) takes skip-activation third, so the package call works.
- **Impact:** after `unmap` the namespace keeps a working IPM from the source and is still reported as mapped. No test asserts the routine mapping is gone (BatchActivate.cls#L129 checks only the skip message).
- **Native check:** confirmed (found by the native checks) — O:nc-nsp-N6-unmap-mapped, O:nc-nsp-N6-unmap-recheck-nca, O:nc-nsp-N6-shell-after-unmap.
- **Model probe:** the exact call `RemoveRoutineMapping(ns, "%IPM.*", 1, .changed)` leaves the mapping and reports no change; with type ALL it removes it (O:nc-nsp-model-env-rtn-slot). A namespace mapped by package only (as `CreateNamespace` leaves it) is unmapped completely (O:nc-nsp-model-unmap-package-only), as the model predicted.
- **Proof:** `nsp_witness_unmap_leaves_routines`: unmap of a namespace mapped from USER removes the package and repo mappings, keeps `%IPM.*`, and the namespace still runs USER's IPM; L1 says it runs none. `nsp_lemma_unmap` proves the intended effect under premises INFO and RTN (no listed target has a routine mapping), i.e. only for package-only mappings (`nsp_witness_unmap_package_only`).

- **Revision (2026-11-13, decision resolved):** DEC-NSP-2 resolved (evidence): the supported route to a local install is `unmap`, then install. **Impact extended:** that route is blocked today. After `enable -map` and `unmap` of NCR4P, the `%IPM.*` routine mapping stays and `CheckModuleNamespace()` still refuses ('mapped from namespace USER-VERIFY'; O:r4-nsp-unmap-then-install-guard, `O!` on new NSP-B77). decisions/research/nsp.md#dec-nsp-2--may-ipm-be-installed-locally-in-a-namespace-that-gets-ipm-by-mapping

### F-NSP-7
- **Statements:** NSP-B23 (the -repos flag maps the repo settings), NSP-B56 (for a mapped namespace, version names the source). See DEC-NSP-6.
- **IRIS did:** in the native-check container, from USER, `enable -map -repos -ns NCM5`, where NCM5 already resolves `%IPM` to USER's database (package mapping, as `CreateNamespace` leaves it), printed "Skipping repository mapping of NCM5 - IPM not mapped from source namespace." and mapped no registries (O:nc-nsp-model-repos-premapped). `GetMapInfo` there lists NCM1, NCM2, NCM5 and USER-VERIFY-VERIFY as mapped from USER-VERIFY, not USER: USER-VERIFY (left by IPM's own verify-phase tests) has a zpm record and resolves `%IPM` to USER's database (O:nc-nsp-model-mapinfo).
- **Cause (inspection):** `AddIPMMappedNamespaces` (ipm/src/cls/IPM/Main.cls#L1628-L1654) keys sources by their `%IPM` database, `mappedFrom(sourceDB) = namespace`, in name order, so the last source by name that shares a database wins; every other namespace on that database is reported as mapped from it. The -repos loop then requires `isMappedFrom(ns) = initNamespace` (Main.cls#L3661).
- **Intent:** README#L77 and the -repos help: repositories are mapped when `%IPM` is mapped from the current namespace; the namespace's IPM code does come from USER's database here.
- **Impact:** once a second namespace with a zpm record shares the source's database (IPM's verify phase, or an installer run in a mapped namespace: F-NSP-5), `enable -map -repos` and `enable -community` from the real source never map registries, and `version`/`information` name the wrong source. The model predicted the one-run mapping before the probe; the probe disagreed, and the model with the observed state (premise UNIQ false) reproduces the skip exactly.
- **Proof:** `nsp_witness_repos_tie_other_source` (models/verus/ns_mapping.rs): with a later-named second source on USER's database, a target already reached by USER's code gets no registries while L1 says USER's. M:nsp-explore-witness-F-NSP-7: the explorer finds these violations only where premise UNIQ fails; M:nsp-conf-nc-nsp-model-mapinfo replays `GetMapInfo` on the observed state.

- **Revision (2026-11-13, decision resolved):** DEC-NSP-6 resolved (assumption): the source is the namespace whose own code database holds IPM; a namespace that reaches it by mapping is never a source (new NSP-B79). The finding **stands**. New instances: NCR4L, just mapped from USER, is listed 'Installed In: USER-VERIFY' (O:r4-nsp-legacy-enable-map); the `install zpm` guard and `unmap` output name USER-VERIFY (O:r4-nsp-unmap-then-install-guard); and (Part B U21, decisions/research/repo.md#u21-full-cleanup-while-another-namespace-borrows-ipm--closed-container-restored) the self-uninstall warning is lost: `uninstall zpm -force -DClean.FullCleanup=1` in USER printed no 'Will affect the following namespaces' line while NCMAP borrowed IPM (O:r4-repo-u21-full-cleanup-with-mapped-ns, O:r4-repo-u21-mapinfo-from-user; `F` and `O!` on UNIN-B53). decisions/research/nsp.md#dec-nsp-6--which-namespace-is-the-source-when-two-zpm-records-share-one-ipm-database

## 08 — Resources and author code

### F-RES-1
- **Statement:** RES-B25 — if a deployed item cannot be added to the package, packaging fails; it never ships the
  source in its place.
- **Code does:** `Document.OnExportItem` sets `tSC = ..OnExportDeployedItem(...)` and on the next line
  `set tSC = $$$OK` (ipm/src/cls/IPM/ResourceProcessor/Default/Document.cls#L256-257). If `AddItemToProject` throws
  inside `OnExportDeployedItem` (L318), `pItemHandled` stays 0 and the error is discarded, so the method falls
  through to the normal source export (L258 onward).
- **Intent:** `Deploy` "If set to true, this source code is not shipped in application packaging"
  (ResourceReference.cls#L39-40).
- **Impact:** on a failure to add an item to the deployed project, the package silently contains that item's source
  instead of object code. Line 257 dates from the original import (blame `^2aaa8cca`), so this is old.
- **Proposed check:** hard to trigger from outside; a unit test can subclass the Document processor so that
  `OnExportDeployedItem` returns an error status without setting `pItemHandled`, then assert `OnExportItem` returns
  that error. Current code is expected to return OK and export source.
- **Native check:** not checkable — no outside trigger makes `AddItemToProject` fail during a package; checking it needs a patched or subclassed Document processor inside IPM, which this run did not build.

### F-RES-2
- **Statement:** RES-B49 — the register phase saves the package file in the module cache of this namespace.
- **Code does:** `Register` is not in `%IPM.DataType.PhaseName` VALUELIST (ipm/src/cls/IPM/DataType/PhaseName.cls#L13),
  so `GetCompletePhases` treats a lone `register` as a custom phase (Lifecycle/Base.cls#L142), and with no matching
  Invoke the lifecycle `%DispatchMethod` raises `<METHOD DOES NOT EXIST>` (Base.cls#L64-76). No `%Register` exists.
  `GetCompletePhasesForOne`/`MatchSinglePhase` still list it (Base.cls#L181, L208).
- **Intent:** module-action help lists "register: saves that artifact into the current namespace's module cache" and
  gives the example `MyModuleName clean register` (ipm/src/cls/IPM/Main.cls#L53, L64). Older code had
  `"publish": ... "Package","Register","Publish"` (commit 4627d0c0), later dropped.
- **Impact:** the documented phase and example fail with an internal error message.
- **Proposed check:** `load` any fixture, then `<module> register`; expect success per help; current code is expected
  to fail with METHOD DOES NOT EXIST.
- **Native check:** confirmed, with a difference — O:nc-res-N13-register. `simplest-module register` fails with `<METHOD DOES NOT EXIST>` `*%Register,%IPM.Lifecycle.Module`. The help example `simplest-module clean register` returns OK: it runs Clean, then Initialize through Package, and no Register step (nothing says the package was not registered). An unknown phase name fails the same way as a lone `register`.

### F-RES-3

- **Code does:** for a developer-mode module, `%MakeDeployed` skips deleting routines (`if 'tDev`, Base.cls#L1909)

- **Impact:** `makedeployed <module>` on a developer's working module removes class source from the namespace and
  marks the module deployed, which also skips later compiles of those classes outside dev mode

- **Proposed check:** `load -dev` the `deployed-mappings` fixture; run `makedeployed deployed-mappings -v`; check

After `load -dev` of deployed-mappings, `makedeployed deployed-mappings -v` printed "Module is in developer mode, will only report what WOULD be deployed...", yet DeployMapA.First went from Deployed=0 to 1, its method source can no longer be read, and the module record has Deployed=1.

## 09 — Developer sync

### F-SYNC-1
- **Statement:** SYNC-B15 — sync applies each change made on disk since the last load or sync (see also DEC-SYNC-1).
- **Code does:** change detection compares disk bytes with the last saved baseline (FileHash.cls#L228-336).
  Baselines are written only after a successful dev-mode compile (Lifecycle/Base.cls#L1235-1244) or a successful
  sync (Pipeline.cls#L149). Retry marks are set only by a failed sync (Pipeline.cls#L210-223). A `compile`,
  `load -dev` or `reload` that loads edited bytes onto the server and then fails (or does not compile) leaves the
  baseline at the earlier content and sets no mark (dev mode keeps loaded code: Utils/Module.cls#L1335-1339).
- **Intent:** sync help "Detects files changed on disk since the last load/sync" (ipm/src/cls/IPM/Main.cls#L111);
  issue #1224 expects that reverting a broken file and syncing "should reload + recompile the modified item". The
  #1224 fix (retry mark, test Sync.cls#L662-709) covers only failures inside sync.
- **Impact:** edit a class so it loads but fails to compile, run `compile <module>` (fails), revert the file to its
  exact earlier bytes, run `sync`: sync reports "Nothing to sync" while the namespace still holds the broken source.
  Same for `reload` followed by a revert.
- **Proposed check:** in the `sync-test` fixture loaded with `-dev`: change `SuperClass.cls` to extend a nonexistent
  class (loads, fails compile); `compile sync-test` (expect failure); restore exact bytes; `sync sync-test -verbose`;
  expected per help: "Updated: src/cls/SyncTest/SuperClass.cls"; expected per code: "Nothing to sync" and
  `$$$comClassDefined("SyncTest.SuperClass")` false or stale.
- **Native check:** confirmed — O:nc-sync-N18-compile-fail-revert. sync-test loaded `-dev`; SuperClass edited to extend NcMissing.Base; `compile sync-test` failed (ERROR #5373) leaving the broken definition on the server (Super NcMissing.Base, not compiled) and the file row at the old hash with SyncFailed=0; exact bytes restored (same SHA-1); `sync sync-test -verbose` said "Nothing to sync", returned OK, and the server class still has the broken superclass and is not compiled. (The old compiled routine still answers GetValue() "original".)
- **Model probes:** predicted by the model before running: the same edit-then-revert after `reload sync-test` (no compile) and after `load -dev -skip-sync` over an existing baseline: in both, `sync` said "Nothing to sync", returned OK, and the server kept the edited source (O:nc-nsp-model-sync-reload-revert, O:nc-nsp-model-sync-skipsync-revert).
- **Proof:** `sync_witness_failed_compile_then_revert`, `sync_witness_reload_then_revert`, `sync_witness_skip_sync_load_then_revert` (models/verus/sync_baseline.rs): each load outside sync that records no baseline breaks the invariant "an unmarked baseline equals the server copy"; after an exact revert, sync succeeds with the server copy different from the disk bytes, which L1 forbids. `sync_lemma_sync`, `sync_lemma_compile` and `sync_lemma_reload` prove L1 under the defect premise OUT (no such load puts non-baseline bytes on the server). M:sync-explore-witness-F-SYNC-1; M:sync-fine-refinement (0 violations on the fine machine's premise-respecting traces).

- **Revision (2026-11-13, decision resolved):** DEC-SYNC-1 resolved (assumption): files that a failed `compile`, `load -dev` or `reload` put on the server are re-detected by the next sync, even after an exact revert (issue #1224's expectation extended to other commands). The finding **stands**; SYNC-B22 now states the intent. If maintainers choose option (b), it becomes documentation. decisions/research/nsp.md#dec-sync-1--failed-load-or-compile-outside-sync
