### F-UNIN-1

Statements: UNIN-B31, UNIN-B66, UNIN-B79.

- **Code does:** `ExecutePhases` calls every resource processor's `OnBeforePhase("Clean")` before the lifecycle's
  `%Clean` runs (Storage/Module.cls#L587-L600, then #L640-L648). `WebApplication.OnBeforePhase` deletes the web app for
  `Clean` (ResourceProcessor/WebApplication.cls#L81-L106) and `CSPApplication.OnBeforePhase` deletes the CSP app and
  purges its files (CSPApplication.cls#L156-L159, #L407-L420). Only later does `%Clean` call `CheckBeforeClean`, which
  may skip the module because a dependent exists or because it has global scope (Lifecycle/Base.cls#L258-L302). The
  same happens for `<module> clean` (Clean.Level=0): the module itself is kept, but its web apps are deleted and its
  `Unconfigure` hook runs (Lifecycle/Module.cls#L17). Module-author `<Invoke Phase="Clean" When="Before">` hooks also
  run before the skip.
- **Intent says:** `uninstall` help, Main.cls#L486-L487: "This will be prevented if other modules depend on the named
  module". Changelog #058 "Prevent uninstallation of dependent module". `module-action` help, Main.cls#L39-L40:
  clean "removes all dependencies that are not required by other installed modules and their resources" (nothing
  about the module it runs on).
- **Impact:** A blocked uninstall prints `Clean SUCCESS`, leaves the module installed, and silently removes its web
  endpoints and CSP files. Same for a module with global scope, and for `clean` on any module with a web app.
- **Native check:** confirmed — `nc-unin-1-blocked-uninstall` (`uninstall nc-web-dep` while `nc-web-top` needs it:
  status OK, "Clean SKIPPED - required by 1 other module" naming `nc-web-top`, then "Clean SUCCESS"; module and its
  class kept; web app `/nc-dep` present before, gone after) and `nc-unin-2-clean-own-module` (`nc-web-w clean`: module
  and class kept, web app `/nc-w` deleted, installer `OnUnconfigureComponent` and `OnUnInstallComponent` each called
  once).
- **Proof:** `unin_witness_blocked_deletes_webapp` (models/verus/uninstall.rs): a wf world where nc-web-dep has a web app and nc-web-top needs it; `uninstall nc-web-dep` returns OK, logs success, keeps the record and deletes the web app, so `l1_blocked_unchanged` and `l1_honest` fail. `unin_witness_clean_own_module`: `<module> clean` deletes the web app and runs the undo hook, so `l1_clean_keeps_target` fails. `unin_witness_recurse_skipped_dep`: the same inside `-r` (below). Positive side: `unin_refines_blocked_unchanged` (premises PG, PW: no web app) and `unin_refines_clean_keeps_target` (PCW, PF). Model check: `repo-explore-unin-blocked-unchanged` (0 violations under the premises, 271,984 without). These positive lemmas hold only under premises that exclude this finding's case; they are not cited as P on the finding's statements (review finding 3), and the witness here is the evidence for the F tag.
- **Native check (model probe):** `nc-repo-model-unin-recurse-skipped-dep`: `uninstall nc-rec-top -r` while nc-rec-other also needs nc-web-dep: status OK, nc-web-dep skipped ("Clean SKIPPED - required by 1 other module"), its class kept, its web app `/nc-dep` deleted, and its history row `uninstall/success`. Statement UNIN-B79.

### F-UNIN-2

Statement: UNIN-B13.

- **Code does:** `uninstall -purge` sets `pParams("Purge")=1` (Main.cls#L505, `dataAlias="Purge"`). No code reads
  `Purge`. The only purge flag consumer is `%Unconfigure`, which reads `pParams("Configure","Purge")` and passes it to
  the installer's `OnUnconfigureComponent` (Lifecycle/Base.cls#L554-L561). Class deletion in `%Clean` uses
  `$system.OBJ.Delete` without an extent-delete qualifier (Base.cls#L387).
- **Intent says:** Main.cls#L505: "Purge data from tables during uninstall."
- **Evidence:** `grep -rn '"Purge"' src` finds only the modifier definition. `git log -S'dataAlias="Purge"'` shows it
  dates from commit 453225a0 (2023 rename) with no reader since.
- **Impact:** Operators who rely on `-purge` keep table data (and installers never see a purge request) without any
  warning.
- **Native check:** confirmed for table data, refined for the installer — `nc-unin-3-uninstall-plain` and
  `nc-unin-3-uninstall-purge`: after both `uninstall nc-purge` and `uninstall nc-purge -purge` the class is gone but
  `^NCPurge.ItemD` still holds the row (`dataAfter=11`). The installer's `pPurge` argument is 0 in both runs. But with
  `-purge` the installer's `pVars("Purge")` is 1 (it is merged in from the command parameters), so an installer *can*
  see the request if it reads its variables array; "installers never see a purge request" above is too strong. The
  underlying IRIS fact: `$system.OBJ.Delete` with flags `-d` keeps a persistent class's data global
  (`nc-unin-env-obj-delete-default`, `dataAfter=11`); with the `e` flag it removes it (`nc-unin-env-obj-delete-e-flag`,
  `dataAfter=0`). IPM's `%Clean` passes `-d` or `d`, never `e`.

### F-UNIN-3

Statement: UNIN-B62.

- **Code does:** `Main.Uninstall` runs the IPM self-removal steps (namespace mapping check, list of modules, the full
  cleanup question, and the shell-exit flag) only when the typed name equals `"zpm"` exactly (Main.cls#L2712,
  `$$$IPMModuleName` = "zpm", inc/IPM/Common.inc#L58). `%IPM.Storage.Module:ExecutePhases` then finds IPM by
  `NameOpen` (case-insensitive index, Storage/Module.cls#L10) or by `ExternalNameOpen` ("IPM", module.xml#L7), and
  `%IPM.Lifecycle.Module:%Clean` deletes IPM's classes. So `uninstall IPM`, `uninstall ipm` or `uninstall ZPM` skip
  the guard and the prompt, and the shell keeps running after IPM's classes are gone.
- **Intent says:** PR #1106 and #1235 describe the guarded self-uninstall; issue #1057 reproduces with
  `zpm "uninstall ipm"`; changelog #1116/#1142 "Fix behavior inconsistencies between install and uninstall for package
  name casing"; UNIN-B4 (names are case-blind and external names are accepted elsewhere).
- **Impact:** Uninstalling IPM from a namespace that borrows it from another (mapped) namespace is not refused, the
  full-cleanup choice is never offered, and the interactive shell continues with missing classes.
- **Caveat:** the case-blind lookup relies on the default SQLUPPER collation of the `Name` and `ExternalName` indexes;
  not observed here.
- **Native check:** confirmed in a namespace that owns IPM; refuted for the mapped-namespace part of the impact.
  `nc-unin-self-external-name-IPM`: in USER, `uninstall IPM` printed no module list, no full-cleanup question and no
  "Exiting shell" line, returned OK, and deleted `%IPM.Main`, `%IPM.Storage.Module` and `%IPM.StudioDocument.Module`
  (it did print the orphan warning). Compare `uninstall zpm` (`nc-unin-self-zpm-answer-no`; log
  `73-repo-self-uninstall-a.log` shows the list, the question and the exit line). In a namespace that borrows IPM by
  `enable -map` (`nc-unin-4-mapped-setup`: IPM classes compiled there, no IPM record there), `uninstall zpm` is refused
  with the mapping error (`nc-unin-4-mapped-uninstall-zpm`), and `uninstall ZPM`, `ipm` and `IPM` fail with "Module ...
  not found" and change nothing (`nc-unin-4-mapped-uninstall-ZPM`, `-ipm`, `-IPM`). So the bypass removes IPM without
  the question or the shell exit only where IPM's record lives. Caveat settled: `nc-unin-env-name-case` shows `Name`
  and `ExternalName` lookups are case-blind (index subscripts `" ZPM"`, `" IPM"`; `NameExists("ZPM")=1`,
  `ExternalNameExists("ipm")=1`).
- **Proof:** `unin_witness_external_name_bypass` (models/verus/uninstall.rs): `uninstall IPM` resolves IPM through ExternalName, deletes IPM's classes, sets no exit flag and asks nothing, so `l1_self_guard` fails. Positive side: `unin_refines_self_guard` under PN (the operator types exactly `zpm`).

### F-UNIN-4

Statement: UNIN-B33.

- **Code does:** `CheckBeforeClean` gets dependents from `GetDependentsList` (Utils/Module.cls#L460-L499), which
  builds the graph of every installed module with `BuildAllDependencyGraphs`. A module whose graph fails to build is
  put in `pErrorList` and skipped (Utils/Module.cls#L615-L622); `GetDependentsList` never looks at `pErrorList`.
- **Intent says:** uninstall help, Main.cls#L486-L487 ("prevented if other modules depend on the named module"); the
  module still lists M among its direct `Dependencies`.
- **Impact:** If any dependent has an unresolvable dependency (for example a missing registry), uninstall without
  `-force` removes M although that dependent needs it.
- **Native check:** confirmed — `nc-unin-5-unresolvable-dependent`: with `nc-ghost-b` needing `nc-ghost-a`, a
  first `uninstall nc-ghost-a` is skipped (control). After adding a need `nc-ghost-missing` (in no registry) to
  `nc-ghost-b`'s stored record, `GetDependentsList` returns 0 dependents and 1 graph error, and `uninstall nc-ghost-a`
  removes `nc-ghost-a` and its class with status OK while `nc-ghost-b` stays installed.
- **Proof:** `unin_witness_unresolvable_dependent` (models/verus/uninstall.rs): nc-ghost-b needs nc-ghost-a but its graph is an error; `uninstall nc-ghost-a` returns OK and removes it, so `l1_dependents_protect` fails. Positive side: `unin_refines_dependents_protect` under PG (every graph builds). Model check `repo-explore-unin-dependents-protect`.

### F-UNIN-5

Statement: UNIN-B12.

- **Code does:** the global resource processor handles Clean by `kill @..Global` only when the optional `Global`

Positive side: `unin_refines_complete` under PGA. These positive lemmas hold only under premises that exclude this finding's case; they are not cited as P on the finding's statements (review finding 3), and the witness here is the evidence for the F tag.

### F-REPO-1

Statement: REPO-B47.

- **Code does:** `%IPM.Repo.Remote.Definition:OnConfigure` (Remote/Definition.cls#L60-L115) never reads
  `pModifiers("token-auth-method")`; only the ORAS class does (Oras/Definition.cls#L118-L120). A remote registry keeps
  the initial `apiKey` and sends the token as an `apikey` header (Http/PackageService.cls#L59-L69).
- **Intent says:** `-token-auth-method` is documented under "HTTP(s) repository" for both kinds
  (Http/Definition.cls#L45): "If set to 'basic' ... 'bearer' ...".
- **Impact:** `repo -r ... -token X -token-auth-method bearer` is accepted and shown, but the registry receives the
  wrong header and rejects the token.
- **Native check:** confirmed — `nc-repo-4-token-auth-method`: `repo -r ... -token t -token-auth-method bearer`
  stores `TokenAuthMethod=apiKey`; the built request carries header `apikey: t` and no `Authorization` header. The ORAS
  control stores `bearer`.

### F-REPO-3

Related decision: DEC-REPO-1. Statements: REPO-B56, REPO-B59, REPO-B60 (F-tagged; the decision stays open).

- **Code does:** `PublishingServer` queries order enabled registries by `DeploymentEnabled`, then token, then
  user+password, then everything else (`ELSE 999`) (Remote/Definition.cls#L117-L129; Oras/Definition.cls#L143-L155),
  and `%Publish` and `unpublish` take the first row (Lifecycle/Base.cls#L1602-L1607; Main.cls#L2782-L2786).
- **Intent says:** module-action help, Main.cls#L56-L57: publish "saves that artifact to the repository for which
  deployment is enabled. Currently, there may only be one of these per namespace." Code allows one per kind
  (REPO-B59).
- **Impact:** With no publish flag set, `publish M` can send a private module to any enabled registry, including the
  public community registry if it is configured with credentials.
- **Native check:** confirmed — `nc-repo-1-publish-no-flag`: with only `nc-repo-a` (token set, publish flag empty),
  `PublishingServer` picks `nc-repo-a`, and `publish nc-repo-pub -v` prints "Publish to: http://127.0.0.1:9/" and fails
  only on the TCP connection, not with "No server found to publish to".
- **Proof:** `repo_witness_publish_fallback` (models/verus/settings.rs): one enabled remote registry with a token and no flag is chosen, so `l1_publish` fails. Positive side: `repo_refines_publish_default` under PH, PU and PK; PH excludes this finding's case. REPO-B59 (one flag holder per namespace, help Main.cls#L56-L57) is premise PU; the code keeps one per kind.

- **Revision (2026-11-13, decision resolved):** DEC-REPO-1 resolved (evidence): the fallback (flag, then token, then user and password, then any other enabled registry) is intended (PR #332 review, commit e4dc908d; PR #569 renamed the column to Default Deployment Registry). **The fallback part of this finding is withdrawn** (REPO-B56 now states it with I and O, new REPO-B109 the order). What remains: (1) a documentation defect, help Main.cls#L56-L57 omits the fallback and says one flag holder per namespace; (2) the code allows one publish flag per registry kind, not per namespace (REPO-B59, REPO-B60 keep `F:F-REPO-3`). Suggested severity drops from High to Low. decisions/research/repo.md#dec-repo-1--publish-with-no--r-and-no-publish-flag

### F-REPO-5

### F-UNIN-11
**`zpm clean` runs the IPM self-uninstall block at level 0: a false orphan warning, and the self-uninstall path in ExecutePhases.**
- **Statement(s):** UNIN-B70, UNIN-B86.
- **Code does:** the IPM-only block (`Lifecycle/Module.cls#L27-L81`) runs at every Clean level and prints "WARNING: N
  module(s) orphaned" and "Reinstalling IPM will automatically re-adopt these modules." while nothing is removed;
  by inspection `ExecutePhases` also treats it as a self-uninstall and skips the after-phase callbacks
  (`OnAfterPhase`, Invoke after-phase hooks; `Storage/Module.cls#L630-L655`).
- **Intent says:** DEC-UNIN-2 resolved (evidence): `zpm clean` is an ordinary level-0 Clean; the warning, full cleanup
  and self-uninstall handling belong only to a real removal (`Clean.Level>0`). Sources: the block's comment "Special
  handling for IPM self-uninstall" (L27), Storage/Module.cls#L630/#L647 comments, PR #1106, wiki 00/02 Clean.

  ExecutePhases part is inspection only.
- **Impact:** an operator is told modules are orphaned when nothing changed; after-phase hooks of `zpm clean` do not run.
- **Severity suggestion:** Low.

- **Impact:** the next search, install or publish sends the old host's credentials to the new host.
