## Resolutions (2026-11-13)

Each decision above was resolved from the round-4 intent research in `decisions/research/`. RESOLVED-EVIDENCE: an
authoritative source settles the intent. RESOLVED-ASSUMPTION: no such source; the most reasonable intent was
chosen and the alternatives are kept here. The Status column carries the verdict. Statements that waited on a
decision no longer carry `OPEN`; where the code contradicts the resolved intent they carry `F` and `O!`.

### DEC-INST-1
- **Verdict:** resolved (evidence).
- **Resolution:** Keep the -dev bypass of the update-package guard (option A) and document it.
- **Key sources:** TestDevMode doc comment InstallModule.cls#L161-L162 and assert #L178; PR #887 commit comments; issue #550; Utils/Module.cls#L1219.
- **Code matches:** Yes; docs lag (F-INST-11: README L62, -dev help, guard error text). INST-B30, new LOAD-B31.
- **Research:** decisions/research/inst.md#dec-inst-1--is-the--dev-bypass-of-the-update-package-guard-public-contract

### DEC-INST-2
- **Verdict:** resolved (assumption).
- **Resolution:** Seed on dev installs too (option A): any install or load that is not an update seeds the steps of the version it puts in place; a later update runs only newer steps.
- **Key sources:** update help Main.cls#L167 ('from the current version'); Update.cls#L467 seeded-not-rerun assertion; issue #550; dev condition added in b5cb11a17 with no stated reason.
- **Alternatives and what would change:** (B) keep and document 'a dev install leaves all steps due', if maintainers want load -dev plus update to exercise every step. (C) seed only steps at or below the installed version (almost A). If B is chosen, INST-B18 returns to its old text and F-INST-8 is withdrawn.
- **Code matches:** No: new F-INST-8 (INST-B18).
- **Research:** decisions/research/inst.md#dec-inst-2--should-an-install-in-developer-mode-seed-update-steps

### DEC-INST-3
- **Verdict:** resolved (assumption).
- **Resolution:** Refuse (option A): a module in developer mode is not overwritten by a non-dev install, named or needed; install stops and names the needed module.
- **Key sources:** wiki 00.-Concepts Developer Mode (maintainer commit cfacdd8); Utils/Module.cls#L109, #L310, #L317-L319.
- **Alternatives and what would change:** (B) allow but warn, if blocking would stop routine installs that share a dev-mode library. (C) keep silent: no source supports it. If B is chosen, INST-B35 says 'warns' and F-INST-9 narrows to the missing message.
- **Code matches:** No: new F-INST-9 (INST-B35).
- **Research:** decisions/research/inst.md#dec-inst-3--should-install-refuse-to-replace-a-needed-module-that-is-in-developer-mode

### DEC-INST-4

- **Resolution:** reinstall M installs again the version that is installed now (option A); the 'latest version' description is stale.
- **Key sources:** Summary Main.cls#L448, examples #L455; code since 9713db77; discussion #942, issue #939.
- **Code matches:** Yes; doc drift in Main.cls#L450 and wiki 02 (F-INST-11). INST-B39.

### DEC-INST-5
- **Verdict:** resolved (evidence).
- **Resolution:** At-least-once (option A): a step may run more than once after a failed, rolled-back or cut-off update; module authors must write steps that are safe to rerun.
- **Key sources:** wiki 08 'Idempotent steps' (written by a PR #887 reviewer); Utils/Module.cls#L1344 comment; IRIS nc-inst-4*, r4-inst-u22-dev-retry.
- **Code matches:** Yes; VersionBase.cls#L6-L20 should say steps must be idempotent (doc note, no F). INST-B67 restated.
- **Research:** decisions/research/inst.md#dec-inst-5--what-delivery-promise-do-update-steps-have

### DEC-INST-6
- **Verdict:** resolved (assumption).
- **Resolution:** If the update lock cannot be taken, update fails with an error saying the lock is busy; it must not report success.
- **Key sources:** Removed PR #887 test TestSimultaneousUpdateFails (d6d346728, removed e232e5056); first lock code 'quit if we cannot' (8ac85b59d); update help Main.cls#L167.
- **Alternatives and what would change:** (b) wait longer, then fail: same contract, other timeout. (c) skip with a warning and a non-OK status: practically (a). Only 'keep success' is ruled out; the assumption is that the test's removal did not withdraw the promise.

- **Research:** decisions/research/inst.md#dec-inst-6--what-should-update-do-when-the-update-lock-is-busy-high
