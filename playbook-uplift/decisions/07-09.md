# Open decisions — modules 07 (namespace), 08 (resources), 09 (sync)

Each row is a question where intent sources disagree or are silent and the uplift must not choose. The
statement or cell that waits on the decision cites it as `OPEN:<id>` or in the Decision column. Evidence for each
side is in the Options column. "Native:" adds what IRIS 2026.1 did in the native checks (observations in
`evidence/iris-observations.json`); the decisions stay open.

## 07 — Namespace ownership

| ID | Module | Question | Options | Owner | Status |
|---|---|---|---|---|---|
| DEC-NSP-1 | 07-namespace | A namespace gets IPM code and repo settings by mapping, then gets its own IPM (installer or `load`). What should happen to the repo settings mapping? | (a) Remove it with the code mapping, since README#L77 says repos are only mapped together with code from the same namespace. (b) Keep it (current code: installer touches only `%IPM` package/routine mapping, Installer.cls#L25-29). ## Resolutions (2026-11-13)

Each decision above was resolved from the round-4 intent research in `decisions/research/`. RESOLVED-EVIDENCE: an
authoritative source settles the intent. RESOLVED-ASSUMPTION: no such source; the most reasonable intent was
chosen and the alternatives are kept here. The Status column carries the verdict. Statements that waited on a
decision no longer carry `OPEN`; where the code contradicts the resolved intent they carry `F` and `O!`.

### DEC-NSP-1
- **Verdict:** resolved (evidence).
- **Resolution:** Option (a): repo settings are mapped only together with IPM code from the same namespace; a namespace that gets its own IPM keeps no repo mapping to the old source (route: unmap, then install).
- **Key sources:** README#L69; PR #663; unmap help Main.cls#L767; wiki 02 unmap.
- **Code matches:** No: F-NSP-5 (new NSP-B78; cell NSP-C28).
- **Research:** decisions/research/nsp.md#dec-nsp-1--repo-mapping-when-a-mapped-namespace-gets-its-own-ipm

### DEC-NSP-2
- **Verdict:** resolved (evidence).
- **Resolution:** Not directly: while a namespace gets IPM by mapping, IPM refuses to install, reinstall or remove itself there; the operator runs unmap, then installs. The installer and a load of IPM should refuse too.
- **Key sources:** PR #485 (implementer comment; commits faf4ebdc, 1de4bd0b); issue #470; help Main.cls#L743 is about namespaces that already have IPM (Main.cls#L3637-L3641, wiki Installation-Patterns).
- **Code matches:** Install/reinstall/uninstall zpm yes; installer and load no (F-NSP-5, NSP-B49); the route is blocked by F-NSP-6 (new NSP-B77).
- **Research:** decisions/research/nsp.md#dec-nsp-2--may-ipm-be-installed-locally-in-a-namespace-that-gets-ipm-by-mapping

### DEC-NSP-3
- **Verdict:** resolved (evidence).
- **Resolution:** Option (a): when IPM becomes available in a namespace with legacy (0.7.x) records, enable -map and enable -community run the same migration as an IPM load.
- **Key sources:** Issue #470 requirement (closed by PR #485); PR #485 commits bf6e6997, 7b10d493; EnableIPM has no migration call.
- **Code matches:** No: new F-NSP-10 (NSP-B74). Native run simulated legacy (r4-nsp-legacy-*); real ZPM 0.7.4 not loaded.
- **Research:** decisions/research/nsp.md#dec-nsp-3--legacy-zpm-records-reached-by-enable--map---community

### DEC-NSP-4
- **Verdict:** resolved (assumption).
- **Resolution:** Option (a): if a step fails, enable -community stops and returns that error, so `zpm "enable -community":1` stops a script.
- **Key sources:** No source speaks to failure; help and wiki 'functionally equivalent' to three commands; other IPM paths report failure (Main.cls#L3904-L3917; quit-on-error argument cc2e4f6c).
- **Alternatives and what would change:** (a') run all three and return a combined error: also meets NSP-B33. (b) keep today's behaviour and document that the command never fails: F-NSP-11 becomes documentation.
- **Code matches:** No: new F-NSP-11 (NSP-B33).
- **Research:** decisions/research/nsp.md#dec-nsp-4--enable--community-when-one-step-fails

### DEC-NSP-5
- **Verdict:** resolved (assumption).
- **Resolution:** Option (b): a load refused by a system need leaves no module record, also in developer mode; the check runs before the developer-mode commit.
- **Key sources:** Issue #106 spec; CHANGELOG#L54; PR #1226; wiki 03 SystemRequirements ('validated before module installation').
- **Alternatives and what would change:** (a) keep the record on purpose (dev mode keeps the manifest to fix it; Utils/Module.cls#L1310, help #L306); then document that -dev can leave a refused module installed and F-NSP-12 becomes documentation.
- **Code matches:** No: new F-NSP-12 (NSP-B66, LOAD-B20).
- **Research:** decisions/research/nsp.md#dec-nsp-5--developer-mode-load-refused-by-a-system-need-keeps-its-record

### DEC-NSP-6
- **Verdict:** resolved (assumption).
- **Resolution:** Option (a): the source of a mapped namespace is the namespace whose own default code database holds the IPM code; a namespace that reaches it by mapping is never a source.
- **Key sources:** -map help Main.cls#L736; issue #470; NSP-D4 (a source has a local install); AddIPMMappedNamespaces (Main.cls#L1628-L1654) has no tie rule; issue #1310 may be the same cause.
- **Alternatives and what would change:** Report a tie as an error instead of guessing. Either way 'last by name' is not intended.
- **Code matches:** No: F-NSP-7 stands (NSP-B56, new NSP-B79), with new instances (install guard, unmap output, self-uninstall warning).
- **Research:** decisions/research/nsp.md#dec-nsp-6--which-namespace-is-the-source-when-two-zpm-records-share-one-ipm-database

### DEC-RES-1
- **Verdict:** resolved (evidence).
- **Resolution:** Option (a): exec/cos run in an isolated context; a namespace switch inside ends with the command. The help example is stale.
- **Key sources:** PR #996 (fixes issue #995, 'namespace isolation'); CHANGELOG#L142; Main.cls#L2435.
- **Code matches:** Yes; help and wiki examples stale (F-RES-6, documentation). RES-B73.
- **Research:** decisions/research/nsp.md#dec-res-1--namespace-switch-inside-exec

### DEC-RES-2

- **Key sources:** Help example Main.cls#L364-L404, wiki example, code since the 2021 import (Main.cls#L2003-L2009).
- **Code matches:** Yes; the 'single array' sentence and the .text example are documentation defects (F-RES-5). RES-B77.
- **Research:** decisions/research/nsp.md#dec-res-2--json-format-of-a-run-from-file-file

### DEC-RES-3
- **Verdict:** resolved (evidence).
- **Resolution:** Option (a): packaging deploys classes in the current namespace whether or not it is in developer mode; the developer reloads from source afterwards.
- **Key sources:** Issue #815 (maintainer decision), PR #898 (ccc8aacf); message Base.cls#L1837.
- **Code matches:** Yes. RES-B23; F-RES-3 (plain makedeployed) is a separate question.
- **Research:** decisions/research/nsp.md#dec-res-3--package-deploys-classes-in-the-current-namespace-also-in-developer-mode

### DEC-SYNC-1
- **Verdict:** resolved (assumption).
- **Resolution:** Option (a): files that a failed compile, load -dev or reload put on the server are re-detected by the next sync, even after an exact revert ('nothing to sync' means the server matches the disk).
- **Key sources:** Issue #1224 and PR #1223 (sync-only fix); wiki and help 'since the last load or sync'; PR #1205 purpose.
- **Alternatives and what would change:** (b) retry marks stay sync-only and the docs say 'after a failed compile, run compile again': F-SYNC-1 becomes documentation and SYNC-B22 returns to its old text.
- **Code matches:** No: F-SYNC-1 stands (SYNC-B22).
- **Research:** decisions/research/nsp.md#dec-sync-1--failed-load-or-compile-outside-sync

### DEC-SYNC-2
- **Verdict:** resolved (evidence).
- **Resolution:** Option (b): with no baseline, the first sync only records the disk as the baseline and loads nothing, also after -skip-sync.
- **Key sources:** -skip-sync help Main.cls#L315 ('records'); CHANGELOG#L12; PR #1291 test Sync.cls#L72-L91; PR #1205 and test Sync.cls#L126-L133; Pipeline.cls#L43-L48.
- **Code matches:** Yes; F-SYNC-2 becomes a documentation defect (new SYNC-B52); SYNC-B15 no longer carries it.
- **Research:** decisions/research/nsp.md#dec-sync-2--first-sync-with-no-baseline-after-load--dev--skip-sync

### DEC-SYNC-3
- **Verdict:** resolved (assumption).
- **Resolution:** Option (b): `sync` with no module name syncs every developer-mode module, shows each failure and a summary naming the failed modules, and returns OK after reporting each failure; `sync <module>` returns the error.
- **Key sources:** PR #1205 ('loops over all DeveloperMode=1 modules and collects failures without throwing'); code 5af3beda (Main.cls#L2383-L2410). Recorded as an assumption (orchestrator override): 'collects failures without throwing' says the loop continues past failures, not that the final status is OK.
- **Alternatives and what would change:** (a) return an error status when any module fails, like `sync <module>`: SYNC-B46 would then carry a new finding. A one-line help note is wanted either way.
- **Code matches:** Yes (SYNC-B46).
- **Research:** decisions/research/nsp.md#dec-sync-3--sync-with-no-module-name-when-one-module-fails

### DEC-SYNC-4
- **Verdict:** resolved (assumption).
- **Resolution:** A variant of option (a), warn: the reload phase stays a no-op for a module with no root inside larger phase lists; the standalone `reload` command tells the operator that nothing was loaded and why.
- **Key sources:** Help Main.cls#L42; Base.cls#L627-L634 ('For now'); sync refuses the same case (Pipeline.cls#L29-L31).
- **Alternatives and what would change:** Fail the standalone command, as sync does for a non-dev module (stricter for scripts; SYNC-B51's text fits both). Failing the phase itself would break `compile` of every non-dev module.
- **Code matches:** No: new F-SYNC-3 (SYNC-B51).
- **Research:** decisions/research/nsp.md#dec-sync-4--reload-of-a-module-not-in-developer-mode
